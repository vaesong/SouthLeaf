# M3 — 全部约定内容可维护

## 目标

按 P02/P03 的 M3 退出信号，实现 2A 合成数据条件下的一套后台运营流程：品牌/联系资料、成员与渠道、六类业务、套餐版本、作品、首页精选；支持草稿、预览、发布/下架、乐观并发冲突和可追踪版本切换。操作员通过真实后台页面维护，不需手工编辑 SQL 或直接改数据库记录。

## 范围

- 重用 S2 已有登录、capability、媒体上传/READY 与作品草稿/发布链路。
- 复用既有公开 DTO 语义，保证小程序合同兼容；不改已应用 public V1、public V2、admin V5/V6 migration。
- 为 M3 增加显式、可重放的 admin/public 增量迁移；只在本次 disposable dual-schema MySQL fixture 验证。
- 六类业务语义必须全部可表达；无套餐是合法空态。价格 `FIXED/FROM/INQUIRY/UNDISCLOSED` 必须显式区分，未确认数值不得推默认。
- 发布新版本时保留历史，不覆盖历史快照；并发编辑用版本/If-Match 拒绝陈旧写入；下架后新查询不回退旧版本。
- 合成演示数据与正式资料明确隔离；不创建生产资料、默认管理员或真实通知。

## 不在范围

- 2B 真实品牌、真实联系方式/价格/授权/媒体素材、生产 grants、正式微信/通知与部署。
- 支付、定金计算、预约入口、订单变更与客户资料。
- FAQ/评价/活动价/多语言站点/页面自由搭建等 D301/D303 明确尚未确认的选项。
- 修改 public V1/V2 或旧 admin migrations、手动修改数据库内容、放宽 Reader/Writer 权限。

## M3 验收标准

1. 通过 admin-web 可维护以上所有已约定内容类型；错误、忙碌、空态、版本冲突和权限不足均真实呈现。
2. 草稿编辑不影响公开读端；发布先服务器校验全部引用/字段/媒体资格，再以单一版本切换原子提交。
3. 每种内容只有一个权威事实；作品授权仍由 S2 gate 管理，M3 不增加第二套授权记录。
4. 发布/下架后 public API 与小程序读取当前版本；旧版本不被当作当前内容；小程序既有合同回归。
5. MySQL/InnoDB 双 schema 的迁移、最小 grants、失败回滚、重复命令、同键异载荷、并发冲突和清理均有可复现证据。
6. 最终证据只使用 owned disposable fixture 和 synthetic content，明确记录失败/限制，不能用 H2/mock/单页面演示代替。
