# 设计状态与文档规范

> 文档编号：D-000
> 文档状态：已确认
> 适用范围：目标架构、阶段一、阶段二、阶段三
> 更新日期：2026-10-06
> 依据：A01-A16、AT01-AT09、P01

## 1. 目的

本文件规定 `docs/设计笔记集/` 中详细设计文档的边界、状态、内容结构和评审方式，避免需求、架构、计划和实现文档互相覆盖。

## 2. 四类文档职责

- A 文档：记录用户需求、业务事实、规则、异常、验收和待确认问题。
- AT 文档：记录总体技术选型、模块边界、状态、权限、事务、错误码和外部契约前置约束。
- P 文档：记录阶段范围、依赖、交付目标和验收方向。
- D 设计文档：记录数据结构、用例、输入输出、接口、内部架构、事务、测试和实现约束。

D 文档不得自行改变 A/AT 中已经确认的经营规则。发现规则冲突时，应回到规则主归属文档修订，并在设计决策记录中说明影响。

## 3. 文档头部

每篇 D 文档必须包含：

```text
文档编号：D-xxx
文档状态：草稿 / 评审中 / 已确认 / 已锁定
适用范围：目标架构 / 阶段一 / 阶段二 / 阶段三
更新日期：YYYY-MM-DD
上游需求：Axx
上游架构：ATxx
关联计划：Pxx
```

## 4. 模块设计最低结构

```text
1. 设计目标
2. 责任边界与规则归属
3. 领域对象和数据归属
4. 状态及状态转换
5. 用例清单
6. 输入、前置条件、权限和幂等
7. 输出、状态变化、错误、通知、任务和审计
8. 对外接口与内部端口
9. 内部分层和依赖方向
10. 事务、并发、唯一约束、重试和补偿
11. 数据安全与隐私
12. 日志、指标和可观测性
13. 测试和验收场景
14. 阶段开放范围
15. 设计假设和待确认问题
```

## 5. 数据和接口分层

设计时至少分开以下模型：

```text
领域模型：表达业务规则和不变量
持久化模型：表达数据库存储和查询需要
接口 DTO：表达对外输入输出和兼容边界
客户端模型：表达页面和任务所需展示数据
```

数据库字段不应直接暴露给客户端；客户端传入的金额、状态、权限和文件路径不能作为最终业务事实。

## 6. 设计状态和锁定规则

- 草稿：可以讨论，不得直接据此实现。
- 评审中：方案完整，等待产品/架构/运营复核。
- 已确认：可作为其他设计和测试输入。
- 已锁定：该阶段实现契约冻结，变更必须新增决策记录并评估兼容影响。

数据库模型草案、接口草案和供应商字段在未评审前只能标记为“草案”，不能写成生产兼容承诺。

## 7. 设计评审检查项

评审至少检查：

- 业务事实是否有唯一权威归属；
- 输入输出是否与角色和资源归属一致；
- 状态是否覆盖成功、失败、处理中、未知和人工补偿；
- 并发、重复请求、乱序回调和超时是否有处理；
- 外部服务是否通过适配层隔离；
- 敏感数据、文件地址和错误响应是否脱敏；
- 通知失败是否不会回滚核心事实；
- 阶段范围是否与 P01 一致；
- 测试场景是否能证明关键不变量；
- 是否把产品建议或设计假设误写成已确认经营规则。
