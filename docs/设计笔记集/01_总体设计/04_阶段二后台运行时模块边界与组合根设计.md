## 1. 目标与设计范围

D-101 定义目标架构的模块化单体逻辑边界；本文把阶段二 S1 的后台安全能力细化到 Java 包、Maven 模块、Spring 组合根、可执行产物和运行进程边界。核心要求不是“同一个 Spring Boot 应用里加一个 admin profile”，而是让公开 Reader 与管理 Writer 的依赖、配置、打包和运行授权都能被结构性检查。

本文建议：保持同一仓库和统一版本治理，按安全信任边界拆分可编译模块与部署产物；公开 API 与管理运行时是两个独立 JVM 进程，管理迁移工具再单独作为显式运维产物。它们仍属于同一业务产品，不因此引入服务网格、跨服务业务事务或复制一套公开业务规则。

本文件是架构分析草案，不是代码变更或数据库部署授权。它只设计运行与依赖边界，不决定经营角色、密码策略细节、HTTP DTO、后台页面或真实账号信息。管理数据库与 Writer 启动校验的精确要求以 D-506 为专门设计。

## 2. 当前实现观察

当前 `backend/pom.xml` 是单一 Maven jar：`cn.zhinan:uniapp-api`；Spring Boot 插件的 `mainClass` 固定为 `cn.zhinan.uniapp.UniappApiApplication`。主程序位于 `cn.zhinan.uniapp` 包根，默认组件扫描覆盖其下所有子包。

后台会话代码当前位于 `cn.zhinan.uniapp.adminsecurity`，其领域/应用/存储对象目前保持普通 Java 类型，`JdbcAdminSessionStore` 没有 Spring 自动发现注解；`AdminDatabaseMigrationMain` 位于同一代码树的 `cn.zhinan.uniapp.tooling`。因此当前主要靠“没有自动注册、没有默认接线”维持隔离，**还没有包根、Maven 依赖图或可执行产物层面的强隔离**。这不是说现有运行时已经扩大权限，而是说明未来新增注解、扫描规则或配置时容易意外耦合。

S1 的目标设计应明确弥补此差距：公开运行时的包树与产物不带管理 Writer 适配器；管理运行时有自己的组合根与 DataSource；管理迁移不随公开 API 自动启动；三者的环境变量、凭据与测试门禁各自独立。

## 3. 架构原则与边界决策

1. **安全边界优先于 profile。** Spring profile 适合选择运行行为，不足以隔离 DataSource、扫描范围、依赖树或可执行产物；不把 `--spring.profiles.active=admin` 当作架构边界。
2. **核心用例依赖内部端口。** 后台会话领域、应用服务和端口保持纯 Java；不得依赖 Spring、Web、JDBC、MySQL、公开读模型或 `PublicRuntimeConfiguration`。
3. **适配器依赖核心，不反向穿透。** JDBC Store 实现会话存储端口；管理运行组合根负责显式构造，不在核心包里使用 `@Component`、`@Configuration` 或自动装配。
4. **公开与管理没有共享 DataSource。** 公开 Reader 不导入管理模块；S1 安全会话 Writer 不连接公开 schema。S2 专用 publication Writer 的有限跨 schema 能力另按 D-507 设计，不共享安全 Writer 的连接池或授权。需要公开业务数据时，未来通过明确的业务端口/公开接口设计，不借用 Reader 凭据或读表捷径。
5. **迁移是运维用例，不是应用启动副作用。** 管理迁移 CLI 与管理 Web/runtime 是不同产物、不同配置和不同身份；运行时不持有 DDL 授权。
6. **结构化解耦，不预拆业务微服务。** 本次的两个进程用于分开信任域、凭据和上线门禁，不引入跨服务业务事务、事件总线或多仓库协调。

## 4. 推荐目标模块图

目标 Maven reactor 保留 `backend/` 作为聚合入口与版本治理位置；聚合父 POM 不含运行 Bean、应用源代码或默认 DataSource。

```text
backend (aggregator POM; no application classes)
├── public-api
│   └── 现有公开应用、公开业务模块、Reader 配置与公开迁移工具
├── admin-security-core             (JDK only)
│   └── 后台安全 domain / application / port；仅含 SessionTokenCodec 端口
├── admin-security-jdbc              (core + Spring JDBC)
│   └── JdbcAdminSessionStore 等显式持久化适配器
├── admin-db-policy                  (JDK only)
│   └── 管理 JDBC URL / schema / TLS 模式的纯策略
├── admin-runtime                    (Spring Boot 管理进程)
│   └── 管理 main、配置绑定、守卫、连接池、组合根、JDK token codec adapter；HTTP 后续接入
└── admin-migration-cli              (Flyway/MySQL 显式运维工具)
    └── AdminDatabaseMigrationMain 与 db/admin-migration 资源
```

依赖只朝一个方向流动：

```text
public-api                 → 公开业务与公开适配器；不依赖任何 admin-* 模块
admin-security-core        → JDK；不依赖 Spring / JDBC / Web / MySQL
admin-security-jdbc        → admin-security-core + Spring JDBC
admin-db-policy            → JDK；不建立连接，不访问数据库，不持有秘密
admin-runtime              → admin-security-core + admin-security-jdbc + admin-db-policy + Spring Boot
admin-migration-cli        → admin-db-policy + Flyway/MySQL Connector + minimal JDBC support（当前 `DriverManagerDataSource` 需要 Spring JDBC；不依赖 Spring Boot 或 admin-runtime）
```

`admin-db-policy` 只承载真正共享且可纯函数验证的数据库目标规则：单主机 URL、凭据/未知/重复参数拒绝、schema 命名和 TLS 模式约束。运行时与迁移 CLI 通过不同策略入口调用：production runtime 与迁移始终 `VERIFY_IDENTITY`；隔离 demo runtime 可按 D-506 允许 `REQUIRED`；共用解析逻辑不能抹平安全级别差异。它不得包含 DataSource、SQL 或业务会话类型。

公开 API 可以继续保留自己的公开数据库迁移工具与公开迁移资源；仅管理 V2 迁移主类和 `db/admin-migration` 资源移入 `admin-migration-cli`。迁移身份、迁移历史和运行身份仍分离。

## 5. 包结构与内部端口

目标 Java 包根如下。公开包根 `cn.zhinan.uniapp` 保持原样；后台安全核心移出该包树，消除公开默认扫描范围包含管理代码的隐性风险。

```text
cn.zhinan.uniapp.*
  公开 API、公开业务、Reader 配置与公开适配器

cn.zhinan.adminsecurity.domain
cn.zhinan.adminsecurity.port
cn.zhinan.adminsecurity.application
  后台账号/会话/权限的纯 Java 核心

cn.zhinan.adminsecurity.adapter.jdbc
  JdbcAdminSessionStore；实现 admin-security-core 的端口

cn.zhinan.admindbpolicy
  URL、schema 与 TLS 的无状态配置校验

cn.zhinan.adminruntime
cn.zhinan.adminruntime.config
cn.zhinan.adminruntime.database
cn.zhinan.adminruntime.crypto
cn.zhinan.adminruntime.web            (仅安全 HTTP 完成后开放)
  Spring Boot 管理组合根、启动守卫、JDK SecureSessionTokenCodec 与未来入站 HTTP 适配器

cn.zhinan.adminmigration
  显式迁移 CLI；不属于 Web 运行上下文
```

应用服务面向 `AdminSessionStore`、`SessionTokenCodec`、`Clock` 等内部端口；不暴露 JDBC 类型。未来 HTTP Controller 只作为入站适配器调用应用服务，不直接注入 `JdbcTemplate`、DataSource 或 repository。业务管理命令仍归各业务模块，不因共享登录而收进 `admin-security-core`。

## 6. 组合根、启动守卫与数据源可信化

`AdminRuntimeApplication` 作为唯一管理 Spring Boot 组合根，显式限定扫描 `cn.zhinan.adminruntime`。核心模块与 JDBC adapter 不依赖自动扫描；由 `AdminRuntimeConfiguration` 逐项创建 `Clock`、token codec、会话用例和 Store。

管理数据库启动链建议封装为单向生命周期：

```text
AdminRuntimeProperties
  → admin-db-policy 校验配置/URL
  → AdminRuntimeDatabaseBootstrap 构造私有 HikariDataSource
  → AdminRuntimeAccountVerifier 核验 DATABASE / CURRENT_USER / TLS / grants
  → VerifiedAdminDataSource（仅成功后产生，限制为组合根内部类型）
  → 显式创建 JdbcAdminSessionStore 与其事务管理器
  → 管理应用可用
```

守卫属于运行基础设施，不属于认证领域：它回答“此进程连接的是否为允许的数据库身份及权限”，不回答“当前请求的用户是谁”。在守卫成功前，管理 DataSource 不作为普通 Bean 供其他组件任意注入；Store 只能依赖 verified wrapper 暴露的同一个底层池。Store 内的 JDBC 与事务管理器继续共用一个 DataSource。

初期管理运行应用配置为非 Web；因此没有服务端口可在守卫失败时接受请求。未来启用 Web 时，守卫须在 Ready/接流量前完成；管理入口只暴露经认证、授权、CSRF 与错误映射保护的路由。公开入口既不扫描也不导入 admin 包；管理入口既不扫描也不导入公开配置。不得用根包 `cn.zhinan` 的宽扫描，不得以 `@Primary` 共享 Reader/Writer，也不得在失败时回退到内存 Store。

## 7. 运行、配置与身份分区

| 产物/进程 | 唯一入口 | 配置与凭据命名空间 | 数据库能力 |
|---|---|---|---|
| `public-api` | `cn.zhinan.uniapp.UniappApiApplication` | 现有公开配置与 `SOUTHLEAF_DB_*` | public schema Reader；权限不变 |
| `admin-runtime` | `cn.zhinan.adminruntime.AdminRuntimeApplication` | `application-admin.properties`、`SOUTHLEAF_ADMIN_DB_*` | 管理 schema runtime Writer；按 D-506 精确表级权限 |
| `admin-migration-cli` | `cn.zhinan.adminmigration.AdminDatabaseMigrationMain` | `SOUTHLEAF_ADMIN_MIGRATION_*` | 管理 schema 的显式迁移身份；不在 runtime 进程使用 |

三个产物在构建、进程、环境变量、连接池和日志上下文上明确分开。部署可共享主机或容器平台，但公开与管理运行凭据不能注入同一进程；迁移 CLI 不随服务启动。管理 HTTP 完成安全闭环前只运行非 Web 校验/内核，不在公网挂管理 listener。生产管理网络的 ingress、TLS 终止和运维访问控制在 2B 部署设计中细化。

## 8. 方案比较与推荐

| 方案 | 优点 | 风险/代价 | 结论 |
|---|---|---|---|
| 同一 Maven jar，两个 main class / profile | 改动最少；短期开发启动方便 | 同一 classpath/产物仍含管理适配器和迁移代码；扫描、配置、依赖隔离仅靠约定；公开发布易意外携带管理能力 | 仅可作隔离开发测试的过渡，不作为生产目标 |
| 同仓库、多 Maven 模块、多可执行产物、独立进程 | 编译依赖、Spring 扫描、配置与交付物均可强约束；仍保留统一仓库/版本；能证明 public jar 不含管理实现 | 需要移动源集、资源和测试；调整 POM 与 PowerShell 启动/验证脚本；短期构建改造较多 | **推荐目标**；与独立信任域和最小权限相符 |
| 分成独立仓库/远程微服务 | 团队和发布完全独立 | 当前会增加版本协调、网络调用、部署与运维负担；会话安全不需要远程业务分布式协作 | 当前不采用；只有团队/扩展/可用性证据支持时再评估 |

推荐第二种，但把拆分限定在安全边界：同一 monorepo 与同一业务产品，公开 API 与管理 runtime 作为不同 deployable；不是为了“微服务化”拆分预约、订单等业务，也不通过远程调用绕过既有模块事务边界。

## 9. 后续迁移顺序与验收门禁

以下是后续实现设计，不表示本轮开始实施；各现有源文件、测试、资源和 PowerShell 脚本的具体模块归属见 [D-105](05_阶段二S1模块拆分与构建迁移设计.md)：

1. 将 `backend/pom.xml` 演进为保持原 `backend` 命令入口的聚合 POM；保留 Maven Wrapper 与统一版本管理，构建产物改为各模块自己的 `target`，避免公开服务与管理测试争用输出目录。
2. 将现有公开源、资源、测试迁至 `public-api`，保持公开 main class、配置语义、运行端口和 Reader 权限不变；保留公开迁移工具与公开 V1 归属。
3. 将 adminsecurity domain/application/port 纯 Java 核心移至 `admin-security-core`，包根迁为 `cn.zhinan.adminsecurity`；其中保留 `SessionTokenCodec` 端口，不引入 Spring/Web/JDBC/MySQL。
4. 将 `JdbcAdminSessionStore` 移至 `admin-security-jdbc`；以显式组合根构造，不加自动发现注解；现有事务与安全审计测试留在其责任模块。将 `SecureSessionTokenCodec` 作为 JDK 适配器置于 `admin-runtime` 的 crypto 包，由运行组合根提供，不让核心依赖随机数实现。
5. 将共用、纯函数的 URL/schema/TLS 规则抽取为 `admin-db-policy`，以回归测试保留 D-505 迁移身份始终 `VERIFY_IDENTITY` 的约束。
6. 将管理迁移 main 与 `db/admin-migration` 资源迁入 `admin-migration-cli`，保证调用仍要求显式 `--migrate`/`--validate` 和独立凭据。
7. 新建 `admin-runtime`；完成专属配置、非 Web 入口、Verified DataSource 启动守卫和架构约束测试。此阶段不开放密码登录/HTTP，不创建真实生产账号。
8. 更新 `backend/scripts/*.ps1`、CI/验收命令和文档链接，使 `backend` 父目录仍可统一构建，运行/IT 测试指向正确模块；在干净的隔离输出目录验证 public/admin 分别可构建。
9. 只有后续安全登录/授权/CSRF 设计与验收完成后，才在 `admin-runtime` 增加受保护 Web 适配器；UI 与真实管理库部署再按 P02 门禁推进。

架构验收至少证明：

- Maven 依赖图无环；`public-api` 不依赖 `admin-*`；admin 核心不依赖 public package。
- `admin-security-core` 不带 Spring、JDBC、Web、Servlet、MySQL 运行依赖；JDBC adapter 只依赖 core 与 Spring JDBC；`SecureSessionTokenCodec` 位于 admin-runtime 并只实现 core 的端口。
- public API jar 中不存在 `cn/zhinan/adminsecurity`、`cn/zhinan/adminruntime`、管理 V2 迁移资源和管理 Writer adapter；public 启动不要求 `SOUTHLEAF_ADMIN_*`。
- admin runtime jar 不包含公开 Controller/Reader 配置，不创建公开 Reader DataSource；S1 只接触管理安全身份。未来 S2 publication adapter 使用独立受限身份，不改变公开 Reader 或 S1 安全 Store 的权限。
- migration CLI 与 runtime 不共用凭据，也不由 runtime 自动启动；public V1 与现有 Reader 回归不变。
- 架构/依赖测试与真实 MySQL 管理授权测试分开报告；没有独立管理测试账号时不得宣称已验证最小权限部署。

## 10. 设计结论与边界

本设计把“两个 Spring Boot main class”从最终解耦标准降为开发期便利手段；目标是同仓库内的模块级依赖隔离、产物级隔离和进程级安全隔离。管理认证核心是独立 bounded context；运行守卫是 `admin-runtime` 的基础设施；数据库迁移是单独运维 CLI；公开 Reader 不依赖或承载任何管理 Writer。

本轮只完成架构讨论与文档更新，不拆 POM、不移动包、不改源码/资源/启动脚本，不运行构建/测试，不迁移/连接管理数据库，不部署账号权限，不处理生产秘密，不重启服务。后续实现须按第 9 节分阶段进行，并遵守 D-506 的 Writer 权限矩阵与 P02 的阶段门禁。

六模块表描述 S1-A 迁移基线；C1 已新增普通 jar `admin-credential-crypto`，故当前为七模块。生产依赖边为 crypto → core + Spring Security crypto/Spring Core/BC；core 不反向依赖技术库，CLI 不依赖 runtime。runtime 暂不接线 crypto/login，public 和 runtime 最终产物都禁止携带新 KDF/provider；C2 必须以真实持久事件与版本化精确权限门禁评审 runtime 新边，不能直接删除检查让构建通过。

边界脚本已覆盖该模块、技术依赖白名单及字节码；正式 jar 不含测试基准入口。[C1 验证指南](../../开发与演示/阶段二S1-C1凭据核心与KDF验证指南.md)。
