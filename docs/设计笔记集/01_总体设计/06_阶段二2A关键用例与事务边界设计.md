## 1. 目的与总体结构

本文将 P02 的 S1–S6 串成可实现、可验证的业务流程，明确谁拥有事实、事务如何提交、跨模块通过哪些端口协作，以及哪些步骤必须 fail-closed。本文不编码、不建库、不运行正式数据，也不扩大支付/履约范围。

```text
Customer/Public API ─┐                 ┌─ Admin API / Admin UI
                     ├─ command/query ─┤
公开只读 Read Model ─┘                 └─ Admin application use cases
             │                                  │
             ▼                                  ▼
 southleaf_public  ← 狭窄发布事务适配器 → southleaf_admin
 (published safe projection)       (canonical private facts)
                                             │
                                  external task/outbox → provider
```

`public-api` 只读公开投影；客户命令通过受限客户业务用例进入私有写模型；`admin-runtime` 使用后台会话/授权并调用同一业务核心的管理用例。任何 Controller 不得绕过 application service 直接组合 JDBC 表。预约/订单写模型与公开读模型是不同边界，不把阶段一 DDL 当阶段二写模型。

## 2. 业务不变量

| 不变量 | 责任模块 | 必须由何处保证 |
|---|---|---|
| 未验证的身份不创建真实客户关系；手机号相同不自动合并账号 | customer/identity | 应用用例 + 唯一约束/人工核验流程 |
| 待确认申请默认 48 小时过期且不占硬档 | reservation | 数据库时间/条件更新 + 定时失效作业；期限是 P02 基线，不含定金流程 |
| 同一可售档期最多一个已确认占用 | reservation | 资源锁/唯一约束/同事务 CAS；不能只依赖页面禁用 |
| 确认预约、排他占档、唯一订单、订单快照、审计与可靠通知任务原子写入 | reservation/order/audit/outbox | 同一 MySQL 事务，外部消息仅提交后发送 |
| 取消/改期不会造成旧档、新档和订单版本不一致 | reservation/order | 按全局排序拿锁，单事务成功或回滚 |
| 公开内容必须满足发布状态、授权、媒体就绪及撤回状态 | content/authorization/media | publication transaction 与公开 projection 同步更新 |
| 任何客户只能读取本人或其明确关联对象的数据 | customer/order | 服务端身份/关系校验，不能信任客户端传入 customerId |
| 金额/名称/产品版本等订单事实不可随内容当前值回写 | order | 确认时保存不可变快照与快照版本 |

如果 Q02 定金/付款规则、Q04 档期/时区规则、Q05 身份关联或 Q06 角色权限未确认，相关正式操作不得伪装为已可上线。阶段二可在合成数据与隔离配置中完成技术验证；任何试验策略都不得套用于真实客户。

## 3. 流程 A：内容编辑、发布与撤回（S2）

### 3.1 编辑与媒体就绪

1. 经后台认证与服务端 permission check，创建或编辑私有 draft；每次保存带 `revision`/`If-Match`，审计记录操作者、对象、操作和结果，不记录凭据/完整敏感正文。
2. 媒体进入私有上传暂存区。服务端检查扩展名、内容签名、尺寸/像素/字节数、可解码性、EXIF/GPS 与恶意载荷；生成衍生版本、hash、不可猜测 storage key。验证未结束时状态为 `PROCESSING`，不得公开。
3. 内容提交预览/发布时，application service 重新读取当前修订、媒体状态、业务资格和 A15 授权范围。不能沿用前端较早加载的检查结论。
4. 通过 D-507 专用 publication port，在同一 InnoDB 跨 schema 事务里更新私有发布状态和安全公开 projection/当前版本；成功后才返回 `PUBLISHED`。媒体对象存储和 CDN 不参与 DB 原子性。

### 3.2 撤回/资格失效

撤回、授权到期或资格失效必须阻止新的公开列表/详情/媒体读取。管理端先读取当前版本，进行权限和并发校验，在同一 publication 事务中写入权威撤回/资格状态并切换公开投影的可见性；事务不成功则不声称撤回完成。媒体适配器在每次受控访问时再次按当前公开资格校验，不把对象存储 key 当作访问授权。缓存失效/私有 CDN 清理是提交后的外部副作用；确认前不能对用户展示“已撤回且所有缓存已清除”。

### 3.3 故障

发布事务回滚时旧 release 保持 active；新对象可以成为待清理孤儿，但不能在公开库留下悬空引用。重复相同 `publicationCommandId` 返回原结果。版本已变化则返回冲突，不得静默覆盖。撤回 DB commit 结果未知时按命令 ID/当前 active version 复查，不直接补写新 release。

## 4. 流程 B：线上预约申请（S5，依赖 S4 身份与档期）

1. 用户先浏览公开业务、套餐和可预约档期；提交预约前按需完成客户认证，公开浏览无需先登录。
2. 服务端从客户会话解析主体，验证关联/联系渠道；不得相信 request body 中的 customerId、价格、套餐名称、可用状态或订单状态。
3. `CreateReservation` 用例校验套餐快照/可售规则、填写字段和客户关系，写入 `PENDING_CONFIRMATION`、过期时点、idempotency 结果及审计/通知任务；默认 48 小时内处理。
4. Pending 申请不持有硬档、不创建已确认订单；可展示“已提交，等待确认”，不可显示“预约完成”。如果仍需防止过度申请，只能增加限流/反滥用策略，不得把软提醒误称档期锁。
5. 创建成功后通知任务在事务内落库，提交后异步发送；响应丢失后相同幂等键重试只返回同一申请。

## 5. 流程 C：后台确认、订单创建与离线登记（S5）

### 5.1 原子确认

`ConfirmReservation(reservationId, slotId, expectedRevision, idempotencyKey)` 在单一业务事务内：

1. 先写/取得命令幂等记录；按固定锁序锁定 reservation 和目标 slot（多个资源按稳定 ID 顺序）。
2. 断言 reservation 尚为 PENDING、未过期、slot 当前可售且没有其他确认占用；在同一数据库约束下建立唯一 slot occupancy。
3. 条件更新 reservation 为 CONFIRMED 并记录操作者/时区明确的确认时间与档期版本。
4. 使用当时套餐、价格、货币、客户联系快照和规则版本创建唯一订单；数据库唯一键确保每个预约最多一个原始订单。
5. 追加审计及可靠通知任务，提交后才向管理端/客户确认成功。

上述任一步失败都回滚，不能出现“档期锁了但预约仍 pending”“已确认但无订单”或重复订单。订单快照只保留完成履约所需最小资料，不复制不必要身份证明。

### 5.2 离线/电话预约

工作人员通过专用“登记离线预约”命令创建来源标记为 `STAFF_OFFLINE` 的申请，并记录经核验的联系方式、操作者和来源；随后复用完全相同的确认/占档/订单命令。不得使用隐藏 API、手工 SQL 或跳过冲突检查来“强制占档”。离线登记先提供可审计数据，不能据此推断线上客户身份已绑定。

## 6. 流程 D：失效、取消、改期与履约最小能力（S5/S6）

- Pending 过期作业使用条件更新 `status=PENDING AND expires_at<=db_now`，只允许一次变为 `EXPIRED`；发送失效通知由 outbox 在提交后处理。与后台确认竞态时只有一个条件更新成功；过期后的确认必须拒绝。
- 取消命令校验角色、当前状态、版本和取消政策版本；阶段二不含退款。在事务内解除占用、更新 reservation/order 状态、写审计和通知任务；重复请求幂等。
- 改期先锁定旧档和新档（统一顺序），确认新档可售后原子建立新占用、更新预约/订单修订和时间快照，再释放旧档；失败回滚保留旧预约。若业务规则要求“新档先预留一段时间”属于 Q04/Q02 待确认，不得在此擅加。
- 阶段二订单履约只允许最小安排备注/时间和待办流转（如 P02/S5 明确）；不实现付款确认、退款、交付私密文件、售后或完整作品交付。

## 7. 锁顺序、幂等与时间

推荐锁顺序（所有命令遵守，不得逆序）：`idempotency command` → `reservation`（按 ID 排序）→ `slot/resource`（资源 ID 排序）→ `order`（按 ID 排序）→ `audit/outbox`。MySQL 对并发插入仍须用唯一约束和捕获冲突后的结果判定；不能仅依赖 `SELECT ... FOR UPDATE` 锁一条尚不存在的占用记录。

命令幂等键作用域为 `actor/tenant + operation + client key`，持久化请求摘要、结果资源 ID、状态与过期/保留规则。相同键不同请求摘要返回 `IDEMPOTENCY_KEY_REUSE`；并发相同命令等待或重读结果，不能产生第二笔业务事实。

有效期、创建时间、预约时间和媒体/授权期限都保存明确 instant（UTC）；面向用户展示时再使用配置的 IANA 时区。业务时区、跨午夜、夏令时、同一天多场次、服务时长/缓冲规则属于 Q04 决定项；在确认前 UI 和 API 不自行把服务器本地时区当规则。

## 8. 审计、通知与外部副作用

业务事实更新与最小审计事件、通知 outbox 在同一事务提交。审计事件应包含 actor id/type、command id、对象类型/ID、动作、前后版本、时间、结果和必要理由码；禁止日志记密码、session token、验证码、完整证据或完整客户隐私内容。

外部发送适配器领取具备到期 lease 的任务，在事务外调用 provider；成功后记录 provider message id/结果。超时语义不明时先按 provider idempotency/correlation 检查，再重试；不能把 exactly-once 外发当作数据库能保证的事实。失败任务呈现待办、尝试次数、下次重试和不可重试原因；人工重试必须幂等并审计。

## 9. 模块交互规则

- `content/works/catalog` 不直接更新 `southleaf_public`；只经 `PublicationPort` 公开发布。
- `customer` 是客户主体与身份关联的唯一入口；预约/订单引用内部 customer id，不用微信 openid/手机号做跨系统主键。
- `reservation` 负责申请、档期可售性、占用和确认状态；`order` 负责不可变的商业快照和后续订单修订，不互相修改对方表。
- `notification` 接受业务事件/明确通知意图；不得从订单状态猜“支付成功”或宣称客户已看见。
- `admin-security` 仅回答认证/会话/权限；业务 use case 收到不可伪造的 actor context，不直接查询 security 表。
- `audit` 与 idempotency/outbox 是共享基础设施端口，保持写入位置/事务契约明确，不依赖静态全局服务。

## 10. 2B 与阶段三门禁

进入 2B 的前提是 G2A 基本功能验收及真实接入清单准备；真实微信身份/回调域名、生产 MySQL grants/migration、实际通知、正式人员角色、真实 A15 授权、备份恢复、HTTPS/域名/CDN 和回滚演练在 2B 集中接入并于正式开放前完成。Q02/Q04/Q05/Q06 中影响正确性的规则在各自设计/实现前确认，实际经营数值和生产资源于 2B 填入并复验；不能把 2B 验收结果倒置成进入 2B 的循环前提。

支付、定金、退款、完整履约/售后、私密交付/下载授权、客服聊天、营销推送、真实个人/儿童影像迁移均不属于本文交付；它们按 P02 阶段三另立设计和验收，不在阶段二里预留未经批准的“已支付”状态。

## 11. 验收场景索引

- 预约申请重放/同键不同 payload、过期与确认竞态、两名客户争抢一档、后台线下与线上争抢同一档。
- 确认事务注入订单/审计/outbox 任一写入故障，验证所有事实回滚；唯一订单约束拒绝第二次确认。
- 改期同时竞争目标档；原档保留直到新档成功，提交失败不丢失原预约。
- 发布使用过期版本、媒体未就绪、authorization 撤回、publication 写入部分失败；公开查询始终满足投影资格规则。
- 通知 provider 超时后重放，不重复预约/订单；失败任务可见可审计。
- 通过独立运行身份、双 schema MySQL 集成测试和负向权限测试证明 D-507/D-506 的边界；H2/Mock 结果不能替代锁、唯一约束或 grant 证据。

## 13. S2-A 单作品上传至撤回事务序

### 13.1 主路径

1. 管理员通过已保护的 HTTPS admin-web 在当前作品命令中上传一个合成 JPEG/PNG。服务端先执行字节/格式/像素限制、完整解码、重编码与元数据清除；原件、`thumbnail`、`preview` 写入专用私有对象根，生成 SHA-256 与随机内部 key。客户端只收到 media ID、状态和允许显示的元数据。
2. 成功完成处理后以 admin business writer 记录 `READY` asset 与 variant 元数据。对象写入与数据库不是一个事务：数据库失败只留下不可公开的孤儿对象，由带引用核验的清理任务处理；任何对象失败都不创建 `READY` 状态或作品绑定。
3. 建立/修改单作品 DRAFT，以强 If-Match 对应当前修订写入新的不可变 revision 和媒体绑定。草稿写入不触碰 public V2、V1 active publication 或公开版本号。
4. 管理端 preview 只读草稿候选版本；状态/原因仅显示安全类别（例如“授权待确认/媒体未就绪”），不返回证据文本、姓名、私下备注、对象 key 或签名 URL。
5. 发布命令按 `(actor, operation, work, idempotency key)` 做 digest 去重并检查 If-Match。按 ADR-005 选定的按作品 V2 overlay，publication port 在 D-507 规定的统一锁序中复核媒体 READY、封面/绑定、公开白名单、当前授权 authority revision/scope/purpose/channel/UTC 时间窗；一次本地事务写 public V2 release、最小授权 projection、active pointer、epoch、命令终态与审计。
6. 既有 public-api 列表/详情从合并后的 CatalogSnapshot 读取公开作品；summary/detail 字段和同源媒体路由不变。游标版本组合 V1 release 与 V2 projection epoch，发布/撤回均使旧游标失效。小程序通过公开作品读取和媒体网关展示 `thumbnail`/`preview`，不是页面 mock。
7. 撤回以新的幂等命令和 If-Match 关闭当前 active pointer 并增加 epoch；不删除对象和历史。新列表/详情不返回该作品；媒体 GET/HEAD 重新检查授权和 access stamp，撤回提交后不得开始新读取。已在提交前发出的字节不可追回。

### 13.2 原子性、并发与失败恢复

草稿修订与上传命令使用各自的乐观版本/幂等范围。publish、withdraw、A15 授权失效共同服从 D-507 锁序；若权威 owner 无法与 publication 边界在一个同实例 InnoDB 本地事务内协调，S2 不得实现“假原子”业务撤回，也不得通过异步补偿对外宣称已撤回。自然到期由读取当下按 UTC `valid_from <= now < valid_until` 判断，定时任务不可作为唯一门禁。

相同 key/摘要重放返回原终态；同 key 不同摘要返回冲突。连接断开、客户端超时或提交响应丢失时先按 key 复查；不可判定提交失败则不盲目新建 publication。授权/数据库/对象/投影读取异常均不返回旧缓存、旧媒体或宽松空授权；公开 GET/HEAD 与管理预览按各自错误契约失败关闭。

### 13.3 2A 证明边界

S2 的 E2E 仅在本机隔离 profile、合成作品/媒体、双 schema MySQL/InnoDB、专用运行身份和可清理对象目录完成。验收需要真实后台 HTTP 会话/CSRF、真实媒体处理、真实 DB grants/事务、真实 public API 和小程序作品页请求。该证据仅证明该合成纵向切片；A15 真实权威接入、2B 平台域名/对象存储/缓存、真机/UAT、生产授权和恢复演练仍分别待验。
