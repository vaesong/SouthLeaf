# 总体模块与依赖设计

> 文档编号：D-101

> 更新日期：2026-10-06
> 上游需求：A04-A16
> 上游架构：AT01、AT04、AT05、AT07、AT08、AT09
> 关联计划：P01

## 1. 设计目标

把 SouthLeaf 的三类客户端、模块化单体后端、数据/文件基础设施和外部适配层组织成可演进的依赖结构。本文只确定逻辑边界和依赖方向，不锁定 Java 包名、数据库表或部署拆分。

## 2. 目标分层

```text
小程序 / 品牌官网 / 管理后台
              ↓
       入口适配与接口层
              ↓
       应用服务与用例编排层
              ↓
       业务模块与领域规则层
              ↓
   持久化端口 / 外部服务端口 / 任务端口
              ↓
 MySQL / 对象存储 / 支付 / 通知 / 运行设施
```

入口层只解析输入、认证、调用应用服务和呈现结果；核心状态、金额、权限、冲突和文件访问资格由服务端业务模块决定。

## 3. 业务模块

| 模块 | 权威事实 | 主要被谁使用 | 不拥有 |
|---|---|---|---|
| content | 品牌资料、公开内容发布 | 小程序、官网、后台 | 作品、订单、私密成片 |
| works | 案例、图片展示元数据、公开资格消费 | 小程序、官网、后台 | 授权同意/撤回事实、私密交付 |
| catalog | 摄影业务、套餐版本、公开服务信息 | 三端、预约、订单 | 预约冲突、支付事实 |
| customer | 身份、客户档案、联系人/拍摄人关系 | 客户端、预约、订单、交付 | 后台角色、支付平台身份 |
| reservation | 预约申请、确认、拒绝、改期、档期占用 | 小程序、后台、订单 | 订单金额、支付、交付 |
| order | 订单交易约定、快照、订单生命周期、履约子域 | 客户端、后台、支付、交付 | 支付事实、文件访问 |
| payment | 支付计划、支付尝试、支付事实、退款、对账异常 | 客户端、后台、订单、交付 | 订单服务内容 |
| delivery | 交付批次、文件业务元数据、私密访问授权 | 小程序、后台、作品资格消费 | 对象存储技术实现 |
| aftersales | 售后问题、受理、升级、解决和关闭 | 客户端、后台、订单/支付/交付 | 覆盖原始业务事实 |
| notification | 通知任务、渠道、模板、重试和失败 | 所有业务模块、后台 | 核心业务状态 |

公开案例授权事实归属 `delivery`/A15；`works` 只消费授权结果并计算公开案例资格；`content` 只负责首页和品牌内容编排。

## 4. 通用后端能力

- auth：客户和后台人员身份认证、会话和令牌；
- authorization：角色、操作、资源归属和状态权限；
- error：稳定业务错误码、安全提示和 request id；
- logging/audit：运行日志、业务审计和安全事件；
- storage：对象存储上传、读取、短期访问和一致性检查；
- task：异步任务、重试、查单、补偿和超时升级；
- config：环境、业务和敏感配置；
- observability：健康检查、慢请求、外部依赖和指标。

通用能力不能直接拥有预约、订单、支付、履约、交付或授权业务事实。

## 5. 关键依赖约束

1. `reservation` 确认用例通过订单应用能力创建订单，不通过直接写订单表完成成单。
2. `order` 保存套餐和价格快照，不在支付或客户查询时读取当前套餐替代历史约定。
3. `payment` 只写支付事实并通过明确应用事件通知订单/交付，不修改订单服务内容。
4. `delivery` 根据支付确认、履约结果、发布状态、身份和授权判断访问，不直接信任对象存储地址。
5. `works` 消费 `delivery` 的公开授权结果，不创建第二套授权同意和撤回记录。
6. `notification` 发送失败不回滚业务事实，任务重试不能创建重复订单、支付、退款或授权。
7. 外部支付、存储、网盘和通知 SDK 只能出现在适配层，业务层依赖内部端口。
8. 模块之间不能互相直接读表形成隐式业务耦合；需要共享时通过只读查询、应用服务或明确事件。

## 6. 跨模块用例边界

| 用例 | 发起模块 | 必须保持的事实 | 外部/异步部分 |
|---|---|---|---|
| 确认预约并成单 | reservation | 冲突校验、排他占档、预约确认、唯一订单和快照连续成立 | 通知异步 |
| 定金支付 | payment | 本地支付意图和订单快照金额先确定 | 支付下单、回调/查单、通知 |
| 确认拍摄完成并激活尾款 | order | 负责人/管理员确认履约后尾款才应付 | 通知异步 |
| 发布交付 | delivery | 文件校验、尾款、授权、发布和期限条件同时满足 | 对象访问凭证、通知 |
| 公开授权撤回 | delivery | 授权事实撤回和审计保留 | works/content 跨端资格刷新、缓存复核 |
| 退款 | payment | 申请、审核、外部结果和原支付事实关联 | 退款平台调用、查询、通知 |

## 7. 当前草案的评审问题

- 是否需要将 `aftersales` 作为独立业务模块，还是初期作为订单/支付/交付的统一工单子域；
- 阶段一是否只建设公开内容授权结果查看，还是同时建设授权申请和记录入口；
- 阶段二是否需要在订单域内先建履约子域的全部状态，还是只开放预约和基础安排；
- 供应商适配层的第一批具体端口和失败语义；
- 未来何种业务复杂度才触发独立 `fulfillment` 模块。
