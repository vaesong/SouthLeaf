# 管理后台内容、预约与订单运营

> 文档编号：D-607

> 更新日期：2026-10-25
> 上游需求：A05、A07、A10-A13、A16
> 上游架构：AT04、AT05、AT06、AT07、AT09

## 1. 设计目标

- 让有既存后台 capability 的受控操作员，在 S2 2A 本地隔离环境完成一个合成作品的上传、编辑、预览、发布、公开读取与撤回闭环。
- 管理 UI 是 `admin-web` 的真实认证后页面，调用同源 `/api/admin/v1`；继续使用 S1-D session、Origin/CSRF 及服务端 capability 检查。隐藏按钮、路由守卫或客户端状态不是安全边界。
- 页面只展示服务端判定后的最小状态，不提供授权事实/证据管理，不扩展未经 Q06 确认的生产角色。发布成功必须来自服务端事务终态，不能用乐观 UI 或静态 mock 替代。
- 本节是 S2 首个纵向切片，不是完整 CMS、真实授权审查系统、2B 平台上线或生产运营批准。

## 2. 内容、作品、业务和套餐维护

S2 页面仅提供作品列表、建立空草稿、单作品详情/修订编辑、单图上传及衍生状态、封面选择/排序、只读预览、发布与撤回。字段按 D-302 的公开白名单收敛到标题、简介、分类码与媒体绑定；不含价格、套餐、客户、档期、订单、联系信息或批量导入。

上传状态明确显示 `RECEIVING / PROCESSING / READY / REJECTED / FAILED_RETRYABLE / WITHDRAWN`。只有服务端确认 `READY` 的 `thumbnail`、`preview` 才可绑定；页面不接收外部图片 URL，不显示原图直链、对象 key 或签名地址。草稿编辑使用强 If-Match 修订 ETag；冲突须提示刷新/复核，不覆盖他人新修订。创建/上传/发布/撤回按 D-403 使用命令幂等键。

所有 2A 画面和对象均使用合成资料及专用可销毁测试目录；不得用真实客户作品、儿童/家庭/婚纱素材或授权证据填充演示。

## 3. 公开授权资格与发布阻断

页面以只读门禁摘要呈现 `VALID / INVALID / UNKNOWN / EXPIRED` 与必要的 scope/purpose/channel/有效期类别。只显示明确可供操作员决策的安全状态，不显示证据文件、主体姓名/联系方式、授权原文、私下说明、法律撤回原因或内部对象地址。

发布按钮可按已知状态禁用以改善体验，但服务端在每次发布、预览媒体及公开读取时都必须重新检查当前权威授权版本、媒体范围和时间窗。`UNKNOWN`、依赖故障、缺行、已到期、scope 不匹配均 fail-closed；UI 不能把失败映射成“已授权”。S2 synthetic profile 的演示判定必须显式标注 `TEST_SYNTHETIC`；生产配置不得加载它。

后台没有“授权/批准/补证/法律撤回”按钮。A15 权威撤回由独立责任边界处理；不能以作品业务下架按钮冒充法律授权撤回。作品撤回后 UI 显示服务端终态及命令 ID，公共列表/媒体路由应已拒绝新读取。

## 4. 固定时段、封档和预约申请

> 本节为 S4/S5 设计契约。页面实现属后续切片；本轮不开放真实客户入口。

### 4.1 固定时段（档期）

时段是**已物化的记录**，不是每次请求现算的规则。后台展示每个时段的开始/结束（UTC instant）、业务时区与显示偏移、容量（阶段二固定为 1）、规则版本与修订号。列表默认按开始时间升序。

时段创建与封档的经营参数——营业时区、营业日、服务时长、缓冲、跨午夜处理、节假日、提前量、容量规则——由调用方以配置形式提供，**不在代码或界面中写死默认值**（Q04 未确认）。当这些参数未确认时，界面只呈现已物化的时段记录，不做"按规则自动生成时段"的承诺。

时段状态只有 `OPEN` 与 `CLOSED`。封档是**对后续确认的单向关闭**：已确认的预约与既有订单不受影响，界面必须同时显示"该时段已有 N 个已确认预约"这类事实，避免操作员误以为封档会撤销已成交的约定。

### 4.2 预约申请

申请入口展示：客户主体、所选套餐版本、期望时段或"由运营确认"、来源（客户线上/线下录入）、失效时间。申请落库后状态为 `PENDING_CONFIRMATION`。

界面必须明确告知三件事：

1. **申请不占档期**。申请期间该时段仍可被他人申请；只有确认才独占时段。
2. **申请有有效期**。阶段二沿用 P02 的 48 小时基线，自申请创建时间起算；界面显示具体失效时刻（UTC）与剩余时间，到期后申请自动失效且不可复活。
3. **申请不等于订单**。确认前不产生订单、不产生金额快照。

同手机号、同微信或姓名相近**不会**自动合并到既有客户；界面在发现可能的既有主体时只给出"可能重复"的候选提示，由操作员显式走关联申请流程（Q05 默认不自动关联）。

### 4.3 操作与幂等

创建申请、封档、提交关联申请都带 `Idempotency-Key`；重复提交同一请求返回同一结果并标记为重放，界面不得因此创建第二份申请。同键异载荷返回冲突错误，界面提示操作员重新发起而不是自动换键重试。



## 5. 确认、拒绝、冲突、取消和改期

### 5.1 确认（原子成单）

确认是本模块风险最高的操作，界面必须表达"这是一次原子提交"：

- 提交前展示将要确认的事实：客户主体、套餐版本与显示名、币种与金额、时段与其 UTC 起止、业务时区与显示偏移、当前预约修订号。
- 提交携带预约的预期修订号（`If-Match`）。若期间有他人改动，返回版本冲突，界面提示刷新后重新核对，**不自动覆盖**。
- 服务端在**单一事务**内完成：占用时段 → 预约转 `CONFIRMED` → 创建唯一订单 → 写入不可变快照 → 写审计与通知 outbox。任一步失败全部回滚，不会出现"档期已锁但预约仍待确认"或"已确认却没有订单"。
- 成功后的界面状态来自服务端事务终态，不使用乐观 UI；显示订单号、快照中的时段与金额。

### 5.2 拒绝

对待确认申请可执行拒绝，状态转 `REJECTED`（终态）。拒绝需填写理由码，界面显示为运营可见的内部类别，不显示给客户。拒绝不释放档期（申请本就不占档）。

### 5.3 冲突

时段被他人抢先确认时返回"时段已不可用"。界面必须：刷新可售时段列表、提示重新选择、**不自动改到别的时段**。自动改期会改变客户已表达的意图，超出运营确认范围。

### 5.4 取消

取消已确认预约：服务端在同一事务内释放时段占用、预约转 `CANCELLED`、订单生命周期转 `CANCELLED` 并追加一条订单修订。界面提示"取消表示服务约定已取消"——阶段二**没有退款语义**，界面不得出现退款、扣费或结算相关按钮或文案。

### 5.5 改期

改期在同一事务内先建立新时段占用、再释放旧时段，失败时**旧时段与原预约时间完全保留**，不会出现两头都空或两头都占。改期冲突（目标时段已被占用）时返回明确冲突，界面不自动另选时段。

改期在订单侧表现为**追加一条修订**（原时段 → 新时段），已确认快照保持不变。界面同时展示"当前安排"与"历史修订"。

### 5.6 权限

确认用 `RESERVATION_CONFIRM`，取消用 `RESERVATION_CANCEL`，改期用 `RESERVATION_RESCHEDULE`。按钮可按 capability 与当前状态禁用以改善体验，但服务端在每次执行时重新校验；界面禁用不是安全边界。



## 6. 确认成单和订单快照查看

### 6.1 订单详情

订单详情是**不可变快照**加**修订历史**两部分：

- 快照区：确认时刻的套餐版本、显示名、币种与金额、价格版本、时段与其 UTC 起止、业务时区与显示偏移、安排修订号、下单主体与来源、确认操作者与确认时间。快照**不可编辑**，界面不提供任何"修改快照"入口。
- 修订区：按修订号升序的追加列表，每条含变更字段、理由码、时间与操作者。修订只追加，界面无删除/编辑入口。

套餐或价格在确认后发生变化时，历史订单显示**仍为快照内容**，不随现价变动。这是刻意的：成交约定不随目录调整而改变。界面不提供"同步到现价"按钮。

### 6.2 不出现的内容

订单页面**没有**支付、定金、退款、履约交付相关的状态字段、标签列或按钮。阶段三才引入这些概念，现在出现会形成错误预期。

订单生命周期只有 `ACTIVE` 与 `CANCELLED`；阶段二的履约状态只有 `UNSCHEDULED`、`SCHEDULED`、`NEEDS_ATTENTION` 三个最小类别，不是完整履约模型。

### 6.3 时间呈现

所有时间点按 RFC3339 UTC 展示并同时给出业务时区的显示偏移，不依赖浏览器所在时区。跨日、跨月与夏令时边界以 UTC 为准，避免"看起来是同一天实际不是"。



## 7. 客户、联系人和隐私信息

### 7.1 客户主体与展示

客户列表与详情展示：内部主体标识、状态、显示名、语言、关联关系与验证状态。**联系值默认掩码**（例如手机号仅保留末两位），展开明文属高敏感操作，需明确权限与审计，且不在界面默认展开。

身份关联以外部身份指纹呈现，**不展示平台原始标识**。关联关系显示角色、用途、验证状态、有效期与是否已撤销。

### 7.2 关联申请

提交关联申请时，界面明确说明：**申请在批准前不产生任何访问权限**。批准动作会创建一条已验证的关系记录并记录操作者与时间；拒绝后该申请为终态。同一作用域存在待处理申请时，界面引导复用既有申请而不是重复发起。

同手机号、同微信、姓名相近**永不触发自动合并**。界面只提示"可能已有相关客户"并引导人工核验（Q05）。

### 7.3 最小化与不可推断

- 客户档案、身份关联、联系信息、预约与订单都是私有管理数据，**不进入公开投影**；公开小程序接口看不到这些信息。
- 订单快照只保留完成服务约定所必需的最小联系快照；当前联系方式更新不改变历史订单显示。
- 界面、日志与错误提示不得包含令牌、对象 key、外部原始 subject 或完整联系值。
- 建立客户关系或预约成功**不推导**任何公开影像授权（A15 授权是独立事实）。

### 7.4 演示资料

所有 S4/S5 界面在 2A 阶段只使用合成资料与专用可销毁测试目录，不出现真实姓名、手机号、微信或真实预约记录；不发送任何真实通知。


## 8. 通知、审计和异常

S2 仅记录最小后台操作审计和命令终态；不发送任何真实通知。M4/M5 的隔离后端能力包含事务 outbox、lease/retry/dead-letter worker，但 runtime 调度、真实 provider 和人工恢复界面仍未接线。权限/存储异常与版本冲突应映射为可行动的安全错误，不得在日志或 UI 暴露密钥、外部 subject 或联系明文。本文 §11 记录实现范围；它不改变 S2 真实通知仍关闭的边界。

## 9. 测试和验收

验收必须走真实后台 session/CSRF、管理 HTTP API、图片解码/衍生、双 schema MySQL/InnoDB 和真实 public-api/小程序作品页请求，不能只跑页面 mock。基本路径为：合成图片上传并校验 → `READY` 和两种衍生图 → 建草稿并预览 → 装载明确标记的 synthetic 授权判定 → 发布 → public 列表/详情与同源媒体读取 → 撤回 → 新的公开 JSON、GET/HEAD 与旧游标均拒绝/失效。

负向检查含伪装/损坏/超限图片、版本冲突、重复与同键异 payload、媒体不 READY、授权缺失/错误 scope/自然到期/依赖不可用、发布事务回滚、未知提交复查、媒体撤回后复读、对象 root 隔离及清理。保留不含秘密/真实资料的可复现证据，列出数据库版本、身份/grants、浏览器/API 测试数、退出码及清理状态。该验收只证明 S2 合成 2A 切片，不覆盖 2B、真实授权、真机或生产。

## 10. 待确认问题

- Q02/Q04/Q05 中尚未确认的经营、预约和订单策略仍开放；不因单作品 S2 闭环推定。
- Q06 的真实后台角色/授权矩阵需负责人批准；S2 只复用已实现 capability gate，不建立默认管理员或新的生产角色。
- A15 权威授权 owner、修订、撤回事件和接受标准须在真实接入前确认；S2 测试授权不可迁移成真实许可。
- 2B 前确认真实作品/人物/监护人资料来源、原件保留、对象存储/扫描/备份、域名/CDN/小程序缓存和撤回传播责任。未确认时继续使用 synthetic profile 并保持生产入口关闭。

## 11. S4/S5 后端能力实施事实与运行边界（2026-10-25）

D-607 §4–§7 仍定义运营端的目标契约；本节区分后端已实现的能力和尚未交付的用户入口，不把数据库集成测试误作 UI/API 验收。

- `backend/admin-booking` 已提供客户主体、外部身份 fingerprint（不接收原始 provider subject）、加密 contact point 写入与 masked-only 读取、需显式批准的客户关联申请、可配置档期、预约确认成单、唯一订单快照、取消/改期修订及事务 outbox 能力。
- 时区、时段、容量与重试策略均由调用方显式提供；不新增经营默认值，不自动合并客户。支付、定金、退款与履约结算字段/能力仍不在此模块。
- 最终隔离验证为用户机器 MySQL 8.4.11/InnoDB **73 单元 + 28 数据库/并发 IT = 101/101**。逐项测试 ID、精确命令与未覆盖项见[跨模块并发/幂等矩阵 D-703 §7.6、§8.3、§8.4](../../07_测试与验证/03_跨模块并发幂等测试.md)；阶段状态见[阶段二实施跟踪 §23](../../../开发与演示/阶段二实施跟踪.md)。
- 这证明的是隔离 schema 上的后端 capability/JDBC 行为，不是 `admin-runtime` Spring/HTTP controller、session/actor 解析、`admin-web` 页、小程序入口、真实通知或生产 grants。outbox dispatcher/worker 需由 runtime 显式注入 retry/lease policy；scheduler/provider/人工死信恢复界面未接线。
- 仅用合成夹具；未触及真实客户、支付、真实通知、生产凭据或 3306。Q02/Q04/Q05/Q06 仍是待确认策略，24 小时 deposit baseline 未变更。
