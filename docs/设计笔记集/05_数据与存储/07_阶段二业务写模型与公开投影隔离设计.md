## 1. 目标与边界

本设计定义阶段二管理写模型与阶段一公开读模型之间的数据隔离、发布投影、数据库身份和事务边界。它补足 D-505/D-506 的 S1 安全身份方案：公开 Reader 不变；管理认证存储、私有业务写入和公开发布投影不是一个“全库 Writer”。

本设计不改写已应用公开 V1，不生成迁移脚本，不确定最终表字段，不配置真实 MySQL/账号/凭据，也不宣称生产授权已完成。V1 继续作为阶段一公开读取基线；阶段二通过 V2+ 增量扩展。2A 只使用隔离测试身份和虚构数据。

## 2. 数据事实分层

```text
管理业务主事实（私有）                 公开发布读模型（仅安全投影）
southleaf_admin                       southleaf_public
────────────────────                  ────────────────────
草稿/修订/客户/预约/订单      publish   已发布品牌/业务/套餐/作品/媒体
A15授权证据和核验事实       ────────→   最小公开资格/可见状态
后台操作者/会话/安全审计                 当前公开版本指针
内部任务/outbox                          不含客户/授权证据/后台凭据
```

| 事实/数据 | 权威归属 | 存储边界 | 可见性 |
|---|---|---|---|
| 品牌、内容草稿、成员与联系配置 | A05 | 私有管理业务 schema | 管理权限范围内可见；发布后只投影经批准字段 |
| 作品、业务、套餐及版本 | A06/A07 | 私有管理业务 schema | 发布前仅后台；发布后生成公开读模型 |
| A15 授权主体、证据、用途、范围、期限、撤回 | A15 | 私有管理业务 schema，严格限权 | 公开库不存证据、身份资料或内部原因 |
| 客户身份、联系方式、线上/线下关联 | customer | 私有管理业务 schema | 仅本人和经授权人员；不投影到匿名公开库 |
| 预约、档期占用、订单快照、修订 | reservation/order | 私有管理业务 schema | 本人和经授权人员；不投影到匿名公开库 |
| 管理账号、密码摘要、会话、权限、安全审计 | adminsecurity | 管理安全表，按 D-506 单独授权 | 不进入公开读模型；业务 Writer 不得读取 |
| 已发布公开内容 | content/works/catalog 发布结果 | `southleaf_public` | 公开 Reader 只读消费 |
| 原始/衍生媒体字节 | media/object storage | 受控非公开存储 | 仅经受控媒体适配器读取；DB key 不是公开 URL |

`admin_*` 安全表和私有业务表可以由同一受控管理 schema 承载，但**数据库账号必须按表集分开**。业务账号不能读取密码摘要、权限、session 或 security audit；安全会话 Store 不能读客户、预约、订单或内容正文。

## 3. Schema 与迁移边界

- `southleaf_public`：保留 V1 已实施公开读模型与当前 Reader 行为。仅允许新增 V2+ 的公开投影字段/表/阻断表；表中只放经过审核的公开字段、公开媒体引用和最小资格投影，不能放客户资料、授权证据、后台备注或私密地址。
- `southleaf_admin`：承载 canonical 管理业务记录及已独立定义的 `admin_*` 安全事实。管理业务迁移与 D-505 管理安全历史按版本追加；不得修改已应用 V2，不自动 baseline/repair/clean。
- 公开 V1 与管理 V2+ 各用各自的显式迁移位置/历史；管理 runtime 不自动跑迁移。若未来把业务迁移拆成独立 history/CLI，需保留 D-104 的唯一迁移身份边界。
- 测试 `southleaf_public_it` 当前是共享测试 schema，只能证明其测试夹具下的 Store/事务实现；另外为运行身份/跨 schema grants 设计隔离管理测试 schema 和用户。测试 schema 不能用正式库替代，也不能据名称宣称已完成部署隔离。
- 两个 schema 可位于同一个受控 MySQL 实例，便于在受支持的 InnoDB 配置下使用同一连接做跨 schema 原子投影。生产部署必须实测并核实该拓扑；若使用不同 MySQL 实例，不能声称跨库 ACID，需另行设计 outbox/saga 与 fail-closed 屏障。

## 4. 数据库身份与连接池能力

以下身份是目标能力，命名为建议，不代表已创建账号或已授予权限：

| 身份 | 允许访问 | 明确拒绝 |
|---|---|---|
| `public_reader` | 现有 `southleaf_public` 公开 schema Reader 权限 | `southleaf_admin` 全部表、DDL、写权限 |
| `admin_security_writer` | D-506 中 `admin_account`/`admin_account_permission`/`admin_session`/`admin_security_audit` 精确权限 | 业务表、公开投影表、DDL |
| `admin_business_writer` | 经批准的私有业务写模型所需表级 SELECT/INSERT/UPDATE/DELETE | `admin_*` 安全表、`southleaf_public`、未归属业务表、DDL |
| `admin_publication_writer` | 已清洗的发布输入/状态表，以及 `southleaf_public` 公开投影表的最小表级权限 | 客户/预约/订单 PII、`admin_*`、公开 schema 通配权限、DDL |
| `admin_migrator` | 显式迁移所需管理 schema DDL/元数据能力 | 运行时注入、公开 Reader 使用、应用启动自动调用 |

所有身份均禁用 root、角色继承、`GRANT OPTION` 和 schema/global `ALL PRIVILEGES`。精确表、列和权限需根据 D-304–D-306/D-301–D-303 的最终读写矩阵生成；本设计不预先授予“业务方便”权限。

**运行池分工：**

1. 会话/权限 Store 只注入 `admin_security_writer`；其 DataSource 守卫与事务规则仍按 D-506。
2. 客户、内容、预约和订单 Repository 只注入 `admin_business_writer`；不把该池交给 Security Store。
3. 发布/撤回事务只通过 `admin_publication_writer` 的专用适配器；该身份不能被 Controller、通用 Repository 或任意 SQL 入口直接获取。
4. 公开 API 继续使用现有 Reader 池，不引入任何 `SOUTHLEAF_ADMIN_*` 配置，也不连接私有 schema。
5. 迁移身份只进入显式 CLI/受控运维环境，不进入任何 Web/runtime 进程。

## 5. 管理业务发布到公开读模型

### 5.1 目标协议

公开读模型不是管理写表的视图别名，而是经过发布校验、授权检查和字段脱敏后生成的安全投影。管理草稿修改不改变公开结果；只有明确发布事务可以切换公开版本。

建议发布/撤回在同一 MySQL 实例内，通过专用 `admin_publication_writer` 连接和一个 InnoDB 本地事务完成：

1. 锁定目标资源及当前发布/授权修订，校验 `If-Match` 或等价版本；
2. 读取已脱敏、可公开的发布输入，不读取 customer/order/证据/后台凭据数据；
3. 重新验证内容完整性、媒体 READY、当前授权主体/范围/用途/渠道/期限及作品资格；
4. 写入新的公开版本及其受控关系，更新 `active_publication`/可见性保护行；
5. 写回私有发布状态/修订和审计关联，提交；任何一侧写入失败则整个本地事务回滚。

对发布版本使用不可变 `content_version`/release 标识；不能原地改写当前公开版本。撤回在同一个受控事务中更新权威授权/发布事实与公开可见性/投影，使提交后的新读取立即拒绝。公开 Reader 继续按当前 public schema 读取，不需要访问 admin schema。

### 5.2 公开投影的安全内容

允许进入公开 projection 的字段须按各模块白名单转换，例如公开标题/描述、业务和套餐展示信息、已批准联系内容、作品公开说明、缩略图/预览引用、公开排序和资格状态。不得序列化整个 admin entity 或任意 JSON。

授权投影只表明“当前公开可见/不可见”所需的最小事实，不含授权人姓名、证据文件、私下说明、监护关系、联系方式、撤回原因或管理员身份。未知、失效、未审核、媒体未就绪或任何依赖不能可信校验时拒绝写入 `eligible` 投影。

### 5.3 外部媒体边界

媒体对象写入/处理属于外部副作用，不能与 MySQL 事务原子提交。流程须先将媒体放入私有根，完成真实格式、大小/像素、衍生图和 SHA-256 校验，再把媒体状态标成可发布；数据库发布事务只引用已 READY 的不可变对象。数据库事务失败会留下待清理孤儿对象，不产生公开引用；不得在事务回滚后“补发 URL”。媒体清理只能在无当前发布/保留版本/备份引用后执行。

## 6. 事务、幂等与故障语义

- 普通草稿命令只改变私有业务数据、版本和审计；不更新公开 projection。
- publish/withdraw 使用专用 publication port + 单一跨 schema 数据源/事务；事务边界包含 canonical 发布状态与 public projection 更新，不包含对象存储、微信、通知、邮件或外部 CDN。
- 重复发布命令必须有稳定的 `publicationCommandId`/幂等键；相同版本重复执行返回原结果，不再新建 release。
- 旧版本编辑使用乐观并发版本；冲突返回 `VERSION_CONFLICT`，不覆盖后写数据。
- 若出现 DB commit 结果未知，服务端以 publication command id 和两个 schema 当前版本复查，不盲目重发新的版本。
- 通知属于独立 outbox/task：在业务事务内登记通知任务，提交后再发送；发送成功不等于客户已读，失败不回滚预约/发布事实。
- 若跨 schema transaction 不可用，发布与撤回功能保持关闭或公开状态 fail-closed；不能在未设计的情况下改成异步双写并宣称原子一致。

## 7. 2A/2B 开放边界

| 能力 | 2A 隔离测试 | 2B 正式接入 |
|---|---|---|
| 私有写模型 | 虚构客户/内容/预约数据，MySQL 测试 schema | 真实业务记录和实际身份 |
| 公开投影 | 合成内容按发布命令写入测试 public schema | 经权属/授权核验的真实内容 |
| authorization | 明确标记的测试授权样本，验证失效/撤回行为 | 工作室确认的证据、范围、主体和责任流程 |
| 媒体 | 可合法用于测试的生成图/来源清楚的样本 | 真正素材、EXIF/GPS 处理和权属证明 |
| 运行身份 | 专用测试账号验证 exact grants | 运维创建独立 runtime/migrator/Writer 身份并验证 |
| Reader | 现有公开 Reader 行为回归 | 公开 Reader 仍不获 admin/business 权限 |

2A 的合成数据不能升级为真实客户同意、真实价格或真实运营资质；不能把测试身份用于生产。

## 8. 数据迁移与扩展规则

- 公开 V1 不修改；公开 projection 新字段/表通过公开 V2+ 追加。
- 管理 V2 安全迁移不修改；业务 canonical 表和必要索引通过管理 V3+ 追加，按 D-104 的 admin migration tool 显式执行。
- 公开和管理迁移必须都能在空隔离库构建、验证重复执行、失败后安全重试；迁移工具不自动创建/删库/修复历史。
- 如业务模型变更需要回填 projection，使用显式版本化 backfill 作业，批次、进度、断点、幂等键和回滚策略需单独设计；不能把业务表全量导出到公开 schema。
- `public_projection_writer` 仅拥有当前投影表需要的权限；新增表、列或 publish SQL 必须同步评审 grant matrix 和权限负向测试。

## 9. 验收设计

1. Reader 无权访问 admin schema；security writer 无权访问业务/public 表；business writer 无权访问 `admin_*` 与 public schema；publication writer 不能访问 customer/order PII、安全表或 public schema 通配权限。
2. publish 成功时 canonical 状态、public 当前版本和授权资格一致可见；任何 public projection 或 admin 状态 SQL 故障都全事务回滚。
3. revoke 成功提交后，同一 public query 入口的列表、详情、首页引用和媒体访问立即不再返回资格；旧 URL/缓存不能恢复。
4. 失败发布不切换 active publication；重复/过期 `If-Match` 不覆盖当前版本。
5. 图片处理失败、DB 回滚、对象存储故障分别符合孤儿清理/隐藏/重试规则；无原图回退或公开永久地址。
6. V1 迁移哈希保持不变；V2+ 只增量；迁移身份与运行身份不同。
7. `southleaf_public_it` 测试不充当跨 schema grants 证据；隔离 `southleaf_admin_it` / `southleaf_public_it` 双 schema 组合验证表级权限与跨 schema 事务。
8. 测试结果分开记为：模块/应用行为、MySQL 事务、跨 schema 权限、正式运维部署；缺少任一证据不合并宣称通过。

## 10. 当前边界与待评审事项

本设计建议同一受控 MySQL 实例托管 `southleaf_admin` canonical 业务/安全数据与 `southleaf_public` projection，以满足有限跨 schema InnoDB 发布事务；若生产部署必须跨数据库实例，必须重做发布一致性/撤回屏障方案。具体业务表和公开投影字段须在 D-304–D-306、D-301–D-303、D-403 定稿后形成表级矩阵。未经另行授权不建库、不改 V1、不部署身份或测试 grant。

## 11. S1/S2 衔接与未关闭的发布细节

本文件的 publication Writer 是 S2 新增能力，不改变 D-506 安全会话 Writer 四表边界。其运行时可位于管理进程内的专用 adapter，但连接池、数据库身份和可访问事实必须独立；Controller 不获取任何 DataSource。S1-A 不引入跨 schema 写入或业务表。

S2-A 可编码设计必须完成以下证明，当前不能把高层流程当作完整表级契约：

1. 明确私有授权证据、权威授权修订、最小公开资格状态和发布输入各自的唯一 owner；publication Writer 只读取/修改所需的非 PII 状态，不为核验授权授予全证据或客户表读取。
2. 权威撤回、发布输入版本与 public 可见性必须通过同一授权边界和事务/锁序更新；禁止 business Writer 先改权威状态，再等待 publication Writer 异步补写却宣称原子撤回。精确表权限须能支持该事实归属，否则先修订设计再编码。
3. 对授权自然到期，公开读取按保存的有效期和当前时间 fail-closed，不能只靠后台定时任务及时更新 eligible 位；时区/时间精度、历史版本恢复和 GET/HEAD/Range 均测试。
4. 明确提交后新请求的资格保证与在途请求/已下载字节的边界；撤回不承诺追回已发送字节。缓存/CDN 必须服从当前资格，不能生成永久公开原图地址。
5. 本地事务依赖受支持的同实例 InnoDB 拓扑；跨实例部署为新的架构决策，不在失败时偷偷切换异步双写。

这些细节由 S2-A 与 D-301/D-302/D-403 一起形成实际迁移、DTO、锁序、grants 和 PUB 用例。S1 结构迁移不等待未来表设计，但 S2-B 不能在本节未关闭时开始发布实现。

## 12. S2-A 单作品媒体发布的表级契约与事务序

### 12.1 所有权与版本边界

- 按 [ADR-005](../08_决策记录/ADR-005_S2单作品发布采用按作品V2公开投影.md)，S2 为首个作品新增 admin schema V5 业务表与 public V2 单作品公开 overlay；既有 admin 安全迁移 V2–V4 保持不变。不得原地改写 public V1 的 `catalog_release`、`active_publication`、`work_business`、`work_media`、`media_asset`、`media_variant`、`public_authorization` 或 `authorization_media`。
- 工作稿与修订的唯一 owner 是 admin schema V5：`admin_work_case`（稳定作品 ID、当前修订/状态）、`admin_work_version`（不可变修订内容）、`admin_work_media_binding`（修订到已 READY 媒体的封面/排序/用途绑定）。媒体 canonical owner 是 `admin_media_asset`、`admin_media_variant`，上传命令是 `admin_media_command`。
- A15 授权事实及其证据只归授权权威 owner。S2 的 `admin_work_authorization_gate` 是供 publication 用例只读的最小判定投影，由 A15 边界更新；只含 authority revision、状态、主体/媒体 scope 摘要、purpose/channel 与 UTC 有效窗、来源/摘要，不含姓名、联系信息或 `evidence_ref`。S2 管理 API 不写此表；隔离合成测试夹具单独标注 `TEST_SYNTHETIC`，不可用于生产 profile。
- 发布命令和审计 owner 是 `admin_publication_command`、`admin_work_publication_state`、`admin_publication_audit`，仅由 publication port 写。公开投影 owner 是 public V2：`public_work_release`（安全字段快照）、`public_work_release_media`、`public_work_release_variant`、`public_work_release_authorization`（最小资格快照）、`active_work_publication`（每作品当前指针/可见状态）及 `public_work_projection_epoch`（游标失效版本）。这些表构成单作品 overlay，不复制整个 V1 catalog。

`public_work_release_authorization` 只允许 `authority_revision`、资格状态、opaque scope/digest、purpose/channel、`valid_from_utc`、`valid_until_utc`、来源标记与发布时间等核验字段；明确禁止原始证据引用、主体姓名/联系方式、私下说明、撤回原因和管理员身份。新 overlay 的授权来源必须显式为 `WORK_OVERLAY_V2`，缺行或故障 fail-closed，不得回退查询 V1 许可。

### 12.2 精确运行身份与 grants

以下为运行身份的封闭表级权限矩阵；迁移 DDL 使用独立迁移身份。不得给业务身份 `GRANT ALL`、schema/global grant、`DELETE`/`DROP`，不得将 S1 安全身份扩权。

| 身份 | 允许范围 | 禁止范围 |
|---|---|---|
| `admin_business_writer` | admin schema V5：`admin_media_asset`=`SELECT/INSERT/UPDATE`；`admin_media_variant`=`SELECT/INSERT`；`admin_media_command`=`SELECT/INSERT/UPDATE`；`admin_work_case`=`SELECT/INSERT/UPDATE`；不可变 `admin_work_version` 与 `admin_work_media_binding`=`SELECT/INSERT` | 授权 gate、publication state/command/audit、public schema、admin V2 安全表和其他业务域 |
| `admin_publication_writer` | admin schema V5 的 `admin_media_asset`、`admin_media_variant`、`admin_work_case`、`admin_work_version`、`admin_work_media_binding`、`admin_work_authorization_gate`=`SELECT`；`admin_work_publication_state`、`admin_publication_command`=`SELECT/INSERT/UPDATE`；`admin_publication_audit`=`SELECT/INSERT`。public V2 的 `public_work_release`、`public_work_release_media`、`public_work_release_variant`、`public_work_release_authorization`=`SELECT/INSERT`；`active_work_publication`=`SELECT/INSERT/UPDATE`；迁移预置的 `public_work_projection_epoch`=`SELECT/UPDATE` | `admin_media_command`、V1 公开表、admin V2 安全表、授权 gate 写权限、其他业务表、删除/DDL |
| `public_reader` | public V1 既有白名单只读，以及 public V2 的 `public_work_release`、`public_work_release_media`、`public_work_release_variant`、`public_work_release_authorization`、`active_work_publication`、`public_work_projection_epoch`=`SELECT` | 所有 admin schema、任意写入及 DDL |
| `admin_security_writer` | 完全沿用 D-506 的既有安全表四表边界 | 不新增 S2 表/grant |

上线前以 `SHOW GRANTS` 与隔离双 schema MySQL 逐表逐操作做正反向验证；包括额外授权、表缺失、错误 schema、错误 CURRENT_USER、只读身份误授写入时启动失败。授权校验不通过不得降级成共享 root、自动建表或 H2/mock 通过。

### 12.3 事务/锁序与撤回边界

admin schema V5 与 public V2 必须是同一受支持 MySQL 实例上的 InnoDB schema；publication port 使用独立连接池/身份，但一次命令在单一连接、本地事务内跨 schema 写入，不使用 XA。禁止跨实例时异步双写；拓扑不满足即关闭发布功能。

固定获取顺序：`admin_publication_command` 的唯一幂等键行 → `admin_work_case` → 目标 `admin_work_version` → 去重后按 media ID 字典序锁定全部 `admin_media_asset`/variant → `admin_work_authorization_gate`（共享锁复核当前权威 revision/时间窗）→ `active_work_publication` → `public_work_projection_epoch` → 追加 `admin_publication_audit`。发布、作品撤回与授权撤回竞争必须遵守同一顺序；涉及多作品的授权撤回按 work ID 字典序扩展，S2 UI 暂不开放批量命令。

发布事务校验 If-Match、资产 READY、修订绑定、scope/purpose/channel、来源、authority revision 与时间窗；成功时写不可变 public release 和媒体/授权白名单投影、更新 active pointer、递增 epoch、记录命令结果/审计后原子提交。草稿编辑不触碰 public V2。作品撤回在事务内关闭 active pointer、递增 epoch 并记录审计，不删除原件/衍生物/历史版本。A15 权威撤回必须在同一事务/锁边界更新 gate 与 public 可见性；不可先独立提交权威状态再依赖异步补写。

`valid_from_utc`/`valid_until_utc` 按 UTC `DATETIME(6)` 规范化；数据库连接 session 固定 `time_zone=+00:00`，缺少时区、精度无法表达或边界含糊的来源拒绝。每次 GET/HEAD（及任何未来支持的 Range）按当前 UTC 时间复核 `valid_from <= now < valid_until`，不能依赖定时任务刷新 eligible 位。已提交撤回保证后续新请求拒绝；媒体在对象缓冲前后复核 access stamp，已发出/已下载字节不可追回。public JSON/媒体使用 no-store，任何未来 CDN 必须保留当前资格门。

### 12.4 幂等、复查与验证门

幂等唯一键至少按 `(actor_id, operation, work_id, idempotency_key)` 作用域，保存规范化请求 digest、目标修订、终态及结果 ID。同键同 digest 返回原结果；同键不同 digest 为冲突。提交超时/连接中断后先按键读取已提交结果，键不存在才可在当前修订仍匹配时重试；不得猜测提交失败或产生第二个 publication。乐观版本冲突返回 409，不覆盖新修订。

S2-B 必须使用双 schema 的独立 MySQL/InnoDB 和不同运行用户验证：精确 grants 正反例、发布/撤回/授权撤回锁竞态、权限/媒体/授权校验故障回滚、自然到期 fail-closed、重复/同键异 payload/未知提交复查、GET/HEAD 与撤回后重新读、public V2 epoch 导致游标失效。H2、mock、页面演示不能代替这些数据库和权限证据。
