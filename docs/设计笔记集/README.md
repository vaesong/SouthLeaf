## 1. 设计笔记集的职责

设计笔记集承接需求分析、总体架构和三阶段计划，回答“如何设计和实现”，但不替代 A/AT/P 文档：

| 文档体系 | 负责回答 | 不负责回答 |
|---|---|---|
| A 需求分析论证 | 用户场景、业务需求、规则、异常和验收 | 数据库字段、API 字段、代码目录 |
| AT 架构与技术选型 | 技术基线、模块边界、状态/权限/事务/错误码契约 | 每个阶段的具体页面实现和完整代码 |
| P 三阶段实施计划 | 阶段范围、依赖、交付目标和验收方向 | 业务规则的重新定义 |
| 设计笔记集 | 数据结构、用例、接口、内部架构、事务、测试和客户端消费设计 | 擅自改变已确认业务规则 |

设计文档可以提出设计假设，但必须标记假设、替换点和评审责任；不能把未确认的经营内容写成既定事实。

## 3. 设计文档状态

每篇设计文档头部必须标记：

```text
文档编号：D-xxx
文档状态：草稿 / 评审中 / 已确认 / 已锁定
适用范围：目标架构 / 阶段一 / 阶段二 / 阶段三
上游需求：Axx
上游架构：ATxx
关联计划：Pxx
```

状态含义：

- **草稿**：正在整理方案，不能作为实现依据；
- **评审中**：已经形成完整方案，等待产品、架构或运营确认；
- **已确认**：设计结论可以作为后续文档和测试输入；
- **已锁定**：该阶段实现使用的契约已冻结，变更必须留下决策记录。

## 4. 设计内容的统一层次

每个业务模块和通用能力都应按以下顺序写设计：

1. 职责、边界和规则归属；
2. 领域对象、数据归属和生命周期；
3. 状态及状态转换；
4. 用例和调用方；
5. 输入、前置条件、身份和幂等要求；
6. 输出、状态变化、错误码、通知、任务和审计；
7. 对外接口和内部端口；
8. 内部分层与依赖方向；
9. 事务、并发、锁、唯一约束、重试和补偿；
10. 权限、隐私和安全边界；
11. 日志、指标和可观测性；
12. 测试场景、验收标准和未决问题；
13. 阶段开放范围和后续扩展点。

数据结构至少区分：

```text
领域模型
  → 持久化模型
  → 接口请求/响应 DTO
  → 客户端展示模型
```

不能让数据库表结构、内部领域对象和客户端 JSON 互相直接绑定。

## 5. 推荐设计顺序

```text
设计总则与术语
  ↓
总体模块、依赖和阶段开放矩阵
  ↓
认证、权限、错误、日志、审计、文件、通知、任务
  ↓
内容、作品、套餐、客户、预约、订单、支付、交付、售后
  ↓
数据模型和存储策略
  ↓
公开、客户、后台和外部接口契约
  ↓
小程序、官网、管理后台消费设计
  ↓
并发、幂等、异常、补偿和测试设计
  ↓
设计评审与阶段实现清单
```

不能先凭页面或数据库表反推业务规则。跨模块用例应先明确事实归属和事务边界，再落数据和接口。

## 6. 当前设计边界

当前允许开始：

- 建立设计文档骨架；
- 细化领域对象、用例、状态、输入输出和内部边界；
- 形成数据库/API 草案并标记为草案；
- 设计通用后端能力、客户端消费方式和测试方案；
- 记录可替换的技术假设和外部契约缺口。

当前不允许直接锁定：

- 未经评审的最终数据库表和迁移脚本；
- 完整生产 API 版本和兼容承诺；
- 支付、对象存储、网盘和通知供应商的未验证字段；
- 阶段范围之外的业务；
- 以客户端按钮、页面缓存或后台直接改状态替代正式业务动作。
