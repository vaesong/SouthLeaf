## 1. 设计目标与范围

客户是阶段二业务主体，不等同于小程序登录身份、手机号、预约联系人或拍摄对象。设计必须支持本人浏览、预约和查看本人订单；为家庭/团体预约保留显式关联模型；不因外部身份或联系方式相同而自动合并记录。管理后台身份和客户身份完全分离，二者不能共用 session、cookie、权限或账号表。

2A 可先用明确标记的合成身份和测试数据验证流程；真实微信身份交换、线上客户关系确认、真实客户通知和正式隐私告知属于 2B 门禁。支付凭据、成片下载授权、完整售后身份核验属于阶段三。

## 2. 身份、客户与关系对象

| 概念 | 含义 | 是否可作为业务主键 |
|---|---|---|
| `Customer` | 工作室侧客户主体，具有内部不可猜测 ID 和最小档案 | 是，内部 ID 仅用于关联；对外 API 不信任客户端传入值 |
| `ExternalIdentity` | 微信/其他 provider 的 subject 与 app/tenant 范围绑定 | 否；只用于认证解析到内部主体 |
| `ContactPoint` | 经验证/未验证的电话、邮箱或其他联系渠道 | 否；可以重复、变更、共享，不能作为唯一 customer key |
| `CustomerRelationship` | 两个主体在某一预约/订单中的明确关系及授权状态 | 否；必须有来源、范围、期限和验证记录 |
| `BookingParty` | 某一次预约中的预订人、联络人、受服务人/参与人等角色 | 否；属于预约/订单上下文快照，不改变账号归属 |

建议把关系角色作为类型而非单一“家长/客户”字段（候选值如 `BOOKER`、`CONTACT`、`SUBJECT`、`PARTICIPANT`、`GUARDIAN`），最终是否需要监护角色及其证据流程由经营方决定。`GUARDIAN` 仅为待确认建模预留，不能据此认定适用年龄或接受某种法律同意。

## 3. 登录身份、客户档案与会话

- 未登录时可浏览公开业务、套餐与当前可预约档期；只在保存预约或查看私有订单时按需要求登录。
- 客户会话由客户认证适配器产生；后台管理会话使用独立认证模块/密钥/会话存储。登录一端的 token/cookie 不能换取另一端权限。
- 2A 使用测试身份提供器，标记 `test-only` 并阻止生产配置启动。不得将公开的 `demo` 身份或固定 subject 用于真实数据。
- 2B 的微信登录使用服务端校验的临时 code 换取身份；只保留应用需要的 provider subject 关联标识和必要审计，不保存 access token/secret，不在客户端接收并信任 openid 作为 owner ID。subject 的加密、可检索 HMAC、轮换和销毁策略须由密钥管理设计确定。
- 客户档案字段从最小化原则开始：内部 ID、创建/更新时间、状态、必要联系点及其验证状态、明确的语言/通知偏好（如需要）。年龄、身份证件、住址、生日、儿童信息、社交账号、支付账号等非预约必需数据不默认收集。
- API 每次取客户/预约/订单范围时从服务器端认证主体解析 `customerId`，然后校验本人或有效关系；不得以 body/query/path 中的 ID 代替授权判断。

## 4. 预约人、联系人、受服务人与交付对象

同一预约中预订人可能不是联系人、拍摄对象或参与人。阶段二只需收集完成联系、档期安排和服务所需的最少角色信息，并在订单确认时保存必要快照。非客户本人参与某次服务不自动获得登录权限；预订人也不自动拥有其他客户历史订单。

每个关系应记录 `relationshipId`、关联主体/预约/订单、role、`verificationStatus`、`purpose/scope`、来源、操作者/时间、有效期限（如有）和撤销状态。授权范围与 A15 的“公开发布授权”是不同事实，不得因建立客户关系或预约成功而推导出可公开影像授权。

## 5. 线上身份与线下记录关联（Q05 未决）

推荐的安全缺省：**不自动关联**。同手机号、同微信号、姓名相似、相同预约时间、导入表格中的匹配值只可作为候选提示，不能自动合并、开放历史订单或转移归属。

可供后续确认的流程设计：

1. 客户发起“申请关联”或后台发现可能重复记录；系统创建待核验 `CustomerLinkRequest`，不改变访问权。
2. 按经营方批准的可靠凭据进行一次性验证；电话 OTP 只能证明当前可接触号码，不能证明另一历史客户记录归属。
3. 对高风险/家庭关系/未成年人场景，按待确认的人工核验要求进行双边确认或工作室复核；记录验证方式、范围、证据引用和操作者，不保存多余证据副本。
4. 获批准后增加可撤销的 relationship/link；不删除原始 customer、不覆盖旧订单 actor，也不把两套登录身份压成一个主键。
5. 拒绝/超时则关闭申请并审计。错误尝试限流，避免通过链接接口枚举客户是否存在。

Q05 未确认前，实现只能采用本人身份映射与明确的测试管理员人工关联；不启用手机号自动合并、家庭账号共享、自动转移订单或真实历史记录认领。

## 6. 关键用例与数据流

| 用例 | 输入信任规则 | 结果 |
|---|---|---|
| 创建线上预约 | 从客户会话解析主体；服务端读取套餐/档期事实；客户端不得传客户 owner/权威价格 | 创建 `PENDING_CONFIRMATION` 申请与幂等结果；不占硬档；无确认订单 |
| 查看预约/订单 | 解析主体并校验本人或已批准关系 | 返回字段白名单 DTO；不存在与无权访问采用不泄露资源存在性的结果策略 |
| 更新联系偏好 | 校验当前客户会话、版本与验证要求 | 只改档案/偏好；不回写历史订单快照 |
| 认领线下记录 | 创建待核验关联申请 | 在审核完成前不能读该记录或历史订单 |
| 注销/删除申请 | 身份确认、保留义务/订单状态检查 | 按核实后的保留规则脱敏/限制/删除；法定/财务保留范围尚待确认 |

命令采用内部 application service，例如 `CreateReservation`、`RequestCustomerLink`、`UpdateContactPoint`；认证 adapter 提供不可伪造 actor context，业务用例不从 HTTP session、静态全局对象或客户端传入 ID 直接取权限。

## 7. 隐私、脱敏、审计与保留

- 客户档案、身份关联、联系信息、预约和订单属于私有管理数据，存于 D-507 的 `southleaf_admin` canonical 管理模型；不进入公开 `southleaf_public` projection。
- 订单/预约只持有完成约定服务、通知和争议处理所需的联系快照。更新当前联系方式不得改变历史交易记录；对历史快照使用更严格的显示权限与留存规则。
- 列表默认掩码联系值；完整值仅由具备明确 capability 的后台操作查看，按需记录查看审计；日志、异常、埋点、URL、分析工具不得复制原值。
- 小程序本地仅短期存会话/必要表单状态；登出、失效、切换账号、注销时清除缓存；禁止将订单/联系信息写入持久日志或第三方分析。
- 身份证件、监护材料、影像授权证据等若经营流程确需采集，须另设加密对象存储、独立访问策略、保留期限、删除/法律保留与审计设计；本设计不默认创建这些字段/文件。
- 保存每项个人数据的目的、字段 owner、读取角色、访问记录、到期/删除处理和备份保留策略。未确认留存期限的真实数据不得接入 2B。

## 8. 数据模型草案

以下为逻辑实体，不是已批准 DDL：

```text
customer(id, status, created_at, updated_at, version)
external_identity(id, customer_id, provider, app_scope, subject_ciphertext,
                  subject_fingerprint, verified_at, status, version)
contact_point(id, customer_id, type, value_ciphertext, value_fingerprint,
              verification_status, verified_at, status)
customer_relationship(id, customer_id, related_customer_id, relation_type,
                      purpose, verification_status, valid_from, valid_until, revoked_at)
customer_link_request(id, requester_customer_id, candidate_ref, method,
                      status, expires_at, reviewed_by, reviewed_at, idempotency_key)
booking_party_snapshot(reservation_id, role, minimal_display_name,
                       contact_snapshot_ref, relationship_ref, version)
```

推荐约束：`external_identity` 在 provider + app scope + subject fingerprint 上唯一；验证字段更新经审计；关系和 link request 使用明确状态与有效期；预留/订单所有权使用内部 ID 与关系记录而非联系方式。加密/HMAC 方案、唯一键空值语义、联系人共享、重复身份处置与删除/匿名化策略须结合 D-505/D-507 和实际密钥方案另行定稿。

## 9. 接口和错误边界

客户 API 契约见 D-402：客户上下文由已验证会话隐式确定；仅 `POST /customer/identity/link-requests` 等经确认的命令允许提交候选关联 reference，不接收可直接授予权限的 `customerId`。访问他人资源统一按“不存在或不可用”结果处理（建议 404 语义，避免存在性枚举）；失效会话为 401，未满足关系/权限为统一拒绝语义，版本冲突为 409。

contact point 变更应采用验证流程；OTP、身份 provider 调用使用限流、单次有效期、请求签名/CSRF 保护和不泄露账号存在性的响应。所有对外 DTO 显式 allowlist 字段，不序列化 domain/entity。

## 10. 身份失效、变更、合并与恢复

- provider 撤销/绑定失效时将 identity 标为不可认证，不删除预约/订单事实；需要重新验证才能恢复关联。
- 联系方式变更新增 contact point 并验证后再标旧联系方式失效；历史预约/订单快照不随之改写。
- 账号重复记录用可追溯 link/merge command，不物理覆盖 customer ID；订单保留原始创建主体和后续合法关联审计。真正“合并/拆分”规则需 Q05 决定及独立回滚/数据权限测试。
- 账号恢复不能仅凭可重复使用的手机号声明历史归属；限制自动恢复、列出待核验步骤并记录审核操作。
- 注销请求不能直接删除未完成预约/订单的关联；先执行业务关闭/法定留存判断，再做脱敏或不可逆删除。留存期限和备份中的删除一致性由 2B 隐私/运维流程确认。

## 11. 测试与验收

- 客户会话 A 不能读取客户 B 的预约/订单、通过变更 URL ID 绕过 owner check，或从不存在/无权响应区分资源是否存在。
- 相同手机号/姓名/provider 信息不能自动合并；重复 provider subject 的唯一约束与恢复路径明确。
- 预约联系人/受服务人/预订者不同，且未经验证的关系不获得本人订单访问；客户 link request 在批准前没有权限效果。
- 管理 session 不能被客户 API 接受，客户 session 不能进入管理 API；日志和错误体无 access token/手机号/外部 subject。
- 联系方式变更不改变既有订单快照；脱敏列表与完整字段权限分别覆盖；审计查看事件不包含秘密。
- 失效/登出/切换身份清除本地私有缓存；过期链接和重放 OTP 不能建立关系。
- 存储隔离由 D-507 的 MySQL grant/reader 负向测试验证；Mock 只能验证应用规则，不能代替运行身份权限证据。

## 12. 阶段开放与待确认问题

2A 可实现内部 customer ID、本人访问、合成登录 adapter、关系模型、客户字段最小化和完整测试；生产微信认证/真实数据留到 2B。Q05 必须确认线下记录认领、手机号变更、家庭/监护关系、合并/拆分、双边验证及本人/代理人订单访问规则。阶段三私密交付要增加独立 recipient/access grant、到期/撤销/下载审计和资料最小化设计，不得复用本设计中“看订单”的普通权限。
