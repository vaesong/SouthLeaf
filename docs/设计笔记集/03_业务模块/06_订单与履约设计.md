## 1. 设计目标与范围

订单是一次已确认服务约定的私有记录。它将确认当时的套餐/业务/价格/档期/联系等必要事实固定为快照，并支持后台查看、最小安排和审计。预约申请未确认前没有正式订单。订单的商业快照不随当前套餐、价目或客户资料变化而改写。

阶段二不收款、不记录“已支付”、不生成定金/尾款到期规则、不退款、不做支付回调、不提供私密成片交付或完整售后。P02 要求的预约确认成单仍须实现；Q02 未确认时，只能以隔离测试价目验证快照结构，不能把金额/定金方案用于真实业务。

## 2. 订单实体、来源与生命周期

每个确认预约创建一个根 `Order`，稳定内部 ID 和公开不可猜测引用分开。源预约唯一，订单不能由客户客户端直接创建或更换 owner。线下电话登记同样走预约确认后成单，不提供独立跳过档期校验的“手工成单”。

阶段二最小状态建议：

- `order.lifecycleStatus = ACTIVE | CANCELLED`；只在有效命令和审计下转移；若后续需要 `CLOSED/COMPLETED`，须有阶段三完整履约规则再扩展，不把“拍摄完成”隐含成付款完成。
- `fulfillmentStatus = UNSCHEDULED | SCHEDULED | NEEDS_ATTENTION` 仅用于 P02 允许的基本安排/待办；具体字段/转移依 D-607 确认。
- 不创建 `paymentStatus`、`depositStatus`、`refundStatus` 或 `deliveryStatus` 字段/接口/按钮。未来阶段三以独立支付/交付事实扩展，不把“未实现”表示成成功或默认已付款。

取消订单与预约/占档必须同一业务事务一致。取消仅表示预约服务约定已取消，不表示退款完成；费用影响、退款和取消窗口属 Q02/阶段三。

## 3. 订单快照与修订

确认事务捕获一个不可变 `OrderSnapshot`，至少包含可追溯版本和当时的业务约定：

- 已选择的业务/套餐 ID 与不可变版本、展示名称、SKU/服务内容摘要及数量；
- 经经营方批准后的货币代码、价格金额/组成、价格版本和当时引用的条款版本（没有经过确认的字段不伪填默认值）；金额使用明确精度/最小单位，不用浮点数；
- 确认的 service slot、UTC start/end、适用时区/显示偏移与 schedule revision；
- 下单主体、经授权的预订联系人最小快照及其验证/关系引用；不复制完整客户 profile、外部 token 或非必要身份证明；
- 创建来源（线上/后台线下）、确认操作者/时间、来源 reservation 和命令幂等关联。

已确认快照不得覆盖更新。后台改期、纠错或批准的商业变更追加 `OrderRevision`（revision number、前后字段差异、原因码、actor、时间、关联命令），可用当前视图重建，但原始 confirmed snapshot 保留。历史订单显示“签约当时”内容，不从当前套餐表动态 JOIN 来冒充历史。

金额、币种、税费/折扣/定金条款必须来自 D-303 中经确认的价目版本。Q02 或币种/税务未确认时，2A 用 synthetic fixture；真实确认命令必须阻止使用未知/空价目，不得擅造 TWD 金额或付款承诺。

## 4. 预约、档期、订单与安排的事实所有权

| 事实 | 唯一责任模块 | 订单如何表示 |
|---|---|---|
| 申请是否 pending/expired/rejected | reservation | 保存来源预约 ID/创建快照引用；不提前生成订单 |
| 某 slot 是否被确认占用 | reservation | 保存确认 slot 及 schedule revision；不单独写另一套 occupancy 真相 |
| 套餐/价格/服务内容当时版本 | catalog/package | 保存不可变 snapshot，不跟随当前模型变化 |
| 客户当前身份/联系方式/关系 | customer | 引用内部 customer ID；复制完成业务所必需的最小 contact snapshot |
| 后台 session/permission | admin-security | 仅记录 actor ID/type 与审计关联，不把登录凭据写订单 |
| 付款、退款、对账 | 阶段三 payment bounded context | 阶段二没有此字段；未来用支付 aggregate/ledger 关联订单 |
| 私密成片/交付访问权限 | 阶段三 delivery | 不能靠 order visibility 推导下载许可 |

每个业务事务由 application use case 协调模块端口；不要由 order repository 直接更新预约表，也不要由客户 API 写 order 表。

## 5. 创建、取消、改期与最小履约安排

### 5.1 确认即创建

`ConfirmReservation` 在 D-305 定义的单一 MySQL 事务中完成：锁定 pending reservation 与 slot、建立唯一 occupancy、更新 reservation、插入唯一订单/初始快照、写 audit 与 notification outbox。任何写入失败整体回滚。唯一键 `source_reservation_id` 防止同一预约重复建单；幂等键重复返回原订单/版本。

### 5.2 取消

取消命令校验 actor/capability、订单与预约状态、expected revision 和当时有效的取消规则。事务中更新预约/订单状态、释放唯一当前 occupancy、追加 order revision/audit/outbox。重复命令返回已取消结果；取消不会清除历史订单或让其转成付款退款状态。退款如将来适用由独立支付流程执行。

### 5.3 改期

只有被确认且未取消的订单可走改期命令。对目标新 slot、旧 slot 与 order/appointment revision 按 D-305 全局锁序操作；先确保新档可占，再写订单安排修订、改变唯一 occupancy、最后释放旧档，全在同一事务成功/回滚。失败时旧预约/订单时间完全保留；目标档冲突返回明确冲突，不自动另选时段。

### 5.4 阶段二最小安排

如阶段二经批准的最小安排需要后台记录拍摄安排、负责人或内部注意事项，使用受权限控制的非公开安排字段/待办，按字段级可见性和审计记录。客户公开订单 API 不返回内部备注、员工个人信息、授权证据、其他客户信息或排班私有内容。具体负责人字段、通知和状态转换需 Q06/经营方确认。

## 6. 客户访问、权限与幂等

客户侧仅允许经 D-304 身份解析后的本人订单，或经过 Q05 批准并且在有效范围内的 relationship。列表采用默认字段白名单和分页；订单详情对无权/不存在统一使用不泄露存在性的错误。更改客户 ID、reservation ID、order ref、分页过滤器不能改变授权边界。

后台查看/编辑/取消/改期分别要求 server-side capability；Q06 未确认时不赋予任何真实角色。高敏字段按需显示、掩码、查看审计；订单导出/批量下载不在阶段二默认开放。

写命令包含 actor context、资源 ID、幂等 key、expected order revision 和命令摘要。重复同一 key+payload 返回稳定结果；同 key 不同 payload 返回 `IDEMPOTENCY_KEY_REUSE`；并发旧 revision 返回 `VERSION_CONFLICT`。记录创建、快照版本、取消、改期、安排变化的最小审计，不记录 token/支付秘密/完整客户材料。

## 7. 数据结构草案

以下是逻辑模型，不是 DDL：

```text
order(id, source_reservation_id UNIQUE, customer_id, lifecycle_status,
      fulfillment_status, snapshot_id, current_revision, created_at, version)
order_snapshot(id, order_id, immutable_payload_or_normalized_lines,
               package_version, price_version, schedule_revision, created_at)
order_revision(id, order_id, revision_no, command_id, actor_ref,
               changed_fields, reason_code, created_at, UNIQUE(order_id, revision_no))
order_contact_snapshot(order_id, role, minimum_contact_fields, source_ref,
                       verification_status, created_at)
```

高敏 contact 快照可单独加密/控权；订单表不放身份 provider token。结构化字段优先于任意 JSON；若使用版本化 JSON snapshot，必须有 schema version、字段 allowlist、校验与历史读取兼容测试，不能把完整 customer/package entity 序列化进订单。

## 8. 事务、通知、审计与重建

订单创建与预约确认共用一个 InnoDB transaction；取消/改期在 reservation/slot/order/audit/outbox 同事务更新。通知邮件/微信、日历、文件服务等外部 I/O 仅在提交后执行；失败记录任务并重试，不回滚订单。任何无法判定的 DB commit 结果按 command ID 读取当前事实，不用新 key 再建订单。

快照/修订需要具备只读历史查看；纠正通过附加 revision，不 UPDATE/DELETE 已确认快照。后台错误修复采用权限限定且必须审计，不提供通用 SQL/任意 JSON 编辑器。

## 9. API 与界面范围

客户 API：只读本人订单列表/详情及允许的预约取消/改期命令；响应给出预约服务状态、确认时套餐摘要、已确认档期、必要联系提示和非敏感下一步。不得包含支付发起、支付处理中、尾款状态或下载 URL。

管理 API：预约确认时同步返回新建 order reference；订单列表可按状态/日期/预约引用分页筛选；详情展示已脱敏快照和 revision history；允许的安排/取消/改期使用独立命令端点。D-402/D-403 定义最终 URI/DTO/error schema。

后台 UI 不出现“标记已付款”“退款成功”“交付成片”“完成售后”等越界按钮；客户 UI 明示“预约已确认/等待确认”而不混淆“订单已创建”与“款项已支付”。

## 10. 并发与数据一致性测试

- 同一 reservation 的两个并发确认只创建一个 occupancy、order、snapshot、audit command 与确认通知。
- 数据库在插入订单、快照、审计、outbox 任一步故障时确认事务回滚；重放不会产生 orphan snapshot/order。
- 当前套餐/价格更新后旧订单仍显示原 snapshot；修订必须 append-only 且 revision 连续。
- 两个并发改期到同一目标 slot 时至多一个成功；失败请求保留旧 schedule 和 order revision。
- 取消与改期并发、客户取消与后台处理并发，只能得到一个有效状态结果；occupancy 与预约/订单一致。
- 客户 A/B 对彼此订单、内部备注、联系快照、审计和 schedule data 进行 IDOR/枚举测试。
- 使用目标 MySQL/InnoDB 和实际测试账号验证唯一约束、锁序、事务和 grants；不能用 H2/纯 mock 宣称已验证。

## 11. 阶段开放与待确认问题

Q02：无支付阶段的定金计时/占档过渡、取消与确认边界；真实固定定金属于 Q03，不重新引入比例原型，退款执行留到阶段三；未确认前阶段二无任何 payment state 或支付按钮。Q04：实际时区、档期/服务时长/缓冲与改期限制。Q05：谁是客户、代理/家庭关系、历史订单认领。Q06：谁能查看/修改/取消、安排和审计客户订单。阶段三必须另行设计支付账本/幂等回调/对账退款、完整履约/缺席/补拍/售后状态、客户隐私留存和私密交付授权；不能把本设计的最小安排状态扩张解释成完整履约。
