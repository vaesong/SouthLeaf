## 1. 设计目标与边界

预约模块管理客户申请、可预约固定时段、后台确认/拒绝、占档、取消与改期。它是档期占用的唯一事实所有者；订单模块保存确认时商业快照；客户模块负责身份与资源归属。支付、退款、定金到期自动释放、私密交付、完整售后不在本文实现范围。

P02 当前基线：待确认申请默认 48 小时失效且不占硬档；确认必须在同一业务事务中完成排他占档、预约确认、唯一订单及快照、审计与可靠通知任务。Q02/Q04 未最终确认的部分必须阻止真实经营策略上线。

## 2. 时间与固定时段模型（Q04 门禁）

- 每个 `ServiceSlot` 是明确提供给预约的固定时间段，包含内部 ID、资源/服务类型、开始/结束 instant、业务时区标识、可售状态、容量（阶段二默认为 1，若容量不是 1 必须另行设计）、规则版本和 revision。
- 时间点以 UTC instant 存储；保留创建时使用的 IANA `ZoneId` 和本地显示值/规则版本，前端只按服务端返回的 display offset 渲染。禁止依赖服务器默认时区。
- 时段进入客户可选列表前必须已物化并具有稳定 ID。后台确认只能占用已存在的可售行；不能仅锁一条不存在的占位记录。临时/离线时段也必须先在同一 schedule 写模型中创建，再复用相同占档命令。
- 具体工作室时区、营业日、服务时长、缓冲、跨午夜、节假日、最短提前量和多资源规则均属 Q04；未确认时使用隔离测试 fixture，不向真实客户展示按猜测生成的开放时间。

## 3. 申请、占用与状态

建议将“申请状态”和“档期占用”分开，避免 pending 申请误占时段：

| Reservation 状态 | 允许转移 | 说明 |
|---|---|---|
| `PENDING_CONFIRMATION` | `CONFIRMED` / `REJECTED` / `EXPIRED` / `CANCELLED` | 默认 48h；不持有硬档，不创建已确认订单 |
| `CONFIRMED` | `CANCELLED` | 已占档且唯一订单；取消政策仍需 Q02/经营方确认 |
| `REJECTED` / `EXPIRED` / `CANCELLED` | 无终态转移 | 再预约创建新申请，保留历史记录 |

改期是对仍为 `CONFIRMED` 的预约执行 `RescheduleReservation`：增加 schedule revision 和 assignment history，预约仍保持 `CONFIRMED`；不另造含义模糊的 `RESCHEDULED` 终态。每个硬档另有 `SlotOccupancy` 当前占用行（`slot_id` 唯一键/主键）；历史变更追加到 assignment history，释放当前占用必须在同一事务完成。

请求可以携带客户偏好的时间范围/套餐，不等同最终确认时间。Pending 记录的申请人、创建渠道、过期 instant、版本和幂等键必须可追溯。

## 4. 待确认申请失效

- `expires_at` 在创建时计算，存为 UTC instant；服务端到期任务以数据库 UTC 当前时间为准，避免节点时钟/时区差异。
- 失效命令使用条件更新：只有 `status=PENDING_CONFIRMATION AND expires_at<=db_now` 才能转成 `EXPIRED`。每个申请最多一个终态更新和一条幂等通知任务。
- 确认与失效并发时，二者对 reservation 行使用同样的锁/版本条件；恰有一个胜出。确认事务读取到已过期申请必须拒绝；过期事务不能改变已确认记录。
- 若租户时钟或后台时钟不可用，不能默认延长有效期。对时告警、过期堆积量和最早延迟应可观测。
- 48 小时是 P02 基线，但从申请提交、客户打开链接还是后台首次处理开始的精确定义应与 P02 产品负责人核对；在用户确认前保持“创建时间起算”的明确候选，不增加定金到期逻辑。

## 5. 排他占档与并发确认

推荐 MySQL/InnoDB 的双重保护：

1. 确认事务先锁 reservation，再锁已物化的 `ServiceSlot` 行（多档按稳定 ID 升序），检查 `slot.status=OPEN`、开始时间/服务类型符合规则、预约仍 pending 且未过期。
2. 插入 `SlotOccupancy(slot_id, reservation_id, assigned_at, revision)`；`slot_id` 唯一约束是最后一道并发保护。即便两个进程同时读到 OPEN，最多一个插入成功。
3. 更新 slot 展示状态/当前版本（若采用派生可用状态则不存第二个真相），更新 reservation、订单快照、审计、outbox，全部同一事务提交。
4. 唯一约束冲突/死锁时回滚并重读赢家状态；对客户或后台返回明确 `SLOT_UNAVAILABLE` / `VERSION_CONFLICT`，不能吞掉冲突后错误确认。

列表可用性是提示，不构成锁。只依赖按钮禁用、缓存、定时刷新或应用层“先查再写”均不满足排他性。

## 6. 线上、电话与微信预约入口

- 线上提交：认证主体从服务端客户会话解析；套餐、价格、可售规则和时段从服务端读取；客户端只提交偏好、必要联系内容和业务问项。创建 pending 申请不占硬档、不成单。
- 管理后台电话/线下登记：记录 `source=STAFF_OFFLINE`、actor、必要联系信息与来源说明；客户身份若未验证必须标记未关联。随后复用相同 pending/confirm/occupancy/订单用例，不提供 SQL/隐藏强制入口。
- 通过微信私聊/电话代客户录入仍是后台可审计命令，不得伪称客户已登录或已同意公开内容。
- 线下确认和线上竞争同一 slot 时，必须命中同一唯一 `SlotOccupancy`；单独的“线下日历”不能旁路冲突。

## 7. 确认即成单

确认成功与订单创建为同一事务：reservation 由 pending 转 confirmed，创建一个唯一 order 和不可变套餐/价格/客户联系/服务内容快照，记录确认时档期版本，写审计及通知任务。唯一约束 `order.source_reservation_id` 保证每个确认预约最多一个原始订单。事务任何步骤失败全部回滚；重复确认使用相同 idempotency key 返回原订单，不创建副本。订单字段与阶段二排除项见 D-306。

## 8. 输入、权限与幂等

| 命令 | 权限主体 | 必需并发控制 | 幂等要求 |
|---|---|---|---|
| `CreateReservation` | 客户本人会话；后台代理需专门 capability | 当前套餐/规则版本、客户主体校验 | client key + actor + operation + request digest |
| `ConfirmReservation` | 后台预约确认 capability（Q06 决定角色映射） | expected reservation revision；slot 唯一占用 | 相同 key 返回相同 reservation/order |
| `RejectReservation` | 后台预约处理 capability | expected revision；pending only | 同一拒绝理由/结果重放 |
| `CancelReservation` | 客户本人或具备后台取消 capability | expected revision；confirmed/pending 分别处理 | 只产生一次状态变化/通知 |
| `RescheduleReservation` | 本人规则/后台排期 capability | expected revision；旧/新 slot 排序加锁 | 重放返回已提交的新档版本 |
| `CreateOfflineReservation` | 后台录入 capability | actor、来源、slot 仍用同一占用约束 | client key + staff actor |

每条命令记录 actor、resource、操作、请求摘要、expected revision、结果 ID 和审计关联；相同幂等键但不同请求摘要返回 `IDEMPOTENCY_KEY_REUSE`。权限在服务端每次检查，UI 隐藏按钮不构成安全校验。

## 9. 事务、锁、约束与补偿

建议同一管理业务 MySQL 事务边界：`idempotency` → `reservation`（ID 排序）→ `service_slot`（ID 排序）→ `slot_occupancy`（唯一约束）→ `order` → `audit`/notification outbox。所有预约命令遵守固定锁顺序，减少死锁；数据库死锁可安全重试的前提是整个 command 幂等。

建议约束包括：每个 slot 最多一个当前 occupancy；每个 reservation 最多一个当前 occupancy；每个 reservation 最多一个原始订单；状态与时间一致（确认必须有 slot/revision，pending 不得有当前 occupancy）；request command idempotency 唯一。具体 MySQL DDL/索引需 D-507 表设计后定稿。

外部通知在事务提交后调用；发送失败重试通知任务，不回滚预约。死锁/唯一冲突需重新读取实际状态；不能执行“补偿删掉订单”掩盖部分提交，因为事务应保证业务记录全有或全无。

## 10. 逻辑数据与 API

候选实体：`service_slot`、`reservation`、`reservation_revision`、`slot_occupancy`、`slot_assignment_history`、`idempotency_command`、`reservation_audit`/共享 audit、notification outbox。客户身份、关系引用和快照按 D-304；订单快照按 D-306。

客户侧公开档期查询是只读且可缓存的 availability hint；预约详情/取消/改期必须检查客户归属。后台提供待确认队列、按日期/状态筛选、确认时选择实际 slot、拒绝、取消、改期和离线登记命令。详细 URI/DTO/error codes 见 D-402/D-403，不在此重复锁死契约。

## 11. 通知、审计与运营指标

创建、确认、拒绝、过期、取消、改期分别有经过批准的通知意图；通知文案、渠道、退订和 provider 由 D-406/2B 确认。通知只使用最少客户信息；provider 超时不能推断未发送或已送达。

审计记录申请来源、操作者、slot 变更前后版本、命令 ID、状态和失败 reason code；不在审计中记 OTP、token 或完整证据。运营观测包括 pending 数量/最早年龄、即将过期、确认冲突率、锁等待/死锁、通知失败/重试、无可用时段和改期冲突。

## 12. 测试与验收

- 两个并发确认争同一 slot：严格一项成功、一项冲突；当前占用和唯一订单只各一。
- 相同预约同幂等键/相同 payload 重放返回同一结果；同键不同 payload 被拒绝。
- 48h 边界、过期作业与确认并发，恰好一个状态转移；pending 从不持有硬占用。
- 线上、后台离线、并发改期都命中同一 slot 唯一约束；改期失败保留旧档和旧修订。
- 在确认过程的订单、审计、outbox 任一写入注入异常，所有业务写回滚；无“预约成功但无订单/通知任务”的部分状态。
- 测试不同 DB 时区、跨日、DST、毫秒精度、锁等待/死锁与恢复；具体日历断言只用已批准 Q04 fixture。
- 使用目标 MySQL/InnoDB 与运行身份验证实际事务/唯一索引；H2/Mock 不能证明并发与 grants。

## 13. 阶段开放与待确认问题

Q02：无支付阶段如何处理既有定金计时与 confirmed reservation/占档过渡、取消政策；实际固定定金由 Q03 在 2B 提供，退款执行仍属阶段三；阶段二 API/UI 不出现付款成功或付款超时假状态。Q04：营业时区、slot 生成、服务时长/缓冲、容量、跨日/节假日、客户是否可选多个偏好。Q05：代预约、家庭关联和客户身份校验。Q06：谁可确认、拒绝、取消或改期及双人复核要求。未确认部分不阻止隔离测试设计，但阻止对真实经营策略作默认推断或进入 2B 上线。
