## 1. 覆盖摘要

| 用例范围 | 主用例数 | 重点风险 | 初始状态 |
|---|---:|---|---|
| `S2-USER-01`～`S2-USER-10` | 10 | 登录误建预约客户、会话串用、openid 落库、旧预约按称呼合并、资料未齐仍提交预约 | `NOT_RUN` |
| `S2-FOOT-01`～`S2-FOOT-05` | 5 | 刷新刷出多条足迹、分享失败挡住页面、传递链认错人、到期删掉用户 | `NOT_RUN` |

执行约束：

- 路径以 D-310 §8 的草案为准。契约锁定前，断言先看业务结果和禁止字段，不把草案字段名写成永久兼容承诺。
- 数据用合成指纹和合成图片。不使用真实 openid、手机号、生产头像或生产密钥。
- 预约入口保持关闭。本文只定义用例，尚未执行，不产生通过结论。

## 2. 用户管理

### S2-USER-01 进入即登录

- **用例 ID**：`S2-USER-01`
- **优先级**：P0
- **规则来源**：A17 §3.1、§7；D-310 §5 U1、§10
- **前置条件**：预约开关关闭。测试指纹 `fp_user_01` 在 `booking_customer` 与 `app_user` 中都不存在。记录两表行数。
- **步骤**：
  1. 小程序冷启动，用该指纹对应的一次性 code 登录。
  2. 观察落地页。
  3. 读取用户行、预约客户行，以及短编号。
- **可观察预期**：
  - 进入首页。
  - `app_user` 增加一行，预约客户表行数不变。
  - 短编号等于指纹前六位的大写。库中没有 openid。
- **执行状态**：`NOT_RUN`

### S2-USER-02 登录失败停在重试页

- **用例 ID**：`S2-USER-02`
- **优先级**：P0
- **规则来源**：A17 §3.1；D-310 §4、§7
- **前置条件**：准备两种失败：微信换码失败；用户库拒绝插入。各记录一次。
- **步骤**：
  1. 分别冷启动。
  2. 尝试打开作品、套餐和「我的」。
  3. 读取用户表和足迹表。
- **可观察预期**：
  - 两种失败都停在重试页，三个页面都不可达。
  - 不新增用户，不新增足迹。
- **执行状态**：`NOT_RUN`

### S2-USER-03 客人修改资料

- **用例 ID**：`S2-USER-03`
- **优先级**：P0
- **规则来源**：A17 §3.2；D-310 §3
- **前置条件**：用户称呼和头像为空。准备一张合法 JPEG，一张超过 512 KiB 的图，一段含控制字符的称呼。
- **步骤**：
  1. 打开「我的」。卡片升起，上面没有「以后再说」，也没有操作说明。
  2. 只选头像，不填称呼，尝试保存。
  3. 选一张合法 JPEG，并保存称呼「枝南客人」。
  4. 用后台读取同一用户。
  5. 分别提交超长图和控制字符称呼。
- **可观察预期**：
  - 只选头像时不能保存，资料仍空。
  - 后台看到「枝南客人」和同一张头像。页面不出现「资料未齐」。
  - 非法称呼和超限图片被拒绝，已保存的资料不变。
  - 卡片不能把空称呼存回去。
- **执行状态**：`NOT_RUN`

### S2-USER-04 后台修改资料

- **用例 ID**：`S2-USER-04`
- **优先级**：P0
- **规则来源**：A17 §3.2、§3.3；D-310 §6 U9
- **前置条件**：客人称呼为「枝南客人」，已有头像。后台持有当前 `version`。
- **步骤**：
  1. 后台把称呼改为「店里记下的称呼」，并写入备注「只给工作人员」。
  2. 用旧 `version` 再保存一次。
  3. 客人重新打开「我的」。
  4. 尝试调用撤下头像的接口。
  5. 后台把称呼清空，客人再打开「我的」。
- **可观察预期**：
  - 客人看到「店里记下的称呼」，响应里没有备注。
  - 旧版本保存被拒绝，库内称呼仍是新称呼。
  - 头像不能被后台撤下。审计有这次工作人员修改，用户页不列出历史。
  - 后台再把称呼清空后，客人重新打开「我的」，看到「微信用户」加短编号，资料卡片再次出现。头像还在。
- **执行状态**：`NOT_RUN`

### S2-USER-05 不能新建、删除或停用

- **用例 ID**：`S2-USER-05`
- **优先级**：P0
- **规则来源**：A17 §3.3、§6
- **前置条件**：管理员已登录。用户列表至少有一行。
- **步骤**：
  1. 检查「用户」页面。
  2. 调用新建、删除、停用对应的草案接口。
  3. 再读该用户。
- **可观察预期**：
  - 页面没有这三项操作。
  - 接口被拒绝。用户行、称呼和头像仍在。
- **执行状态**：`NOT_RUN`

### S2-USER-06 按指纹接上旧预约

- **用例 ID**：`S2-USER-06`
- **优先级**：P0
- **规则来源**：A17 §3.3、§4；D-310 §2.2
- **前置条件**：`booking_external_identity` 已有指纹 `fp_user_06` 和一条预约申请。`app_user` 没有这个人。另有指纹 `fp_user_06b` 没有预约。
- **步骤**：
  1. 用 `fp_user_06` 登录。
  2. 打开「我的」和后台用户详情。
  3. 用 `fp_user_06b` 登录并读取「我的」申请。
  4. 把 `fp_user_06b` 的称呼改成与 `fp_user_06` 相同后再读申请。
- **可观察预期**：
  - `fp_user_06` 出现在用户列表，两处都能看到原申请。预约状态不变。
  - `fp_user_06b` 的申请为空。称呼相同之后仍然为空。
- **执行状态**：`NOT_RUN`

### S2-USER-07 同名搜索

- **用例 ID**：`S2-USER-07`
- **优先级**：P1
- **规则来源**：A17 §3.3、§4
- **前置条件**：两个用户称呼都是「同名」，短编号不同。
- **步骤**：

### S2-USER-08 会话隔离并且不保存 openid

- **用例 ID**：`S2-USER-08`
- **优先级**：P0
- **规则来源**：A17 §4、§7；D-310 §8、§11
- **前置条件**：持有一个有效用户凭证和一个有效后台凭证。公开作品响应可抓取。
- **步骤**：
  1. 用用户凭证调用后台用户详情和后台保存。
  2. 用后台凭证调用 `PUT /api/v1/public/users/me`。
  3. 用预约会话凭证调用用户会话接口。
  4. 检索用户表、足迹表、审计和请求日志。
  5. 请求公开作品详情，检索响应正文。
- **可观察预期**：
  - 前三步都被拒绝，资料不变。
  - 检索结果没有 openid、session_key 和临时 code。
  - 公开作品响应没有用户 id、称呼、备注、指纹和足迹。
- **执行状态**：`NOT_RUN`

### S2-USER-10 资料未齐不能提交预约

- **用例 ID**：`S2-USER-10`
- **优先级**：P0
- **规则来源**：A17 §3.2、§7；D-310 §9；D-305 §6
- **前置条件**：用户已登录。准备三种资料：头像和用户名为空；只有用户名；两项都有。记录预约客户表行数。预约开关关闭时，只做「我的」上的卡片，提交那一半不适用。
- **步骤**：
  1. 资料为空时打开「我的」，再点卡片上方的暗处。
  2. 切到首页再回到「我的」。
  3. 只补上用户名后再进「我的」。
  4. 两项都补上后再进「我的」。
  5. 在资料重新置空后打开预约页，只查看档期，读取预约客户表。
  6. 选好套餐和时段后按下提交，再点卡片上方的暗处。
  7. 再次按下提交，在卡片里保存头像和用户名。
- **可观察预期**：
  - 第一次进入「我的」出现卡片，没有「以后再说」和操作说明。关上后仍停在「我的」，底栏可以切换。
  - 再次进入「我的」时卡片再出现。只缺头像时，卡片里只有头像。两项都有时，不再自动弹出。
  - 只看档期时，预约客户表行数不变。
  - 按下提交先出现同一张卡片。关上后没有新申请，预约客户表行数仍不变。
  - 两项都保存成功后，申请才提交，预约客户表这时增加。
- **执行状态**：`NOT_RUN`

## 3. 访客足迹

### S2-FOOT-01 打开页面并在 30 秒内去重

- **用例 ID**：`S2-FOOT-01`
- **优先级**：P0
- **规则来源**：A17 §5.1；D-310 §6
- **前置条件**：用户已登录。作品 `work_foot_01` 已发布。
- **步骤**：
  1. 打开该作品详情。
  2. 30 秒内用新的 `clientEventId` 再打开一次。
  3. 31 秒后再打开一次。
  4. 让登录失败并停留在重试页，检查足迹。
- **可观察预期**：
  - 第一次留下一行，页面和作品 id 正确。
  - 30 秒内的第二次不增加行。31 秒后的第三次增加一行。
  - 重试页不产生足迹。
- **执行状态**：`NOT_RUN`

### S2-FOOT-02 发出分享

- **用例 ID**：`S2-FOOT-02`
- **优先级**：P0
- **规则来源**：A17 §5.1、§5.2；D-310 §8
- **前置条件**：作品详情可分享。分享接口可分别成功和失败。
- **步骤**：
  1. 在接口可用时点分享。
  2. 记录返回路径和卡片行。
  3. 在接口失败时再点分享。
- **可观察预期**：
  - 成功时路径含 `sls`，卡片行存在。没有任何字段表示对方已收到。
  - 失败时分享仍可发出，路径不含 `sls`，不新增卡片。作品页没有报错阻断。
- **执行状态**：`NOT_RUN`

### S2-FOOT-03 两跳传递

- **用例 ID**：`S2-FOOT-03`
- **优先级**：P0
- **规则来源**：A17 §5.2、§5.3；D-310 §5 U10
- **前置条件**：用户甲、乙都已登录。
- **步骤**：
  1. 甲在作品详情发出卡片 S1。
  2. 乙打开带 S1 的路径，再发出 S2。
  3. 丙打开一个不存在的 `sls`。
  4. 读取甲、乙的时间线和 S1 的传递。
- **可观察预期**：
  - 甲有发出 S1。乙有从 S1 打开，以及发出 S2。S2 的上一张是 S1。
  - 传递页能看出这两跳，没有群名和第三个人。
  - 丙的打开还在，上一跳为空。
- **执行状态**：`NOT_RUN`

### S2-FOOT-05 超过 180 天的明细删除

- **用例 ID**：`S2-FOOT-05`
- **优先级**：P0
- **规则来源**：A17 §5.4、§7；D-310 §11
- **前置条件**：同一用户有一条 181 天前的打开、一张 181 天前的卡片，以及一条当天的打开。称呼、头像、备注已填写。
- **步骤**：
  1. 运行到期删除。
  2. 读取足迹、卡片、用户和按天次数。
- **可观察预期**：
  - 181 天前的打开和卡片不在。当天的打开还在。
  - 用户、称呼、头像、备注还在。
  - 按天次数里没有用户 id、指纹和短编号。
- **执行状态**：`NOT_RUN`
