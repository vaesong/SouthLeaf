## 1. 从哪里开始

本目录回答测试体系怎么搭建、文档如何分层、用例如何设计和结果如何验收。当前先形成与实现无关的测试设计；用例没有执行，不代表产品通过验收。本文及新增文档处于评审中，测试规则建议经评审后使用，不改变上游经营规则或接口契约。

阅读顺序：D-701 总体策略 → D-705 用例规范 → D-706 数据目录 → D-711～D-716 详细用例 → D-707 执行与证据 → D-708 追踪和待决项。D-702 保留业务验收场景，不承担详细步骤与执行流水账。

## 5. 怎么逐步搭建

1. 以 A/AT/P 和已评审的 D 设计明确规则、阶段边界、来源版本及待决项。
2. 对关键规则形成决策表、状态转换表、权限表和故障序列，评审断言能否被观察。
3. 用详细用例和合成数据完成桌面推演；发现歧义回到规则主归属，设计缺口登记 D-708。
4. 实现可用后，把同一份业务用例映射到单元、集成、接口、页面、微信目标环境和真机测试。自动化脚本引用用例 ID；框架和脚本名称后置。
5. 对每个候选版本生成执行批次，保留实际证据、缺陷和复测；按 D-707 门禁决定是否验收。
6. 后续阶段增加预约、支付和私密交付用例时，仍回归阶段一公开资格、数据最小化和旧链接规则。

## 6. 当前交付边界

本轮形成文档方案和详细用例；不安装测试框架、不运行产品测试、不锁定 API/数据库、不新增阶段一后台、不提交或部署。未评审接口字段、缓存传播目标、真实资料和真机设备等见 D-708。文档完整性检查与产品测试执行必须分别报告。

## 7. 当前完成状态

截至 2026-10-09，阶段一测试体系文档已经形成完整基线：D-701～D-708 定义策略、场景、专项、用例方法、数据环境、证据门禁和追踪待决项，D-711～D-716 落地 54 个主用例。D-702 的 46 个场景与 D-704 的 8 个故障补充均有唯一详细用例，无缺号或重号；BIZ 另要求六类摄影业务形成 24 次强制参数化执行。

这里的“完成”指测试体系和测试用例设计可以进入评审并可供候选实现执行，不代表产品已经达到阶段一验收结论。当前没有候选实现执行批次，全部用例为 `NOT_RUN`，D-707 的 12 项阶段一质量门禁也均应保持 `NOT_RUN`。编码实现具备可执行环境后，由测试工作按 D-707 建立批次、执行、留证、登记缺陷和复测；只有所有强制门禁均为 `PASS`，才能判定阶段一产品验收通过。
