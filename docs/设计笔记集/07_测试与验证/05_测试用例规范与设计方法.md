# 测试用例规范与设计方法

> 文档编号：D-705
> 文档状态：评审中
> 适用范围：目标架构、阶段一
> 更新日期：2026-10-09
> 上游需求：A05-A08、A15-A16
> 上游架构：AT04、AT09
> 关联计划：P01

## 1. 目的与边界

本文规定 SouthLeaf 测试场景如何转成可执行用例，以及用例的层级、编号、字段、状态、参数化、设计方法、变更和评审规则。阶段一用例与具体编程语言、测试框架、类名、表名和供应商无关；编码完成后，再把同一业务断言映射到实际接口、页面、日志和数据观察点。

本文不修改 A、AT、P 或其他 D 文档中的业务规则，不把草案接口字段写成生产兼容承诺，也不把设计推演等同于产品执行。本文及依照本文新增的用例初始均为“评审中”；没有实际执行记录时，执行状态只能是 `NOT_RUN` 或因明确前置缺失而登记为 `BLOCKED`，不得写成已通过。

## 2. 测试层级与证明责任

| 层级 | 主要对象 | 必须证明 | 不能单独证明 |
|---|---|---|---|
| L0 设计推演 | 规则、决策表、状态转换、故障序列 | 规则完整、断言可观察、待决项已暴露 | 实现正确、环境可用 |
| L1 单元/领域 | 公开资格、价格语义、参数边界、状态转换 | 纯规则在输入组合和边界上成立 | 数据库、网络、微信能力 |
| L2 接口集成 | 公开数据源、查询过滤、事务结果、依赖适配 | 服务端过滤、错误语义、数据最小化、恢复结果 | 页面交互、微信系统能力 |
| L3 接口契约 | HTTP/传输映射、DTO、兼容边界 | 已锁定字段、状态码、分页和错误外层一致 | 业务规则只靠字段名成立 |
| L4 页面/H5 辅助 | 展示模型、路由、加载/空态/错误、请求竞争 | 客户端消费和状态反馈正确 | 微信分享、合法域名、系统联系和真机生命周期 |
| L5 微信目标环境 | 目标构建、微信开发者环境、目标基础库 | 小程序接口、分享入口、域名配置和微信生命周期可用 | 真实设备差异已全部覆盖 |
| L6 真机与真实内容核验 | 约定设备、网络、真实公开资料 | 真实品牌、价格、联系方式、授权、撤回和客户可见结果 | 未纳入设备和网络组合的兼容性 |

同一主用例可以在多个层级执行，但每个层级必须有独立的观察点和执行记录。H5 或接口成功不能替代微信目标环境与真机结果；截图不能替代服务端过滤、媒体资格或缓存失效证据。

## 3. 追踪层级和对象区分

追踪链固定为：

```text
上游规则/设计章节
  → 验收场景
  → 主用例
  → 用例变体
  → 执行记录
  → 证据/缺陷
  → 批次门禁结论
```

| 对象 | 唯一职责 | 是否包含实际结果 | 计数规则 |
|---|---|---:|---|
| 验收场景 | 描述需要证明的业务目的和结果 | 否 | D-702 为 46 个既有场景 |
| 主用例 | 把一个场景展开为前置、步骤、断言和证据要求 | 否 | 阶段一基线为 54 个 |
| 用例变体 | 为主用例绑定一组参数、环境或故障条件 | 否 | 每个强制组合分别计数 |
| 执行记录 | 记录某批次、某环境、某变体的一次实际尝试 | 是 | 每次尝试一条；复测新增记录 |
| 证据 | 支撑某条实际断言的原始或脱敏材料 | 是 | 可被一条执行记录引用多个 |
| 缺陷 | 描述预期与实际差异及影响 | 是 | 不替代执行记录 |

阶段一采用“一场景一主用例”的基线映射，主用例沿用场景 ID，但两者不是同一份内容：D-702 保留验收意图，D-711～D-716 承载可执行步骤。变体不是新主用例；执行记录也不能反写到主用例正文中。

## 4. 编号规则

### 4.1 主用例

D-702 的 46 个场景原编号原样沿用：

- `S1-NAV-01`～`S1-NAV-05`：5 个；
- `S1-CONT-01`～`S1-CONT-05`：5 个；
- `S1-BIZ-01`～`S1-BIZ-04`：4 个；
- `S1-WORK-01`～`S1-WORK-06`：6 个；
- `S1-PKG-01`～`S1-PKG-05`：5 个；
- `S1-API-01`～`S1-API-08`：8 个；
- `S1-STATE-01`～`S1-STATE-08`：8 个；
- `S1-CACHE-01`～`S1-CACHE-05`：5 个。

D-716 根据 D-704 §4 补充 `S1-FAULT-01`～`S1-FAULT-08`，共 8 个。阶段一主用例总数为 `46 + 8 = 54`。已有 ID 永不因排序、拆文档或实现变化而重用；废止时保留 ID 和替代关系。

### 4.2 变体、执行与缺陷

- 变体 ID：`<主用例ID>-V<两位序号>`，例如 `S1-BIZ-01-V01`；参数名称另列，不把供应商或设备名称写入永久 ID。
- 执行批次 ID：按 D-707 使用 `TB-S1-<候选版本>-<环境>-<日期>-<序号>`。
- 执行记录 ID：`ER-<批次短标识>-<主用例ID>-V<序号>-A<尝试序号>`。
- 缺陷 ID：使用缺陷系统生成的稳定 ID；文档中只引用，不另造平行编号。

同一变体首次执行为 `A1`，修复后复测为 `A2`；不得覆盖首次失败或受阻记录。候选版本、环境名中不允许包含客户姓名、电话或密钥片段。

## 5. 主用例字段模板

以下模板用于 D-711～D-716；不适用的字段写“无”，不能删除安全与追踪字段。

```markdown
### <主用例 ID> <名称>

- 来源：<A/AT/P/D 文档编号与章节>
- 业务目的：<本用例要证明的业务结果>
- 优先级：P0 / P1 / P2
- 设计状态：草稿 / 评审中 / 已确认 / 已废止
- 就绪状态：未就绪 / 受阻 / 就绪
- 适用层级：L0～L6，可多选
- 前置条件：<公开状态、资格、页面位置、依赖状态>
- 数据引用：<D-706 数据集 ID，不粘贴真实隐私数据>
- 时间条件：<时钟点或符号边界；无则写“无”>
- 依赖与替身：<真实依赖、替身行为、故障注入点>
- 待决项：<D-708 编号；无则写“无”>

#### 变体
| 变体 ID | 参数 | 强制性 | 就绪状态 | 受阻原因 |
|---|---|---|---|---|
| <ID> | <键值组合> | 必选/条件必选/扩展 | <状态> | <待决项或无> |

#### 步骤与断言
| 步骤 | 操作/输入 | 可观察断言 | 观察层级 | 证据要求 |
|---:|---|---|---|---|
| 1 | <动作> | <页面/API/数据/任务/日志的确定结果> | <层级> | <证据类型> |

- 清理/恢复：<仅清理本 runId 隔离资源；说明故障恢复>
- 禁止替代证据：<例如“仅截图不能证明服务端过滤”>
- 最近评审：<日期、角色、结论；不得预填通过>
```

断言必须描述可观察结果，不使用“功能正常”“符合预期”等循环表述。页面、API、持久化结果、任务、日志和审计是不同观察面；主用例应只选证明规则所需的最小组合。

## 6. 优先级

| 优先级 | 定义 | 阶段一示例 | 门禁含义 |
|---|---|---|---|
| P0 | 安全、隐私、公开资格、不可逆泄露或核心不变量 | 未授权/资格未知不得公开；撤回后旧链接与媒体不得恢复；公开响应无敏感字段；客户端不能伪造资格 | 零失败；未执行或受阻也不能放行 |
| P1 | 客户主要路径、真实经营事实、一致性与可恢复性 | 四 Tab、六类业务、套餐价格语义、联系、加载恢复、分页、故障收敛 | 主流程必须全执行，门禁按 D-707 判断 |
| P2 | 不改变核心事实的非关键视觉、辅助兼容和扩展组合 | 非关键文案细节、非目标设备的补充观察 | 可排入后续，但不能伪装成已覆盖 |

优先级属于测试排序，不等于缺陷严重度。一个 P1 用例可能发现阻断缺陷；一个 P0 用例也不能因缺陷被标成低严重度而绕过门禁。

## 7. 三维状态模型

### 7.1 设计状态

| 状态 | 含义 | 允许动作 |
|---|---|---|
| 草稿 | 字段或断言尚未完整 | 补充设计，不进入正式验收 |
| 评审中 | 内容完整，等待规则、架构、运营或测试复核 | 可做 L0 推演，不代表可执行 |
| 已确认 | 来源、断言和变体经评审确认 | 可作为执行基线 |
| 已废止 | 上游范围变化或被其他用例替代 | 保留追踪和替代 ID，不执行新批次 |

### 7.2 就绪状态

| 状态 | 含义 | 典型原因 |
|---|---|---|
| 未就绪 | 用例本身尚未达到执行条件 | 步骤不完整、断言不可观察、数据配方缺失 |
| 受阻 | 用例设计可用，但外部前置未满足 | DTO 未锁定、域名未配置、设备清单未评审、真实授权资料未提供 |
| 就绪 | 指定变体在指定层级具备数据、环境、构建和观察能力 | 可以纳入执行批次 |

就绪状态应落实到变体和层级。接口字段待评审可以阻塞精确契约变体，但不得阻塞公开资格、数据最小化等不依赖字段名的业务断言。

### 7.3 执行状态

执行状态仅存在于执行记录：

- `NOT_RUN`：没有开始执行；这是所有新用例的默认状态。
- `PASS`：本次记录的全部适用断言均有证据且符合预期。
- `FAIL`：至少一条适用断言与预期不符。
- `BLOCKED`：已尝试执行，但环境、数据、权限或待决条件使结果无法判定。

设计状态、就绪状态、执行状态互不推导。“已确认 + 就绪”仍是 `NOT_RUN`；设计评审通过不能生成 `PASS`。主用例汇总不得掩盖变体结果，任何强制变体 `FAIL`、`BLOCKED` 或 `NOT_RUN` 都必须单列。

## 8. 参数化规则

1. 参数值来自 D-706 的数据集、环境或符号边界，不在步骤中复制大量数据。
2. 每个变体只表达一组可复现参数；运行时生成值必须写入执行记录。
3. D-702 的四个 BIZ 主用例必须逐类覆盖儿童、亲子全家福、婚纱、写真、孕照、证件照，即 `4 × 6 = 24` 次强制参数化执行。
4. 套餐覆盖 `FIXED`、`FROM`、`INQUIRY`、`UNDISCLOSED` 四种价格语义；不得把询价、未披露或未确认价格变成固定价或 0 元。
5. 作品至少覆盖合格、资格未知、授权撤回、下架和媒体单项失败；资格未知与媒体读取失败不能合并为同一变体。
6. 入口差异可能改变风险时，首页、列表、详情、分享/旧链接、后台恢复分别建立变体。
7. 网络、依赖和任务故障按故障点、时序与恢复动作参数化，不能只把 HTTP 状态码换值。
8. 组合数量过大时，P0 组合全覆盖；P1 先覆盖每个业务类别和每种关键语义，再对非关键交叉使用成对组合。删减组合必须记录理由和评审结论。

参数化只减少重复步骤，不减少断言和独立结果记录。一次循环输出若不能逐项定位数据、结果和证据，不算 24 次 BIZ 执行。

## 9. 用例设计方法

### 9.1 等价类与边界值

为合法、非法、缺失、未知和超限输入分别建类。已锁定数值使用 `最小值−1、最小值、最小值+1、最大值−1、最大值、最大值+1`；尚未评审的分页上限、TTL、传播时限和性能目标只使用符号边界，如 `LIMIT−1/LIMIT/LIMIT+1`、`T_expire−ε/T_expire/T_expire+ε`，待上游确认后替换参数值，不擅自填数。

字符串至少覆盖空值、允许字符、非法字符、刚好最大长度和超过最大长度。公开 ID、筛选和分页必须同时验证错误稳定、无内部异常泄露和无越权结果。

### 9.2 决策表

关键规则先写决策表，再生成变体。作品公开资格的最低决策表如下：

| 已发布 | A15 资格 | 媒体绑定/用途 | 公开结果 |
|---|---|---|---|
| 是 | 有效 | 有效 | 可生成公开 DTO；媒体仍须经受控网关复核 |
| 是 | 未知/超时 | 任意 | fail-closed，统一公开不可用 |
| 是 | 无效/撤回/失效 | 任意 | 统一公开不可用 |
| 否/已下架 | 任意 | 任意 | 统一公开不可用 |
| 是 | 有效 | 单个可选媒体读取失败 | 主资源可按契约保留文字和其他媒体；失败项不可泄露原始地址 |

决策表中的“任意”不是省略测试：安全结果相同的组合可合并为等价类，但至少保留一个代表变体及合并依据。

### 9.3 状态转换

对页面使用 `idle → loading → success(nonEmpty)/success(empty)/unavailable/error`，对媒体子项使用 `hiddenPendingEligibility → loading → loaded/failed`。用例必须包含：

- 合法转换及客户可见反馈；
- 旧请求晚到、快速切换、后台恢复和主动重试；
- 禁止转换，例如资格未确认时从本地缓存直接进入 `loaded`；
- 服务端确认撤回、下架或不可用后清理旧状态，弱网不能使其回退为可见。

业务或页面状态名称以后发生实现映射变化时，更新映射列，不改变“未知资格不得公开”等业务断言。

### 9.4 故障序列

故障用例按时间线编写，而不是只写“模拟失败”：

```text
T0 建立带 runId 的初始事实并记录基线
T1 发起公开读取、更新、资格核验或下架意图
T2 在已声明的调用前/调用后/持久化前/持久化后注入故障
T3 观察对外结果、业务事实、调用次数、任务、日志和审计
T4 恢复依赖并按设计执行重试、重放或人工动作
T5 观察最终收敛、幂等结果和残留公开面
T6 只清理本 runId 资源并保留脱敏证据
```

“明确拒绝”和“结果未知”必须分开；响应丢失、重复执行、乱序、进程重启和数据不匹配分别形成可定位变体。重试成功不能抹去首次故障证据。

## 10. 变更、评审与废止

### 10.1 变更规则

- 上游业务规则变化：先修改规则主归属文档，再更新场景、主用例、变体和追踪关系。
- 接口字段、路径或模型名称变化：更新 D-706 映射和用例观察点；不得删除或弱化业务断言。
- 环境、设备、域名、供应商或发布流程变化：更新就绪条件和环境引用，不改永久主用例 ID。
- 修正步骤但不改变业务目的：递增用例修订版本，已有执行记录继续引用当时版本。
- 业务目的拆分：保留原 ID 并登记替代关系，新 ID 只追加不重排。
- 缺陷修复：新建复测执行记录，不把失败记录改为通过。

每次候选版本执行必须冻结用例版本、数据配方版本、环境标识和待决项快照；执行中修改用例时，受影响记录作废并说明原因，不能无痕覆盖。

### 10.2 评审角色与检查项

| 评审角色类型 | 主要检查 |
|---|---|
| 业务/产品规则负责人 | 场景是否忠实于 A、P 范围，真实内容与价格语义是否正确 |
| 架构/接口负责人 | 观察点、错误语义、依赖边界和可测试性 |
| 内容/运营责任人 | 品牌、联系、发布、下架和真实内容来源 |
| 授权/隐私责任人 | 公开资格、撤回、敏感字段和证据使用边界 |
| 小程序/发布责任人 | 微信目标环境、域名、版本和真机条件 |
| 测试负责人 | 变体、数据、边界、故障、证据和门禁完整性 |

评审结论只能是“同意确认”“退回修改”或“带待决项继续评审”。带待决项不能自动把受影响变体标为就绪。TTL、设备清单、媒体供应商、正式域名和发布流程在上游确认前保持待评审，不在本文件锁定。

## 11. 当前基线

截至 2026-10-09，阶段一基线为 54 个主用例：D-702 的 46 个场景加 D-716 的 8 个故障补充。详细用例、数据、执行证据和追踪分别由 D-711～D-716、D-706、D-707、D-708 承担。

当前只建立测试体系，不代表任何实现已执行或产品已验收。所有执行结果初始为 `NOT_RUN`；受未决条件影响的具体变体在执行批次建立时登记为 `BLOCKED`，不得以未执行、桌面推演或文档评审替代 `PASS`。
