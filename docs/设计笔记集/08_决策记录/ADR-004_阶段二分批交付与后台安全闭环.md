# ADR-004：阶段二分批交付与后台安全闭环

> 状态：已确认（用户委托范围内的工程决策；S1-A/B/C1 已实现；后续增量未实现，不代表经营规则或生产部署批准）。
> 日期：2026-10-18；范围：P02 的 2A/S1–S2。
> 关联：[P03](../../计划/P03_阶段二分批交付与编码执行计划.md)、[ADR-003](ADR-003_阶段二管理安全与公开读取隔离.md)、[D-104](../01_总体设计/04_阶段二后台运行时模块边界与组合根设计.md)、[D-201](../02_通用后端/01_认证与会话设计.md)。

## 1. 背景

会话核心和 JDBC 已有实现，但仍与公开 API 同一 Maven 源树；登录、HTTP、后台 UI 未完成。继续直接增加 Controller 会扩大扫描/配置耦合；一次铺开所有后台页面则无法证明权限、事务和发布的真实闭环。现有章节骨架和跨文档编号偏差也会造成验收误判。

用户委托工程承担一般技术选择，先完善设计与编码计划。经营决策和生产操作仍需独立授权。

## 2. 决定

### 2.1 以可独立验收的纵向切片推进

S1 拆为 A 模块/产物隔离、B 非 Web 运行守卫、C 凭据与受控账号生命周期、D HTTP/最小后台登录。先关闭每批真实风险，再扩展媒体发布。P02 的 S0–S7 编号不变；没有一次性编写全部未来业务详细设计的前置要求。

### 2.2 模块化单体，按信任边界分产物/进程

采用 D-104 的六模块和聚合父 POM。public-api 不依赖 admin；core 主代码不依赖框架；JDBC adapter 向内依赖端口；迁移 CLI 不进入 runtime。公开/管理是独立 JVM，不引入业务微服务、注册中心、分布式事务或消息中间件。

模块按真实责任出现：S1-A 不预建媒体/预约/订单空模块。S1-C 中若维护库 KDF 同时被 runtime 和账号 CLI 使用，新增 `admin-credential-crypto`（核心端口的技术实现）及 `admin-account-cli`，不让 CLI 依赖 Boot runtime，也不把实现反塞到 core。现有随机 token codec 按 D-105 保持 runtime adapter，不为凑公共模块移动。

### 2.3 身份与权限分区，而不是一个万能 Writer

- 公开 Reader：公开 schema 只读，权限和行为保持。
- 管理安全 runtime：只访问精确安全表；登录与会话认证不拥有账号更新权限。
- 账号运维 CLI：显式执行、独立身份/权限矩阵；不与迁移 DDL 身份共用，不作为 Web 后门。
- S2 的业务 Writer 与 publication Writer：独立 adapter/连接池/精确权限；不能复用安全 Writer。
- 发布需要有限跨 schema 事务时按 D-507 设计；这是 S2 发布适配器的能力，不是让安全 Store 或普通业务 Repository 访问公开库。

最小权限矩阵随实际 SQL 和迁移版本演进；不在 S1-A/B 预授未来权限。B 的四表契约与 C 新认证审计表的扩展分别测试、记录版本，不能用“未来要用”放行未知 grants。

### 2.4 凭据使用维护库，核心只认识端口

选择 Argon2id，采用受维护的 Spring Security crypto 适配器及其需要的加密提供者，禁止手写 KDF。最低参数基线为内存 19,456 KiB、迭代 2、并行度 1、盐 16 字节、输出 32 字节；真实开发依赖版本与目标硬件基准在 S1-C 锁定，可调高但不默默调低。资源占用必须与登录限流/KDF 并发上限一起测试。

选择原因：密码与高熵随机会话令牌是不同威胁模型，不能复用 SHA-256 token digest。参数版本化、旧版本校验和显式升级由维护库实现；不新增生产默认密码。FIPS 或环境约束若出现，需新 ADR 选择合规替代方案，不能静默改算法。

### 2.5 同源 HTTPS 后台，服务端会话，维护框架 CSRF

后台采用 Vue 3 + TypeScript + Vite、Vue Router；初期不引入全局状态库，以组合函数管理身份状态。基础表单/布局选 Element Plus，版本在 S1-D 初始化时验证兼容性并锁入 lockfile；不在本轮臆造最新版本。浏览器 E2E 选 Playwright，单元/组件测试选 Vitest 与 Vue Test Utils。

admin-web 独立于原生微信 frontend，不修改小程序运行依赖。构建后与管理 API 同源部署；开发也经受信任本地 HTTPS 反向代理，不把放宽 Secure Cookie/CSRF 当作开发便利。

管理会话放 host-only HttpOnly Secure Cookie，不用 localStorage/JWT 替代已有撤销模型。HTTP 安全层使用维护中的 Spring Security Web/CSRF 机制，桥接现有认证用例；关闭默认用户、默认 form login、Basic、remember-me 和额外 HttpSession 认证持久化。CSRF 采用其 CookieCsrfTokenRepository，严格配置 __Host- cookie、header 名称和登录/退出轮换，并叠加明确 Origin 检查。核心不依赖 Spring Security。

### 2.6 适度扩展，不预建平台

不引入 Redis/MQ/工作流引擎。2A 管理登录限流先以单进程有界状态实现；重启和多实例边界必须公开记录，生产若需要多实例或持续全局限流，由独立 ADR 决定共享存储/边缘防护，不能宣称内存限流具备全局一致性。

未来客户身份不复用后台 Cookie/角色；客户写入口的组合根和部署边界在 S4 设计，保持 public-api Reader-only。通知以数据库 outbox/任务和可替换 provider port 实现，不把任务机制放入认证核心。

## 3. 放弃的方案

| 方案 | 不采用理由 |
|---|---|
| 单 jar + admin profile 作为最终边界 | 无法证明 classpath、扫描、配置与凭据的结构隔离 |
| 先做全套后台页面再接服务 | 容易用假状态掩盖身份、事务、发布资格与故障语义 |
| 直接使用公开表 CRUD 做后台 | 混淆草稿/私有事实与安全公开投影，扩大 Reader 暴露面 |
| 先部署生产账号/真实图片来联调 | 2A 可用隔离身份/合法测试媒体；真实资源属于 2B |
| 自写密码算法、通用超级 Writer、默认管理员 | 风险不可接受且缺乏必要性 |

## 4. 影响与验收

增加少量构建和启动配置，但可通过依赖图、最终产物和拒绝路径自动证明边界。迁移期间保持公开行为，避免大爆炸式同时改认证业务。采用维护库仍需版本/依赖扫描、Cookie/代理配置测试和资源压测，不自动获得安全认证。

验收依据 D-105/D-506/D-201/D-403/D-606/D-703；每批报告真实证据和未验证限制。技术设计认可不等于 task start、生产部署、经营规则批准或提交推送授权。

## 5. C1 落地补充（2026-10-18）

六模块是 S1-A 的迁移基线；C1 已新增真实实现的 `admin-credential-crypto` 普通 jar，当前七模块。它只依赖 core 和维护库，不依赖 runtime；本批尚无 runtime crypto 接线或账号 CLI，不预建 CLI 空模块。

沿用 §2.4 的 Spring 方案：BOM 实际解析 crypto 7.1.1，显式 Spring Core 7.0.9，provider 固定 BC 1.86。新写入调高为 m65536/t3/p1；最低档 m19456/t2/p1 只验证并提示运维升级，均限 v19/salt16/hash32。新参数不是 RFC 的 p4 原样配置。静态无队列预算最多 2；未知算法/参数与不规范 PHC 在库调用前拒绝，避免任意资源消耗及库解码告警泄漏。

两档独立参考向量、真实库测试、本机 512MiB 堆负载和解析后 OSV 已通过，详见 [C1 指南](../../开发与演示/阶段二S1-C1凭据核心与KDF验证指南.md)。C1 G1 不包含 C2 新 SQL/grants、C3 运维恢复/创建策略或生产负载；这些必须在各自接续批次冻结和验证。不得把维护库内存副本可擦除、dummy 恒定时间或本机指标直接当作生产保证。
