## 1. 目录职责

| 子目录 | 编号 | 职责 | 是否承载实施阶段 |
|---|---|---|---|
| `需求分析论证/` | `A01`、`A02`、`A03` 及后续 `A` 系列 | 产品定位、用户场景、业务需求、事实证据、需求规则和验收标准 | 否 |
| `架构与技术选型/` | `AT01`、`AT02` 及后续 `AT` 系列 | 模块边界、技术选型、架构设计、状态/权限/事务/错误码等技术前置契约 | 否 |
| `计划/` | `P01` 及后续 `P` 系列 | 三阶段范围、依赖、交付目标和验收方向 | 是，仅承载计划阶段 |

### 1.1 为什么高风险业务规则在 AT05

高风险规则的经营结论来自需求分析，但 AT05 的职责不是替代 A 系列需求文档，而是把进入架构设计前必须锁定的规则整理成决策矩阵，并明确它们对状态机、并发、权限、支付、退款和交付的影响。因此 AT05 放在 `架构与技术选型/` 是有意的。

后续第六步进入逐模块详细需求时，A 系列可以继续补充或引用这些已确认规则，例如预约、订单、支付和交付专题；但不应在 A 文档和 AT05 中重复维护两套互相冲突的规则。

## 4. 文档维护规则

- A 文档维护需求事实、场景、规则和验收，不写技术接口、数据库字段或实施阶段。
- AT 文档维护技术选型、架构边界以及让业务规则可实现、可审计、可补偿的技术契约。
- P 文档维护阶段范围和交付计划，不反向定义业务规则。
- 同一条业务规则只保留一个明确的主归属，其他文档通过引用说明，避免多处复制后产生冲突。
