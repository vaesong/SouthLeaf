## 1. 文档目的

本文件明确高风险业务用例的本地事务边界、并发控制、唯一性、幂等键、外部调用顺序、失败补偿和人工处理入口。

它不定义最终数据库表或 API 字段，而是先确定实现必须遵守的可靠性契约。最终表结构和接口契约必须能够证明满足本文件的要求。

## 2. 总体不变量

- MySQL 本地事务只能保证本地数据原子性，不能假设覆盖微信支付、退款、对象存储或网盘等外部服务。
- 外部调用不放在长事务中等待；优先采用“本地记录意图/处理中 → 外部调用 → 幂等落库 → 任务重试或人工补偿”的流程。
- 任何重复请求、重复回调、重复任务和网络重试都不能产生重复订单、重复硬占档、重复成功收款、重复退款或重复交付授权。
- 以数据库唯一约束作为最终并发兜底，以应用层校验改善用户体验；不能只依赖前端查询结果。
- 所有高风险状态变更必须记录操作者或系统身份、时间、原因、来源请求标识和关联业务号。
- 同一资源的锁定顺序必须稳定；需要同时锁多个资源时按固定排序获取，避免死锁。
- 失败补偿必须可观察：有任务状态、重试次数、最后错误、下次执行时间和人工处理入口。

## 3. 核心用例矩阵

| 用例 | 本地事务边界 | 并发/唯一约束 | 幂等键 | 外部调用顺序 | 失败补偿 |
|---|---|---|---|---|---|
| 提交线上预约申请 | 写入申请、套餐引用、来源和审计 | 不创建硬占档；同一客户重复提交按业务规则提示或允许多申请 | 客户端请求幂等键 | 无 | 重试返回原申请，不重复创建 |
| 后台录入线下预约 | 写入客户匹配/创建、预约来源和申请 | 必须走同一冲突校验服务 | 后台请求幂等键 | 无 | 失败整体回滚；保留错误日志 |
| 确认预约并自动成单 | 冲突校验、预约确认、硬占档、订单创建、套餐/价格/服务快照、支付计划、审计 | 同日期+固定时段的有效占用唯一约束；锁定时段后再写占用；订单与预约一对一约束 | 确认用例幂等键 + 预约唯一业务号 | 不调用外部支付；通知通过事务性任务/outbox | 唯一冲突返回业务冲突；重复请求返回既有订单 |
| 预约拒绝/超时 | 更新预约状态、拒绝/失效原因和审计 | 仅允许当前状态转换；避免与确认并发覆盖 | 预约状态变更幂等键 | 通知异步执行 | 任务失败重试，人工可补发 |
| 取消已确认预约/订单 | 更新取消事实、释放占用、生成退款申请意图（如适用） | 锁定预约/订单/占用，固定顺序；禁止已终止记录再次取消 | 取消请求幂等键 | 先落本地取消和退款意图，再调用退款渠道 | 退款任务重试；释放失败进入补偿队列 |
| 改期 | 新时段冲突校验和占用、创建修订记录、旧占用释放、支付归属/调整记录 | 新时段先占用成功后再释放旧时段；同一订单修订版本序列唯一 | 改期请求幂等键 + 修订号 | 不在本地事务内调用支付/退款 | 新时段冲突回滚；支付调整失败进入人工处理 |
| 延长定金截止时间 | 更新订单截止时间和审计 | 只允许待定金订单；使用版本控制避免覆盖新截止时间 | 延长请求幂等键 | 无 | 写入失败可重试；过期任务必须读取最新值 |
| 修改期限默认配置 | 写入配置版本和审计 | 只影响新申请、订单或交付批次；已有记录不回写 | 配置变更请求幂等键 | 无 | 写入失败可重试；配置变更通知后台操作人 |
| 定金逾期失效 | 读取订单、核验收款、更新订单/分期、释放占用、写任务和审计 | 锁定订单、分期和占用；与支付回调固定锁顺序 | 订单+截止时间版本+任务号 | 不调用支付；通知异步 | 发现处理中/已支付则不失效；释放失败人工补偿 |
| 创建在线支付单 | 写入支付尝试和处理中状态 | 同一分期未有有效处理中单时才创建；金额必须匹配 | 分期号+支付幂等键 | 本地记录意图后调用微信支付，再保存预支付信息 | 外部调用超时进入待查单，不盲目重建支付单 |
| 支付回调 | 验签、校验商户/订单/金额/分期、落支付事实、更新分期、更新必要摘要 | 外部支付单号唯一；同一分期成功事实唯一；回调与查单按支付单锁定 | 外部通知号/支付单号+事件类型 | 只做本地事务，不同步调用其他外部服务 | 失败重试回调；任务查单；人工核对 |
| 主动查单 | 记录查单任务结果、按回调同一规则应用支付事实 | 与回调共用支付单/分期锁和唯一约束 | 支付单号+查单批次 | 外部查单后本地幂等落库 | 结果未知继续退避；超过阈值人工核对 |
| 登记线下收款 | 写支付事实、付款凭证/备注、核验状态和审计 | 金额、分期和核验状态校验；重复凭证需提示 | 线下收款凭证号或后台请求幂等键 | 无 | 未核验不得计入可用已付金额；人工复核 |
| 确认拍摄完成并激活尾款 | 更新履约完成、激活尾款分期、写审计 | 订单履约版本控制；已完成重复请求返回原结果 | 订单号+履约动作号 | 不调用外部服务 | 事务回滚；可重试，不重复激活尾款 |
| 发起退款 | 写退款申请、审核事实、退款处理中状态和审计 | 退款累计金额不得超过可退金额；同一支付事实避免重复有效退款 | 退款申请号/外部退款幂等号 | 本地落意图后调用外部退款 | 超时进入处理中，查退款或人工处理 |
| 退款回调/查询 | 校验外部结果、更新退款事实和分期/订单摘要 | 外部退款单号唯一；成功退款事实不可覆盖 | 外部退款单号+事件类型 | 外部查询后本地落库 | 失败退避、人工核验和客户通知 |
| 上传文件登记 | 写文件元数据/上传会话和交付归属 | 对象标识、业务文件标识和版本唯一 | 上传会话号/文件客户端幂等键 | 先创建上传意图，再向对象存储申请上传 | 孤立对象清理和上传会话过期 |
| 文件上传校验 | 更新文件校验状态、哈希/大小/类型元数据 | 文件版本控制；只有已校验才能发布 | 文件号+校验版本 | 对象存储检查/读取元数据后本地落库 | 失败标记待重传，不发布 |
| 发布交付批次 | 更新批次发布状态、访问截止时间、授权和审计 | 只有校验完成且满足尾款/授权条件；发布动作幂等 | 批次号+发布版本 | 不把永久对象地址暴露给客户 | 失败保持未发布；重试或人工处理 |
| 交付入口到期下架 | 更新客户侧访问截止/下架状态和审计 | 按批次版本控制；不能删除工作室原文件 | 批次号+截止时间版本+任务号 | 通知异步执行 | 任务重试；下架与原文件保管分离 |
| 网盘人工补充交付 | 写补充交付记录、接收人、范围、链接有效期和操作者 | 需授权负责人；避免重复发放无效链接 | 补充交付请求号 | 先审计落库，再生成/登记外部链接 | 链接失败重新生成；保留旧链接撤回记录 |

## 4. 预约与档期并发规则

### 4.1 确认并发

1. 确认用例读取申请当前状态和套餐版本。
2. 按固定顺序锁定日期与固定时段对应的工作室冲突资源。
3. 在锁保护下检查是否存在有效硬占档。
4. 只有冲突检查通过，才在同一事务内写入占用、确认预约、订单和快照。
5. 依赖唯一约束处理最后一道并发竞争；失败时返回稳定的业务冲突错误。

申请列表显示“可选”不代表成功。线上确认、后台线下录入、改期和定时释放必须走同一冲突规则。

### 4.2 改期并发

- 新时段先校验和占用，旧时段后释放。
- 同一订单不能同时产生两个生效修订版本。
- 付款归属变更、补收或退款不与数据库事务假设为原子；必须记录待处理状态。
- 改期失败不能破坏原订单和原占用。

### 4.3 失效与支付回调竞争

定金逾期任务和支付回调可能同时到达。两者必须对订单、分期和支付事实采用一致的锁顺序，并在更新前重新读取最新支付状态：

- 已确认支付或结果处理中：不得直接释放档期；
- 明确未支付且已过截止：才允许订单失效并释放档期；
- 结果未知：进入待查单/人工补偿，不以任务先后顺序作结论。

## 5. 支付与退款可靠性

### 5.1 在线支付

- 创建支付单先在本地记录支付意图和金额快照，再调用外部支付服务。
- 外部调用超时不等于支付失败；状态进入处理中并由查单任务确认。
- 回调必须验签、校验商户号、外部支付单号、订单号、分期号和金额。
- 同一成功支付事实不可被前端返回、重复回调或人工普通编辑覆盖。
- 重复、超额或金额不符付款进入待分配/待退款，不自动计入其他分期。

### 5.2 线下收款

线下现金、转账或线下微信收款与在线支付共同写入支付事实，但必须保存付款方式、金额、时间、经办人、凭证/备注和核验状态。未核验收款不能直接满足定金、尾款或交付门槛。

### 5.3 退款

- 退款金额由取消/异常责任、未交付部分和负责人审核结果决定，不由订单状态单独推导。
- 退款申请、审核、外部请求、外部结果和人工处理是不同事实。
- 外部退款未知或失败进入处理中/失败待处理，有限重试后转人工。
- 退款幂等号必须稳定复用，不能因网络超时盲目创建新的退款请求。

## 6. 文件与交付一致性

- 对象存储上传成功不等于业务文件已发布；必须完成元数据和完整性校验。
- 数据库记录已上传但对象不存在时，进入待重试/异常状态；对象存在但无业务记录时，进入孤立对象清理队列。
- 发布交付批次时只引用已校验文件；发布状态和客户访问授权在本地事务内记录。
- 尾款付清前不生成任何成片访问地址；付清后带水印预览和正式下载分别按用途授权，正式下载不限次数且不加水印，访问和下载均记录审计。
- 客户入口到期只关闭小程序访问，不触发原文件物理删除；工作室网盘补充交付必须独立审计，链接有效期由工作室每次设置。
- 申请失效默认 48 小时、定金支付默认 24 小时、小程序交付入口默认 1 周，三者均支持后台配置；每笔记录保存实际截止时间，配置修改不回写历史记录。
- 签名 URL 是短期技术凭证，不是长期业务授权；每次访问仍需先通过应用层权限判断。

## 7. 任务、通知与人工补偿

所有异步任务至少需要：

- 任务类型和业务主键；
- 幂等键；
- 状态：待执行、执行中、成功、待重试、失败待人工；
- 重试次数、最后错误、下次执行时间；
- 创建来源、request id 和审计关联号。

适合任务化处理的场景：

- 预约申请超时；
- 定金到期复核和档期释放；
- 支付查单和对账；
- 退款查询、重试和通知；
- 交付入口到期下架；
- 对象存储孤立文件清理；
- 客户提醒和失败通知。

人工补偿入口至少支持：

- 重新查单；
- 重新发送通知；
- 审核或修正线下收款；
- 审核退款失败；
- 释放异常占用；
- 恢复错误下架的交付入口；
- 登记网盘补充交付。

人工补偿不能直接修改最终状态而不保留原事实；应通过带原因的业务动作或补偿记录完成。

## 8. 仍需补齐的技术契约

- 日期/固定时段冲突的具体唯一键表达和数据库隔离级别；
- 订单修订版本、支付归属和退款转移的精确规则；
- 支付渠道接口字段、签名、查单和退款 SLA；
- 对象存储分片/直传、回调和病毒或内容校验策略；
- 任务调度、退避、最大重试次数和告警阈值；
- 错误码、request id、审计字段和敏感数据脱敏规则。
