## 1. 文档目标与边界

本文件在完整需求全景和三阶段计划之后，建立一层总体模块框架和系统边界，为技术选型、架构设计和后续模块详细分析提供共同基线。

本文只回答：

- 系统有哪些入口、业务域和横向能力；
- 每个模块负责什么、不负责什么；
- 模块之间怎样依赖；
- 哪些能力必须统一建设；
- 哪些架构决策可以现在确定，哪些必须等待业务规则确认。

本文暂不定义：

- 具体数据库表、字段和索引；
- 具体 API 路径、请求参数和响应结构；
- 页面原型和视觉细节；
- 每个业务模块的完整状态机；
- 技术实现代码、部署脚本和开发排期。

## 2. 总体架构判断

### 2.1 产品形态

SouthLeaf 是单个摄影工作室使用的品牌展示、预约、订单、支付和成片交付平台，包含三类产品入口：

1. **微信小程序**：客户的主要移动端入口，承担公开浏览以及后续预约、订单、支付和交付访问。
2. **品牌官网**：面向公众的品牌与案例展示入口，复用公开内容，但可以采用不同的信息组织和访问路径。
3. **工作室管理后台**：工作室内部维护内容、处理预约、管理客户与订单，并跟进支付、履约和交付。

三类入口不直接各自实现业务规则，而是通过统一的业务后端访问同一套业务数据和规则。

### 2.2 初期架构形态

建议采用：

> **模块化单体后端 + 多入口客户端 + 关系型主数据库 + 对象存储 + 外部平台适配层**

模块化单体不是把所有代码混在一起，而是在一个可独立部署的后端应用中按业务域组织模块，并通过模块边界、依赖方向和统一契约保持解耦。

初期不建议直接采用微服务、事件驱动全链路或复杂工作流引擎。原因是当前产品只服务一个工作室，业务规则仍在收敛，团队和运维规模有限；过早拆分会增加分布式一致性、部署和排查成本。

### 2.3 核心业务链路

```text
公开内容
  ↓
作品 / 摄影业务 / 套餐
  ↓
电话或微信联系，或提交预约申请
  ↓
工作室核对档期与服务条件
  ↓
确认预约
  ↓
形成订单
  ↓
定金支付
  ↓
拍摄与履约
  ↓
尾款支付
  ↓
后期制作与私密成片交付
```

此链路中的预约、订单、支付和交付是不同业务对象，不能用一个“状态字段”混合表示。

## 3. 分层模块框架

### 3.1 入口与客户端层

| 入口 | 主要职责 | 不负责 |
|---|---|---|
| 微信小程序 | 移动端公开浏览、客户预约、订单查看、支付和交付访问 | 自行判断档期冲突、计算最终应付金额、确认支付结果 |
| 品牌官网 | 品牌、作品、业务、套餐和联系信息展示，必要时提供预约入口 | 绕过统一业务规则直接写入订单或支付状态 |
| 工作室后台 | 内容维护、预约处理、客户与订单运营、支付和交付跟进 | 把业务规则全部写成页面特例；直接修改底层数据绕过审计 |

客户端只承担展示、输入、交互和状态呈现；最终业务判断由后端完成。

### 3.2 业务应用层

#### A. 品牌与内容模块

负责：

- 首页、品牌介绍、服务流程、团队、地址和联系方式；
- 内容草稿、预览、发布、下架；
- 内容排序和展示配置；
- 面向小程序和官网的公开内容查询。

不负责：

- 预约和订单中的业务快照；
- 客户私密照片；
- 支付和客户身份判断。

#### B. 作品与案例模块

负责：

- 作品分类和案例组织；
- 案例标题、说明、封面和图片顺序；
- 作品与摄影业务、套餐的可选关联；
- 公开展示状态；
- 消费 A15 提供的公开授权资格和撤回结果。

不负责：

- 私密成片交付；
- 自动根据作品生成订单；
- 将作品分类自动当作可预约业务。

公开作品与客户成片必须在数据权限和文件访问策略上隔离。

#### C. 摄影业务与套餐模块

负责：

- 当前确认的六类摄影业务：儿童、亲子全家福、婚纱、写真、孕照、证件照；
- 标准套餐、价格、时长、服务包含项和适用范围；
- 套餐发布、下架、排序和展示；
- 套餐与作品的关联；
- 套餐版本或历史快照所需的业务信息。

不负责：

- 预约是否冲突；
- 订单形成后的支付状态；
- 交付文件权限。

订单形成时应保存当时确认的套餐内容和价格快照，公开套餐后续调整不应改变既有订单约定。

#### D. 客户与身份模块

负责：

- 客户身份识别；
- 联系人资料和拍摄人资料；
- 微信身份、手机号或人工建立的客户记录关联；
- 客户与预约、订单、支付和交付记录的关联；
- 客户资料的隐私和访问边界。

不负责：

- 公开访客浏览权限；
- 工作室人员的业务操作权限；
- 支付渠道自身的身份认证。

客户身份与后台工作人员身份应分别建模，不能默认共用一套权限判断。

#### E. 预约与档期模块

负责：

- 客户提交具体日期和时间段；
- 预约申请状态；
- 工作室确认、拒绝、取消和改期；
- 可预约日期、时间段和临时不可用时间；
- 档期冲突识别；
- 预约处理记录和工作室备注。

不负责：

- 在未经确认时直接生成正式订单；
- 直接创建支付单；
- 代替订单模块保存最终交易约定。

当前已确认规则是“客户提交申请，工作室确认后才成立，确认后自动形成订单”：待确认申请不占硬档，同一日期和固定时段允许多个待确认申请；工作室确认时重新校验冲突，成功后建立排他占用。阶段二首版按同一日期和固定时段判断冲突，电话/微信线下预约与线上预约共用同一冲突源。

#### F. 订单与履约模块

负责：

- 预约确认后形成订单；
- 保存客户、业务、套餐、日期、时间段和价格快照；
- 订单生命周期；
- 拍摄准备、拍摄完成和履约备注；
- 取消、改期和异常终止的订单记录；
- 为支付和交付提供明确的业务上下文。

不负责：

- 公开套餐的当前价格；
- 支付平台的签名与回调验签；
- 文件上传和下载权限的具体实现。

订单状态与支付状态、交付状态分开管理，避免“已支付”被误解为“已拍摄”或“已交付”。

#### G. 支付与退款模块

负责：

- 定金和尾款的应付计划；
- 支付单和支付状态；
- 支付平台下单、回调、查单和幂等；
- 退款申请和退款状态；
- 支付异常和对账所需记录。

不负责：

- 决定订单是否成立；
- 前端单方面确认支付成功；
- 修改订单原始服务内容。

外部支付平台通过适配层接入，业务模块只依赖内部支付能力和标准支付结果，不在订单模块中散落平台 SDK 调用。

#### H. 成片交付模块

负责：

- 交付任务和交付状态；
- 原片、精修图、视频或其他交付文件的归属；
- 私密访问、预览、下载和有效期；
- 客户访问权限；
- 公开案例授权与客户成片的隔离。

不负责：

- 公开作品内容管理；
- 自动认定客户已经完成付款；
- 直接暴露对象存储永久地址。

## 4. 横向基础能力

横向能力不属于某一个具体业务域，但必须通过统一方式提供，避免各模块各写一套。

### 4.1 认证与权限

分为：

- 客户身份认证：支持公开浏览，预约、订单和私密交付需要可靠身份识别；
- 后台人员认证：管理员及后续可能的摄影师、运营人员；
- 授权控制：按角色、资源归属和操作类型判断；
- 会话和令牌管理：统一过期、刷新、撤销和异常处理；
- 敏感操作保护：支付、退款、交付授权、客户资料查看和批量下架需要更严格控制。

认证回答“你是谁”，授权回答“你能做什么”，资源归属回答“你能访问哪一条记录”，三者不能混为一个登录判断。

### 4.2 错误处理与错误码

统一错误处理至少区分：

1. 参数校验错误；
2. 身份认证失败；
3. 权限不足；
4. 资源不存在或不可访问；
5. 业务状态不允许；
6. 外部服务失败；
7. 系统内部异常。

对客户端返回稳定的错误码、用户可理解的提示和请求追踪标识；不要直接把 Java 异常、SQL 信息、堆栈或第三方响应原文暴露给用户。

内部日志保留详细异常和堆栈，外部响应只返回必要信息。错误码应稳定、可文档化，不能把 HTTP 状态码和业务错误码混成一套含义。

### 4.3 日志与审计

分为三类：

- **应用运行日志**：启动、请求、依赖调用、异常和性能信息；
- **业务操作日志**：预约确认、拒绝、改期、订单处理、支付状态变更、内容发布、下架、交付授权等；
- **安全审计日志**：登录、登出、失败登录、权限拒绝、敏感资料访问、退款和权限变更。

日志规范：

- 使用统一日志门面和结构化字段；
- 每个请求有 request id/trace id；
- 记录操作者、业务对象、动作、结果和时间；
- 不记录密码、令牌、支付密钥、完整手机号、私密文件地址等敏感内容；
- 日志按级别、环境和保留策略管理；
- 业务审计记录不能只依赖普通文本日志。

### 4.4 文件与媒体

文件能力统一封装，业务模块只关心文件归属、类型、状态和访问策略，不直接拼接存储地址。

至少区分：

- 公开作品图片；
- 后台待发布素材；
- 客户私密成片；
- 原片、精修图、视频或交付压缩包；
- 临时上传文件。

上传需校验类型、大小、扩展名和归属；私密文件使用短期授权访问，不使用永久公开链接。

### 4.5 通知

通知能力统一封装，业务模块发布“预约已确认”“待支付”“尾款待支付”“成片已交付”等业务事件，由通知模块决定具体渠道和模板。

通知发送失败不能回滚已成功的核心业务操作；通知应有重试、幂等和失败记录。

### 4.6 配置与密钥

配置分为：

- 环境配置：数据库、外部服务地址、运行环境；
- 业务配置：工作室资料、可配置规则和展示设置；
- 敏感配置：支付密钥、对象存储密钥、认证密钥。

敏感配置不进入前端、不写入 Git、不出现在日志和异常响应中。开发、测试、生产环境配置隔离，禁止把本机路径、明文密码和 localhost 地址作为生产默认配置。

### 4.7 可观测性与运维

至少具备：

- 健康检查；
- 应用错误和慢请求记录；
- 数据库和对象存储依赖可用性监测；
- 支付回调和通知失败监测；
- 备份与恢复验证；
- 关键业务指标：预约申请、确认、拒绝、订单形成、定金支付、尾款支付和交付完成。

初期不必引入复杂监控平台，但接口、日志和关键业务记录应预留可观测性字段。

## 5. 模块依赖原则

建议依赖方向如下：

```text
入口层
  ↓
应用编排层
  ↓
业务模块
  ↓
领域规则与持久化/外部适配
  ↓
基础设施
```

具体原则：

1. Controller/页面不直接访问 Repository、数据库或对象存储。
2. 业务模块不直接依赖具体支付、短信或云厂商 SDK，使用内部端口和适配器。
3. 订单不读取套餐当前数据来替代订单快照。
4. 支付不反向修改订单服务内容，只更新支付事实并通知订单履约。
5. 交付不直接判断收款平台结果，依据订单/支付模块提供的业务状态。
6. 公开内容查询和客户私密交付查询使用不同的授权策略。
7. 横向能力由统一组件或应用服务提供，不在各业务模块复制实现。
8. 模块之间优先通过明确的应用服务、领域事件或内部接口协作，不通过互相读表形成隐式耦合。

## 6. 当前建议的后端模块目录方向

以下是逻辑边界示例，不是最终 Java 包名或必须一次性创建的目录：

```text
backend
└── src/main
    ├── java/.../content
    ├── java/.../works
    ├── java/.../catalog
    ├── java/.../customer
    ├── java/.../reservation
    ├── java/.../order
    ├── java/.../payment
    ├── java/.../delivery
    ├── java/.../admin
    ├── java/.../notification
    └── java/.../common
        ├── auth
        ├── error
        ├── logging
        ├── audit
        ├── storage
        ├── config
        └── observability
```

实际包结构应在总体架构设计阶段结合依赖方向和测试策略确定，不应因为当前原型已有 `controller/service/repository/entity` 目录就直接把所有未来业务堆进去。

## 7. 当前可确定与待确认

### 7.1 现在可以作为架构基线

- 单工作室，不做多租户和多工作室平台；
- 小程序、官网、管理后台共用统一后端；
- 初期采用模块化单体，不直接拆微服务；
- 内容、作品、套餐、客户、预约、订单、支付、交付分域；
- 日志、错误处理、认证权限、文件、通知、配置、审计和可观测性作为横向能力统一建设；
- 公开内容与客户私密成片隔离；
- 订单保存形成时的套餐和价格快照；
- 外部支付和云存储通过适配层接入。

### 7.2 进入详细设计仍需确认

- 不同业务的时长、人数、地点和业务专属字段；
- 各套餐的具体固定定金金额、尾款说明和版本管理方式；
- 改期提前通知期限、可改期次数和修订版本展示方式；
- 退款审核、部分退款计算和人工处理流程；
- 成片分批交付、原文件保管、备份、恢复和物理删除策略；
- 客户登录与线下电话/微信记录合并方式；
- 后台角色数量、敏感操作复核和摄影师首版权限；
- 官网是否直接提交预约及其与小程序入口的差异；
- 支付、对象存储、网盘和通知供应商的具体契约；
- 真实部署环境、域名、备案、备份和合规要求。

## 8. 架构完成判断

本文件达到总体边界基线的条件：

- 业务模块和横向模块职责不重叠；
- 入口层不承载核心业务判断；
- 预约、订单、支付、交付的边界清楚；
- 公开内容与私密文件访问隔离；
- 日志、错误处理、认证授权、审计和配置不再作为事后补丁；
- 高风险业务规则被列为待确认，而不是由架构文档擅自决定。
