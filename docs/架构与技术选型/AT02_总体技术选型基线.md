## 1. 选型目标

技术选型服务于以下产品事实和工程目标：

- 单个摄影工作室，不做多工作室平台；
- 产品包含微信小程序、品牌官网和工作室后台；
- 业务从公开展示逐步扩展到预约、订单、支付和私密成片交付；
- 需要长期维护内容、图片和业务记录；
- 需要专业、解耦、可扩展，但不以复杂基础设施为目标；
- 需求仍会继续细化，选型应保留调整空间；
- 支付、身份、隐私和文件访问需要可靠的服务端控制。

本文是选型基线，不等同于最终架构设计。技术版本、云厂商套餐、部署拓扑和详细依赖应在架构设计和验证阶段锁定。

## 2. 选型结论总览

| 领域 | 建议基线 | 选型性质 | 说明 |
|---|---|---|---|
| 小程序 | 原生微信 JS/JSON/WXML/WXSS | 阶段一已批准并实施 | 单一 frontend 源码，见 ADR-002 |
| 官网 | 独立 Web 方案待定；优先评估 Nuxt 3，简单场景可复用 uni-app H5 | 待验证 | 取决于 SEO、内容运营和官网交互深度 |
| 管理后台 | Vue 3 + TypeScript + Vite + 企业级 UI 组件库 | 方向确定，组件库待定 | 表格、表单、筛选和运营操作优先 |
| 后端 | Spring Boot 4.1.1 + Java 21 | 当前实施基线 | 版本与兼容性以 POM 及实际验证为准 |
| 后端形态 | 模块化单体 | 建议确定 | 先保持单体部署，按业务域解耦 |
| API | REST/JSON + 统一错误响应和鉴权约定 | 建议确定 | 适合小程序、官网和后台的多客户端访问 |
| 主数据库 | MySQL | 建议确定 | 支撑客户、预约、订单、支付和审计等关系数据 |
| 数据访问 | Spring JDBC + MySQL + Flyway | 阶段一已实施 | 公开发布读模型与授权事实分离；无 JPA/CRUD 兼容链路 |
| 图片与成片 | 对象存储，数据库保存元数据和权限关系 | 建议确定 | 公开作品和客户私密成片分开授权 |
| 缓存 | 初期不强制引入 Redis | 延后 | 先用数据库约束、事务和幂等解决核心一致性 |
| 消息队列 | 初期不引入 | 延后 | 通知失败可先用任务表/重试机制，规模上升再评估 |
| 支付 | 微信支付小程序支付，服务端负责下单、回调、查单和退款 | 阶段三方向确定 | 外部支付 SDK 放在适配层 |
| 认证 | 客户身份与后台人员身份分离设计 | 方向确定，产品方式待定 | 具体登录和绑定方式需结合小程序场景确认 |
| 日志 | SLF4J + Logback 结构化规范 | 延续并加强 | 当前工程已存在基础日志依赖和滚动文件配置 |
| 错误处理 | 统一异常映射、稳定错误码、用户提示与 request id | 必须建设 | 当前已有基础全局异常处理，但需规范化 |
| 审计 | 独立业务/安全审计记录 | 必须建设 | 不以普通文本日志替代敏感操作审计 |
| 通知 | 内部通知接口/事件 + 渠道适配 | 方向确定，渠道待定 | 预约、支付和交付状态变化可复用 |
| 配置 | 分环境配置 + 密钥外置 + 业务配置数据化 | 必须建设 | 清除本机路径、明文密码和环境耦合 |
| 可观测性 | 健康检查、错误、慢请求、关键业务指标 | 方向确定 | 初期不强制复杂平台 |
| 测试 | 单元测试 + Web 层/应用层测试 + 关键链路集成测试 | 必须建设 | 当前测试覆盖明显不足 |
| 部署 | 先选择稳定的单体部署方式，容器化可作为标准化手段 | 待环境确认 | 不在选型阶段提前绑定具体云厂商 |

## 3. 客户端技术

### 3.1 微信小程序：原生微信

按 ADR-002 与用户确认，阶段一已转为微信原生 App/Page/Component，保留批准 UI、六页面和公开 API。当前仅服务微信目标，移除 uni-app/Vue/Vite 运行和编译链，不保留长期双轨；原生不是普遍优于 uni-app 的结论，也不锁定未来 Web 后台的框架。

运行时零 npm 包，Prettier 为锁定开发依赖。请求、严格 DTO 映射、页面生命周期与纯展示转换分层；真实数据经 API 提供。构建显式配置 SOUTHLEAF_API_ORIGIN，生成运行配置和微信项目配置。正式配置及真实设备验收在阶段二，阶段一不能绕过发布守卫或冒充正式上线。

微信模板必须通过实际开发者工具编译和 UI 回归，Node 检查不能替代。格式、测试、安装审计、源码导出重建、实际 HTTP 与六路回归证据见收敛交付记录。

### 3.2 品牌官网：根据 SEO 和运营目标选择

候选方向：

1. **Nuxt 3**：适合需要搜索引擎收录、品牌内容长期运营和服务端渲染/静态生成的官网。
2. **uni-app H5**：适合官网只是小程序的轻量同步展示，且希望最大化复用现有代码的场景。

建议先确认：

- 是否以搜索引擎自然流量为重要获客来源；
- 官网是否需要独立的内容页面和文章/案例结构；
- 官网是否直接提交预约，还是主要引导电话、微信和小程序；
- 是否愿意维护两套展示端的体验差异。

在这些问题确认前，不把官网技术方案完全锁死；无论选哪条路线，内容和业务数据都应来自统一后端。

### 3.3 管理后台：Vue 3 + TypeScript + Vite

后台与客户端的任务不同，优先选择成熟的后台 UI 组件体系，重点支持：

- 表格和筛选；
- 表单校验；
- 图片和文件上传；
- 草稿、预览、发布、下架；
- 预约处理和冲突提示；
- 订单、支付和交付状态操作；
- 权限和操作反馈。

组件库具体选择放到后台界面设计和工程基线阶段，不影响当前总体架构方向。

## 4. 后端与业务架构

### 4.1 Spring Boot + Java 21

当前工程使用 Spring Boot 4.1.1、Java 21、Web MVC、Spring JDBC、MySQL 和 Flyway。保留模块化单体、领域/应用/端口边界和技术适配器；旧 JPA/CRUD 路径已移除。

选择理由：

- 与现有代码一致，减少迁移成本；
- 适合 REST API、事务、认证、校验、定时任务和外部服务适配；
- Java 21 适合长期维护和现代语言特性；
- Spring 生态适合后续补充安全、监控、对象存储和支付 SDK。

版本原则：

- 使用经兼容性与安全验证的受支持 Spring Boot 稳定版本，当前 POM 为 4.1.1；
- Java 21 作为统一运行时；
- 版本由依赖兼容性和部署环境验证后锁定，不在本文盲目升级；
- 依赖保持最小化，避免为了“可扩展”一次性加入大量中间件。

### 4.2 模块化单体

后端保持一个可部署应用，但内部按业务域分层：

```text
content
works
catalog
customer
reservation
order
payment
delivery
admin
notification
common
```

每个业务模块建议具备清晰的：

- 对外应用服务；
- 领域规则；
- 数据访问边界；
- 外部适配接口；
- 模块级测试。

初期不把模块直接拆成独立仓库或微服务。只有出现明确证据时才考虑拆分，例如独立扩缩容需求、独立发布节奏、媒体处理负载明显隔离或团队边界发生变化。

### 4.3 API 风格

建议采用 REST/JSON，并统一以下契约：

- 资源命名和 HTTP 方法；
- 分页、排序、筛选和时间格式；
- 成功响应和错误响应结构；
- request id/trace id；
- 客户端与后台的权限范围；
- 幂等请求和重复提交处理；
- 版本兼容策略。

当前公开响应包含稳定 code、用户安全 message、data、requestId 与 meta；分页携带 nextCursor/contentVersion。错误不返回内部异常原文。后续管理/客户写接口单独设计字段校验与认证语义，不恢复旧响应兼容。

## 5. 数据与文件技术

### 5.1 MySQL

MySQL 作为主数据存储，适合：

- 摄影业务和套餐；
- 作品和内容元数据；
- 客户、预约、档期和订单；
- 支付事实、退款和对账记录；
- 交付任务、文件元数据和授权；
- 管理员、角色、审计和配置。

一致性要求：

- 订单、支付、预约等关键操作使用明确事务边界；
- 金额使用整数分或明确的定点类型，禁止浮点金额；
- 状态变更有合法转换校验；
- 订单保存套餐和价格快照；
- 数据库约束用于防止重复和越权关联；
- 生产环境禁止依赖 `ddl-auto=update` 自动变更结构，应使用可审查的数据库迁移流程。

### 5.2 对象存储

图片和成片放在对象存储中，MySQL 只保存：

- 文件元数据；
- 业务归属；
- 类型和大小；
- 上传和处理状态；
- 公开/私密策略；
- 访问授权和有效期。

建议建立至少两类访问策略：

- **公开作品**：公开读或通过 CDN/加速域名访问；
- **客户成片**：私有读，由服务端签发短期访问地址或代理访问。

对象存储具体选用腾讯云 COS 或其他兼容服务，取决于最终部署环境、价格、区域、备份和合规要求。业务代码通过内部 StoragePort/适配器接入，避免散落厂商 SDK。

## 6. 认证、权限与安全

### 6.1 身份模型

至少区分：

- 公开访客；
- 客户；
- 工作室管理员；
- 后续可选的摄影师/运营人员。

公开访客不应被迫登录才能浏览公开内容。预约、订单、支付和私密成片访问需要可靠的客户身份。后台使用独立认证入口和更严格的操作权限。

### 6.2 授权模型

初期可以采用基于角色与资源归属的授权：

- 客户只能访问自己的预约、订单和成片；
- 后台管理员按角色获得内容、预约、订单、支付、交付和用户资料权限；
- 敏感操作要求记录操作者并可审计；
- 所有访问控制在服务端执行，前端隐藏按钮不构成安全边界。

### 6.3 安全基线

- 密码、令牌、支付密钥和对象存储密钥不写入代码；
- 生产配置与开发配置分离；
- 日志脱敏；
- 文件上传校验类型、大小和归属；
- 外部回调验签、幂等和重放保护；
- 管理后台需要防止越权访问；
- 重要操作需要审计记录；
- 数据备份和恢复应实际演练。

## 7. 日志、错误处理与审计基线

### 7.1 日志

继续使用 SLF4J + Logback，但统一日志格式和字段：

- timestamp；
- level；
- service/environment；
- requestId/traceId；
- operator/user identifier（脱敏）；
- module/action；
- duration；
- result/error code。

日志级别建议：

- `ERROR`：系统异常、外部依赖失败、数据一致性风险；
- `WARN`：可恢复异常、业务拒绝、重试和降级；
- `INFO`：关键业务过程和重要生命周期；
- `DEBUG`：开发调试，不在生产输出敏感数据。

当前 `application.properties` 已配置滚动文件日志，但仍需补充环境区分、结构化输出、敏感字段脱敏、集中采集和保留策略。

### 7.2 错误处理

统一异常层负责把异常映射为：

- HTTP 状态；
- 稳定业务错误码；
- 用户安全提示；
- request id；
- 字段级校验错误（如适用）。

推荐错误分类：

```text
VALIDATION_ERROR
UNAUTHENTICATED
FORBIDDEN
RESOURCE_NOT_FOUND
BUSINESS_STATE_INVALID
CONFLICT
EXTERNAL_SERVICE_ERROR
INTERNAL_ERROR
```

客户端根据错误类别决定提示、重试、跳转登录或刷新状态，不根据后端异常原文或平台字符串判断。

当前 GlobalExceptionHandler 已将公开参数、游标冲突、资源不可用、依赖不可用及未知异常映射到稳定状态与安全提示，包含 requestId，不返回原始异常信息。管理端与客户身份错误契约在阶段二继续建设，不能把匿名公开读取的错误模型直接等同全部后续接口。

### 7.3 审计

业务审计记录至少覆盖：

- 管理员登录和权限变更；
- 内容发布、下架和删除；
- 预约确认、拒绝、改期和取消；
- 订单关键状态变更；
- 支付、退款和线下收款录入；
- 客户资料和私密成片访问；
- 交付授权、撤回和下载策略变更。

审计记录应保存动作、操作者、目标对象、前后关键状态、结果和时间，不保存不必要的敏感原文。

## 8. 通知、任务与外部服务

### 8.1 通知

通知模块先抽象“业务事件 -> 通知任务 -> 渠道发送”，初期可以使用数据库任务记录和有限重试，不必立即引入消息队列。

候选事件包括：

- 预约提交；
- 预约确认或拒绝；
- 订单生成；
- 定金待支付或支付成功；
- 尾款待支付或支付成功；
- 成片已交付。

具体使用订阅消息、短信、邮件或人工微信通知，等待运营规则和平台资质确认。

### 8.2 定时任务

可用应用内定时任务处理：

- 预约申请超时提醒；
- 支付过期检查；
- 通知重试；
- 交付链接过期；
- 数据清理和备份检查。

任务必须有幂等、执行记录、失败重试和人工补偿入口。只有当任务量或可靠性要求超过单体能力，再评估独立调度器或消息队列。

### 8.3 支付适配

阶段三接入微信支付小程序支付时，业务层只依赖内部支付接口：

- 创建定金/尾款支付单；
- 获得待支付参数；
- 接收并验签支付通知；
- 主动查单；
- 申请和查询退款。

前端支付回调不能作为唯一事实来源，后台必须以回调验签或主动查单确认支付状态。

## 9. 部署与环境

运行服务的数据库身份和媒体目录来自环境变量，本机脚本从系统凭据库读取账号；不将秘密写入代码或客户端。阶段二仍须正式身份隔离、证书/域名校验及独立部署。

建议至少区分：

- local：本地开发；
- test：联调和测试；
- production：正式运行。

每个环境独立配置：

- 数据库连接；
- 对象存储桶和访问域名；
- 微信小程序 AppID；
- 支付商户配置；
- 日志级别和输出；
- 回调地址；
- 文件访问策略。

部署形态可以优先评估：

1. 单体后端 + MySQL + 对象存储的简单托管部署；
2. Docker 化的单体应用，配合托管数据库和对象存储。

是否使用具体云厂商、容器编排或 CDN，等待预算、地域、备案、访问量和运维能力确认后决定。

## 10. 测试与质量工程

建议建立分层测试：

- 领域规则单元测试：状态转换、金额和预约冲突；
- 应用服务测试：预约确认生成订单、支付状态更新、交付授权；
- Web/API 测试：认证、权限、错误响应、分页和幂等；
- 基础设施集成测试：MySQL、对象存储、支付回调；
- 客户端测试：关键路径、错误状态和真机适配；
- 端到端测试：浏览 -> 预约 -> 确认 -> 订单 -> 支付 -> 交付。

阶段一已有单元/架构、真实 MySQL、严格客户端映射、源码导出重建和微信模拟器回归；具体计数以收敛交付记录为准。它们不替代后续订单/支付用例或正式设备/生产验收。

## 11. 明确不提前引入的技术

在没有业务和性能证据前，暂不默认引入：

- 微服务和服务网格；
- Kubernetes；
- 消息队列；
- Elasticsearch；
- 复杂工作流引擎；
- 多租户框架；
- 独立推荐系统；
- 大型数据仓库；

这不是永久排除，而是把引入条件放在真实需求、规模和运维能力之后。

## 12. 需要后续验证的技术决策

1. 官网 SEO 和独立内容能力是否要求采用 Nuxt 3；
2. 客户登录采用微信身份、手机号绑定还是组合方式；
3. 对象存储和部署地域、域名、备案与合规要求；
4. 管理后台角色及是否需要独立摄影师账号；
5. 预约冲突与并发程度是否需要 Redis 或数据库锁策略；
6. 通知渠道和失败重试要求；
7. 成片文件规模、下载流量、访问有效期和备份策略；
8. 支付商户资质、退款和对账流程；
9. 是否需要容器化和持续集成；
10. 业务指标、日志集中采集和告警平台。

## 13. 推荐推进顺序

```text
1. 整体模块框架与系统边界
2. 总体技术选型基线
3. 用预约、订单、支付、交付四类关键场景验证选型
4. 确认高风险业务规则
5. 完成总体架构设计：模块、数据、接口、权限和外部适配边界
6. 继续深入各业务模块需求
7. 将技术依赖和验证结果映射回 P01
8. 进入分阶段实现
```

当前 AT01 和 AT02 都属于架构/选型讨论基线，不替代后续详细需求专题，也不直接授权开始实现。
