## 1. 文档目的

本文件把总体模块框架、技术选型和关键链路验证进一步整理为架构设计草案，作为后续详细架构设计的输入。

本文件重点确定：

- 模块边界及其职责；
- 逻辑业务对象及其关系；
- 入口、应用服务、业务模块和基础设施之间的边界；
- 状态归属和跨模块协作原则；
- 权限、事务、幂等和补偿的设计原则；
- 支付、存储、通知等外部服务的适配边界；
- 仍然阻塞详细设计的业务决策。

本文件不直接确定：

- 数据库表、字段、索引和迁移脚本；
- 完整 API 路径、请求参数和响应 JSON；
- 页面原型、组件结构和视觉方案；
- 具体云厂商套餐、部署脚本和生产密钥；
- 第 4 步已确认规则之外的具体数据库字段、接口字段、运营配置和实现细节。

## 2. 架构设计原则

### 2.1 目标架构与阶段开放分离

目标架构可以一次性定义全部业务边界，但三阶段计划只逐步开放能力：

- 架构回答“系统长期有哪些边界和能力”；
- 计划回答“每个阶段开放哪些能力”；
- 需求专题回答“每个业务规则和用户场景是什么”。

阶段一暂不开放预约、订单、支付和客户业务操作，不代表目标架构中不需要为这些业务预留边界。

### 2.2 模块化单体优先

后端先采用一个可独立部署的模块化单体：

- 模块拥有明确的业务对象和应用服务；
- 模块通过应用服务、内部端口或明确事件协作；
- 模块不通过互相直接读表形成隐式依赖；
- 外部服务通过适配器隔离；
- 未来有明确的规模、发布或团队边界时再评估拆分服务。

模块化单体不是把所有业务类放在一个公共包中，也不是把现有 `controller/service/repository/entity` 目录简单扩大。

### 2.3 架构事实、设计假设和业务决策分离

后续文档和实现必须使用三种状态：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| 架构不变量 | 当前已经可以固定的边界或安全要求 | 进入架构约束和测试 |
| 设计假设 | 为了继续设计而暂时采用的方案 | 标明可替换，不冒充业务事实 |
| 业务待决策 | 需要工作室负责人确认的经营规则 | 不在技术文档中擅自定论 |

例如，“私密成片不能由对象存储直接决定访问权限”是架构不变量；“初期使用数据库任务表处理通知重试”是设计建议；“尾款付清后才开放带水印预览和正式下载”是已确认业务规则。

## 3. 总体分层与依赖方向

```text
微信小程序 / 品牌官网 / 工作室后台
                ↓
       入口适配与接口层
                ↓
       应用服务与用例编排层
                ↓
        业务模块与领域规则层
                ↓
   持久化端口 / 外部服务端口 / 任务端口
                ↓
 MySQL / 对象存储 / 微信支付 / 通知渠道 / 运行设施
```

### 3.1 入口适配与接口层

负责：

- 接收请求和解析输入；
- 认证信息提取；
- 参数格式校验；
- 调用应用服务；
- 返回统一成功或错误响应；
- 注入和传递 request id/trace id。

不负责：

- 判断档期冲突；
- 计算最终支付金额；
- 直接操作数据库、对象存储或支付 SDK；
- 仅通过隐藏按钮实现权限控制。

### 3.2 应用服务与用例编排层

负责：

- 组织一次完整的用户或后台用例；
- 调用相关业务模块；
- 定义事务边界；
- 执行权限和资源归属检查；
- 发布任务或内部事件；
- 把领域结果转换为接口层所需结果。

应用服务不应成为没有业务归属的“万能服务”。一个用例应有明确的发起模块和结果归属。

### 3.3 业务模块与领域规则层

负责：

- 业务对象的规则和状态转换；
- 业务不变量；
- 对外提供明确的应用服务或内部端口；
- 保存属于本模块的事实。

不负责：

- 直接拼接 HTTP 响应；
- 依赖具体云厂商 SDK；
- 绕过其他模块的公开应用服务直接修改其数据。

### 3.4 基础设施与适配层

负责：

- 数据库访问；
- 对象存储访问；
- 微信支付调用和回调验签；
- 通知渠道调用；
- 定时任务执行；
- 日志、指标和运行环境集成。

基础设施层不得把供应商的原始状态、异常文本和内部密钥泄露给上层或客户端。

## 4. 业务模块边界

### 4.1 content：品牌与内容

**拥有：**

- 品牌资料；
- 首页编排；
- 工作室介绍；
- 服务流程；
- 团队公开资料；
- 联系方式和地址；
- 内容草稿、预览、发布和下架事实。

**提供：**

- 已发布公开内容查询；
- 后台内容编辑和发布用例。

**不负责：**作品案例的图片集合、摄影业务套餐、预约或订单。

### 4.2 works：作品与案例

**拥有：**

- 作品案例；
- 作品分类和标签；
- 案例图片及展示顺序的业务元数据；
- 与摄影业务或套餐的可选关联；
- 案例公开展示状态，以及对公开授权结果的消费。

**不负责：**公开授权的同意/撤回事实、客户私密成片、预约资格、订单生成和客户交付权限。

“创始人档”可以作为作品或品牌分类保留，不能未经确认变成可预约摄影业务。

### 4.3 catalog：摄影业务与套餐

**拥有：**

- 摄影业务目录；
- 标准套餐；
- 价格和服务内容；
- 适用范围、时长和展示顺序；
- 套餐发布、下架和版本信息。

当前需求确认保留儿童、亲子全家福、婚纱、写真、孕照、证件照六类业务，但技术上应保持业务目录可配置，不将六类写成不可删除的代码枚举。

**不负责：**预约冲突、订单支付状态、私密文件访问。

### 4.4 customer：客户与身份

应区分以下概念：

- **登录身份**：用于认证和会话；
- **客户档案**：工作室业务关系中的客户记录；
- **联系人**：预约和订单中的沟通对象；
- **拍摄人**：实际接受摄影服务的人；
- **交付授权对象**：允许访问成片的人。

这些对象可能在真实场景中是同一个人，但不能在架构上默认等同。

**拥有：**客户档案、身份绑定、联系人/拍摄人关联和客户资料访问规则。

**不负责：**后台员工权限、订单业务状态和支付平台身份。

### 4.5 reservation：预约与档期

**拥有：**

- 预约申请；
- 预约处理状态；
- 档期可用性和占用事实；
- 确认、拒绝、取消和改期记录；
- 预约处理备注。

**边界原则：**

- 预约申请、预约确认和档期占用是可区分的业务事实；
- 阶段二首版采用可配置固定时段，按同一日期和固定时段判断冲突；
- 待确认申请不占硬档，同一时段允许多个待确认申请并行存在；
- 工作室确认预约时重新校验冲突，并在同一用例中建立排他占用和创建订单；
- 电话/微信线下预约与线上预约共用同一冲突源；
- 客户端展示的可用状态不是最终占用结果。

**不负责：**订单服务内容、支付事实和成片授权。

### 4.6 order：订单与交易约定

**拥有：**

- 预约确认后的交易约定；
- 套餐、价格和服务内容快照；
- 订单商业生命周期；
- 客户、预约和履约的关联；
- 订单取消、改期和异常终止记录。

订单必须保存形成时的约定，不依赖读取当前公开套餐来恢复历史事实。工作室确认预约并成单时冻结套餐、价格、服务内容、日期和固定时段快照；改期使用修订版本，原记录不可覆盖。

#### 履约状态的归属决定

拍摄准备、拍摄安排和拍摄完成属于订单履约子域，初期不拆成独立部署模块，以避免订单和履约产生不必要的分布式边界。逻辑上仍然单独维护履约状态，不并入支付或交付状态。

未来如果拍摄排班、摄影师协作或履约流程明显复杂，再评估独立的 `fulfillment` 模块。

### 4.7 payment：支付与退款

**拥有：**

- 定金和尾款支付计划；
- 支付单和支付尝试；
- 支付成功/失败/处理中等支付事实；
- 退款事实；
- 对账和支付异常记录。

**边界原则：**

- `payment` 拥有支付事实和支付汇总；
- `order` 拥有交易约定和订单生命周期；
- 支付回调不能修改订单的服务内容；
- 订单需要支付摘要时，通过应用服务或明确的只读投影获取；
- 未知结果进入处理中或待查单，不直接标记失败。

### 4.8 delivery：成片交付

**拥有：**

- 交付任务和交付批次；
- 交付文件业务元数据；
- 文件校验、发布、撤回和删除状态；
- 客户访问授权及有效期；
- 私密交付访问授权、有效期和撤回结果；
- 向 A06 提供公开授权资格、范围、有效期和撤回结果的消费输入。

公开案例授权的同意、范围、有效期、证据和撤回事实由 A15/`delivery` 持有，`works` 只消费授权结果并计算案例公开资格。`storage` 只负责对象存储技术操作，不能决定客户是否有权访问。`delivery` 根据身份、订单、支付/履约事实和私密授权策略决定是否签发短期访问地址。

### 4.9 notification：通知

**拥有：**

- 通知任务；
- 模板和渠道选择；
- 发送、重试和失败记录。

通知失败不回滚预约、订单、支付或交付等核心业务事实。通知任务应通过同库任务表或事务性 outbox 可靠地产生。

## 5. 横向能力边界

### 5.1 auth：认证

认证只回答“当前请求是谁”，不直接决定“能访问哪条业务数据”。

- 客户认证和后台人员认证分开；
- 公开浏览无需客户登录；
- 预约、订单和成片访问需要可靠身份；
- 外部支付回调依赖平台签名，不依赖客户会话。

### 5.2 authorization：授权

授权组合判断：

```text
角色 + 操作 + 资源归属 + 当前业务状态
```

前端是否显示按钮不构成授权边界。所有客户数据、支付、退款、交付授权和后台敏感操作在服务端重新判断。

### 5.3 error：错误处理

统一提供：

- 参数校验错误；
- 未认证；
- 无权限；
- 资源不存在或不可见；
- 业务状态冲突；
- 外部服务错误；
- 系统内部错误；
- request id。

客户端只接收稳定错误码和安全提示，不接收异常堆栈、SQL、密钥或第三方原始响应。

### 5.4 logging 与 audit：日志和审计

- `logging` 记录应用运行和诊断信息；
- `audit` 记录业务和安全操作事实；
- 普通日志不能替代审计；
- 预约处理、订单变更、支付/退款、内容发布、成片授权和敏感资料访问应具备审计记录；
- 日志和审计均需脱敏，禁止记录密码、令牌和永久私密文件地址。

### 5.5 storage：文件技术能力

只提供：

- 上传会话或上传凭证；
- 对象写入和读取；
- 短期签名地址；
- 对象元数据；
- 删除和一致性检查。

不提供业务权限判断，不保存订单、客户或支付状态。

### 5.6 task：任务和补偿

统一处理：

- 通知重试；
- 支付查单和对账；
- 交付链接过期；
- 孤立文件清理；
- 数据备份检查；
- 人工补偿任务。

任务必须具备幂等键、执行状态、重试次数、最后错误和人工处理入口。

### 5.7 config 与 observability：配置和可观测性

配置负责环境差异和敏感密钥外置；可观测性负责健康检查、错误、慢请求、外部依赖和关键业务指标。二者不能由各业务模块分别实现一套。

## 6. 逻辑对象关系

以下只描述对象级关系，不等同于数据库表结构：

```text
内容发布记录 ──> 作品案例 ──> 公开媒体资产
摄影业务 ──> 套餐版本 ──> 作品/套餐关联

登录身份 ──> 客户档案
客户档案 ──> 联系人 / 拍摄人关系
客户档案 ──> 预约申请 ──> 档期占用事实

预约确认 ──> 订单
订单 ──> 套餐 / 价格 / 服务内容快照
订单 ──> 履约记录
订单 ──> 支付计划 ──> 支付单 / 支付事实 / 退款事实
订单 ──> 交付任务 ──> 交付批次 ──> 交付文件 ──> 访问授权
```

### 6.1 必须保持的关系约束

- 已确认预约是否最多一个订单，需要结合改期/重建规则最终确定；
- 订单快照取得时点必须明确，不能在不同用例中随意变化；
- 档期占用是独立逻辑事实，不能由订单存在与否隐式推断；
- 支付计划、支付事实和订单状态互有关联，但不能互相覆盖所有状态；
- 交付资格通过明确的业务策略判断，不能简单等同于“订单存在”或“已支付”；
- 作品公开媒体资产和客户私密交付文件在授权上隔离。

## 7. 接口边界

### 7.1 公开查询接口

面向访客和公开页面，只返回：

- 已发布品牌内容；
- 已发布作品和公开媒体；
- 已发布摄影业务和套餐；
- 工作室公开联系方式和地址。

禁止返回草稿、下架内容、客户资料、私密文件或后台备注。

### 7.2 客户业务接口

面向已识别客户，提供：

- 提交和查看自己的预约；
- 查看预约处理结果；
- 查看自己的订单和支付摘要；
- 发起允许的定金/尾款支付；
- 访问获得授权的成片。

客户接口不能允许客户端传入后直接覆盖价格、支付状态、订单服务内容或交付授权。

### 7.3 后台管理接口

面向授权工作室人员，提供：

- 内容、作品、业务和套餐维护；
- 预约和档期处理；
- 客户和订单运营；
- 支付、退款和线下收款处理；
- 交付文件和授权管理；
- 审计与异常补偿操作。

敏感接口必须要求独立权限和审计，不因同属后台就全部开放。

### 7.4 外部回调和任务接口

包括：

- 支付平台回调；
- 存储上传完成或媒体处理结果；
- 通知重试；
- 支付查单、对账；
- 文件清理和一致性检查。

外部回调先经过验签、身份映射、幂等检查和业务对象匹配，再调用对应应用服务，不能直接改写跨模块数据。

## 8. 用例级事务与补偿边界

| 用例 | 本地事务重点 | 外部调用和补偿 |
|---|---|---|
| 提交预约 | 创建预约申请、关联客户、写幂等记录 | 通知异步任务；失败可重试 |
| 确认预约 | 校验状态、资源和权限，写确认和档期事实 | 通知异步任务；冲突返回稳定错误 |
| 确认并创建订单 | 只有在“确认即成单”规则确定后，才将确认和成单放在一个本地事务 | 通知任务不影响主事务 |
| 支付下单 | 创建支付意图/支付单，锁定本地金额依据 | 调用支付平台；未知结果进入查单 |
| 支付回调/查单 | 验签、幂等写入支付事实、更新支付汇总 | 通知或订单投影失败可重试 |
| 退款 | 创建退款事实并记录退款状态 | 退款平台调用、查单和人工补偿 |
| 文件上传 | 创建上传会话、登记完成和校验状态 | 对象存储失败重试；清理孤立对象 |
| 发布交付 | 校验文件完成、权限和业务资格，写发布与授权 | 通知异步任务；授权撤回可重复执行 |
| 后台敏感操作 | 业务变更和审计记录尽量同一事务 | 外部通知失败不回滚业务事实 |

支付平台和对象存储不能与 MySQL 假设共享分布式事务。外部操作的可靠性依赖状态机、幂等、查单、重试和人工补偿。

## 9. 状态归属原则

详细状态值和转换矩阵另行设计，但归属先固定如下：

| 事实 | 权威归属 | 其他模块如何使用 |
|---|---|---|
| 内容/作品/套餐发布 | 对应内容模块 | 通过公开查询读取发布结果 |
| 预约申请和处理 | `reservation` | 订单读取确认结果，不自行改写 |
| 档期占用 | `reservation` 或排期子域 | 订单引用，不由订单存在隐式推导 |
| 订单商业生命周期 | `order` | 支付和交付读取订单资格 |
| 拍摄履约进度 | `order` 的履约子域 | 支付和交付读取明确履约事实 |
| 支付计划、支付单、退款 | `payment` | 订单读取支付摘要，交付读取授权条件 |
| 交付任务和文件 | `delivery` | 客户通过授权结果访问 |
| 通知发送 | `notification` | 业务模块只提交通知任务 |
| 审计记录 | `audit` | 各模块提交操作事实 |

## 10. 当前架构不变量、设计假设与业务输入

### 10.1 架构不变量

- 单工作室产品，不建立多租户业务前提；
- 采用模块化单体；
- 入口层不承载核心业务判断；
- 公开内容与客户私密成片隔离；
- 支付、存储、通知使用适配层；
- 支付事实、订单生命周期、履约进度、交付状态分开归属；
- 服务端执行认证、授权、冲突判断和金额校验；
- 敏感操作可审计，日志脱敏；
- 外部服务未知结果进入待处理/待查单/补偿路径。

### 10.2 设计假设

- 初期使用同库任务表或事务性 outbox，不立即引入消息队列；
- 初期履约逻辑作为订单子域，不独立部署；
- MySQL 事务和约束足以支撑初期档期和订单一致性；
- 对象存储通过短期签名地址提供私密文件访问；
- 官网和小程序复用统一后端内容与业务服务。

这些假设需要在详细设计和关键场景测试中验证，不是永久承诺。

### 10.3 已确认业务约束

以下规则已经由 AT05 确认，属于架构必须支持的业务输入：

- 阶段二采用可配置固定时段；待确认申请不占档，同一时段允许并行申请；确认时建立排他占用；
- 线上和电话/微信线下预约共用同一冲突源；临时封档不自动取消已确认预约；
- 工作室确认预约时自动生成订单，并冻结套餐、价格和服务内容快照；
- 定金按套餐配置固定金额，订单生成后默认 24 小时内支付；逾期失效并释放档期；迟到支付在原时段可用时自动恢复，否则进入退款/人工处理；
- 改期保留原记录并创建修订版本，已支付定金经协商后沿用；
- 拍摄完成由负责人或管理员确认并触发尾款；尾款逾期不自动取消或退款；
- 首版允许后台登记线下收款，不支持任意部分付款；支付和退款未知结果进入处理/补偿流程；
- 首版交付精修图片和原片，尾款付清后开放带水印预览和不限次数的无水印正式下载；
- 默认授权预约联系人，公开案例必须明确同意；小程序交付入口默认开放 1 周并支持配置，到期下架但不自动删除工作室原文件；
- 申请失效、定金支付和小程序交付开放期均支持后台配置，历史记录保存实际截止时间。

### 10.4 进入详细设计待补充输入

以下不是第 4 步经营规则阻塞项，而是进入模块详细设计时需要补齐的内容：

- 各摄影业务的预约字段、敏感字段和校验规则；
- 改期提前通知期限、可改期次数和修订版本展示方式；
- 退款审核页面、部分退款计算和人工处理流程；
- 官网是否直接提交预约及其与小程序入口的差异；
- 摄影师账号是否在首版启用及其分配交互；
- 原文件内部保管、备份、恢复和物理删除策略。
