### 关于阶段范围，必须说明

P01 §1、§3.3.4 明确：阶段一只交付小程序公开展示，不交付完整后台；**并未规定 MySQL 是唯一合法数据源**。因此，采用服务端受控文件本身不是架构错误，也不应为了“专业”提前建设预约、订单、支付或完整后台。

但 P01 同时要求公开数据受控维护、授权可核验、撤回可验证。允许当前全部使用演示数据，并不等于这些正式验收项已经完成。若你的交付要求进一步包含“关键展示数据真正落库”，当前实现还不满足，需要补最小数据库适配与迁移，而不是仅填写数据库连接串。

- 前端有统一请求/错误处理和映射层，处理受控媒体 URL、演示模式、旧请求失效及前后台重查。

### 3.2 两条链路

```text
旧链路：/api/categories、/api/packages
       → CategoryService / PackageService
       → JPA Repository → MySQL（当前两表为空）

新链路：小程序 → /api/v1/public/*
       → PublicQueryService → 各公开读取端口
       → Json*Reader / PublicCatalogSource
       → catalog.json 或配置的外部 JSON
```

j130 实测：旧分类/套餐 GET 均返回 0 项；新 businesses/packages 均返回 6 项。旧 CRUD 即使将来写入 MySQL，也**不会自动同步到当前新展示页面**。

新链路虽然不读数据库，但同一个 Spring Boot 应用仍启用 JPA/数据源自动配置，因此服务启动仍依赖数据库可用。现在是“文件提供新展示数据，同时数据库成为启动依赖”，不是公开读取层已经完全独立部署。

### 3.3 数据库建设缺口

- 没有看到完整的版本化迁移链路（Flyway/Liquibase 等）和阶段一新模型建表/导入验收。
- 当前 `ddl-auto=update`，不适合作为正式环境受控迁移机制。
- `data.sql:1–4` 使用 `desc`，而实际列为 `description`，且未提供非空字符串主键 id；不能直接作为可执行的初始化方案。
- JPA `services/reminder` 最终落在 varchar(255)，不适合未来较长服务数组/说明；当前展示未使用这些列。
- 未见本轮可证明的备份恢复演练、最小权限应用账号和正式数据库运维验收。

**建议：明确文件模式还是数据库模式，再补对应的受控发布方案。若落库，保留现有公开端口和前端契约，实现阶段一最小的数据模型、迁移、导入、发布状态与读取适配，不扩展完整后台产品。**

## 四、风险清单与处理优先级

> P0：如果要对外部署，必须先消除的阻断项。P1：正式交付/上线前闭环。P2：工程一致性和可维护性收尾。这里的优先级不是“已经遭受攻击”的结论。

### R01 · P0 · 旧写接口仍开放在应用中

**证据**：`CategoryController.java:34/44/57`、`PackageController.java:26/43/53` 注册新增、更新、删除；pom 和本次源码扫描未见 Spring Security 或相应拦截/鉴权实现。j139 对 add 路由的匿名 OPTIONS 返回 200、Allow 含 POST。j130 显示应用监听 `::`:8090。

**影响**：如果将该应用直接对外暴露，不能依赖“小程序没放按钮”保护旧数据库写操作。当前未验证外部防火墙/网关，不宣称互联网已可访问；也没有为了证明问题发起破坏性写入。OPTIONS 只证明路由存在，权限缺口结论来自代码检查。

**处理**：阶段一优先默认关闭旧 CRUD/旧扫描路由或只在显式本地开发 profile 注册；公开部署仅放行明确公开读取路由。无需因此开发完整登录后台。

### R02 · P1 · 数据库高权限账号和跟踪配置中的明文凭据

**证据**：j133 确认为 root；j140 确认密码非空且非环境占位；`application.properties` 已被 Git 跟踪。配置还包含本机路径、useSSL=false、allowPublicKeyRetrieval=true、show-sql=true 和 ddl-auto=update。

**影响**：环境耦合、误部署和凭据传播风险；root 超出普通展示服务所需权限。当前 MySQL 只监听回环，不能据此说数据库已暴露公网。

**处理**：开发/测试/正式 profile 分离，凭据环境注入、最小权限应用账号、迁移账号分离；若凭据曾提交/分享，按历史暴露范围轮换，不能只删当前文件。正式环境按部署方式配置加密连接和日志策略。

### R03 · P1 · 新旧数据源没有业务闭环

**证据**：第三节 SQL/API 对照；Json 公开读取器未调用 JPA Repository。

**影响**：容易误以为“数据库维护了，页面就更新”；新展示模型无法通过现有数据库表维护。它是“交付口径和数据维护缺口”，不是前端接口造假，也不是 P01 规定必须立即上数据库。

**处理**：明确单一正式事实来源、发布责任和更新路径；若要求落库，新增适配器并做接口/数据库一致性与重启持久性验证。

### R04 · P1 · 迁移与初始化脚本不可作为可重复交付基线

**证据**：`backend/src/main/resources/data.sql` 与实际表列/主键不一致；只有旧两张表，未发现版本化迁移；DDL 自动 update。

**处理**：建立最小版本迁移、测试种子与正式资料导入分离、幂等初始化、空库建库和升级验证；先修脚本再执行，不能对现库直接试跑旧 data.sql。

### R05 · P1 · 正式公开授权与撤回协议未接通

**证据**：`JsonPublicAuthorizationReader.java:15–36` 从作品同一 JSON 中读取授权块；`ScopedPublicAuthorization`/候选评估端口尚未成为实际权威链路。P01 §3.3.4 和 D-002 要求 A15 事实归属及未知/撤回拒绝。

**影响**：现有 ALLOWED/confirmed/rightsConfirmed 是演示或维护标记，不是可核验的真实人物授权证据。production 的目录批准标记不能代替用途/渠道/图片范围/期限与当前性检查。文件撤回测试通过，也不证明跨系统并发撤回、前台持续展示和在途流的正式协议已完成。

**处理**：只补阶段一必要的公开授权记录、权威来源、范围/版本消费和撤回验收，不要求提前实现阶段三私密交付产品。

### R06 · P1 · 正式媒体准备流程与旧静态目录绕行风险

**证据**：`JsonPublicMediaReader.java:77–103` 有大小、扩展名、简单签名、路径与所属检查，但没有完整图片解码/尺寸限制、EXIF 清理等发布处理。`application.properties` 仍把旧本机 Images 目录映射为静态资源；`Utils.java:36–42` 拼接目录扫描。

**边界**：j130 检查该旧静态目录当前不存在，**没有证明已泄露真实图片**。但如果将受控/私密图片放进这类静态根目录，可能绕过新公开资格网关。旧路径扫描也未做新网关那样的 canonical-root 约束。

**处理**：正式公开衍生图准备/验证流程，私有原图与公开产物分离；移除旧静态直出映射和扫描链路，禁止复用作私密交付。

### R07 · P1 · 前端依赖告警未处理

**证据**：j132 使用 npm 官方 registry 的完整 audit 返回 **51 个依赖包告警条目：29 high、13 moderate、9 low、0 critical**。这不是 51 个独立漏洞，也不是 29 个可直接攻击小程序的入口。最初 npm 镜像审计接口不支持，j131 的 404 不代表安全。

直接依赖告警涉及 dcloud 相关包、Vite、Rollup、Vue、vue-i18n 等；实装 Vite 5.2.8、Rollup 4.14.3、Vue 3.4.21、vue-i18n 9.14.4。部分来自构建/开发服务或 SSR 依赖链，不一定进入微信运行时代码。npm 的 prod/dev 标记也不能直接等同“是否打入小程序”。

**处理**：按实际可达性分拣、dcloud 兼容版本矩阵整体升级并回归；不要直接运行 `npm audit fix --force`，其建议可能切换不兼容版本线。生产不开放开发服务器。本轮未完成 Java 全量传递依赖 CVE 扫描，不能对后端依赖作“无漏洞”结论。

### R08 · P1 · 正式 AppID、域名、设备与真实资料验收未完成

**证据**：j143：manifest AppID 未配置，而项目配置存在 AppID。j137 在提供 HTTPS 示例 origin 后仍按预期拒绝 release：缺已确认 AppID。之前模拟器能打开不代表 AppID 归属、合法域名或手机网络已验收。

**处理**：统一确认正式 AppID、HTTPS/合法域名与部署；真机检查分享、返回/恢复、弱网、图片预览、系统复制、真实二维码与撤回场景。当前所有人员/账号/二维码继续是演示内容。

### R09 · P1 · 缺少可签字的阶段验收批次

**证据**：D-707 要求冻结候选、配置、数据和强制门禁；当前工作区有大量未跟踪文件、报告/构建会被覆盖，未形成对应完整验收归档。D-708 的历史 NOT_RUN 不能自动转为本次 PASS。

**处理**：先处理阻断缺口，再按 D-707 建立可追溯候选与批次，映射强制场景/变体/设备；审查敏感配置和生成目录后选择性提交/归档，不能简单 `git add .`。

### R10 · P2 · 文件快照、聚合和游标一致性不足

**证据**：`PublicCatalogSource.data()/refresh()` 多次读取文件；首页、授权、媒体组合调用重复取数。`CatalogCursor.after()` 游标只包含最后 ID，ID 不在新集合时返回空；前端虽收到 contentVersion，但分页没有以它统一冻结/重置快照。

**影响（静态推断，未修改现有目录做破坏复现）**：更新中聚合数据与 meta 版本可能不完全一致，跨版本分页会混合或提前结束；频繁校验的开销随目录增长放大。演示小数据可用，不宜据此承诺大规模维护与事务发布。

**处理**：请求级一致快照、发布版本、游标绑定查询/版本、版本变化重查；文件模式使用受控原子替换。保持对撤回/未知的安全拒绝，不能为缓存性能回退到旧许可。

### R11 · P2 · 仍有品牌硬编码和历史死代码

**活跃链路**：`index.vue:16/82/105` 有固定英文品牌和分享标题；作品/服务/关于列表的分享标题也固定包含品牌名。业务品牌一旦更换，不会全部跟随接口更新。

**处理**：品牌英文名/分享文案按品牌接口或统一品牌配置消费；归档/标记未使用组件和旧 API，增加构建及业务值扫描。UI 文案、布局模式、分页上限和测试夹具中的示例 ID 属合理代码/策略常量，不必把一切字符串都搬进数据库。

### R12 · P2 · 文档存在当前状态漂移

**证据**：最新运行指南/验证记录已更新到 42/19 与模拟器结果，但 `docs/README.md` 仍写 32/8，收尾计划还写目标工具待执行，D-002 部分叙述仍为早期前端基线。不同时间的“删除排序/恢复排序”记录需要明确现行条款。

**处理**：建立单一当前验收状态表，正文同步现状，历史按日期/版本保留；需求主文档、接口、测试映射与实施记录各有职责，不把后补说明当作完成正式评审。

### R13 · P2 · 可维护性和旧数据模型技术债

- 前端部分 Vue 方法高度压缩，加载/价格/详情模板有重复；缺少一致的 lint/格式化/持续集成门禁，Node 的源码结构断言不能替代组件与设备交互测试。

**处理**：先隔离旧链路，再适量拆分发布快照/映射/公开资格服务与前端复用逻辑；以测试保护小步重构，不为“专业”引入微服务或重写框架。

### R14 · P2 · 容量与运行观测缺口

公开读取没有看到限流/容量保护；演示图片按请求动态编码，HEAD 也走内容读取，反复文件校验/扫描可能放大成本。尚无本轮可证明的负载、连续可用性、备份恢复和告警演练。

应按阶段一真实访问量建立轻量限流、超时、指标与容量测试；媒体优化不得绕过资格复检。不能把 P2 当作“正式部署永远不必做”。

## 七、建议收尾顺序与完成标准

### 第一批：安全与运行隔离

1. 默认关闭/隔离旧 CRUD、旧扫描和静态直出；外部部署只开放必要公开读取。
2. 拆配置、移凭据、使用最小权限账号；轮换历史凭据、检查部署暴露范围。
3. 分类处理依赖告警，兼容升级并重复构建/接口/模拟器检查。

完成标准：未认证写入不能到达业务写逻辑；不暴露私有媒体；正式配置不使用 root 或仓库内密码；SCA 剩余项有可验证的影响与处置结论。

### 第二批：正式数据来源与最小持久化/发布闭环

1. 明确文件还是 MySQL 为单一正式数据源；若要求落库，落实最小迁移、导入与端口适配。
2. 建立公开授权来源、范围/当前性和撤回联动，不依赖演示许可。
3. 准备经过核验的品牌、团队、账号、二维码和公开衍生图；去除残余品牌硬编码。
4. 验证发布、下架、错误更新拒绝与重启后数据一致；不开发预约/支付/完整后台。

### 第三批：工程质量与阶段验收

1. 合并当前文档状态、建立需求—实现—测试—证据追踪；小步清理重复/死代码。
2. 校准 AppID、HTTPS、发布入口与手机可达性。
3. 冻结候选、配置/数据/素材版本，执行强制真机/异常/撤回门禁并归档。

**只有完成对应范围和强制门禁后，才将阶段一标为“正式验收完成”。在此之前，建议标记为“演示版本已完成，工程收尾与正式验收进行中”。**
