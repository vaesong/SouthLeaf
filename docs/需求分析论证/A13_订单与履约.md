## 1. 专题目的

本专题分析 SouthLeaf 在预约确认之后如何形成订单、固化客户约定、安排拍摄、记录履约、处理取消和服务异常，并在拍摄完成后把尾款支付和成片交付衔接给后续专题。

订单是工作室对一次已确认服务约定的业务承载，履约是工作室实际执行这次约定的过程。两者都不能被简单等同为支付状态或某个后台编辑字段。

本文件回答：

- 订单何时产生，什么条件下才算形成；
- 预约确认如何同时建立订单、硬占档和订单快照；
- 套餐、价格、服务内容、日期和固定时段如何作为历史约定保留；
- 定金支付、履约安排和订单推进之间如何衔接；
- 工作室如何安排拍摄并让客户看到有意义的进度；
- 谁可以确认拍摄完成，何时激活尾款；
- 缺席、工作室取消、补拍、改期和服务异常如何处理；
- 订单状态、支付状态、履约状态和交付状态如何保持独立；
- 客户、负责人、管理员和摄影师分别能看什么、做什么；
- 订单和履约主路径、异常路径及验收标准如何定义。

本专题不定义数据库表、API 字段、锁、唯一索引、调度器或页面组件。订单、支付、退款、履约和交付状态的技术约束引用 AT05-AT09；A13 负责订单与履约的用户任务、业务事实、操作边界和业务验收。

A13 的核心判断是：

```text
预约申请不是订单；
只有工作室确认预约时，才在同一业务动作中建立排他占档、生成唯一订单并冻结订单快照；
订单状态、支付状态、履约状态和交付状态分别维护；
负责人或管理员确认拍摄完成后才激活尾款；
缺席、取消、补拍和服务异常记录为独立履约结果或事件，不覆盖原始历史事实。
```

## 2. 专题边界与规则归属

### 2.1 A13 拥有的需求

A13 负责以下订单与履约需求：

- 预约确认自动成单的订单业务结果；
- 订单与预约、档期、客户、套餐版本和后续修订的关系表达；
- 订单快照、订单历史和不可静默覆盖的约定；
- 订单从待支付定金到履约完成的客户和工作室体验；
- 定金支付作为订单进入后续履约条件的业务衔接；
- 拍摄前安排、准备、拍摄中和拍摄完成的履约任务；
- 负责人、管理员和摄影师在履约过程中的职责边界；
- 缺席、取消、补拍、服务异常和履约中断的业务处理体验；
- 拍摄完成确认、尾款激活和后期交付的交接条件；
- 订单修订、改期版本和历史记录的可追溯性；
- 客户侧订单与履约状态的安全投影；
- 订单与履约相关的通知、待办、异常和人工补偿入口；
- 订单与履约功能、场景、异常和验收标准。

### 2.3 A13 的唯一主规则

订单与履约域必须保持以下事实关系：

```text
提交预约申请 ≠ 订单
预约确认 = 排他占档 + 唯一订单 + 订单快照
订单存在 ≠ 定金已支付
定金已支付 ≠ 拍摄已完成
拍摄已完成 ≠ 尾款已支付
尾款已支付 ≠ 成片已经发布
成片已发布 ≠ 所有人都拥有访问权
履约异常 ≠ 自动退款
后台编辑备注 ≠ 修改订单事实
改期 ≠ 覆盖原订单和原履约历史
```

订单快照是客户和工作室在确认成单时形成的历史约定。后续套餐调价、下架或服务项调整不得回写既有订单。确认后的价格或服务内容如确需变化，必须走有权限、可审计、需要客户确认的修订/重新约定流程，不能通过普通编辑框直接覆盖原订单。

## 3. 已确认规则与证据口径

### 3.1 已确认订单规则

以下规则来自 A04、A12、AT05 和 AT06，作为 A13 的业务基线：

- 订单只在工作室确认预约时自动生成；提交预约申请不产生订单；
- 确认预约时重新校验日期和固定时段冲突；
- 确认成功同时建立排他档期占用、预约确认和唯一订单；
- 订单生成时冻结套餐版本、业务归属、价格、固定定金、服务内容、拍摄日期和固定时段等约定；
- 订单默认进入待支付定金状态，定金支付期限默认 24 小时，实际截止时间按订单保存；
- 定金金额来自套餐配置的固定金额，不使用历史原型中的 30% 或 50% 比例；
- 定金支付事实由 A14 负责确认，前端支付返回不能单独作为成功事实；
- 定金逾期前必须核验成功支付、支付处理中、待查单和线下收款待核验等状态；
- 明确未支付且超过截止时间时，订单进入失效处理并释放对应档期；
- 订单失效后收到迟到支付时，原日期/固定时段仍可用才重新校验并尝试恢复，已被占用时不自动恢复；
- 改期保留原预约、订单快照和支付事实，创建新的修订版本；新时段先校验和占用成功，再释放旧时段；
- 定金已支付是进入后续履约安排的必要条件之一，但支付状态和履约状态分开维护；
- 履约至少区分待安排、已安排/待拍摄、拍摄中（确有必要时）、已完成、异常和已取消；
- 负责人或管理员显式确认拍摄完成后，才激活尾款应付；
- 摄影师可以查看被分配的拍摄安排并记录必要履约信息，但不能直接确认拍摄完成、触发尾款、改价、退款或发布交付；
- 客户缺席、工作室取消、补拍和服务异常作为独立履约结果或事件记录；
- 尾款逾期只标记逾期，不自动取消订单或退款，已完成履约事实继续保留；
- 尾款付清前不开放成片预览和下载；交付和公开授权由 A15 独立判断；
- 订单取消、退款成功、履约完成和交付完成不是同一个状态；
- 订单、支付、履约和交付的每次高风险变更都需要操作者/系统身份、时间、原因或来源和审计关联；
- 重复确认、重复拍摄完成、重复取消、重复改期和任务重试不能产生重复订单、重复尾款或重复履约事实。

### 3.2 证据口径

| 标记 | 含义 |
|---|---|
| 已确认需求 | 用户讨论、A04、A12 或 AT05/AT06 已明确的订单与履约约束 |
| 原型证据 | 当前代码、页面或构建产物中确实出现的订单/拍摄/定金线索，只证明历史页面表达过该方向 |
| 产品建议 | 为形成可运营订单与履约体验提出的方案，仍需工作室实际流程验证 |
| 待验证行为 | 尚无真实订单、拍摄记录、缺席、补拍和交付数据支持的判断 |
| 待确认经营内容 | 拍摄准备、地点、提醒、后期时限、补拍次数、异常响应时限等实际运营规则 |

当前工程没有真实订单、支付、履约或拍摄完成记录。历史页面中的“50% 定金”“30% 定金”“拍摄结束后 5 个工作日支付尾款”“产品交付时间 15 个工作日”等文案属于原型证据或历史示例，不是当前订单规则。现行定金固定金额、24 小时期限、拍摄完成后激活尾款和交付门槛以 A04、AT05 和本专题为准。

## 4. 当前工程证据与问题

### 4.1 客户侧只有订单和相册占位入口

当前 `frontend/pages/my/my.vue` 展示“未付款”“进行中”“已完成”“全部订单”“我的相册”等入口，但入口点击后仍显示“开发中，敬请期待”。当前没有可验证的：

- 订单列表和订单详情；
- 订单与预约的关系；
- 套餐、价格、定金和尾款快照；
- 订单截止时间和逾期状态；
- 履约安排、拍摄日期和固定时段；
- 拍摄完成确认和尾款激活；
- 客户取消、改期、缺席或服务异常处理；
- 订单历史、修订版本和通知记录；
- 尾款逾期、交付门槛和无权限反馈。

这说明当前页面只提供了未来客户中心的视觉入口，不能证明订单或履约状态已经存在。

### 4.2 套餐页存在历史定金和服务文案

当前 `frontend/pages/package/package.vue`、`frontend/pages/package/pkgdetail.vue` 及构建产物中存在：

- 全款 50% 作为定金；
- 全款 30% 作为定金；
- 拍摄小时数、原片数量、精修数量和相册等服务描述；
- 尾款在拍摄结束后若干工作日支付；
- 交付时间从收到尾款开始计算。

这些内容可以作为旧原型的表达证据，但不同页面和套餐之间存在不一致，且没有套餐版本、固定定金配置、订单快照或后台维护支撑。不能将历史页面中的比例、数量、时限直接带入现行订单。

### 4.3 后端没有订单和履约能力

当前后端没有订单实体、订单控制器、履约服务、拍摄完成动作、尾款激活、改期修订、异常事件或客户订单查询能力。现有套餐数据中的 `services` 仍属于原型级字符串，不足以证明服务内容已经结构化，更不能证明可以可靠冻结到订单快照。

### 4.4 当前实现不能支撑订单事实

当前请求封装只按数字 `code === 200` 判断成功，token 也只有读取雏形。工程尚未形成：

- 预约确认和订单创建的统一业务动作；
- 订单归属与客户身份关系；
- 稳定的支付和履约错误语义；
- 负责人、管理员和摄影师权限；
- 拍摄完成的责任边界；
- 订单与预约、支付、交付的审计关联；
- 失败重试、人工补偿和并发幂等。

订单不能由前端根据套餐页面或“我的”页面入口自行拼装。订单事实必须由统一业务流程产生，并由客户侧和后台重新读取。

### 4.5 当前问题结论

| 问题 | 当前表现 | 订单/履约风险 |
|---|---|---|
| 没有订单生成 | 无预约确认和自动成单 | 客户无法获得确定的交易承载 |
| 没有快照 | 套餐由页面硬编码或原型接口提供 | 调价后历史约定可能被覆盖 |
| 定金文案不一致 | 同时存在 30% 和 50% | 客户和工作室无法确定应付金额 |
| 没有支付衔接 | 无定金、尾款和支付事实 | 订单可能被错误认为已付款 |
| 没有履约状态 | 只有“进行中/完成”占位入口 | 客户无法判断拍摄准备和完成事实 |
| 没有责任边界 | 无负责人/管理员/摄影师动作控制 | 摄影师可能越权触发尾款或改订单 |
| 没有异常事件 | 缺席、补拍和服务异常无记录 | 退款和客户沟通缺少事实依据 |
| 没有修订历史 | 改期只能覆盖原信息 | 价格、日期和支付历史不可追溯 |
| 没有交付门槛 | 相册入口与尾款无授权关系 | 未付尾款可能被错误开放成片 |
| 没有审计补偿 | 无任务、通知和人工处理路径 | 失败后无法判断和恢复真实状态 |

## 5. 订单与履约角色任务地图

### 5.1 预约联系人/客户

客户主要负责：

- 查看确认后的订单约定；
- 在截止时间前支付或配合核验定金；
- 查看拍摄日期、固定时段、地点和准备事项；
- 按约参加拍摄并提供必要信息；
- 在需要时提出改期、取消、补拍或问题处理请求；
- 查看拍摄完成、尾款应付和后续交付状态；
- 根据授权和支付条件访问成片。

客户不能：

- 自行确认预约或创建订单；
- 修改套餐、价格、服务内容、日期或固定时段快照；
- 通过客户端把履约状态改成已完成；
- 直接激活尾款、确认线下收款或发布成片；
- 因为是拍摄参与人就自动访问订单或成片。

### 5.2 工作室负责人

负责人主要负责：

- 处理订单确认、异常、改期和取消的高风险决定；
- 审核订单修订、套餐/价格变化和客户重新确认；
- 处理工作室原因取消、缺席争议、补拍和重大服务异常；
- 确认拍摄完成并触发尾款；
- 查看完整订单、履约、支付摘要和审计；
- 决定尾款逾期、退款和交付异常的人工处理路径。

负责人不应通过直接编辑最终状态代替确认、取消、改期或拍摄完成等业务动作。

### 5.3 管理员

管理员主要负责：

- 查看待支付定金、待安排拍摄和待处理异常；
- 联系客户并补充订单履约信息；
- 安排已满足条件的拍摄任务；
- 记录拍摄开始、缺席、取消、补拍和一般服务异常；
- 在授权范围内确认拍摄完成并触发尾款；
- 发起改期、取消、退款或补偿处理；
- 查看客户可见状态和通知结果。

管理员默认不能直接修改订单快照、任意改价、最终审核退款金额或绕过高风险审计。

### 5.4 摄影师

摄影师主要消费被分配的履约安排：

- 查看必要的日期、固定时段、地点、业务类型和拍摄准备信息；
- 查看完成拍摄所需的最小客户资料；
- 记录拍摄开始、拍摄备注、缺席或需要补拍的事实；
- 按授权上传与订单关联的文件，文件进入校验流程；
- 向负责人或管理员提交拍摄完成建议或履约异常。

摄影师不能：

- 确认预约、创建订单、占用或释放档期；
- 修改套餐、价格、服务内容和订单快照；
- 直接确认拍摄完成或激活尾款；
- 审核退款、登记或核验线下收款；
- 发布、撤回公开案例或改变客户成片授权。

### 5.5 系统任务与外部身份

系统任务可以执行定金期限复核、订单失效、档期释放、提醒、通知重试和一致性检查，但不能替代负责人确认拍摄完成，也不能根据时间自动推断拍摄已经完成。

支付回调只能推进支付事实，由 A14 规则处理；对象存储只能提供文件能力，不能判断订单是否完成或客户是否有交付权限。

## 6. 订单形成与订单快照

### 6.1 订单形成前提

订单形成前必须满足：

- 预约申请仍然处于可以确认的状态；
- 预约联系人和必要身份关系可追踪；
- 摄影业务和套餐版本仍能被识别；
- 客户需要确认的套餐、价格、服务内容和时段变化已经处理；
- 日期和固定时段经过最新冲突校验；
- 当前时段未被其他确认动作占用或后台封档；
- 工作室确认操作具有相应权限。

“客户选择了套餐”“客户提交了预约”“客户与工作室聊过时间”都不能单独形成订单。

### 6.2 确认预约并成单主路径

```text
后台打开待确认预约
  → 核对客户、业务、套餐版本、服务内容、日期和固定时段
  → 检查是否有需要客户重新确认的变化
  → 重新校验档期冲突和封档状态
  → 成功建立排他占档
  → 预约变为已确认
  → 自动创建唯一订单
  → 写入不可变订单快照
  → 建立定金应付和实际截止时间
  → 创建客户通知和后台待办
  → 客户进入订单详情
```

确认成功必须让客户获得明确的订单标识、订单约定、定金金额、定金截止时间和后续步骤。确认失败不能留下“已占档但无订单”“已生成订单但没有预约”或“重复订单”等半成功结果。

### 6.3 订单快照内容范围

订单快照至少需要表达客户在确认时已经接受的约定：

- 摄影业务和套餐版本上下文；
- 套餐名称或客户可理解的服务名称；
- 订单总价；
- 固定定金应付金额；
- 尾款应付金额；
- 已确认的服务内容和必要限制；
- 拍摄日期；
- 固定时段及其开始、结束信息；
- 预约联系人和必要的订单关系；
- 订单形成时的来源和确认时间；
- 可能影响履约理解的已确认备注或说明。

具体字段和敏感资料范围由第 5/6 步技术设计继续拆解。A13 只要求快照能够让客户、工作室和审计人员在套餐发生变化后仍然还原当时的订单约定。

### 6.4 快照不可变和订单修订

以下行为不能直接覆盖原订单快照：

- 修改套餐名称或版本；
- 改变订单总价、定金或尾款；
- 删除或替换已确认服务内容；
- 修改原拍摄日期和固定时段；
- 删除客户已确认的约定备注；
- 把客户原因取消改写成工作室原因取消；
- 把已完成履约改写成未开始；
- 把已经发生的收款、退款或交付事实抹除。

如果客户和工作室确实协商改变订单内容，应进入修订/重新约定流程：

1. 记录原订单和原快照；
2. 明确变化内容、原因和提出方；
3. 重新校验新日期/时段或服务条件；
4. 说明定金、尾款和退款/补收影响；
5. 取得客户确认；
6. 形成新的生效修订版本；
7. 通过订单详情展示原安排与当前安排的关系。

“修订版本”是对历史约定的补充，不是删除历史。价格、服务和支付变化的具体审核与资金处理由 A14 继续定义。

## 7. 订单状态与客户可见进度

### 7.1 订单主状态基线

A13 使用 AT06 的订单状态基线：

| 状态 | 含义 | 客户应理解的下一步 |
|---|---|---|
| 待支付定金 | 预约已确认并已生成订单，等待定金结清 | 在截止时间前支付或联系工作室 |
| 定金已付 | 定金成功事实已确认，可进入履约安排 | 查看拍摄安排并准备拍摄 |
| 服务中 | 已满足履约条件，正在进行拍摄或后续服务 | 查看履约和后期进度 |
| 已完成 | 约定服务和交付流程已经完成 | 查看仍然有效的交付入口或历史 |
| 已取消 | 订单因客户、工作室或其他业务原因终止 | 查看取消原因和资金处理 |
| 已失效 | 待支付定金订单超过截止时间且未形成有效收款 | 重新联系工作室或重新申请 |

订单主状态不能承载所有进度。支付分期、退款、履约和交付需要各自显示自己的当前状态。

### 7.2 客户侧综合进度

客户侧可以用易懂的只读进度表达：

```text
预约已确认，待支付定金
  → 定金已确认，待拍摄
  → 拍摄已安排
  → 拍摄进行中
  → 拍摄已完成，待支付尾款
  → 尾款已确认，后期制作中
  → 成片已发布
  → 交付入口已到期或订单已完成
```

这只是多个领域状态的安全投影，不能通过修改进度文字反向改变订单、支付、履约或交付事实。

客户必须能够区分：

- 订单是否已经生成；
- 定金是否已经支付成功或仍在处理中；
- 拍摄是否已经安排；
- 拍摄是否由工作室确认完成；
- 尾款是否已经激活、逾期或结清；
- 成片是否已经发布；
- 当前是否因身份、授权、支付或交付期限不能访问。

### 7.3 后台侧工作状态

后台需要按任务而不是只按订单状态组织待办，例如：

- 待确认成单；
- 定金即将到期；
- 支付处理中或待核验；
- 已付定金但未安排拍摄；
- 即将拍摄但资料未齐；
- 当日待拍摄；
- 摄影师已提交履约信息，待负责人/管理员确认；
- 拍摄完成待激活尾款；
- 尾款逾期待跟进；
- 补拍/服务异常待处理；
- 交付条件已满足但文件未发布；
- 通知、任务或外部服务失败待人工。

后台待办不应把系统任务失败误显示为订单取消，也不应把客户备注当成已经确认的履约事实。

## 8. 定金与履约衔接

### 8.1 订单生成后的定金阶段

订单生成后：

- 形成唯一订单和定金应付；
- 记录订单生成时的实际支付截止时间，默认 24 小时；
- 客户可以进入定金支付入口；
- 未确认预约不能提前支付定金；
- 未付定金订单不能被误认为已经满足履约条件；
- 工作室可以查看待支付、支付处理中和待核验状态。

定金应付金额来自订单快照中的固定金额。支付时不能重新读取当前套餐价格或当前定金配置。

### 8.2 定金支付成功后的履约资格

定金成功结清后，订单具备进入拍摄安排的基础条件。工作室仍需根据实际经营流程确认：

- 拍摄日期和固定时段是否需要再次向客户提醒；
- 拍摄地点、准备事项和参与人资料是否齐全；
- 是否需要负责人确认特殊业务；
- 是否存在客户提出的改期或服务变化；
- 是否存在尚未处理的支付、身份或资料异常。

定金支付成功不等于拍摄已经安排，也不等于拍摄已经完成。

### 8.3 定金逾期、失效和迟到支付

定金截止时间到达时，订单失效任务必须先检查：

- 定金是否已成功支付；
- 在线支付是否仍在处理中或待查单；
- 线下收款是否已经登记但待核验；
- 工作室是否已审计延长截止时间；
- 订单是否已经取消、改期或进入其他修订；
- 是否已经有新的生效安排。

只有明确没有有效收款且确实超过截止时间，订单才进入失效处理，并释放相应档期。订单、支付尝试、预约确认和释放历史继续保留。

订单失效后收到迟到支付或迟到回调：

- 原日期/固定时段仍可用时，重新执行排他校验，成功后按恢复规则处理；
- 原日期/固定时段已被其他确认预约占用时，不自动恢复；
- 支付事实进入 A14 的退款或人工处理路径；
- 客户看到处理中/待人工，不被承诺一定恢复原拍摄安排；
- 不能因为钱已经到账就直接抢回已经释放的档期。

## 9. 履约生命周期

### 9.1 履约状态基线

A13 使用 AT06 的履约状态基线：

| 状态 | 含义 | 典型进入条件 |
|---|---|---|
| 待安排 | 订单已经满足基础履约条件，但拍摄安排尚未完成 | 定金已结清或工作室允许进入准备流程 |
| 已安排/待拍摄 | 拍摄日期、固定时段和必要安排已确认 | 工作室完成排期和准备信息确认 |
| 拍摄中 | 确有中途履约动作，需要向工作人员表达过程 | 拍摄已经开始 |
| 已完成 | 负责人或管理员确认本次拍摄已完成 | 完成拍摄事实经过授权操作确认 |
| 异常 | 存在影响正常服务、交付或付款的待处理问题 | 缺席争议、设备/人员问题、质量或范围异常 |
| 已取消 | 当前履约安排被终止 | 取消事实已确认并记录原因 |

是否在客户侧展示“拍摄中”由实际流程验证。如果拍摄过程很短或工作室不需要中间操作，客户可以只看到“已安排/待拍摄”和“拍摄已完成”。后台内部仍应能记录必要事件。

### 9.2 拍摄安排

工作室完成履约安排时，需要让客户和执行人员能够理解：

- 订单对应的业务和服务内容；
- 拍摄日期和固定时段；
- 已确认的拍摄地点或集合信息；
- 参与人和工作室需要知道的必要资料；
- 拍摄前准备事项；
- 联系工作室的方式；
- 如有变化，谁负责确认和通知。

地点、联系人、准备事项和业务特有资料属于最小必要信息。摄影师只应看到完成拍摄所需的信息，不能因被分配订单就看到客户的完整隐私资料或支付明细。

### 9.3 拍摄前准备

拍摄前，工作室需要能够识别：

- 定金是否已成功支付或获得授权的线下核验；
- 订单是否仍为有效安排；
- 日期和固定时段是否发生改期或取消；
- 预约联系人、实际拍摄人和参与人是否发生变化；
- 业务特有的准备资料是否齐全；
- 客户是否收到时间、地点和准备提醒；
- 是否存在未处理的身份、支付或服务异常。

拍摄前提醒的具体时间、渠道和是否需要客户确认，需由工作室继续验证。提醒失败不能改变订单或履约事实。

### 9.4 拍摄开始与拍摄中

工作室或被分配的摄影师可以记录拍摄开始、现场备注和必要履约事件。此类记录用于帮助工作室协作和处理异常，不自动改变订单价格、服务范围、尾款或交付授权。

摄影师提交的“已拍摄”“拍摄完成建议”需要进入负责人或管理员确认流程。提交记录和最终确认记录必须能够区分。

### 9.5 拍摄完成与尾款激活

拍摄完成必须由负责人或管理员显式确认：

1. 核对订单、客户和本次拍摄安排；
2. 核对拍摄是否确实完成，是否存在补拍或服务异常；
3. 记录确认人、确认时间和必要原因/备注；
4. 将履约状态推进为已完成，或保留为异常/补拍处理中；
5. 只有确认属于正常完成时，才激活尾款应付；
6. 向客户发送尾款应付和后续交付条件；
7. 将后期制作和交付准备交接给 A15。

拍摄完成确认与尾款激活必须保持一致：不能显示“拍摄未完成但尾款已激活”，也不能因为预约日期已经过去就自动激活尾款。

摄影师不能直接触发尾款。摄影师的履约记录可以作为负责人/管理员确认时的输入，但不是最终业务事实。

### 9.6 尾款逾期与履约事实

尾款被激活后：

- 客户可以看到尾款金额、应付条件和支付结果；
- 尾款支付由 A14 维护在线/线下支付事实；
- 尾款逾期只标记逾期并进入工作室跟进；
- 不自动取消订单；
- 不自动撤销已完成拍摄；
- 不自动退款；
- 尾款未结清前，A15 不开放成片预览和下载；
- 已完成履约事实和尾款逾期事实分别保留。

## 10. 改期、取消、缺席、补拍与服务异常

### 10.1 改期

改期需要客户与工作室协商，不允许客户直接覆盖订单日期。工作室同意后：

- 选择新的日期和固定时段；
- 先校验并尝试占用新时段；
- 新时段成功后再释放原时段；
- 保留原预约、原订单快照、原履约和支付事实；
- 创建新的修订版本；
- 按协商结果沿用定金、补收差额或进入退款处理；
- 让客户确认新的日期、时段和服务约定；
- 通知客户原安排、新安排和资金处理结果。

如果新时段冲突，原安排不能被破坏。改期失败不能先释放原档，也不能把原订单标记为已改期后再等待人工寻找新档。

改期的提前通知期限、可改期次数、费用、哪些阶段仍可改期以及拍摄完成后的补拍规则，仍需实际经营确认。

### 10.2 客户取消

客户主动取消或因客户原因无法拍摄时：

- 记录发起人、时间、原因和客户可见结果；
- 按当前状态释放尚未继续占用的档期；
- 定金原则上不退；
- 特殊退款或改期由工作室按权限人工决定；
- 已付尾款的处理由 A14 根据已履约和未交付部分处理；
- 订单保留取消前的支付和履约历史；
- 客户看到取消结果、资金处理状态和联系入口。

无故缺席、未按约提供必要资料、客户临时改变需求导致无法履约等，属于客户原因的候选情形，但最终归类和处理应由工作室按真实情况记录，不应由系统仅凭一个按钮自动推断。

### 10.3 工作室原因取消

工作室因人员、设备、经营安排或其他工作室原因无法履约时：

- 负责人或授权管理员发起并说明原因；
- 联系客户并提供改期或取消路径；
- 原订单和履约历史保留；
- 释放原档期；
- 已收定金按已确认规则全额退回；
- 退款事实由 A14 独立产生并跟进；
- 通知记录和操作审计完整保留。

不能通过临时封档、删除预约、修改客户备注或标记“客户取消”来规避工作室原因取消的责任处理。

### 10.4 客户缺席

客户缺席时，工作人员需要记录：

- 原定日期和固定时段；
- 到场/联系情况；
- 缺席确认人和确认时间；
- 客户是否有提前通知；
- 是否存在不可归责事件或工作室原因；
- 是否提供补拍或改期；
- 定金、尾款和退款的后续处理入口。

缺席不能直接等同于订单完成，也不能只把订单改为取消而删除现场事实。客户原因缺席通常适用定金原则上不退，但特殊处理仍由工作室审核并记录。

### 10.5 补拍

补拍是对原履约不足或服务异常的后续安排，不是删除原拍摄记录后重新开始。补拍需要：

- 关联原订单和原履约事件；
- 说明补拍原因和责任归属；
- 重新选择并校验日期/固定时段；
- 明确补拍范围、参与人和客户确认内容；
- 保留原拍摄记录和已完成部分；
- 说明对尾款、退款和交付时间的影响；
- 补拍完成后由负责人或管理员再次确认履约结果。

补拍是否额外收费、由谁承担、最多几次和是否需要重新占档，需工作室确认。未经确认不能自动把补拍当作免费或当作全新订单。

### 10.6 服务异常

服务异常包括但不限于：

- 拍摄内容与订单服务约定明显不一致；
- 人员、设备或现场问题导致拍摄未完整完成；
- 拍摄质量或数量需要复核；
- 客户对服务过程提出异议；
- 后期或交付环节影响订单承诺；
- 由于异常需要补拍、部分交付或退款评估。

服务异常应形成独立事件或案件记录，至少让工作室能够知道：发生什么、何时发生、谁发现、谁处理、客户是否知情、当前下一步是什么。异常记录不能直接覆盖订单快照，也不能自动推导退款金额。

负责人根据异常事实决定补拍、继续履约、部分交付、全额/部分退款或其他补偿；A14 负责退款和资金事实，A15 负责交付和授权影响。

## 11. 订单取消、失效与历史

### 11.1 订单失效与订单取消的区别

订单失效通常表示待支付定金订单超过截止时间且没有有效收款；订单取消表示客户、工作室或其他业务原因主动终止已形成的订单。两者都可能释放档期，但原因、通知、退款和客户下一步不同。

客户侧至少要能区分：

- “订单已失效：定金未在期限内确认到账”；
- “订单已取消：已记录取消方和原因”；
- “支付处理中：暂不能判断订单是否应失效”；
- “退款处理中：订单终止不代表退款已经完成”。

### 11.2 订单历史不可删除

以下历史不能通过普通编辑删除：

- 预约确认和成单时间；
- 原套餐、价格和服务快照；
- 原日期、固定时段和档期结果；
- 定金和尾款支付尝试及支付事实；
- 改期修订和客户确认；
- 取消、缺席、补拍和服务异常；
- 拍摄完成确认和尾款激活；
- 退款申请、处理中、成功或失败；
- 交付发布、撤回和客户访问记录；
- 操作者、系统任务、通知和人工补偿。

历史记录不等于所有内容都向客户公开。客户只看与自己订单有关的安全摘要，工作人员按角色和最小必要原则访问完整记录。

### 11.3 订单归属与身份

预约联系人默认是订单客户关系和后续私密交付关系的主要对象，但需要区分：

- 预约联系人；
- 实际拍摄人；
- 参与人；
- 付款人；
- 被授权交付人。

实际拍摄人不会因为被记录在订单中就自动拥有订单详情、支付信息、改期权或成片下载权。家庭成员、同手机号人员或同一地址人员也不会自动获得订单访问权。

## 12. 通知与客户反馈

### 12.1 客户需要知道的关键事实

订单和履约页面至少需要说明：

- 订单是否已经生成；
- 当前套餐、价格、定金和尾款约定；
- 拍摄日期和固定时段；
- 定金或尾款的截止/应付条件；
- 当前履约阶段；
- 工作室是否需要客户补充资料或确认改期；
- 拍摄是否已经由授权工作人员确认完成；
- 尾款是否已经激活、支付成功、处理中或逾期；
- 成片是否已经发布以及访问前置条件；
- 当前异常和客户下一步；
- 联系工作室的可靠入口。

### 12.2 客户可见文案原则

| 业务事实 | 客户可见表达 | 不应使用的表达 |
|---|---|---|
| 预约已确认并生成订单 | 工作室已确认预约，订单已生成 | 已提交订单，等待系统处理 |
| 待支付定金 | 请在截止时间前支付定金，逾期可能导致订单失效 | 已为你永久保留 |
| 支付结果未知 | 支付结果确认中，请勿重复支付 | 已支付成功 |
| 已安排拍摄 | 拍摄已安排，请查看日期、时段和准备事项 | 系统自动完成 |
| 拍摄完成待尾款 | 工作室已确认拍摄完成，尾款已可支付 | 拍摄结束自动扣款 |
| 尾款逾期 | 尾款已逾期，订单和履约记录仍保留，请联系工作室 | 订单自动取消 |
| 履约异常 | 工作室正在处理服务问题，下一步是…… | 系统错误 |
| 交付未开放 | 成片尚未发布，或尾款/授权条件尚未满足 | 文件不存在 |
| 订单失效 | 定金未在有效期限内确认到账，订单已失效 | 预约被删除 |
| 订单取消 | 订单已取消，原因和资金处理状态如下 | 已退款（若退款尚未成功） |

### 12.3 需要通知的事件

可能需要通知客户：

- 订单确认和定金截止；
- 定金临近到期；
- 定金成功、处理中、待核验或异常；
- 订单失效和原档期释放；
- 拍摄安排、时间/地点变化和准备提醒；
- 改期请求、改期成功或新时段冲突；
- 客户取消、工作室取消和退款处理；
- 拍摄完成、尾款激活和尾款逾期；
- 补拍、服务异常和处理结果；
- 交付发布、交付入口到期和补充交付。

通知失败不回滚订单或履约事实。客户打开订单详情时仍应看到服务端真实状态，后台可以重发通知并查看失败原因。

## 13. 异常、可靠性与人工补偿

### 13.1 确认成单异常

确认预约时出现冲突、套餐失效、身份异常或系统异常：

- 不能显示订单已生成，除非服务端已有完整订单事实；
- 不能留下有效占档但没有订单；
- 并发竞争返回明确的冲突结果；
- 重复请求返回既有订单和当前状态；
- 套餐变化要求重新报价/确认，不静默替换；
- 服务异常保留 request id 或安全联系编号；
- 后台能够看到失败原因和待人工入口。

### 13.2 定金逾期与支付回调竞争

定金逾期任务和支付回调可能同时到达。处理结果不能取决于哪个请求先返回：

- 已成功或处理中/待查单，不得直接失效并释放档期；
- 明确未支付且已过截止时间，才进入失效和释放；
- 线下收款待核验时不能直接当作未支付；
- 结果未知进入查单或人工处理；
- 迟到支付需要重新校验档期，不能直接恢复。

支付事实的确认、查单和退款由 A14 主责，A13 负责订单失效、履约资格和客户反馈的衔接。

### 13.3 重复拍摄完成

负责人或管理员重复点击确认拍摄完成、网络超时后重试或多个工作人员同时操作时：

- 只允许形成一次有效拍摄完成事实；
- 不重复激活尾款；
- 不生成多个尾款分期；
- 返回当前履约和尾款状态；
- 记录重复操作或并发竞争；
- 如果首次操作处于处理中，后续操作不能绕过处理状态。

### 13.4 通知或任务失败

订单失效、拍摄完成、尾款激活、改期和取消后的通知失败时：

- 订单、履约和支付事实不回滚；
- 后台显示通知/任务失败和重试入口；
- 重试不能创建重复订单、尾款或履约事件；
- 超过自动重试次数进入失败待人工；
- 客户通过订单详情仍能读取真实状态。

### 13.5 人工补偿

人工补偿至少需要支持：

- 重新核对订单和支付状态；
- 重新发送订单、履约或尾款通知；
- 延长定金截止时间；
- 处理异常占档和迟到支付；
- 发起或审核改期、取消、补拍和服务异常；
- 补录履约事件并关联原始来源；
- 恢复错误的订单/履约显示状态，但不删除原事实；
- 将未完成操作转给负责人审核。

人工补偿必须有权限、原因、操作者、时间、前后状态和关联业务号。不能使用“万能编辑”直接把订单改成已完成、把拍摄改成未发生或删除客户的历史。

## 14. 功能需求清单

### 14.1 订单生成与快照

- 预约确认时重新校验冲突并自动生成唯一订单；
- 订单与预约、档期、客户和套餐版本关联；
- 记录订单生成时间、来源、操作者和审计；
- 冻结业务、套餐、价格、固定定金、尾款、服务、日期和固定时段快照；
- 订单生成后进入待支付定金；
- 保存订单实际定金截止时间；
- 客户可从已确认预约进入唯一订单；
- 重复确认返回既有订单而不创建重复事实。

### 14.2 客户订单中心

- 查看订单列表和安全摘要；
- 查看订单详情、当前修订和历史约定；
- 查看定金、尾款和资金处理状态；
- 查看拍摄日期、固定时段、地点和准备事项；
- 查看履约进度、异常和工作室下一步；
- 提交改期、取消、补拍或问题处理请求；
- 查看订单失效、取消、退款处理中和交付未开放等状态；
- 会话过期后恢复到原订单任务，不重复发起动作；
- 无权限访问不泄露订单是否存在和敏感信息。

### 14.3 后台订单运营

- 按状态、日期、固定时段、负责人和待办查看订单；
- 查看订单快照和修订历史；
- 查看定金截止、支付处理中、待核验和逾期任务；
- 仅通过业务动作处理延长、改期、取消和异常；
- 不允许直接覆盖套餐、价格、服务和支付事实；
- 查看客户、拍摄人、参与人和必要隐私资料；
- 维护拍摄安排和准备事项；
- 记录缺席、补拍、取消和服务异常；
- 确认拍摄完成并激活尾款；
- 查看通知、任务、审计和人工补偿结果。

### 14.4 摄影师履约协作

- 查看被分配的拍摄安排；
- 查看完成拍摄所需的最小客户资料；
- 记录拍摄开始、现场备注和履约事件；
- 提交拍摄完成建议；
- 登记缺席、补拍建议和服务异常；
- 按授权上传文件并进入校验；
- 不能直接确认完成、激活尾款、改价、退款或发布成片。

### 14.5 改期、取消和异常

- 申请并审核改期；
- 新时段先校验和占用，成功后释放旧时段；
- 创建修订版本并保留原订单和支付事实；
- 客户确认新的服务约定；
- 记录客户原因、工作室原因和不可归责事件；
- 处理客户缺席和工作室无法履约；
- 关联补拍、服务异常、退款和交付影响；
- 客户看到安全原因和下一步，内部原因单独保存。

### 14.6 拍摄完成与尾款交接

- 负责人/管理员查看待确认履约事件；
- 核对订单、拍摄安排和异常；
- 显式确认拍摄完成；
- 只在正常完成或明确允许的履约结果下激活尾款；
- 尾款激活操作幂等并审计；
- 尾款逾期仅标记并进入跟进；
- 将尾款和交付条件传递给客户和 A14/A15；
- 不因拍摄日期经过自动激活尾款。

## 15. 验收标准

### 15.1 订单形成和快照

1. 客户提交预约申请时不会生成订单。
2. 工作室确认预约时，系统重新校验日期和固定时段冲突。
3. 确认成功同时产生已确认预约、有效硬占档、唯一订单和订单快照。
4. 确认失败不会留下已占档无订单、已确认无订单或半个订单。
5. 订单快照至少能还原确认时的业务、套餐、价格、固定定金、服务、日期和固定时段。
6. 套餐调价、下架或服务项变化不会回写既有订单。
7. 订单不能通过普通编辑框直接覆盖已确认商业约定。
8. 重复确认、刷新、网络超时和重试不会创建第二个订单或第二个有效占档。
9. 客户可以从已确认预约进入唯一对应订单。

### 15.2 定金和订单失效

1. 订单生成后进入待支付定金，确认前没有定金支付入口。
2. 定金金额来自订单生成时的固定金额，不读取历史 30%/50% 文案或当前套餐动态价格。
3. 订单保存实际定金截止时间，默认 24 小时；修改默认配置不回写已有订单。
4. 客户可以看到定金金额、截止时间、逾期后果和支付处理中提示。
5. 定金逾期任务执行前复核成功支付、处理中、待查单和线下待核验收款。
6. 明确未支付且超过截止时间的订单才进入失效和档期释放。
7. 订单失效保留订单、预约、支付尝试和审计历史。
8. 迟到支付在原时段可用时重新校验并尝试恢复，在原时段已占用时不自动恢复。
9. 迟到支付不能仅凭到账结果直接抢回已释放档期。

### 15.3 履约安排

1. 定金成功后，工作室能够看到待安排履约任务。
2. 客户能够查看已确认的日期、固定时段、地点/集合信息和准备事项。
3. 摄影师只能查看被分配且完成履约所需的最小资料。
4. 支付成功不会自动显示拍摄已安排或拍摄已完成。
5. 工作室能够记录准备资料缺失、时间变化和客户沟通结果。
6. 拍摄安排变更会保留原安排并向客户提供明确的新安排。
7. 通知失败不回滚订单或履约事实，后台可以重发。

### 15.4 拍摄完成和尾款

1. 摄影师不能直接确认拍摄完成或激活尾款。
2. 负责人或管理员能够查看履约记录并显式确认拍摄完成。
3. 拍摄完成确认记录操作者、时间、订单和必要原因。
4. 仅在拍摄完成确认成功后，尾款才进入应付状态。
5. 重复确认拍摄完成不会重复激活尾款或生成多个尾款分期。
6. 客户能够看到“拍摄已完成、尾款待支付”的清晰状态。
7. 尾款逾期不会自动取消订单、撤销拍摄完成或自动退款。
8. 尾款未付清时，交付入口继续关闭。
9. 拍摄日期经过不会自动触发拍摄完成或尾款。

### 15.5 改期和订单历史

1. 客户不能直接修改已确认订单日期或固定时段。
2. 改期需要工作室协商和相应权限。
3. 改期先校验/占用新时段，再释放原时段。
4. 新时段冲突时，原订单、原履约和原档期不被破坏。
5. 改期创建新的修订版本，原快照和支付事实保持可追溯。
6. 客户能够确认新的日期、时段、服务约定和资金影响。
7. 定金沿用、补收或退款结果不隐藏在订单主状态中。
8. 重复改期请求返回既有处理结果，不创建两个生效修订。

### 15.6 取消、缺席、补拍和服务异常

1. 客户取消、工作室取消和不可归责事件显示不同的责任结果。
2. 工作室原因取消时，客户能够看到改期/退款路径，定金退款由独立流程确认。
3. 客户原因缺席不会被系统静默标记为工作室取消。
4. 缺席记录包含日期、时段、发现人、原因和后续处理。
5. 补拍关联原订单和原履约事件，不删除原拍摄记录。
6. 服务异常可以记录发现、处理、责任、补拍/退款/交付影响和当前下一步。
7. 异常不会自动推导退款金额或直接覆盖订单快照。
8. 客户能够看到安全的异常结果和联系入口，不能看到内部争议或其他客户资料。

### 15.7 权限、隐私和审计

1. 客户只能查看本人订单或被明确授权的订单资源。
2. 实际拍摄人、参与人和付款人不会因被记录而自动拥有全部订单权限。
3. 摄影师不能查看不必要的支付、审计和完整客户资料。
4. 负责人和管理员的订单、履约、退款和交付操作按权限区分。
5. 高风险动作记录操作者/系统身份、时间、原因、前后状态和关联业务号。
6. 人工补偿不能删除订单、支付、履约和修订历史。
7. 客户错误访问订单时，不泄露订单是否存在、对象存储地址或其他客户信息。
8. 错误提示不暴露 SQL、Java 堆栈、第三方原始响应或内部资源标识。

### 15.8 可靠性和异常

1. 并发确认不产生重复订单、重复占档或半成功结果。
2. 定金逾期任务与支付回调并发时，不会误释放已支付或处理中订单的档期。
3. 重复拍摄完成不会重复激活尾款。
4. 通知、查单、失效和人工补偿任务具有可观察的失败和重试结果。
5. 业务异常能够区分可重试、处理中和失败待人工。
6. 重复请求返回既有业务结果或稳定业务错误，而不是生成新事实。
7. 订单、支付、履约和交付的状态不会通过一个综合状态被相互覆盖。

## 16. 验证方式

### 16.1 负责人和工作人员核验

需要工作室负责人和管理员确认：

- 定金支付成功后是否立即进入拍摄安排，还是仍需人工二次确认；
- 拍摄安排由谁负责，客户是否需要主动确认日期/地点；
- 拍摄地点、集合点和准备事项如何维护；
- 六类摄影业务分别需要哪些拍摄前资料；
- 哪些资料需要客户确认，哪些只供工作人员内部使用；
- 是否启用独立摄影师账号和分配流程；
- 摄影师能否记录拍摄开始、现场备注和补拍建议；
- 拍摄完成由负责人、管理员或双人复核确认；
- 是否需要“拍摄中”状态，还是只保留已安排和已完成；
- 客户缺席的判断、联系等待时间和定金处理；
- 工作室原因取消的具体场景和通知方式；
- 补拍适用条件、次数、费用和档期规则；
- 服务异常由谁受理、谁审核、多久反馈；
- 尾款支付期限、逾期提醒和人工催收方式；
- 尾款已付后后期制作和交付预计如何反馈；
- 订单完成的经营含义，是交付发布完成还是所有售后结束；
- 订单修订需要客户确认到什么程度；
- 订单、履约、支付和交付历史需要保留多久；
- 哪些通知必须送达，哪些只需在订单详情可查。

### 16.2 脱敏场景验证

至少准备以下场景：

1. 线上预约确认成功，同时产生唯一订单、硬占档和订单快照。
2. 电话/微信后台录入的预约与线上预约竞争同一固定时段，只有一个确认成单成功。
3. 两个工作人员重复确认同一预约，第二次返回既有订单而不是新建订单。
4. 套餐在待确认期间调价，工作室重新报价并取得客户确认后成单。
5. 订单生成后套餐下架，既有订单仍能读取原快照。
6. 客户未支付定金，逾期任务与支付回调同时到达，系统不误释放已支付或处理中订单的档期。
7. 定金逾期订单收到迟到支付，原时段可用时重新占档恢复，已被占用时进入退款/人工处理。
8. 定金成功后，后台将订单安排为具体拍摄日期和固定时段，客户收到准备提醒。
9. 摄影师记录拍摄完成建议，但不能激活尾款；负责人确认后尾款才变为应付。
10. 负责人重复确认拍摄完成，系统不生成重复尾款或重复通知。
11. 客户缺席，后台记录原因和现场事实，不自动伪装成工作室取消。
12. 工作室原因取消已确认订单，原订单保留，档期释放并进入定金退款流程。
13. 客户申请改期，新时段冲突，原订单和原档期不被破坏。
14. 改期成功，新修订经客户确认后成为当前安排，原快照和支付事实仍可查看。
15. 拍摄过程中发生服务异常，系统记录事件、处理责任和补拍/退款影响，不直接完成订单。
16. 补拍关联原订单，原拍摄事实保留，补拍完成后再次由负责人/管理员确认。
17. 尾款逾期，订单和履约记录保留，交付入口继续关闭，不自动退款。
18. 客户身份会话过期后返回订单详情，不重复发起取消、改期或支付动作。
19. 实际拍摄人访问预约联系人订单，系统根据授权拒绝并且不泄露完整订单内容。
20. 摄影师访问非分配订单，系统拒绝并且不泄露订单存在性。
21. 订单确认或拍摄完成通知失败，后台重发通知但不生成重复业务事实。
22. 系统任务失败进入待人工，人工通过带原因的业务动作补偿，不直接覆盖历史。

### 16.3 客户可用性验证

使用目标客户、负责人、管理员和摄影师观察：

- 客户是否理解预约确认后才有订单；
- 客户是否能区分订单、定金、拍摄完成、尾款和成片交付；
- 客户是否知道定金截止时间和逾期后果；
- 客户是否能找到拍摄日期、固定时段、地点和准备事项；
- 客户在支付处理中、订单失效、改期冲突和服务异常时是否知道下一步；
- 客户是否把“拍摄完成”误解为“尾款已支付”或“成片已发布”；
- 工作人员能否在不覆盖原订单的情况下处理改期、取消和补拍；
- 摄影师能否完成必要协作而不接触不必要的财务和隐私信息；
- 负责人/管理员能否明确判断何时可以激活尾款；
- 工作室能否从历史记录还原客户当时确认的套餐、价格、时间和服务。

没有真实订单和履约基线前，不设定订单转化率、定金逾期率、拍摄完成时长、补拍率和异常解决时长目标；这些指标由 A16 在真实运营后确定。

## 17. 待确认经营内容与产品决策

以下事项需要负责人和实际工作人员确认：

1. 定金支付成功后是否立即进入履约安排，是否存在人工确认环节。
2. 拍摄安排由谁负责，客户是否需要确认地点和准备事项。
3. 六类摄影业务分别需要哪些拍摄前资料和参与人信息。
4. 拍摄地点是固定工作室、客户指定地点还是两者都有。
5. 是否需要记录化妆、服装、道具、交通和场地准备事项。
6. 是否启用摄影师账号、分配规则和摄影师可见资料范围。
7. 是否需要“拍摄中”状态以及客户侧展示方式。
8. 拍摄完成的确认人、复核方式和允许的补充证据。
9. 尾款应付期限、提醒时间、逾期处理和线下核验方式。
10. 尾款付清后后期制作和交付的大致服务承诺如何表达。
11. 订单何时被视为业务完成，是交付发布、客户下载完成还是售后结束。
12. 客户缺席的判断标准、等待时间、联系方式和定金处理。
13. 工作室原因取消的分类、客户沟通方式和替代日期规则。
14. 不可归责事件发生时改期、定金沿用和退款的具体优先级。
15. 改期提前通知期限、次数、费用和拍摄完成后的补拍规则。
16. 补拍的责任归属、收费方式、次数和服务范围。
17. 服务异常的受理人、响应时限、升级规则和客户可见状态。
18. 套餐或服务内容在订单确认后的修订条件和客户确认方式。
19. 订单修订是否需要负责人审核，管理员可以处理到什么范围。
20. 订单历史、履约事件、客户沟通和支付摘要的保留及导出要求。
21. 哪些订单和履约通知必须通过微信、短信、站内或电话送达。
22. 订单完成后客户继续查看历史订单的期限和可见范围。
23. 尾款未付清但出现工作室服务异常时，如何处理交付和退款沟通。
24. 交付入口到期后，订单页面保留哪些历史信息和补充交付入口。
25. 订单与履约指标的统计口径，例如确认到定金、定金到拍摄、拍摄到尾款和异常处理时间。

## 19. 结论

当前工程只有客户中心订单/相册入口和历史套餐文案，没有订单、支付、履约、拍摄完成或尾款激活能力。A13 以已经确认的经营规则为准，建立订单与履约的完整目标：

```text
工作室确认预约时重新校验冲突；
成功后同时建立排他占档、唯一订单和不可变订单快照；
订单进入固定定金待支付阶段，支付事实和履约状态分别维护；
定金成功后形成履约安排，客户可以查看日期、时段和准备事项；
负责人或管理员确认拍摄完成后才激活尾款；
摄影师只能协作记录，不能直接触发尾款；
缺席、取消、补拍和服务异常保留为独立履约事件；
改期创建修订并保护原订单、支付和履约历史；
尾款逾期不自动取消，交付权限由支付、发布和授权条件共同判断；
所有高风险动作可重试、可审计、可人工补偿，但不通过普通编辑覆盖历史事实。
```

A13 不定义数据库、API、锁或页面组件。它为 A14 支付退款、A15 成片交付与公开授权、A16 横向衡量以及后续详细设计提供订单快照、履约状态、责任边界、异常事件和验收输入。拍摄准备字段、地点规则、摄影师启用范围、补拍政策和异常响应时限仍需工作室负责人确认，确认前不应锁定最终技术模型。
