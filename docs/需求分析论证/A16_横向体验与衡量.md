## 1. 专题目的

本专题不新增某一个独立业务域，而是分析客户、预约联系人、工作室负责人、管理员和摄影师在小程序、官网及工作室后台之间如何连续完成任务，如何理解订单和服务状态，如何面对异常、等待和权限限制，以及工作室如何衡量产品是否真正可用、可运营和可持续改进。

摄影业务跨越公开内容、预约申请、预约确认、订单、定金、拍摄履约、尾款、成片交付、私密授权和公开案例授权。客户不应该被要求理解内部模块名称，也不应该因为换了端、换了入口或发生了异步处理，就失去上下文或得到互相矛盾的状态。

本文件回答：

- 小程序、官网和后台如何围绕同一业务事实保持连续；
- 客户如何从公开内容自然进入联系、预约、订单、支付和交付任务；
- 预约申请、档期冲突、订单、支付、履约、交付和授权状态如何让不同角色看懂；
- 加载、空状态、处理中、失败、无权限、下架、冲突和入口到期如何反馈；
- 通知、待办、人工支持和补偿如何形成闭环；
- 如何验证客户、工作人员和后台操作人员能完成主要任务；
- 哪些事件可以用于衡量访问、转化、服务履约、异常和人工工作量；
- 当前哪些结论是工程证据、已确认需求、产品建议或待验证指标。

本专题不定义数据库表、API 字段、前端组件、错误码实现、消息队列、埋点 SDK、部署方式或具体客服系统。业务状态和可靠性约束引用 A04、A08-A15 及 AT05-AT09；A16 负责跨端体验、状态表达、通知与衡量需求。

A16 的核心判断是：

```text
客户看到的是一条连续的服务旅程，而不是多个相互独立的页面
公开浏览、预约申请、预约确认、订单生成和支付不是同一个成功状态
客户看到的状态必须来自当前业务事实，不能只来自上一次页面结果
处理中不等于失败，通知成功不等于业务动作成功
无权限、未发布、已到期、已下架、已冲突和系统异常需要分别表达
工作人员需要可执行的下一步，而不只是一个错误提示
指标用于发现任务阻塞和服务质量，不用于替代业务事实
```

## 2. 专题边界与规则归属

### 2.1 A16 负责的横向需求

A16 负责以下跨模块体验和衡量内容：

- 小程序、官网和工作室后台的跨端任务连续性；
- 公开内容到联系、预约和客户身份触发的上下文传递；
- 预约、订单、支付、履约、交付和授权的客户可理解状态；
- 加载、空状态、处理中、成功、失败、冲突、无权限、下架、失效和到期的反馈原则；
- 客户侧、工作室侧和系统任务侧的通知与待办关系；
- 失败重试、联系工作室、人工处理和补偿入口的体验要求；
- 客户、工作人员和后台操作人员的可用性验证；
- 跨端关键业务事件、服务质量指标、人工工作量和客户体验指标；
- 指标口径、事件边界、隐私最小化、数据质量和基线建立要求；
- 跨模块回归验收和脱敏验证场景。

### 2.3 横向唯一主规则

跨模块体验必须遵守以下关系：

```text
公开浏览 ≠ 已提交预约
已提交预约 ≠ 预约已确认
预约已确认 = 才能形成正式订单
订单已生成 ≠ 定金已支付
支付成功 ≠ 拍摄完成
拍摄完成 ≠ 尾款已支付
尾款已支付 ≠ 成片已发布
成片已发布 ≠ 当前身份一定有访问权
公开授权同意 ≠ 私密交付授权
通知已发送 ≠ 业务动作已成功
页面显示成功 ≠ 服务端事实已经确认
```

各模块的状态变化只能由其业务事实驱动。A16 不允许通过改变展示文案、手工修改汇总状态或埋点结果来替代预约确认、支付确认、拍摄完成、交付发布、授权撤回等正式业务动作。

## 3. 已确认规则与证据口径

### 3.1 已确认的横向体验规则

以下规则来自用户讨论、A04、A08-A15 和 AT05-AT09：

- 小程序、官网和后台服务于同一个摄影工作室，不形成多工作室、多租户的产品体验；
- 公开内容可以匿名浏览，进入预约、订单、支付、私密交付或需要客户资料的任务时再触发身份要求；
- 官网可以承担搜索、分享和深层内容理解，小程序承担客户持续使用和业务任务；两端共享已发布的公开事实；
- 电话、微信等线下预约需要由工作室录入统一预约事实，不能形成独立于系统之外的第二套档期；
- 待确认预约申请不代表预约成功，也不代表已经占用硬档；
- 预约确认时需要重新校验档期，竞争失败应明确提示重新选择或等待工作室处理；
- 预约确认同时生成订单，订单金额、服务内容、日期和固定时段以冻结快照为准；
- 定金和尾款是不同支付阶段，尾款只有在负责人或管理员确认拍摄完成后才进入应付；
- 支付结果未知或处理中时，客户不能被引导重复支付；
- 线下收款登记不等于已核验的支付事实；
- 尾款未付清前不开放成片预览和下载；交付发布、身份归属、私密授权和入口期限仍需要分别满足；
- 公开案例默认不公开，私密交付授权不等于公开授权；授权撤回需要停止受影响的公开展示并保留审计；
- 小程序交付入口默认开放 1 周，入口到期不等于工作室删除原文件；
- 客户无权访问、交付未发布、尾款未付、入口到期、文件异常和服务暂不可用必须避免混成一个“加载失败”；
- 后台任务需要显示阻塞原因、责任角色、下一步、重试或人工处理入口；
- 通知失败不能回滚预约、支付、退款、履约、交付或授权事实；客户重新进入业务详情时以服务端当前状态为准；
- 高风险动作需要 request id、任务/操作记录和可追溯审计，客户提示不得暴露内部异常、他人资料、永久对象地址或第三方原始响应。

### 3.2 当前工程证据

当前工程主要是公开展示原型，横向体验能力尚未形成：

- `frontend/pages/about/about.vue`、`frontend/pages/my/my.vue` 和 `frontend/pages/works/works.vue` 存在“开发中，敬请期待”等占位反馈；
- `frontend/pages/my/my.vue` 使用硬编码测试身份和订单、相册等入口，不能证明正式客户中心已经存在；
- 首页加载异常主要记录到 `console.error`，没有统一的客户可见恢复路径；
- `frontend/api/api.js` 仍以数字 `code === 200` 判断成功，未完整消费 AT09 的稳定业务错误码；
- 后端 `ApiResponse.success()` 仍以 `200` 作为成功码，`GlobalExceptionHandler` 仍以粗粒度 `400/500` 和异常消息返回错误；
- 当前没有正式通知中心、客户待办、后台异常队列、支付处理中展示、退款进展、交付到期提醒或售后工单闭环；
- 当前没有真实客户访问、预约、支付、履约、交付、授权撤回、通知失败或人工补偿数据；
- 当前工程没有独立官网应用和独立管理后台，现有 uni-app H5 入口、原型页面和后端接口不能直接证明最终跨端体验已经确定。

这些证据只说明当前原型和能力缺口，不把历史占位、固定文案、测试数据和控制台日志当成正式需求或服务目标。

## 4. 跨端连续性与任务地图

### 4.1 客户跨端主路径

客户可能从小程序、官网、搜索结果、社交分享、电话或微信进入。无论入口不同，业务上下文都应在后续任务中保持一致：

```text
发现品牌/作品/摄影业务
  → 理解适用场景和套餐
  → 联系工作室或提交预约申请
  → 等待确认并获得当前结果
  → 查看订单快照和定金待办
  → 支付定金或查看处理中状态
  → 查看拍摄日期、固定时段和履约状态
  → 等待负责人确认拍摄完成
  → 支付尾款或查看尾款处理状态
  → 等待交付发布
  → 查看私密成片、预览、下载和入口期限
  → 申请家庭成员授权或反馈问题
  → 单独处理公开案例授权和撤回
```

客户在每一个节点至少需要知道：

- 我当前在哪个业务环节；
- 当前事实是什么；
- 还需要我做什么，或者需要等待谁处理；
- 下一次状态变化可能是什么；
- 发生问题时找谁、带什么信息和能否重试；
- 当前页面和上一个入口之间是什么关系。

### 4.2 官网到小程序或联系入口

官网的深层页面、公开作品、套餐和分享链接可能直接被访问。进入业务任务时：

- 作品、业务、套餐、联系和预约入口应保留来源上下文；
- 从官网跳转小程序后，客户应能回到同一作品、套餐或预约意图，而不是重新从首页查找；
- 公开内容下架、授权撤回或版本失效时，旧链接需要显示安全且可理解的不可用提示，并提供品牌首页或联系入口；
- 官网不能展示已经失去公开资格的案例，也不能把私密交付入口暴露为公开页面；
- 电话/微信联系入口需要说明其作用，不应让客户误以为发送联系方式就已经提交预约或锁定档期；
- 预约和支付等需要身份、订单或状态事实的任务，应明确引导进入小程序或由工作室人工处理。

官网具体采用直接预约、引导小程序或两者并行仍需结合 SEO、内容深度和运营能力验证，但无论采用哪种入口，状态和业务事实不能分叉。

### 4.3 小程序客户任务地图

小程序应围绕客户任务组织，而不是只围绕后端模块名称组织：

| 客户任务 | 需要理解的状态 | 主要下一步 |
|---|---|---|
| 了解工作室 | 内容已发布、内容暂不可用、联系方式 | 浏览作品、查看套餐、联系工作室 |
| 提交预约 | 可申请、已提交待确认、已失效、资料待补充 | 等待确认、补充信息、重新提交 |
| 查看预约 | 待确认、已确认、已拒绝、已冲突、已取消、已过期 | 等待、查看订单、联系工作室、重新选择时段 |
| 查看订单 | 待付定金、定金已付、进行中、已完成、已取消、已失效 | 支付、查看履约、查看尾款、查看交付 |
| 支付定金/尾款 | 待支付、处理中、已成功、明确失败、待人工核验 | 支付、等待查单、联系客服，不重复支付 |
| 查看拍摄安排 | 已排期、进行中、已完成、异常、已取消 | 按约拍摄、查看工作室联系路径、等待补偿 |
| 查看成片 | 未准备、上传/校验中、已准备未发布、已发布、已到期、已撤回 | 等待发布、预览、下载、联系工作室 |
| 管理交付授权 | 默认有权、已授权、待核验、已撤回、已过期 | 查看、申请家庭成员授权、联系工作室 |
| 处理公开授权 | 未请求、待确认、已同意、已拒绝、已撤回、争议待核验 | 明确同意范围、撤回、等待处理 |
| 提交售后问题 | 已提交、受理中、处理中、待客户补充、已解决、已关闭 | 补充资料、等待处理、确认结果 |

### 4.4 工作室后台横向任务地图

后台不应要求工作人员在多个模块之间凭记忆拼接客户任务。工作台至少能够按待办、阻塞和风险聚合：

- 待确认预约和即将失效的申请；
- 待支付定金、定金处理中、定金逾期和迟到支付；
- 即将拍摄、当天拍摄、履约异常和待负责人确认拍摄完成；
- 待激活尾款、尾款处理中、线下收款待核验和退款待审核；
- 待上传、校验失败、发布前阻塞、交付已发布但即将到期；
- 家庭成员授权待核验、公开授权待确认、授权撤回后待跨端复核；
- 通知发送失败、外部服务处理中、重试超过阈值和人工补偿；
- 客户咨询、访问拒绝、支付争议、文件异常和售后升级。

每一项待办至少需要显示：

- 关联客户和订单的最小必要信息；
- 当前业务状态和阻塞原因；
- 责任角色或建议处理人；
- 最后一次处理时间；
- 是否可以重试、需要审核或必须联系客户；
- 处理后预期改变的业务事实；
- 操作需要的幂等、审计和权限提示。

后台可以按业务域筛选，但不能通过直接编辑一个汇总状态来替代正式的确认、核验、发布、撤回、退款或补偿动作。

## 5. 状态可理解性与反馈规范

### 5.1 状态表达的最小结构

客户侧状态反馈至少包含：

```text
状态名称
+ 当前事实
+ 对客户的影响
+ 客户下一步或等待对象
+ 可执行的安全操作
+ 联系工作室或 requestId 的路径（必要时）
```

后台侧状态反馈还需要包含：

```text
业务状态
+ 阻塞原因
+ 责任角色
+ 最近一次尝试
+ 是否可重试
+ 是否需要人工核验
+ 可能影响的客户和订单范围
+ 审计/任务关联
```

状态名称不应直接暴露内部枚举、Java 异常、数据库值、外部支付原文或对象存储路径。相同业务状态在不同端可以使用不同长度和语气，但不能改变事实含义。

### 5.2 主要状态反馈

| 场景 | 客户应理解什么 | 客户下一步 | 后台应看到什么 |
|---|---|---|---|
| 页面加载中 | 系统正在读取当前事实 | 等待或安全返回 | 请求是否超时、是否可重试 |
| 内容为空 | 当前没有可展示内容，不等于系统故障 | 查看其他内容或联系工作室 | 内容是否未发布、已下架或配置缺失 |
| 预约已提交 | 申请已收到但尚未成功预约 | 等待确认，关注通知 | 待确认申请、失效时间、冲突风险 |
| 预约冲突 | 该固定时段已被其他确认动作占用 | 重新选择时段或联系工作室 | 竞争请求、处理时间和占档事实 |
| 预约处理中 | 系统仍在处理，不应重复提交 | 等待并刷新当前结果 | 任务状态、重试次数、异常原因 |
| 定金支付处理中 | 支付结果尚未确认，不能再次付款 | 等待查单或联系客服 | 外部支付单、查单任务、超时和人工入口 |
| 付款明确失败 | 本次支付没有形成成功支付事实 | 按提示重新支付或联系工作室 | 失败原因、是否可重试、原支付意图 |
| 线下收款待核验 | 工作室已登记但尚未确认到账 | 等待人工核验 | 经办人、凭证、金额、核验任务 |
| 拍摄完成待确认 | 拍摄可能已结束，但负责人尚未确认履约完成 | 等待工作室处理 | 谁可确认、待办时长和异常关联 |
| 尾款待支付 | 拍摄完成已确认，尾款进入应付 | 支付尾款或查看线下核验 | 尾款金额、期限、支付事实 |
| 交付未发布 | 文件可能已准备，但工作室尚未开放客户访问 | 等待发布或联系客服 | 文件校验、发布前阻塞、责任人 |
| 交付已发布 | 文件已发布，但仍需满足身份、尾款、授权和期限 | 预览或下载 | 访问授权和入口截止时间 |
| 入口已到期 | 小程序访问已关闭，原文件不等于已删除 | 联系工作室申请人工补交 | 到期批次、补交状态和原文件保管 |
| 无私密访问权限 | 当前身份不满足订单归属或显式授权 | 使用正确身份或联系工作室 | 不向客户暴露他人资料和资源存在性 |
| 公开授权待核验 | 公开展示还不能确认 | 补充主体/范围/证据或等待负责人 | 受影响内容、核验人和风险范围 |
| 公开授权已撤回 | 相关公开展示正在停止或已停止 | 联系工作室了解处理进度 | A06/A05 跨端下架和外部入口复核 |
| 外部服务处理中 | 支付、退款、上传或通知尚未得到最终结果 | 等待系统处理，不重复发起 | 外部调用、任务、重试和人工阈值 |
| 服务暂不可用 | 当前服务暂时不能完成请求 | 稍后重试或联系工作室 | 系统告警、影响范围和恢复进度 |

### 5.3 必须区分的反馈类型

#### 加载中

加载中只说明当前请求尚未返回，不应让客户误以为预约已提交、支付已成功或交付已发布。长时间加载时应提供安全返回、刷新或联系路径；后台应能识别超时和重复操作风险。

#### 空状态

空状态需要说明“当前没有什么”，并给出有意义的下一步。例如没有已发布作品、没有订单、没有可访问交付、没有待处理售后，分别对应不同文案和入口。空状态不能掩盖权限拒绝、资源下架或服务异常。

#### 处理中

处理中表示业务结果尚未最终确认。客户可以刷新或离开后再次进入，但不能被引导重复提交支付、退款、预约确认或交付操作。后台需要显示处理责任、最近一次尝试和超时升级路径。

#### 失败

失败需要区分明确失败、未知结果和待人工核验。明确失败允许在业务规则允许时重试；未知结果优先查单或补偿；金额不匹配、越权、授权争议和重复支付不能通过普通重试掩盖。

#### 无权限

无权限提示应让当前用户知道如何获得帮助，但不能泄露其他客户、订单、家庭成员、授权主体或对象路径。对于交付访问，至少区分“需要登录/身份失效”“尾款未付”“交付未发布”“入口已到期”和“当前身份未授权”。

#### 下架、失效和过期

内容下架、套餐版本失效、预约申请过期、订单失效、支付期限到期、交付入口到期和公开授权撤回不是同一事件。客户需要知道当前入口不能继续做什么，以及是否可以重新申请、联系工作室或等待人工处理。

#### 冲突

档期冲突、订单版本冲突、支付重复、退款重复和授权范围冲突都应提示事实冲突，而不是统一显示“操作失败”。能够重新读取后继续的冲突与必须转人工的冲突要分别表达。

## 6. 通知、待办和客户支持

### 6.1 通知原则

通知是状态变化的辅助通道，不是业务事实本身。每一条通知都应：

- 对应已经确认的业务事实或明确的处理中状态；
- 说明发生了什么、影响什么、客户下一步是什么；
- 带回安全的业务入口，而不是永久资源地址；
- 不在通知文本中暴露订单金额、家庭成员、敏感影像或其他不必要的隐私；
- 失败后可在后台查看、重试或转人工；
- 通知重复不会重复创建订单、支付、退款、授权或交付事实；
- 客户重新打开业务详情时，以服务端当前状态为准，即使旧通知延迟或丢失也不改变事实。

### 6.2 建议的客户通知节点

以下通知点是产品建议，具体渠道和时间需要工作室验证：

- 预约申请已提交、待工作室确认；
- 预约已确认并已生成订单；
- 预约被拒绝、时段冲突或申请即将失效；
- 定金待支付、定金支付处理中、定金到账或订单因逾期失效；
- 即将拍摄、拍摄安排变更、改期或取消；
- 拍摄完成已确认、尾款进入应付；
- 尾款支付处理中、到账、失败或线下收款待核验；
- 交付准备中、交付发布、交付入口即将到期或已经到期；
- 交付文件暂不可用、授权变更、家庭成员授权生效或撤回；
- 公开案例授权请求、授权记录、公开撤回处理结果；
- 退款申请受理、审核、处理中、成功或失败待人工；
- 售后问题已受理、需要客户补充、已升级或已解决。

通知渠道可以包括小程序订阅/服务消息、短信、电话或微信人工联系，但是否启用、谁负责发送和客户如何同意需要另行确认。不得在未确认渠道能力前，把某一渠道写成必然可用。

### 6.3 后台待办和升级

后台待办应按紧急性、业务影响和责任角色帮助工作人员排序：

- 即将导致客户损失机会或订单失效的事项优先，例如待确认预约、定金即将逾期、支付未知；
- 影响付款、拍摄或交付的阻塞事项优先，例如线下收款待核验、尾款待激活、文件校验失败；
- 涉及隐私、公开授权、越权或金额不符的事项进入高敏感人工复核；
- 重试超过阈值、长期处理中或跨端撤回未完成的事项进入负责人升级；
- 客户连续咨询、访问拒绝或售后超时需要合并显示，避免多个工作人员重复处理。

待办的优先级不能改变业务事实，也不能让没有权限的工作人员直接执行高风险动作。

### 6.4 客户支持闭环

客户从任一错误或异常状态进入支持路径时，工作室至少能够获得：

- 当前客户身份和可见范围内的订单/预约上下文；
- 客户看到的状态和安全提示；
- request id 或业务单号；
- 最近一次可观察操作和时间；
- 是否存在支付、退款、上传、通知或授权任务；
- 工作室可以执行的下一步和不能执行的限制。

客户支持不能通过口头承诺绕过状态、权限、支付或授权规则。人工处理完成后，客户应能在业务详情看到真实结果，必要时收到处理完成通知。

## 7. 异常恢复与人工补偿体验

### 7.1 客户侧恢复原则

客户侧恢复动作按照风险从低到高分层：

1. 安全刷新当前状态；
2. 返回列表重新进入；
3. 在业务规则允许时重试同一动作；
4. 等待外部支付、退款、上传或查单完成；
5. 联系工作室并提供 request id 或业务单号；
6. 由有权限工作人员执行核验、补偿或重新确认。

客户不能通过重复点击来解决处理中、金额不符、越权、授权争议或订单归属异常。界面需要在高风险状态下明确禁止重复操作，而不是仅依靠工作人员事后解释。

### 7.2 后台补偿任务体验

后台补偿任务至少要让工作人员知道：

- 原始动作想完成什么；
- 当前本地事实和外部结果分别是什么；
- 已经尝试了几次、最后错误是什么；
- 当前是否安全重试；
- 重试会不会造成重复支付、重复退款、重复发布或重复通知；
- 是否需要负责人审核或客户确认；
- 补偿成功后哪些状态和通知会发生变化；
- 补偿失败后如何升级和留下审计。

人工补偿场景包括但不限于：

- 支付结果未知后的查单、对账和迟到支付处理；
- 退款处理中或失败后的查询、重试和人工协商；
- 线下收款凭证和金额核验；
- 文件对象存在但业务登记缺失，或业务记录存在但对象缺失；
- 交付发布、撤回、到期任务失败；
- 授权撤回后的公开端、缓存和外部分享复核；
- 通知发送失败后的重试或人工联系；
- 售后问题升级、补拍、改期或退款协商。

补偿不是把最终状态字段改成“成功”。补偿必须通过业务动作产生新的事实，并保留操作者、原因、时间、范围、前后结果和关联任务。

### 7.3 异常信息的客户和后台分层

客户看到的是安全、可理解和可行动的信息；后台看到的是足以排障但经过脱敏的信息；内部日志保留必要的技术细节。三层信息不能混用：

| 信息层 | 应包含 | 不应包含 |
|---|---|---|
| 客户提示 | 当前影响、下一步、重试/等待/联系路径 | 堆栈、SQL、对象路径、第三方原始响应、他人资料 |
| 后台处理 | 业务号、状态、阻塞原因、任务、责任人、重试和补偿入口 | 不必要的完整身份证明、支付敏感信息、永久下载地址 |
| 内部日志/审计 | request id、task id、调用结果、耗时、异常堆栈和安全事件 | 未脱敏的无关客户资料和不受控文件内容 |

## 8. 可用性与可访问性验证

### 8.1 客户可用性任务

至少观察客户能否完成以下任务：

- 从作品或套餐理解摄影业务、适用对象和联系/预约入口；
- 区分“提交预约申请”和“预约成功”；
- 在预约冲突或申请过期后找到重新选择时段的路径；
- 理解订单已生成、定金待支付和支付处理中之间的差异；
- 不因支付处理中而重复付款；
- 找到拍摄日期、固定时段、改期/取消联系路径和履约状态；
- 理解拍摄完成后仍需支付尾款；
- 理解尾款已付但交付尚未发布时需要等待工作室；
- 区分带水印预览、无水印正式下载、私密交付和公开案例授权；
- 找到交付入口截止时间，并理解到期不等于原文件删除；
- 知道家庭成员为什么需要后台显式授权；
- 在无权限、下架、过期、处理中和服务不可用时采取正确下一步；
- 提交支付、交付、授权或售后问题，并能向工作室提供安全的业务上下文。

### 8.2 工作室和后台可用性任务

至少观察负责人、管理员和摄影师能否完成与其权限匹配的任务：

- 从统一待办识别即将失效、冲突、支付未知、履约异常和交付阻塞；
- 处理线上和电话/微信录入的预约，并理解同一档期的竞争结果；
- 从预约确认进入订单，并看到快照和定金待支付事实；
- 确认拍摄完成、激活尾款，且摄影师不能越权触发；
- 登记和核验线下收款，识别金额不符和重复付款；
- 查看订单、支付、履约和交付的独立状态，避免用一个状态替代其他事实；
- 上传、校验和发布成片，识别文件错误订单、尾款未付和授权缺失；
- 添加或撤回家庭成员交付权限，且不授予订单/支付操作权；
- 记录公开授权、撤回并确认官网、小程序和案例入口的处理结果；
- 处理入口到期后的网盘补交并记录接收人、范围、有效期和原因；
- 在支付、退款、通知、文件和授权异常中判断重试、等待、审核还是人工补偿；
- 从审计和 request id 还原一次客户问题的处理过程。

### 8.3 一致性和可访问性要求

产品验证时至少关注：

- 同一状态在小程序、官网入口和后台不出现互相矛盾的名称或结果；
- 关键状态不只通过颜色、图标或动画表达，文字必须足以理解；
- 失败、处理中和无权限状态对色觉差异用户仍可区分；
- 重要操作、金额、日期、固定时段、入口期限和风险提示清晰可读；
- 错误提示靠近相关任务，且不因 Toast 短暂消失而使客户无法恢复；
- 网络较慢、页面返回、重复进入和设备切换不会丢失已提交的业务上下文；
- 客户不需要记住内部订单状态枚举或技术术语；
- 后台列表在订单较多、异常较多和待办集中时仍能按优先级扫描和处理；
- 涉及儿童、家庭成员、公开授权和付款的信息只显示当前角色完成任务所需的最小范围。

## 9. 衡量框架

### 9.1 衡量原则

指标用于回答“客户是否完成任务”“工作室是否能及时处理”“系统是否让事实变得清楚”和“异常是否得到恢复”，不用于替代订单、支付、履约、交付或授权事实。

所有指标必须：

- 明确定义事件、开始点、结束点、分母、时间范围和排除条件；
- 区分客户主动行为、工作人员操作、系统任务和外部回调；
- 不把页面打开、通知发送或按钮点击直接当成业务成功；
- 可按端、摄影业务、套餐、入口来源、结果状态和是否人工介入进行脱敏聚合；
- 避免记录不必要的姓名、手机号、影像内容、支付敏感信息和家庭关系细节；
- 保留事件版本和口径变化，避免改口径后无法解释历史数据；
- 在真实基线建立前，不承诺具体转化率、响应时长或满意度目标。

### 9.2 客户任务和转化指标

以下指标是建议的衡量方向，不是已经确认的经营目标：

| 指标方向 | 建议口径 | 识别的问题 |
|---|---|---|
| 公开内容有效访问 | 已发布内容详情的有效查看次数/会话，排除重复刷新和后台访问 | 内容是否能被正常发现 |
| 联系入口使用 | 客户主动点击电话/微信/预约入口次数，区分入口来源 | 客户是否找到下一步 |
| 预约申请完成率 | 开始填写预约到成功提交申请的比例 | 表单、身份或信息要求是否阻塞 |
| 预约确认率 | 有效预约申请中最终确认、拒绝、冲突和过期的分布 | 档期供给和人工确认是否清晰 |
| 确认到成单成功率 | 已确认预约中成功形成唯一订单的比例 | 预约和订单衔接是否稳定 |
| 定金支付完成率 | 进入定金待支付的订单中形成已确认定金支付的比例 | 金额、期限和支付体验是否阻塞 |
| 支付处理中重复尝试率 | 处于支付处理中时再次发起支付的比例 | 客户是否理解未知结果 |
| 客户自助完成率 | 无人工介入完成预约查看、支付状态查看、交付访问或问题提交的比例 | 产品是否减少不必要咨询 |
| 交付访问成功率 | 满足访问条件的预览/下载请求中成功完成的比例 | 交付权限、文件和短期访问是否稳定 |
| 入口到期后补交率 | 到期批次中实际申请人工补交的比例 | 期限是否符合客户需求和沟通预期 |

这些指标必须与后台确认、支付事实、交付发布和访问审计分开记录，不能用点击次数替代业务结果。

### 9.3 服务质量和人工工作量指标

建议工作室建立以下运营指标：

| 指标方向 | 建议口径 | 识别的问题 |
|---|---|---|
| 预约确认处理时长 | 从有效申请提交到确认/拒绝/冲突结果的时间 | 人工确认是否及时 |
| 预约过期率 | 待确认申请超过有效期限的比例 | 待办提醒和运营容量是否不足 |
| 定金逾期率 | 定金订单到期仍未确认到账的比例 | 期限、通知和客户理解是否合理 |
| 支付未知处理时长 | 支付进入处理中到最终确认或人工结案的时间 | 查单、对账和外部依赖是否可靠 |
| 退款处理时长 | 退款申请到最终成功/失败待人工的时间 | 审核和外部退款能力是否匹配 |
| 履约异常率 | 已确认订单中发生缺席、取消、补拍或服务异常的比例 | 履约流程和服务质量问题 |
| 成片按期发布率 | 进入可交付条件后在约定时间内发布的比例 | 后期制作和交付准备是否稳定 |
| 文件校验失败率 | 上传文件中校验失败或需要重传的比例 | 文件整理、上传和质量控制问题 |
| 交付访问失败率 | 已发布且授权有效的访问请求中失败的比例 | 文件、权限、链接或设备问题 |
| 授权撤回处理时长 | 撤回请求到公开端停止展示并完成复核的时间 | 内容下架和授权闭环是否可靠 |
| 通知失败率 | 已生成通知中发送失败或无法确认送达的比例 | 渠道可靠性和人工跟进负担 |
| 人工补偿率 | 业务任务中进入人工核验/补偿的比例 | 自动化闭环和外部依赖成熟度 |
| 超时待办量 | 超过内部处理期限仍未完成的事项数量 | 工作室运营积压和升级需求 |
| 客服重复咨询率 | 同一业务问题在一定时间内重复联系的比例 | 状态表达或通知是否不足 |

内部服务时间目标、客户响应承诺和告警阈值尚未确认。没有真实数据前，先记录事件和分布，不强行设定目标值。

### 9.4 状态清晰度和体验指标

定量指标之外，需要通过访谈或任务测试观察：

- 客户能否正确复述“预约申请”和“预约成功”的差别；
- 客户能否判断支付是否成功、是否应该重复支付；
- 客户能否说出尾款、交付发布和入口期限之间的关系；
- 客户能否区分私密交付授权与公开案例授权；
- 工作人员能否在不查看技术日志的情况下判断下一步；
- 工作人员是否会把处理中当失败、把通知成功当业务成功或直接手改状态；
- 无权限提示是否既不泄露信息又能引导客户解决；
- 入口到期、文件异常和授权撤回是否造成大量重复咨询；
- 客户和工作人员是否能从同一业务详情获得一致事实。

### 9.5 事件和数据质量要求

进入详细设计前需要进一步确认事件目录，但事件语义至少覆盖：

- 公开内容查看、内容下架/失效访问；
- 预约申请开始、提交、确认、拒绝、冲突、过期、取消和改期；
- 订单生成、定金待支付、定金确认、订单失效和人工延长；
- 支付发起、处理中、查单、成功、明确失败、重复/超额/金额不符；
- 线下收款登记、核验、拒绝和待人工；
- 拍摄排期、开始、完成、缺席、取消、补拍和履约异常；
- 尾款激活、尾款支付、退款申请、审核、处理中、成功和失败待人工；
- 文件上传、校验、重传、发布、撤回、到期、预览、下载和访问拒绝；
- 私密授权新增、变更、撤回、到期和公开授权请求、同意、拒绝、撤回；
- 通知生成、发送、失败、重试和人工联系；
- 售后提交、受理、补充资料、升级、解决和关闭；
- 人工补偿开始、重试、审核、成功、失败和升级。

每类事件需要能区分：

- 发生时间和客户端展示时间；
- 业务事实状态和展示结果；
- 客户、工作人员、系统任务或外部服务触发；
- 端和入口来源；
- 业务号和安全关联标识；
- 是否首次、重复、重试或补偿；
- 是否成功、处理中、明确失败或未知。

事件采集失败不能阻止预约、支付、交付或授权等正式业务动作，也不能通过补发指标事件伪造业务成功。指标缺失需要进入数据质量检查和补偿范围，但不能回写业务事实。

## 10. 功能需求清单

### 10.1 跨端客户体验

- 小程序、官网和联系入口共享当前已发布的公开内容事实；
- 从作品、业务或套餐进入联系/预约时保留必要上下文；
- 从官网深层页面进入小程序后可以回到相关内容或预约意图；
- 客户可以在一个连续路径中查看预约、订单、支付、履约、交付和授权相关任务；
- 客户离开页面后重新进入，看到的是当前服务端事实而不是过期本地结果；
- 公开内容、套餐、预约申请、订单、支付、交付和授权的失效/撤回入口能够安全处理；
- 客户能够识别当前需要自己操作、等待工作室、等待外部服务或联系人工的状态。

### 10.2 状态和异常反馈

- 统一表达加载、空状态、处理中、明确失败、未知结果、无权限、冲突、下架、失效和到期；
- 客户侧提示使用稳定、可理解和不泄露隐私的文案；
- 后台显示状态、阻塞原因、责任角色、下一步、重试和补偿入口；
- 支付处理中不允许客户无依据重复付款；
- 无权限、未发布、尾款未付、入口到期和文件异常不显示为同一个错误；
- 网络、外部服务或通知异常不覆盖已经确认的业务事实；
- 旧链接、旧页面和缓存内容在下架、授权撤回或版本失效后提供安全结果；
- 所有高风险失败都能关联业务号、request id 或任务记录进行支持和审计。

### 10.3 通知和工作室待办

- 预约、订单、支付、履约、交付、授权、退款和售后重要状态有可配置的通知节点；
- 通知生成和业务事实相互独立，发送失败有重试/人工处理；
- 后台能按即将失效、阻塞、高敏感和超时事项聚合待办；
- 待办显示当前责任角色、最近处理、下一步和影响范围；
- 客户从通知进入业务详情时读取最新事实；
- 客服或工作人员可以查看安全上下文并记录处理结果；
- 重复通知、重试和人工联系不会产生重复业务事实。

### 10.4 可用性、隐私和可访问性

- 客户能通过任务名称而不是内部模块名称理解主要流程；
- 颜色、图标和动画不是状态的唯一表达方式；
- 关键日期、固定时段、金额、支付结果、访问期限和风险提示清晰可读；
- 处理中、失败和无权限状态支持安全离开、刷新和恢复；
- 后台在多订单、多异常和跨角色协作下仍可扫描和执行；
- 客户和工作人员只能看到完成当前任务所需的最小资料范围；
- 私密交付、公开案例和授权撤回的反馈不向无关人员暴露敏感内容。

### 10.5 衡量和运营改进

- 记录跨端关键任务和状态转换事件；
- 区分页面行为、业务事实、通知结果和人工补偿；
- 统计客户转化、服务时效、失败恢复、交付质量、授权处理和人工工作量；
- 指标定义包含事件、分母、时间范围、排除条件和版本；
- 支持按端、入口、摄影业务、套餐和结果状态做脱敏分析；
- 监测事件缺失、重复、延迟和业务事实与指标不一致；
- 在真实运营基线建立前不写死经营目标和服务等级。

## 11. 验收标准

### 11.1 跨端连续性

1. 客户从官网、作品、套餐、电话或微信进入预约意图后，工作人员能够在统一预约事实中继续处理。
2. 客户从公开内容进入小程序或联系入口后，能够理解自己正在处理的作品、业务或套餐上下文。
3. 客户重新进入订单、支付、履约或交付详情时，展示当前服务端事实，不依赖上一次页面缓存。
4. 公开内容下架、套餐版本失效或授权撤回后，官网、小程序公开入口和旧链接不会继续把内容当成有效公开资源。
5. 私密交付不会因公开页面、分享入口或静态作品路径而被匿名访问。
6. 电话/微信联系不会被界面误示为已提交预约或已锁定档期。

### 11.2 状态理解和异常反馈

1. 客户可以区分预约申请、预约确认、订单生成和定金支付。
2. 同一固定时段发生竞争时，成功确认的一方获得明确结果，其他申请收到冲突或待处理结果，不显示为预约成功。
3. 支付处理中时，客户可以看到等待查单或联系客服的路径，不能被引导重复付款。
4. 线下收款登记但未核验时，客户和后台都不会把它当作已确认收款。
5. 拍摄完成待确认、尾款待支付、尾款处理中和交付未发布分别有不同状态和下一步。
6. 尾款未付、交付未发布、无私密授权、入口到期、文件异常和系统不可用不会共用一个模糊错误。
7. 无权限提示不泄露其他客户、订单存在性、家庭成员或对象存储路径。
8. 对明确失败、未知结果、处理中和待人工核验，客户提示和后台处理入口分别正确。
9. 旧链接、重复提交和页面返回不会改变已经确认的业务事实或绕过当前权限。

### 11.3 通知、待办和人工处理

1. 重要业务状态变化有对应的客户可见入口或后台可见待办，即使通知未送达也不丢失事实。
2. 通知发送失败不会回滚预约、支付、退款、履约、交付或授权事实。
3. 后台能按责任角色和阻塞原因识别待处理事项，并给出安全下一步。
4. 支付、退款、文件、授权和通知的处理中/失败事项有重试、查单、审核或人工补偿路径。
5. 人工补偿保留操作者、原因、时间、范围、前后结果、request id 或 task id。
6. 补偿操作不会通过直接修改汇总状态掩盖原始失败，也不会造成重复支付、退款、发布或授权。
7. 客服能够根据客户看到的提示、业务号和 request id 找到当前可处理事实。

### 11.4 可用性和隐私

1. 受测客户能在不学习内部状态枚举的情况下完成预约查看、支付状态判断和交付访问。
2. 受测客户能理解尾款已付、交付已发布、入口已到期和公开授权撤回之间的差异。
3. 受测工作人员能在后台找到预约冲突、支付未知、履约异常、文件校验失败和授权待核验任务。
4. 摄影师只能执行被授权的拍摄和文件任务，不能通过横向体验入口确认完成、触发尾款、处理退款或发布公开案例。
5. 关键状态不只依赖颜色、图标或短暂 Toast，网络慢和重复进入时仍能恢复。
6. 客户、家庭成员、工作人员和匿名访客只能看到完成当前任务所需的最小资料。

### 11.5 衡量和数据质量

1. 预约、订单、支付、履约、交付、授权、通知、售后和补偿的关键事件可以区分业务事实与页面行为。
2. 业务成功指标不使用单纯的按钮点击、页面打开或通知发送替代。
3. 每个核心指标都有明确的事件、分母、时间范围、排除条件和版本。
4. 指标采集失败不会阻止业务动作，也不会通过补发事件伪造业务成功。
5. 能够识别重复事件、延迟事件、缺失事件和指标与业务事实不一致。
6. 在真实数据不足时，系统先形成可审计的基线，不提前承诺未经验证的转化率、响应时间或满意度目标。

## 12. 脱敏验证场景

至少准备以下场景：

1. 客户从官网某个作品进入小程序后，仍能看到对应作品上下文，而不是回到无关首页。
2. 客户点击电话/微信联系后，没有产生预约成功或档期占用事实。
3. 客户提交预约申请后立即离开，再次进入时看到“待确认”，而不是“已预约成功”。
4. 两个申请同时竞争同一日期和固定时段，只有一个确认动作成功，另一方得到冲突结果。
5. 待确认申请超过有效期限，客户看到已失效和重新申请路径，后台看到失效原因。
6. 预约确认成功后自动生成订单，客户可以看到订单快照和定金待支付事实。
7. 定金支付请求超时，客户看到处理中，重复进入不会创建第二笔支付意图。
8. 支付明确失败时可以按规则重试，支付金额不符时转人工而不是继续重试。
9. 工作室登记线下收款但未核验，订单和尾款门槛不会被错误满足。
10. 拍摄完成后负责人未确认，客户看不到尾款已激活，摄影师不能通过自己的入口触发尾款。
11. 尾款已付但成片仍在上传或校验，客户不能预览或下载，并能看到等待原因。
12. 成片已发布但当前访问身份未被授权，客户收到安全的授权提示，不能推断其他家庭成员信息。
13. 预约联系人交付访问成功，实际拍摄人未被显式授权时不能访问。
14. 小程序交付入口到期后客户无法继续访问，但后台仍能看到原文件保管和人工补交入口。
15. 公开案例授权撤回后，作品列表、案例详情、首页引用和分享入口停止后续公开展示，私密交付不被删除。
16. 外部分享缓存暂时未清除时，后台生成复核和跟进待办，客户侧不显示内部争议信息。
17. 通知发送失败时，客户重新进入业务详情仍能看到最新状态，后台能重试或人工联系。
18. 交付发布任务执行结果未知，客户不会看到已发布，后台进入重试或人工核验。
19. 对象存储已有文件但业务登记失败，系统不向客户开放，后台可以定位孤立对象并补偿。
20. 客户在网络慢时重复点击支付、预约或下载，系统不会生成重复业务事实。
21. 同一 request id 关联一次客户请求及其异步任务，工作人员能从支持入口找到当前处理结果。
22. 后台工作人员尝试直接改订单、支付、交付或授权汇总状态时被阻止或要求走正式业务动作。
23. 摄影师可以上传候选文件，但不能发布交付、确认拍摄完成、激活尾款、退款或公开案例。
24. 客户提交售后问题后，能看到受理、处理中、待补充、已解决或已关闭，而不是只收到一次 Toast。
25. 指标采集失败时预约、支付或交付仍按业务规则执行，数据质量任务单独记录缺失事件。

## 13. 待确认经营内容与产品决策

以下内容需要负责人和实际工作人员结合真实运营确认：

1. 官网与小程序之间最终采用直接预约、引导小程序还是两者并行。
2. 官网和小程序公开内容发布后的同步时效、缓存策略和旧链接处理责任。
3. 客户身份触发的最小节点，以及预约联系人、付款人、拍摄人和被授权交付人的关联方式。
4. 预约申请、预约确认、定金支付、尾款支付、交付发布和授权变更的客户通知渠道。
5. 哪些通知需要客户显式订阅、确认或允许人工电话/微信跟进。
6. 通知发送失败后的重试次数、人工联系时限和负责人。
7. 预约申请、定金支付、尾款支付、退款、交付发布和售后问题的内部响应时限。
8. 后台工作台按角色、按时间、按风险或按客户旅程聚合待办的优先级。
9. 哪些处理中事项允许客户主动刷新，哪些必须等待系统任务或人工处理。
10. 支付、退款、文件、授权和通知异常达到什么条件后升级负责人。
11. 客户咨询、访问拒绝、支付争议和文件问题使用统一售后入口还是分业务入口。
12. 客户联系工作室时需要提供哪些业务号、request id 或安全验证信息。
13. 客户满意度、客服响应、交付准时率和人工补偿是否纳入首版运营记录。
14. 真实运营开始后多久建立第一版转化、时效、异常和人工工作量基线。
15. 哪些指标按摄影业务、套餐、入口、端和客户来源分组，哪些只保留工作室总体汇总。
16. 事件和审计记录的保留范围、访问角色、脱敏方式和删除/归档责任。
17. 是否需要支持客户在多个设备或多个端之间切换，以及身份失效后的恢复方式。
18. 是否需要考虑视力、色觉、网络质量、低端设备和长时间任务等可访问性测试范围。
19. 通知、缓存或外部分享无法即时更新时，客户承诺文案和人工补偿方式。
20. 售后问题的升级层级、工作时间、节假日处理和客户响应承诺。
21. 是否允许负责人对单个订单或交付批次进行例外延长、恢复或补交，以及审批要求。
22. 指标目标值和服务等级应在什么真实样本量后确认，避免以原型阶段数据作经营承诺。

## 14. 后续专题输入

A16 为后续详细设计和实现准备以下横向输入，但不直接锁定实现方案：

- A05/A06：公开内容、作品和案例必须消费当前发布与授权资格，撤回后跨端停止公开展示；
- A07：套餐展示、版本失效和订单快照前后的信息连续性；
- A08：客户任务地图、上下文传递、加载/空/冲突/处理中/无权限/到期状态反馈；
- A09：官网深层链接、公开内容失效、官网到小程序或联系入口的连续性；
- A10：后台工作台待办、异常聚合、责任角色、重试、审核和补偿入口；
- A11：身份失效、预约联系人、家庭成员、最小必要资料和隐私分层；
- A12：申请待确认、固定时段冲突、申请失效、确认和改期的客户反馈；
- A13：订单快照、定金期限、履约状态、拍摄完成和尾款激活的状态表达；
- A14：支付处理中、线下收款待核验、退款处理中、售后状态和人工跟进；
- A15：交付未发布、已发布、入口到期、私密授权、公开授权撤回和补交体验；

- AT06：预约、订单、支付、退款、履约和交付状态边界；
- AT07：客户、负责人、管理员、摄影师、系统任务和对象存储身份权限；
- AT08：外部调用、任务重试、幂等、人工补偿和审计要求；
- AT09：稳定错误码、HTTP/业务语义、request id、任务 id 和脱敏错误响应。

后续详细设计需要把本专题的状态表达、通知、待办、事件和指标口径转换为可执行契约，但必须先复核本专题的待确认经营内容，不得把产品建议直接当作已确认经营规则。

## 15. 结论

当前工程尚未形成正式的跨端业务体验：小程序原型有硬编码和占位入口，官网没有独立实现，后台没有独立运营界面，请求层和异常层仍使用粗粒度数字码与 Toast/控制台反馈，也没有通知、待办、售后、交付和指标闭环。

A16 建立的横向需求基线是：

```text
小程序、官网和后台围绕同一个工作室和同一组业务事实协作；
客户从公开浏览到预约、订单、支付、履约、交付和授权拥有连续上下文；
预约申请、预约确认、订单、支付、履约、交付和授权分别表达，不能用一个成功状态替代；
加载、空、处理中、明确失败、未知结果、无权限、冲突、下架、失效和到期分别反馈；
通知是业务事实的辅助通道，通知失败不能回滚业务动作；
后台待办必须告诉工作人员阻塞原因、责任人、下一步、重试和人工补偿路径；
支付、退款、文件、授权和通知异常需要可观察、可审计、可恢复，不能靠直接改汇总状态掩盖；
客户和工作人员都应能理解下一步，且敏感资料按最小必要原则展示；
指标必须区分页面行为、通知结果、业务事实和人工补偿，先建立基线再确认目标；
真实运营前不锁定通知渠道、服务时限、指标目标和所有可访问性细节。
```

A16 不定义数据库、API、组件、埋点实现或部署方案。它完成第六步对横向体验、状态反馈、通知、人工补偿、可用性和衡量需求的补齐，为后续统一复核 A04-A16、调整三阶段计划和开展详细设计提供输入。
