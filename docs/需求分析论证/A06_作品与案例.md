## 1. 专题目的

本专题分析 SouthLeaf 的公开作品与摄影案例能力：工作室如何整理代表作品，客户如何按分类浏览并理解作品风格，案例如何关联摄影业务或套餐，作品图片如何组成可阅读的案例，以及公开展示授权变化后如何停止展示。

本文件回答：

- “作品”“案例”“图片”和“一次拍摄”在产品上如何区分；
- 案例的最小展示单元是什么，如何支持单图和多图案例；
- 分类、标签、摄影业务和套餐如何关联但不混为一谈；
- 客户如何浏览列表、分类、详情、图片和相关案例；
- 作品公开状态、图片有效性和客户公开授权如何共同决定能否展示；
- 作者、摄影师和其他贡献者如何署名，成员停用后历史案例如何保持清晰；
- 首页引用和案例详情中的相关作品如何避免产生失效或未授权内容；
- 当前工程中哪些内容只是历史原型，不能直接作为正式案例数据。

本文件不定义数据库表、API、对象存储厂商、文件处理方案、后台组件、视觉配色或具体实施阶段；也不重新定义品牌内容、摄影业务与套餐、客户身份、预约、订单、支付和私密成片交付的主规则。

## 2. 专题边界与规则归属

### 2.1 A06 拥有的需求

A06 负责以下作品与案例需求：

- 公开作品案例的概念、粒度和内容边界；
- 案例与一张或多张公开图片的组织关系；
- 作品分类、标签及其浏览和筛选用途；
- 案例与摄影业务、套餐的可选关联及公开展示方式；
- 案例标题、摘要、说明、封面、图片顺序和公开展示信息；
- 案例级公开资格如何由作品状态、图片状态和授权结果共同决定；
- 案例详情、图片浏览、分类浏览、相关作品和关联服务入口；
- 作者、摄影师及其他公开贡献者在案例中的署名关系；
- 案例失效、下架、授权撤回或图片缺失时的公开端行为；
- 作品后台维护任务、公开展示校验和案例相关验收标准。

### 2.2 A06 只引用、不拥有的需求

| 对象或规则 | 主归属 | A06 允许做什么 | A06 不得定义什么 |
|---|---|---|---|
| 品牌与首页 | A05 | 提供可被引用的案例、封面、标题、摘要和有效性结果 | 首页区块顺序、推荐位管理、品牌文案和公共内容发布流程 |
| 摄影业务与套餐 | A07 | 建立案例与已发布业务/套餐的关联，提供跳转入口 | 业务目录、价格、服务内容、定金、时长和预约资格 |
| 客户身份与参与者 | A11 | 说明案例涉及公开授权对象和必要的身份边界 | 客户身份绑定、联系人、拍摄人、家庭成员和敏感资料规则 |
| 私密成片交付 | A15 | 将公开案例与私密交付明确分开，消费交付结果的公开资格影响 | 尾款门槛、交付批次、私密文件访问、签名地址、交付期限和原文件删除 |
| 公开授权事实 | A15 | 消费授权是否有效、适用范围和撤回结果，并将结果用于案例公开判断 | 授权主体、同意证据、撤回事实和隐私效力的主记录 |
| 团队公开资料 | A05 | 在案例中引用作者或贡献者的公开称呼及署名快照 | 团队介绍、公开履历、后台账号、排班和工作人员权限 |
| 通用内容生命周期 | A05 | 遵循草稿、预览、发布、下架和恢复的公共内容规则 | 重写全站内容发布流程或跨端内容事实 |
| 技术状态、权限、文件和审计 | AT01-AT09 | 提供业务语义和验收要求 | 数据库字段、接口、事务、幂等、存储、错误码和权限实现契约 |

### 2.3 A06 与 A15 对公开授权的拆分

现有文档同时将公开案例授权分别提到 A06 和 A15。为避免同一条事实出现两套主记录，本专题采用以下职责拆分：

- **A15 拥有授权事实**：谁同意、同意了哪些对象、允许什么用途和渠道、有效期是什么、证据是什么、谁在何时撤回，以及撤回对客户私密交付文件的影响。
- **A06 拥有案例公开资格的消费规则**：一个案例在满足什么条件后可出现在公开列表、详情、首页引用和相关作品中；授权撤回或失效后，案例如何从公开端消失。
- **A05 拥有首页编排**：哪些有效案例放在首页、展示顺序和区块位置如何维护。
- **A11 拥有身份关系**：预约联系人、拍摄人、家庭成员、监护人及其他授权对象如何识别和关联。

因此，“公开授权有效”是 A06 判断案例能否公开的必要输入，但授权同意和撤回本身不在 A06 重复定义。公开展示资格与私密交付权限也不是同一个授权结果。

### 2.4 A06 的核心规则

公开作品案例只有在以下条件同时满足时，才可以被匿名访客看到或被 A05 首页引用：

1. 案例本身处于可公开的已发布状态；
2. 案例至少有一项可公开展示且处理完成的图片；
3. 案例所使用的图片、人物和内容没有超出有效公开授权范围；
4. 关联的作者署名、业务/套餐入口和公开文案均可正常展示；
5. 案例没有被工作室主动下架、标记为不可公开或因异常进入隐藏状态。

“原型中曾经展示过”不能替代正式发布和明确授权。无法证明公开授权有效的历史客户照片，默认不得继续作为公开案例展示。

## 3. 证据口径

| 标记 | 含义 |

| 已确认需求 | 已由用户讨论、A01-A05 或架构基线明确的产品要求 |
| 原型证据 | 当前代码确实存在的页面、文案、资源或接口，只能证明历史原型曾表达该能力 |
| 产品建议 | 为形成可运营产品提出的候选方案，仍需结合工作室实际确认 |
| 待确认经营内容 | 案例名称、公开授权、业务关联、作者资料等需要负责人提供权威内容 |

当前仓库没有经过确认的公开案例清单、客户授权记录、案例历史、正式图片版权资料或作品运营记录。前端硬编码的标题、作者、日期、分类和本机图片路径不能直接转为现行经营事实。

## 4. 当前工程证据与问题

### 4.1 作品列表原型

`frontend/pages/works/works.vue` 当前通过页面内的 `allWorks` 数组维护作品，原型对象包括：

- `id`；
- `title`；
- `description`；
- `author`；
- `category`；
- `package`；
- `imageSrc` 图片数组；
- `time` 日期字符串。

当前页面按分类过滤作品，列表只展示第一张图片、标题、分类和部分说明。作者、套餐和日期虽然在数据中存在，但没有形成稳定的公开展示和关联规则。

当前分类数组也直接写在页面中，包含“全部”“创始人档”、儿童、亲子全家福、婚纱、写真、孕照和证件照。历史原型证据表明六类摄影业务需要保留，但作品分类不应自动等同于摄影业务分类；“创始人档”在未确认前只能作为历史作品/品牌分类线索，不能自动成为可预约业务。

### 4.2 作品详情原型

`frontend/pages/works/workdetail.vue` 接收路由中的 `id`，但详情数据仍然是固定的单个作品，且只有当传入 id 为 `1` 时才赋值。当前存在：

- 访问其他作品 id 时页面可能为空；
- 列表中第一条作品分类为“创始人档”，详情中却显示为“写真”；
- 详情只展示固定图片数组和固定说明；
- 没有真实的作品查询、无效详情提示、相关作品或关联服务入口；
- 没有对图片公开状态、授权状态、作者状态和下架结果进行处理。

这说明详情页只是视觉与交互原型，不能证明作品数据已经具备可运营的一致性。

### 4.3 首页作品副本

`frontend/pages/index/index.vue` 另行硬编码一组首页作品，与作品列表维护两套内容源。当前已经出现标题、图片或文案可能漂移的风险，且首页作品没有稳定引用关系。

A06 的需求结论是：首页只能引用已公开有效的案例，不能复制一份独立的作品内容；首页区块和顺序由 A05 管理，案例变为不可公开时，首页必须隐藏或提示引用失效。

### 4.4 分类和接口证据

当前后端存在分类、套餐和轮播相关的基础接口，但没有作品案例实体、作品详情接口、案例分类接口、图片上传管理、公开授权或案例发布接口。

当前还存在以下概念混用：

- 后端 `Category` 同时被套餐和作品原型借用；
- 前端分类字段存在 `name`、`desc`、`icons` 等与后端不同的命名；
- 图片字段同时使用 `icons`、`imageSrc` 和 `images`；
- 业务目录、作品分类和套餐分类没有形成清晰关系；
- 分类初始化数据与前端展示分类不一致；
- 作品页、首页和详情页之间没有统一的作品数据来源。

作品分类、摄影业务分类和套餐分类应作为可以关联但不必一一对应的概念维护。不能因为一条作品属于“写真”或“创始人档”，就自动推导客户可以预约同名服务。

### 4.5 图片与媒体证据

现有作品图片主要位于 `frontend/static/works/`，随前端资源打包，当前没有：

- 作品或案例媒体记录；
- 图片用途、替代文本、说明、顺序和封面角色管理；
- 图片公开状态和授权范围；
- 上传、替换、处理、校验、失败重试和引用检查；
- 图片撤回后停止公开访问的能力；
- 公开展示图片与客户私密原片、精修图之间的隔离规则。

后端轮播能力只是扫描固定本机目录，不能作为作品案例的正式媒体管理方式。公开案例图片与客户交付文件必须保持业务边界和访问边界分离：前者服务匿名公开展示，后者服务经授权客户访问。

### 4.6 现状问题结论

| 问题 | 当前表现 | 产品风险 |
|---|---|---|
| 作品内容硬编码 | 列表、首页和详情页各自维护作品数据 | 修改需要依赖开发者，内容容易漂移 |
| 详情不完整 | 只有固定 id 的详情内容 | 客户点击其他案例可能看到空白或错误 |
| 分类混用 | 作品分类、业务分类和套餐分类没有清晰边界 | 作品展示可能误导客户预约服务 |
| 图片无权威管理 | 图片随前端包发布，缺少媒体记录 | 单图撤回、替换和追溯困难 |
| 授权缺失 | 没有客户公开授权和撤回记录 | 未授权客户照片可能持续公开 |
| 作者为自由文本 | `author` 没有成员引用、署名快照和历史处理 | 成员停用后历史署名不稳定 |
| 首页重复维护 | 首页作品不引用作品对象 | 首页和作品详情内容不一致 |
| 无生命周期 | 没有草稿、预览、发布、下架和恢复 | 测试数据或错误内容可能直接公开 |
| 无公开/私密分域 | 作品展示和客户相册均未形成正式能力 | 公开案例与私密成片边界不清 |
| 无自动化验证 | 现有测试没有覆盖作品场景 | 授权撤回、失效引用和空状态容易回归 |

## 5. 用户问题与产品价值

### 5.1 潜在客户的问题

潜在客户浏览作品时需要快速理解：

- 工作室实际擅长哪些摄影方向；
- 某组照片是单张展示、完整案例还是客户私密相册；
- 作品有哪些风格、人物类型、场景或业务关联；
- 一组案例包含哪些图片，是否能代表完整拍摄效果；
- 该案例是否可以进一步了解对应业务或套餐；
- 当前看到的内容是否为正式公开作品，而不是测试或过期内容。

如果列表、详情和首页内容不一致，或作品分类直接被理解为预约业务，客户会无法判断工作室能力和下一步行动。

### 5.2 工作室的问题

工作室需要：

- 不修改源码即可新增、编辑、排序和下架案例；
- 用一组有序图片表达一次完整拍摄或一个主题，而不是重复创建多条单图记录；
- 按作品分类和标签组织内容，同时关联对应业务或套餐；
- 明确哪些客户照片允许公开，哪些只能用于私密交付；
- 客户撤回公开授权后，能够及时停止公开展示并保留处理记录；
- 保留成员停用后的历史署名，不让历史案例出现错误人员信息；
- 在发布前发现缺图、无授权、失效关联和不完整文案；
- 让首页和作品详情引用同一份有效案例事实。

### 5.3 产品价值

A06 的目标不是建设面向所有摄影机构的内容平台，而是让单工作室能够持续维护一套可信的公开作品集：案例结构清楚、图片顺序稳定、分类可理解、公开边界可证明、首页引用不漂移、客户可以从作品自然进入相关服务。

## 6. 概念与对象边界

### 6.1 术语建议

| 术语 | 产品含义 | 是否对客户公开 |
|---|---|---:|
| 作品图片 | 一张用于表达摄影效果的图片，可作为案例中的一项内容 | 是，前提是公开资格有效 |
| 作品案例 | 一组围绕同一主题、同一次拍摄或同一表达目的组织的公开展示内容 | 是，前提是案例整体可公开 |
| 拍摄记录 | 工作室内部对某次真实服务的业务记录，可作为案例来源 | 不一定 |
| 公开作品集 | 访客可以浏览的已发布案例集合 | 是 |
| 客户私密成片 | 交付域管理的客户精修图、原片或其他交付文件 | 仅对授权客户，不属于公开作品集 |
| 摄影业务 | 工作室对外提供的业务类型，如儿童、亲子全家福、婚纱、写真、孕照、证件照 | 是，规则由 A07 管理 |
| 套餐 | 某一业务下的标准服务约定 | 是，规则由 A07 管理 |
| 作品分类 | 用于组织和浏览案例的展示维度 | 是，可按公开内容展示 |
| 标签 | 对案例风格、场景、人物或主题进行的辅助描述 | 可选公开 |

### 6.2 案例粒度的产品建议

产品建议以“作品案例”为客户可浏览的最小主要单元，以有序图片集合表达同一主题或一次拍摄的代表性结果；最终案例粒度仍需负责人确认：

- 单张作品可以作为只有一张图片的案例；
- 多张相关图片应放入同一个案例，保持封面和展示顺序；
- 同一张图片不应因为首页、分类页和详情页不同展示位置而复制成多个作品对象；
- 一次拍摄可以产生一个或多个案例，但是否这样拆分需要工作室按实际运营习惯确认；
- 拍摄记录和公开案例可以有关联，但拍摄记录不是自动公开的理由；
- 客户私密交付中的原片和精修图不因被选入交付批次就自动成为公开案例图片。

在负责人确认案例粒度前，不能据此锁定最终数据结构或迁移历史作品。

### 6.3 分类与标签

建议区分：

- **作品分类**：用于主要浏览入口，例如儿童作品、亲子全家福作品、婚纱作品、写真作品、孕照作品、证件照作品，或其他品牌栏目；
- **标签**：用于描述风格、场景、人物、季节、色调、拍摄方式等辅助信息；
- **摄影业务分类**：表示工作室提供什么服务，由 A07 维护；
- **套餐所属业务**：表示标准套餐归属于哪一摄影业务，由 A07 维护；是否另设套餐展示分组由 A07 结合实际经营确认。

产品建议：

- 一个案例至少归入一个作品分类；
- 一个案例可以有多个辅助标签；
- 分类和标签均支持排序、停用和发布状态；
- 停用分类或标签不应抹去历史案例事实；
- 没有有效内容的分类不应在公开端展示为空入口；
- 标签是否公开显示、是否支持客户筛选、是否用于相关作品匹配，需要结合实际案例数量确认；
- “全部”是浏览聚合入口，不应作为真实业务分类保存；
- “创始人档”暂按作品/品牌栏目处理，不自动转换为业务或套餐。

### 6.4 案例与业务/套餐的关联

案例可以关联已发布的公开摄影业务或套餐，目的是帮助客户理解作品对应的服务方向。案例与业务/套餐的具体关联基数仍需负责人确认；在确认前，关联关系应满足：

- 关联是可选的，不能强迫每个案例都有业务或套餐；
- A06 只展示关联对象的公开名称和进入详情的入口；
- 价格、时长、服务内容、定金和预约资格始终读取 A07 的权威事实；
- 业务或套餐下架后，案例不应复制旧价格或继续显示失效预约入口；
- 业务名称调整、套餐版本变化或套餐下架不应修改案例本身的历史说明；
- 关联失效时，后台应提示工作室修复、替换或移除关联；
- 案例属于某一业务不代表客户可以直接预约同样的拍摄内容。

## 7. 用户任务与目标旅程

### 7.1 访客浏览作品

1. 访客从首页、底部导航或品牌页面进入作品；
2. 看到可浏览的作品分类或全部案例入口；
3. 按分类或可用标签缩小范围；
4. 浏览案例封面、标题、摘要和必要的作者/业务信息；
5. 打开案例详情，按顺序查看图片和说明；
6. 进入相关业务或套餐，或返回继续浏览；
7. 通过电话、微信或后续预约入口联系工作室。

作品浏览只产生浏览行为，不产生预约、订单、支付或客户交付访问事实。

### 7.2 访客查看案例详情

案例详情至少应帮助访客回答：

- 这组作品表达什么主题或服务风格；
- 作品包含多少张公开图片，当前图片顺序是什么；
- 作品属于什么展示分类，有哪些辅助标签；
- 是否有公开显示的作者或工作室署名；
- 是否关联摄影业务或套餐；
- 下一步应继续浏览、了解服务还是联系工作室。

图片加载失败、案例失效或案例被撤回时，详情页不得显示残缺的内部路径、客户隐私或已失效授权信息。

### 7.3 工作室整理和发布案例

1. 工作室整理案例标题、说明、分类、标签和图片；
2. 选择封面并调整图片顺序；
3. 按需要关联公开业务或套餐；
4. 设置作者/贡献者的公开署名方式；
5. 确认公开展示授权结果和图片使用范围；
6. 预览访客看到的列表和详情；
7. 完成公开校验后发布；
8. 后续可编辑、下架、恢复或处理授权撤回；
9. 首页或其他公开页面引用时，只能选择当前有效案例。

案例的编辑、发布和下架不改变既有订单中的套餐快照，也不改变客户私密交付文件。

## 8. 作品案例内容规则

### 8.1 案例基本内容

案例至少需要能够表达：

- 对外标题；
- 面向访客的简短说明或摘要；
- 可公开展示的图片集合；
- 封面图片；
- 图片展示顺序；
- 至少一个作品分类；
- 可选标签；
- 可选作者或贡献者署名；
- 可选摄影业务或套餐关联；
- 可选的拍摄时间或时间描述；
- 当前公开状态和更新时间信息。

拍摄时间、客户姓名、内部订单号、客户联系方式、内部备注和未授权人物信息不得因为是原始拍摄资料就自动公开。

### 8.2 图片集合

每个案例的图片集合需要：

- 至少有一张可公开展示图片才能进入公开状态；
- 明确哪一张是封面；
- 明确图片顺序，不能依赖文件系统返回顺序；
- 支持替换、增加、移除和重新排序；
- 图片异常、缺失或未完成处理时不能通过公开校验；
- 可以为公开展示准备适合浏览的媒体版本，但不因此改变客户私密交付原文件；
- 删除或替换被首页、详情或相关作品引用的图片前，提示影响范围；
- 一张图片被多个案例使用时，授权范围和撤回影响必须可追溯；
- 公开案例不应把原片、未处理素材或包含客户内部信息的文件直接暴露给访客。

### 8.3 封面与摘要

封面是案例在列表、首页引用和分享场景中的代表图片。封面必须来自该案例的图片集合，并满足当前公开资格。

封面失效时：

- 后台提示工作室选择新的有效封面；
- 公开端不应继续显示已失效图片；
- 如果案例仍有其他有效图片，可以进入待修复状态，但不能在未确认的情况下自动使用客户私密文件；
- 如果没有任何有效图片，案例从公开端隐藏。

摘要和标题应帮助访客理解案例，不得写入内部订单号、客户真实姓名、未授权的客户经历或未经确认的奖项、数量和业绩描述。

### 8.4 作者与贡献者署名

案例可以显示工作室署名，也可以显示一名或多名公开贡献者。贡献者角色可以包括摄影师、修图师、妆造或其他实际需要对外说明的角色，但具体角色范围需负责人确认。

署名规则建议：

- 公开显示名与后台账号、真实身份资料分开；
- 案例发布时保存当时的公开署名表达，避免成员改名或停用后历史案例无故改变；
- 成员停用后，已发布案例可以保留历史署名，但不再出现在当前团队公开列表；
- 未确认的作者不得用原型中的自由文本直接公开；
- 不因案例显示“摄影师”就赋予该成员后台权限、排班资格或客户指定资格；
- 需要多人署名时，明确主次顺序或统一署名方式；
- 作者未知、匿名或工作室统一署名时，要有明确的展示规则，不显示内部账号标识。

是否允许客户查看作者详情、是否允许客户按作者筛选作品，不在本专题直接确定，需结合团队实际资料和 A05/A08 继续确认。

## 9. 公开展示、授权与撤回

### 9.1 公开资格的组合条件

案例公开资格不是一个孤立的“公开/不公开”开关，而是以下条件的组合结果：

- 案例已通过内容编辑和发布校验；
- 至少一张图片可用且允许公开展示；
- 图片、人物和案例说明没有超出授权用途与渠道；
- 公开授权仍处于有效期内；
- 案例没有被工作室主动下架或标记为不可公开；
- 关联的公开作者、业务和套餐不会造成隐私或误导。

工作室可以编辑草稿，但草稿、未发布、已下架、授权缺失、授权过期或授权撤回的案例不得进入匿名公开列表。

### 9.2 授权事实由 A15 管理

A15 负责记录和解释：

- 授权主体和其身份关系；
- 授权涉及的图片、案例或其他对象范围；
- 允许的用途、公开渠道和有效期；
- 同意证据、授予时间和经办人；
- 撤回人、撤回时间、撤回原因和处理结果；
- 儿童、孕照、家庭合影等需要额外确认的参与者或监护人关系。

A06 不把“客户没有反对”“历史页面曾展示”或“文件来自工作室”解释为公开同意。

### 9.3 授权撤回后的公开行为

公开授权撤回或失效后的处理必须以授权实际覆盖范围为准，不能把“撤回一张图片”和“撤回整个案例/人物的公开授权”混为一件事：

- **案例级或人物级授权撤回**：案例不再出现在公开列表、分类列表、首页引用和相关作品推荐中；公开详情链接返回统一的不可用或已下架提示，不显示撤回原因、客户身份或内部备注。
- **单张图片级授权撤回**：只从公开图片集合中移除该图片，并重新校验封面、顺序和案例是否仍满足公开条件；若案例仍有足够且合规的图片，可以继续公开，但后台必须提示修复或重新确认。
- **无法继续公开的情形**：案例没有剩余有效图片、封面无法替换、案例主题依赖已撤回图片，或负责人确认敏感案例不宜保留时，整个案例隐藏。
- 公开图片停止后续公开访问，并按既有公开媒体策略处理缓存、分享和搜索入口；后台保留授权和撤回审计。
- 仅撤回公开展示不等于删除客户私密交付文件；小程序交付入口到期、网盘补充交付、公开授权撤回和原文件删除是不同事件，不能混为一个状态。

当前产品建议是尊重授权粒度：单图撤回默认移除单图并重新计算案例资格，案例级撤回默认隐藏整案。儿童、孕照和家庭合影等敏感案例是否一律整案隐藏，需要负责人确认后再作为统一运营规则。

### 9.4 部分图片失去资格

一个案例中只有部分图片失去公开资格时：

- 先从公开图片集合中移除失效图片，并重新校验封面和顺序；
- 如果仍有合规图片且案例仍能准确表达主题，可以继续公开，但后台必须提示修复；
- 如果没有有效图片、封面无法替换，或案例主题无法在剩余图片中成立，整个案例隐藏；
- 任何自动保留或替换都不能使用未授权的私密交付文件；
- 对整案授权撤回，不适用“保留剩余图片”的单图处理方式。

## 10. 浏览与展示规则

### 10.1 作品列表

公开作品列表应支持：

- 查看已发布且公开资格有效的案例；
- 按作品分类浏览；
- 在有足够内容时按标签筛选；
- 显示封面、标题、摘要或必要的分类信息；
- 进入案例详情；
- 在没有内容、筛选无结果或内容正在维护时显示明确空状态；
- 不显示草稿、已下架、授权缺失或仅供私密交付的案例。

“全部”只表示所有当前有效公开案例，不等于某个业务类型或套餐分类。

### 10.2 案例详情

详情页应支持：

- 显示当前有效封面和有序图片集合；
- 浏览大图或连续图片；
- 显示标题、说明、分类和可公开标签；
- 显示经过确认的工作室或作者署名；
- 提供关联业务或套餐入口；
- 提供相关作品推荐；
- 提供返回分类或作品列表的路径；
- 在案例失效、图片不可用或加载失败时给出统一提示。

详情页不得返回客户真实姓名、联系方式、内部订单信息、授权证据、私密文件地址或未发布内容。

### 10.3 相关作品

相关作品用于帮助客户继续浏览相近风格或主题，不是自动复制首页推荐。产品建议按以下优先级生成或维护候选：

1. 工作室人工明确关联的案例；
2. 同作品分类且当前公开资格有效的案例；
3. 具有相关公开标签或业务关联的案例；
4. 没有可用候选时隐藏区块。

无论采用人工配置还是规则匹配，相关作品必须满足：

- 不能推荐当前正在查看的案例本身；
- 必须已发布且公开资格有效；
- 不能因为历史关联而继续展示已撤回、下架或授权过期的案例；
- 不应引入随机且无法解释的推荐；
- 候选全部失效时显示稳定空状态或直接隐藏，不展示占位卡片。

相关作品的最终人工配置方式和自动匹配范围待负责人确认。

### 10.4 关联业务和套餐

案例详情可以提供“了解相关业务”“查看套餐”等入口，但要明确：

- 这是信息导流，不代表客户已经选择、预约或购买；
- 关联对象已下架或不允许公开时，不显示失效入口；
- 价格和服务内容不能写死在案例文案中；
- 案例中历史拍摄内容不保证等同于当前套餐内容；
- 客户需要预约时进入 A12 规定的联系或预约路径。

## 11. 案例生命周期

### 11.1 案例状态

案例需要区分内容编辑状态和公开资格：

| 状态 | 含义 | 公开端可见 |
|---|---|---:|
| 草稿 | 正在整理或等待补充信息 | 否 |
| 待校验 | 内容已整理，等待图片、授权或关联检查 | 否 |
| 已发布 | 内容已通过发布检查且允许公开 | 是，仍需授权结果有效 |
| 已下架 | 工作室主动停止公开展示 | 否 |
| 待修复 | 已发布内容出现图片、授权或关联异常 | 默认否，直到修复并重新发布 |
| 已归档 | 历史内容保留记录但不再作为当前公开内容 | 否 |

“已发布”不等于永久公开。授权过期、授权撤回、图片失效或案例被下架后，公开资格应立即失效或进入待处理状态。

### 11.2 草稿和预览

案例编辑期间需要：

- 保存标题、说明、分类、标签、图片和关联对象的草稿；
- 在草稿不完整时保留编辑内容和错误提示；
- 预览访客看到的列表卡片、详情和图片顺序；
- 预览明确标识为预览，不被匿名访客访问；
- 在预览阶段发现缺图、无封面、无分类、失效关联、作者不可展示和授权缺失；
- 不因保存草稿或打开预览而改变公开端。

### 11.3 发布

发布前至少检查：

- 标题和必要说明完整且适合公开；
- 存在有效封面和至少一张公开图片；
- 图片顺序明确，资源可读取；
- 分类有效，标签不存在明显冲突；
- 作者署名和关联业务/套餐可以安全展示；
- 公开授权结果有效且范围覆盖当前展示内容；
- 不含客户私密信息、测试文案和内部备注。

发布成功后，公开列表、详情、相关作品和首页引用只能读取新生效的公开内容。发布失败时，应保持原来已公开的版本，不出现部分图片或部分文案已更新的不可解释状态。

### 11.4 下架与恢复

下架后：

- 公开列表、分类、详情、相关作品和首页引用均停止展示；
- 直接访问案例时返回统一不可用提示；
- 历史草稿、内容记录和审计信息保留；
- 不修改既有订单中的套餐快照；
- 不自动删除客户私密交付文件。

恢复前需要重新检查图片、授权、作者和业务关联，不能因为历史上曾经发布过就跳过当前公开校验。

## 12. 编辑、发布与权限需求

### 12.1 负责人

负责人可以：

- 新建、编辑、预览、发布、下架和恢复案例；
- 管理分类、标签、封面、图片顺序和公开说明；
- 处理授权失效、撤回、图片缺失和引用异常；
- 维护作者/贡献者公开署名；
- 关联或解除公开业务、套餐；
- 查看案例变更和公开资格相关审计。

### 12.2 管理员

管理员可以承担日常案例整理、编辑和预览。是否允许管理员直接发布、下架以及处理高敏感案例，需要结合 A10 和工作室内部职责确认。

至少需要有一个可执行发布和下架操作的角色，否则案例无法实际运营。儿童、孕照、家庭合影等敏感案例是否必须由负责人复核，待工作室确认。

### 12.3 摄影师或其他工作人员

摄影师是否可以创建案例草稿、上传候选图片或补充说明，需要由工作室确认。默认建议：

- 可以提交草稿或素材建议；
- 不能单独发布公开案例；
- 不能修改客户公开授权事实；
- 不能把私密交付文件直接设置为公开作品；
- 不能因为自己是案例作者就获得客户资料、订单或交付文件之外的权限。

### 12.4 审计要求

至少需要能够追溯：

- 案例创建、编辑、发布、下架、恢复和归档；
- 图片增加、移除、替换、排序和封面变更；
- 分类、标签和业务/套餐关联变更；
- 作者/贡献者署名变更；
- 公开资格变化和授权结果触发的隐藏；
- 首页或相关作品对案例的引用变化。

审计记录操作者、时间、动作、对象和必要的变更摘要，不向公开端暴露授权证据、内部备注、客户联系方式或永久私密文件地址。

## 13. 异常与人工兜底

### 13.1 无案例或无结果

- 没有任何公开案例时，显示可信的空状态，不显示测试作品或占位图片；
- 某分类没有有效案例时，提示暂无相关作品，并允许返回全部作品；
- 标签筛选没有结果时，清晰显示当前筛选条件和返回操作；
- 不因为历史有过案例就展示当前已下架内容。

### 13.2 图片缺失或处理失败

- 后台标记缺失、不可读取或未完成处理的图片；
- 未通过校验的图片不能进入公开发布；
- 已发布案例中图片异常时，公开端隐藏异常图片或整个案例，不能暴露本机路径；
- 如果封面异常，后台提示重新选择；
- 处理失败支持重试或人工替换，并保留必要记录。

### 13.3 授权缺失或撤回

- 授权不明确时，默认不公开；
- 授权过期或撤回后，公开列表、详情、首页和相关作品同步停止展示；
- 后台显示待处理状态和影响范围；
- 对外提示不泄露客户身份、撤回原因或内部审核信息；
- 客户私密交付文件仍由 A15 按交付授权和订单规则处理。

### 13.4 关联失效

业务、套餐、作者或分类被下架后：

- 案例不复制旧对象内容作为长期替代；
- 后台标记失效关联；
- 公开端移除不可访问的关联入口；
- 案例在其他条件满足时可以继续展示，但不应出现空链接或错误跳转；
- 工作室可以替换或移除关联。

### 13.5 详情访问失效

已下架、授权撤回、案例不存在或访客访问无权公开的案例，统一返回明确但不泄露内部原因的不可用提示。不能显示：

- 客户姓名和联系方式；
- 内部订单或拍摄记录；
- 授权证据和撤回原因；
- 本机目录、对象存储内部地址或调试堆栈；
- 仍可访问的私密交付文件。

## 14. 跨端一致性要求

小程序、官网和后台在公开案例事实上应保持一致：

- 案例标题、公开说明、分类、标签和有效公开图片一致；
- 案例发布、下架和授权有效性结果一致；
- 作者公开署名和公开业务/套餐关联不互相矛盾；
- 已撤回或已下架案例不能在某一端继续显示；
- 首页引用、作品列表和案例详情不能各自保存独立内容副本。

不同端可以有：

- 不同的案例展示数量；
- 不同的列表布局和图片裁切方式；
- 不同的摘要长度；
- 官网专用的分享标题、摘要和公开元数据；
- 小程序专用的电话、微信和后续预约入口。

不同端不得：

- 显示不同的案例标题、作者或授权状态而没有明确业务原因；
- 用私密交付图片替代公开案例图片；
- 绕过公开授权展示客户照片；
- 将作品分类直接表达为预约成功或已购买服务；
- 因首页缓存或历史链接继续展示已失效案例。

## 15. 功能需求清单

### 15.1 案例维护

- 新建、编辑、保存和复制案例草稿；
- 设置标题、说明、封面、图片集合和图片顺序；
- 设置作品分类和标签；
- 维护可公开的作者/贡献者署名；
- 关联已发布的摄影业务或套餐；
- 预览访客列表和详情效果；
- 发布、下架、恢复和归档；
- 查看案例当前公开资格及阻塞原因。

### 15.2 分类与标签

- 新建、编辑、排序、停用作品分类；
- 新建、编辑、排序、停用标签；
- 查看分类和标签下的有效案例数量；
- 没有有效案例时不在公开端显示空分类；
- 停用后保留历史关联，不破坏已保存的案例记录；
- 与业务目录和套餐分类保持概念分离。

### 15.3 公开浏览

- 公开作品列表；
- 按分类浏览；
- 按标签筛选或搜索，是否提供待负责人确认；
- 案例详情；
- 多图顺序浏览；
- 作者/工作室署名展示；
- 关联业务或套餐入口；
- 相关作品推荐；
- 无结果、加载失败、案例下架和授权撤回提示。

### 15.4 公开资格与失效处理

- 公开发布前校验图片、案例、授权、作者和关联内容；
- 授权失效或撤回后停止公开展示；
- 案例部分图片失效时提示修复并按规则隐藏失效内容；
- 首页和相关作品自动不再消费失效案例；
- 保留变更、下架、撤回影响和处理记录；
- 公开案例与私密交付文件分开处理。

## 16. 验收标准

### 16.1 案例内容与浏览

1. 工作室无需修改源码，即可创建案例、维护标题、说明、封面、图片顺序、分类和标签。
2. 一个案例可以包含一张或多张有序图片，访客看到的顺序稳定且可维护。
3. 访客可以从作品入口浏览有效案例，进入详情并查看公开图片和说明。
4. 案例详情可以展示公开分类、标签、经过确认的署名和可用的业务/套餐入口。
5. 不存在的、已下架的或已撤回公开授权的案例不会显示残缺内容或私密信息。
6. 无内容、无结果和图片异常时，有明确空状态和返回路径。

### 16.2 分类、关联与一致性

1. 作品分类、标签、摄影业务分类和套餐分类在公开含义上可区分。
2. “全部”只聚合当前有效公开案例，不作为业务分类。
3. 案例关联业务或套餐时，公开端读取对象的权威名称和状态，不复制价格或服务内容。
4. 业务、套餐、作者或分类失效后，不产生空链接、错误跳转或继续可预约的误导入口。
5. 首页、作品列表和详情页引用同一案例事实，不分别硬编码内容。
6. 首页推荐和相关作品只能消费当前有效公开案例。

### 16.3 发布、下架与授权

1. 案例支持草稿、预览、发布、下架、恢复或归档等可理解的内容状态。
2. 草稿、待校验、已下架和授权缺失的案例不会进入匿名公开端。
3. 发布前能发现无图片、无封面、失效关联、未确认署名和授权缺失等问题。
4. 发布失败时，原已发布版本保持不变，不出现部分更新。
5. 公开案例必须有明确有效的授权结果；历史页面展示不能替代授权。
6. 案例级或人物级授权撤回后，案例列表、详情、首页引用和相关作品停止公开展示；单张图片授权撤回后，该图片停止公开，并重新计算案例剩余内容的公开资格。
7. 撤回公开授权不会自动删除客户私密交付文件，也不会改变订单快照。
8. 公开授权事实、客户身份关系、首页编排和私密交付访问分别由对应专题负责，不重复建立互相冲突的规则。

### 16.4 署名与敏感信息

1. 作者或贡献者公开署名不直接等于后台账号、排班资格或客户指定资格。
2. 团队成员停用后，历史案例的已确认署名按明确规则保留或转换，不显示内部账号标识。
3. 儿童、孕照、家庭合影等敏感案例没有明确公开授权时不得展示。
4. 公开页面不返回客户真实姓名、联系方式、订单号、授权证据、内部备注或私密文件地址。
5. 无法证明图片来源、授权范围或公开用途时，案例默认不可公开。

### 16.5 公开与私密文件边界

1. 公开案例图片与客户私密交付文件在产品访问目的上明确区分。
2. 作品详情不会因为客户已支付尾款或存在交付批次而自动展示私密文件。
3. 客户交付入口、尾款门槛、带水印预览和无水印下载由 A15 负责，A06 不绕过这些条件。
4. 公开案例下架或授权撤回时，客户私密交付仍按 A15 的规则处理。

## 17. 验证方式

### 17.1 负责人访谈与资料核验

需要负责人提供并确认：

- 当前正式公开案例清单；
- 每个案例的标题、说明、分类、标签和业务/套餐关联；
- 图片是否为公开案例图片、客户私密交付图片或两者均不可公开；
- 客户公开授权的来源、范围、有效期和撤回方式；
- 儿童、孕照、亲子全家福等敏感案例的授权主体和额外要求；
- 作者/贡献者的公开称呼、署名顺序和历史成员处理方式；
- “创始人档”是作品栏目、品牌栏目还是其他经营概念；
- 相关作品推荐采用人工配置、规则匹配还是暂不提供。

### 17.2 脱敏案例验证

至少准备以下脱敏案例：

- 一组拥有完整公开授权的多图案例；
- 只有一张图片的单图案例；
- 没有公开授权但存在私密交付文件的客户案例；
- 部分图片授权撤回的案例；
- 作者已停用但历史署名需要保留的案例；
- 关联套餐已经下架的历史案例；
- 没有有效图片或封面失效的案例；
- 首页和相关作品同时引用、随后被撤回的案例。

用这些案例验证公开列表、详情、首页引用、相关作品、授权撤回和私密交付边界，而不是只验证正常的图片展示。

### 17.3 体验验证

观察潜在客户是否可以：

- 从首页找到作品入口；
- 理解作品分类与摄影业务的差别；
- 从列表进入正确的案例详情；
- 读懂图片集合、作者署名和关联服务；
- 区分“查看作品”“联系工作室”和“提交预约”；
- 在案例下架、无结果或图片异常时理解发生了什么。

观察工作室是否可以：

- 不依赖开发者维护案例和图片顺序；
- 在发布前发现无授权和失效引用；
- 处理授权撤回后产生的公开影响；
- 找到历史署名和案例变更记录；
- 不误把私密交付文件设置为公开案例。

## 18. 待确认经营内容与产品决策

以下事项仍需要工作室负责人确认：

1. 案例最小单元是“一次拍摄的一组照片”、主题作品集，还是两者都支持；一次拍摄是否允许拆成多个公开案例。
2. 当前正式作品分类是否直接采用儿童、亲子全家福、婚纱、写真、孕照、证件照，是否另有品牌栏目或风格分类。
3. “创始人档”的真实含义，以及它是否只作为作品/品牌栏目。
4. 标签是否需要公开展示、客户筛选和相关作品匹配；正式标签词表由谁维护。
5. 案例与摄影业务、套餐之间允许怎样的关联基数；历史套餐下架后案例如何展示关联说明。
6. 是否公开拍摄时间、拍摄地点、人物类型、风格和其他案例说明；哪些内容属于客户隐私。
7. 是否公开作者/摄影师姓名、公开称呼、头像、职位和案例关联；是否支持多作者和其他贡献角色。
8. 团队成员停用、离职或不再公开后，历史案例默认使用原署名、工作室署名还是匿名。
9. 是否已经取得现有历史作品的公开展示授权；没有证据的旧作品是否全部转为不可公开待确认。
10. 儿童、孕照、亲子全家福和婚纱案例是否需要负责人逐案复核或额外授权主体。
11. 部分图片撤回时，是保留其他图片继续公开，还是整个案例下架；不同业务是否有不同要求。
12. 相关作品采用人工配置、同分类匹配、同标签匹配，还是暂时隐藏。
13. 摄影师或其他工作人员是否可以提交案例草稿、上传候选图片或编辑说明；谁有最终发布和下架权。
14. 是否需要公开作品搜索；如果需要，客户可搜索标题、分类、标签还是其他公开信息。
15. 历史前端硬编码作品如何逐条核实、迁移和清理，哪些图片只能保留在工作室内部。

## 19. 后续专题输入

A06 为后续专题提供以下输入：

- A05：可被首页引用的案例条件、失效引用处理和跨端公开一致性；
- A07：案例关联摄影业务/套餐时的公开名称、版本和入口边界；
- A08：小程序作品列表、详情、图片浏览、空状态、联系和预约入口；
- A09：官网作品展示深度、公开分享信息和搜索入口；
- A10：案例上传、草稿、预览、发布、下架、授权异常和日常修复任务；
- A11：案例涉及的联系人、拍摄人、家庭成员、监护人和敏感信息边界；
- A15：公开授权事实、撤回事实、私密交付文件边界和授权结果消费方式；
- A16：作品浏览完成、信息可信度、公开内容正确率和失效案例处理指标。

## 20. 结论

当前工程已经证明 SouthLeaf 需要作品列表、分类入口、案例详情、多图展示、首页代表作品和关联服务入口，但现有实现仍以硬编码、固定详情和静态图片为主，不能作为正式作品运营能力。现有分类、作品、套餐和图片之间也存在概念混用和内容源不一致问题。

A06 确立的目标是：以作品案例为公开浏览单元，以有序图片集合表达完整作品，以作品分类和标签帮助客户理解和筛选，以可选业务/套餐关联帮助客户继续了解服务；案例只有在内容已发布、图片可用、公开授权结果有效且没有异常时才能公开展示。

公开授权的同意、证据、有效期和撤回事实由 A15 统一负责，A06 负责消费授权结果并定义案例如何从公开端消失；首页区块和推荐顺序由 A05 负责；业务与套餐事实由 A07 负责；客户身份和敏感关系由 A11 负责。公开作品案例与客户私密成片始终保持不同的业务目的和访问边界。

在负责人确认案例粒度、正式分类、历史作品授权、作者署名和部分图片撤回规则前，A06 应保持为“证据基线与目标需求稿”，不应据此直接锁定最终数据结构、接口契约或历史内容迁移结果。
