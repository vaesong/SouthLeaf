## 1. 专题目的

本专题分析 SouthLeaf 如何接收、处理和跟进摄影预约申请，以及工作室如何维护可预约日期和固定时段、确认档期、处理冲突、改期、取消和异常。

预约是客户表达拍摄意向到工作室作出排期承诺之间的业务边界。它必须明确区分：

- 客户浏览业务和套餐；
- 客户提交预约申请；
- 工作室确认预约并排他占档；
- 确认时自动生成订单；
- 订单之后的定金、履约和支付。

本文件回答：

- 客户如何选择业务、套餐、日期和固定时段并提交申请；
- 预约联系人、实际拍摄人和必要业务资料如何进入预约；
- 电话/微信预约如何由后台录入并与线上申请使用同一档期事实；
- 待确认申请是否占档、是否允许同一时段多个申请；
- 工作室确认时如何重新校验冲突并自动成单；
- 申请 48 小时失效、临时封档、定金逾期、迟到支付和档期释放如何衔接；
- 改期、取消、拒绝、补充信息和套餐版本变化如何反馈；
- 客户、负责人、管理员和摄影师分别看到和执行什么；
- 预约主路径、异常路径和验收标准如何定义。

本专题不定义数据库表、API 字段、锁、唯一索引、调度器或页面组件。预约状态、并发、事务、幂等和错误码分别引用 AT05-AT09；A12 负责预约任务、客户体验、工作室操作和业务验收。

A12 的核心判断是：

```text
预约申请是客户提出希望，不是档期承诺；
待确认申请不占硬档，同一日期和固定时段可以并行存在；
只有工作室确认动作重新校验成功，预约才成立、档期才排他占用，并在同一业务动作中生成订单；
线上、小程序、官网直提和电话/微信后台录入都必须进入同一预约事实和冲突规则。
```

## 2. 专题边界与规则归属

### 2.1 A12 拥有的需求

A12 负责以下预约与档期需求：

- 客户提交预约申请的入口、前置说明和必要信息；
- 预约联系人、实际拍摄人/参与人和套餐上下文的预约组织；
- 预约申请状态、客户可见状态和工作室处理任务；
- 日期和可配置固定时段的展示、选择和后台维护体验；
- 待确认申请不占硬档、同一时段并行申请和确认竞争结果；
- 线上预约、官网预约和电话/微信预约的统一进入规则；
- 工作室确认、拒绝、补充资料、重新确认和预约失效；
- 临时封档、档期释放、冲突、迟到支付触发的预约恢复条件；
- 改期、取消和工作室原因无法履约时的预约处理体验；
- 预约相关的通知、待办、异常和客户下一步；
- 预约记录的来源、版本、操作责任和客户可见历史；
- 预约领域的功能、场景、异常和验收标准。

### 2.3 A12 的唯一主规则

预约域必须保持以下事实关系：

```text
浏览套餐 ≠ 提交预约申请
提交预约申请 ≠ 预约成功
待确认申请 ≠ 硬占档
“可申请” ≠ 已确认可拍摄
确认预约 = 重新校验冲突 + 建立排他占档 + 自动生成订单
确认预约后才出现定金支付入口
申请失效 ≠ 订单失效
订单定金逾期失效 ≠ 预约申请被普通删除
临时封档 ≠ 自动取消已有确认预约
电话/微信预约 ≠ 可以绕过系统档期校验
改期 ≠ 覆盖原预约和历史约定
```

同一预约记录需要保存客户提交时的套餐/版本、日期、固定时段、来源和实际申请截止时间。工作室确认时重新校验当前有效业务条件，但不能静默改变客户理解的套餐、价格或服务内容；如需改变，必须重新报价并取得客户确认，或拒绝原申请后重新提交。

## 3. 已确认规则与证据口径

### 3.1 已确认预约规则

以下规则来自 A04、AT05 和 AT06，作为 A12 的业务基线：

- 客户提交具体日期和固定时间段；
- 阶段二首版使用工作室可配置的固定时段；
- 待确认申请默认 48 小时失效，实际截止时间保存到每笔申请；
- 同一日期和固定时段可以存在多个待确认申请；
- 待确认申请不占硬档；
- 工作室确认时重新校验冲突，只有一个确认动作成功占档并成单；
- 电话/微信形成的预约由后台统一录入，并与线上预约共用同一冲突源；
- 确认预约时同时完成预约确认、排他占档、订单生成和套餐/价格/服务快照；
- 临时封档不自动取消已确认预约；
- 申请拒绝、失效、冲突和需要补充资料是不同业务结果；
- 改期保留原记录并创建新修订，已付定金可按协商沿用；
- 取消需要记录发起方、原因、档期释放和后续退款处理；
- 定金支付默认 24 小时，订单定金逾期后才进入订单失效和档期释放规则；
- 迟到支付必须重新校验原时段，不能只因到账直接抢回档期。

### 3.2 证据口径

| 标记 | 含义 |
|---|---|
| 已确认需求 | 用户讨论、A04、A11 或 AT05/AT06 已明确的预约约束 |
| 原型证据 | 当前代码、页面或接口中确实出现的预约线索，只证明历史页面表达过该方向 |
| 产品建议 | 为形成可运营预约体验提出的方案，仍需工作室实际排期验证 |
| 待验证行为 | 尚无真实预约申请、冲突处理、改期和取消记录支持的判断 |
| 待确认经营内容 | 固定时段表、提前期、业务特有字段、改期次数和实际排班规则 |

当前工程没有真实预约记录、固定时段配置、档期表、冲突日志、客户申请或工作室排期材料。不能根据历史页面中的“在线预约”“日历”按钮推断预约已经可用，也不能从套餐文字推断实际可拍时间。

## 4. 当前工程证据与问题

### 4.1 只有预约占位入口

当前 `frontend/pages/about/about.vue` 存在“在线预约”按钮和日历/预约相关入口，但交互仍是“开发中，敬请期待”或占位提示。工程没有可验证的：

- 预约表单页面；
- 日期和固定时段选择；
- 预约联系人和拍摄人信息；
- 预约申请提交接口；
- 预约结果、失效或冲突页面；
- 预约列表和预约详情；
- 后台预约处理和确认成单；
- 电话/微信预约录入；
- 档期配置和封档功能。

这说明当前工程只证明产品曾经规划过在线预约，不证明任何预约状态或档期事实已经成立。

### 4.2 没有预约或档期后端能力

当前后端控制器主要覆盖分类、套餐和轮播，没有预约、固定时段、档期占用、冲突校验、客户关联或订单生成相关控制器和服务。现有套餐接口也不能提供稳定的业务版本、预约选择资格或固定时段输入。

因此，不能直接以现有页面跳转、套餐 ID 或前端日期参数作为预约事实。预约状态必须由统一业务服务产生，并由客户侧和后台重新读取。

### 4.3 当前套餐数据不能直接作为预约输入

A07 已明确当前原型中的套餐标题、价格、活动期、服务项和定金比例存在测试、错配和历史文案问题。预约申请只能引用：

- 已发布且有效的摄影业务；
- 已发布且有效的套餐版本；
- 套餐允许直接预约或明确允许咨询的选择资格；
- A07 提供的当前固定定金和服务约定。

套餐失效、版本替代、价格变更或固定定金缺失时，预约不能静默使用旧客户端缓存提交。

### 4.4 当前身份和返回路径不足

A11 已核实当前只有 token 读取雏形和测试“我的”页面，A08 已明确提交预约需要可追踪的身份关系。当前不存在：

- 提交前身份确认；
- 预约联系人绑定；
- 申请重复提交防护；
- 会话过期后的原任务恢复；
- 电话/微信预约与线上客户身份关联。

预约表单不能依赖客户端缓存的客户姓名或手机号作为归属事实。

### 4.5 当前问题结论

| 问题 | 当前表现 | 预约风险 |
|---|---|---|
| 预约仅是占位 | 只有“在线预约”按钮，无真实表单 | 客户误以为预约已支持 |
| 没有固定时段配置 | 前端无日期/时段数据，后台无维护入口 | 无法形成统一排期 |
| 没有待确认状态 | 无申请、确认、拒绝、失效结果 | 客户无法判断预约是否成立 |
| 没有冲突源 | 无档期占用、冲突校验和并发处理 | 线上线下可能重复占档 |
| 没有统一录入 | 电话/微信不进入系统预约 | 工作室日历和系统状态分裂 |
| 套餐不稳定 | 硬编码和历史定金比例混用 | 预约可能引用错误价格/服务 |
| 没有身份绑定 | 测试用户和 token 雏形 | 预约记录无法可靠归属 |
| 没有订单衔接 | 无确认成单和订单入口 | 预约、订单和支付容易混为一谈 |
| 没有改期/取消 | 无历史修订和责任处理 | 无法保留约定或处理退款 |
| 没有异常补偿 | 无失败队列和人工处理入口 | 冲突、迟到支付和封档无法安全恢复 |

## 5. 预约角色与任务地图

### 5.1 潜在客户

潜在客户在预约前需要：

- 了解业务、套餐、价格、固定定金和预约说明；
- 判断自己要预约哪类服务；
- 选择具体日期和工作室提供的固定时段；
- 知道当前是提交申请，不是成功占档；
- 知道工作室确认前不需要支付定金；
- 知道申请可能因冲突、套餐变化或服务条件被拒绝。

潜在客户不应因为查看可提交时段就被当作已预约，也不应看到其他客户申请或已占用的隐私信息。

### 5.2 预约联系人

预约联系人负责：

- 提交或确认预约资料；
- 接收工作室处理结果；
- 在需要时补充信息或重新确认套餐变化；
- 与工作室协商改期、取消和服务异常；
- 预约确认后查看对应订单。

预约联系人可以不是拍摄人。A11 规定的身份关系必须在预约记录中保持清楚。

### 5.3 工作室负责人

负责人主要负责：

- 配置可预约固定时段、服务规则和临时封档；
- 处理高风险预约冲突、工作室原因取消和异常恢复；
- 审核特殊改期、取消、订单期限延长和退款影响；
- 查看完整排期、客户资料和审计记录；
- 决定套餐变化是否允许重新报价并要求客户确认。

负责人不需要亲自处理所有普通申请，但后台必须能够将需要其介入的预约任务集中呈现。

### 5.4 管理员

管理员主要负责：

- 查看待确认申请和即将失效申请；
- 处理线上申请、补充资料和客户联系；
- 录入电话/微信预约；
- 按权限确认、拒绝、标记待补或发起改期/取消；
- 查看确认结果、订单生成和通知状态；
- 处理不涉及最终高风险财务决定的预约异常。

管理员确认预约时必须使用统一确认成单动作，不能通过修改状态字段绕过冲突校验。

### 5.5 摄影师

摄影师主要消费已确认的拍摄安排：

- 查看被分配的日期、固定时段、地点和必要客户信息；
- 不查看待确认申请和未分配客户的完整资料；
- 不确认预约、占档、释放档期或改期；
- 不能因为发现时间冲突而直接改动预约事实；
- 可以反馈排期冲突和履约风险，由负责人/管理员处理。

### 5.6 系统任务和外部身份

系统任务可以执行申请超时失效、提醒、订单定金逾期复核和档期释放，但必须按 AT08 记录任务状态、幂等关系和失败结果。系统任务不能直接把预约改成确认，也不能绕过工作人员审计。

## 6. 预约申请信息需求

### 6.1 预约前置说明

客户点击预约前，需要看到：

- 选择的摄影业务和套餐名称/版本；
- 价格、固定定金和尾款说明；
- 可选择的是具体日期和固定时段；
- 提交后等待工作室确认；
- 待确认申请不占排他档期；
- 申请默认 48 小时有效，具体截止时间以提交后记录为准；
- 确认前不支付定金；
- 套餐、日期、时段或业务条件可能需要工作室重新确认；
- 联系工作室的电话和微信入口。

文案不能使用“立即下单”“已锁定”“预约成功”等会把申请误解为确认的表达。

### 6.2 必要申请资料

预约申请至少需要：

- 摄影业务；
- 套餐版本，或明确为先咨询业务；
- 具体日期；
- 工作室提供的固定时段；
- 预约联系人及可追踪联系方式；
- 实际拍摄人或参与人数等业务确需的资料；
- 客户备注和希望工作室确认的事项；
- 来源上下文，例如案例、业务页、套餐页、官网或电话/微信。

业务特有字段由 A03、A07、A11 和真实经营资料继续确认。不得因为其他摄影平台常见做法而默认收集身份证号、精确住址、健康信息或全部家庭成员信息。

### 6.3 联系人、拍摄人和参与人

表单需要让客户理解：

- 预约联系人是谁；
- 谁是实际拍摄人；
- 是否有多名参与人；
- 哪些资料用于工作室联系，哪些用于拍摄准备；
- 预约联系人默认是后续客户业务关系和私密交付对象，但不等于所有拍摄人。

儿童、亲子全家福、婚纱和孕照等业务可能需要多人或监护人信息，但字段范围、是否必填和谁能看到必须按业务确认。

### 6.4 业务和套餐版本

客户提交时引用的套餐必须是可识别版本。客户应看到：

- 所属摄影业务；
- 套餐名称和版本上下文；
- 当前价格表达；
- 固定定金和尾款；
- 服务项目和必要限制；
- 是否可直接提交预约或需要先咨询。

预约提交不能在客户端自行复制价格或把历史活动价写入申请。服务端需要重新读取和校验当前有效套餐版本。

### 6.5 日期和固定时段

客户只能从工作室配置并对当前日期开放的固定时段中选择：

- 不能任意输入开始/结束时间伪装成固定时段；
- 时段需要有明确的开始时间和结束时间；
- 过去日期、未开放日期和后台封档日期不可提交；
- 客户看到的是可申请状态，不是最终成功承诺；
- 公开展示可申请时段不显示其他客户信息或内部原因。

首版冲突资源为同一工作室、同一日期和同一固定时段，不单独管理摄影师、场地或设备资源。后续如经营方式变化，再由相关专题扩展资源排程。

## 7. 预约状态和业务结果

### 7.1 预约状态

| 状态 | 含义 | 是否占硬档 | 客户下一步 |
|---|---|---:|---|
| 待确认 | 申请已提交，工作室尚未作出最终决定 | 否 | 查看详情、等待或联系 |
| 需要补充 | 申请资料或业务条件不足 | 否 | 补充资料或联系工作室 |
| 需要重新确认 | 套餐、价格或时段条件变化，需要客户确认 | 否 | 查看变化并确认/重新选择 |
| 已确认 | 工作室已确认、排他占档并生成订单 | 是 | 查看订单和定金截止 |
| 已拒绝 | 工作室未接受本次申请 | 否 | 重新选择或联系 |
| 已失效 | 申请超过保存的实际截止时间 | 否 | 重新提交 |
| 时段冲突 | 确认时已被其他预约先占用 | 否 | 重新选择日期/时段 |
| 已取消 | 客户或工作室按规则终止预约 | 否 | 查看原因和后续处理 |
| 已改期 | 原预约不再作为当前安排，已关联新的修订 | 由新记录决定 | 查看新修订或联系 |
| 处理中 | 系统或工作人员已接收动作但最终结果未定 | 以当前业务事实为准 | 查看状态，不重复提交 |

内部状态可以比客户侧更细，但客户侧必须能区分申请、确认、冲突、失效和取消。

### 7.2 预约状态不变量

- 只有已确认预约可以持有有效硬占档；
- 只有确认并成单后才存在对应订单；
- 待确认申请可以并行存在，不得阻塞其他申请提交；
- 申请失效不删除申请、客户或操作历史；
- 已确认预约不能被普通封档或编辑静默覆盖；
- 改期不能直接改写原日期和原时段；
- 重复确认不能创建第二个订单或第二个有效占档；
- 预约取消和订单退款是不同事实，必须分别记录。

## 8. 客户侧主路径

### 8.1 从套餐到预约申请

```text
套餐详情
  → 查看价格、固定定金、服务项和预约说明
  → 点击提交预约申请
  → 身份确认/建立可追踪联系人
  → 选择具体日期和固定时段
  → 填写联系人、拍摄人和必要需求
  → 查看提交前确认
  → 提交申请
  → 显示待确认、申请标识和实际截止时间
```

验收重点：

- 客户知道提交的是申请，不是成功预约；
- 客户知道待确认不占排他档；
- 客户知道确认前不能支付定金；
- 返回套餐、登录或网络失败后不会重复提交；
- 提交结果可以从客户中心和通知进入同一预约记录。

### 8.2 从作品或业务到预约

```text
案例详情/业务详情
  → 进入关联业务或套餐
  → 查看当前有效版本
  → 进入预约说明
  → 提交预约申请
```

案例来源只帮助客户理解风格和选择背景，不把案例图片或作品分类直接当作预约业务/套餐。关联套餐失效时，应引导客户查看当前套餐或联系工作室。

### 8.3 申请提交后的跟进

客户可以查看：

- 申请标识；
- 业务、套餐版本、日期和固定时段；
- 预约联系人和已提交的必要资料；
- 当前状态；
- 实际失效时间；
- 工作室是否需要补充或重新确认；
- 联系电话/微信和下一步。

客户不能在待确认状态下看到定金支付入口，也不能通过刷新生成新的申请或直接改成已确认。

## 9. 后台档期和预约处理

### 9.1 固定时段配置

后台需要让负责人或授权管理员维护：

- 可预约日期范围或日期规则；
- 固定时段的开始和结束时间；
- 某日期/时段是否开放提交；
- 临时封档和解除封档；
- 业务是否需要先咨询而不能直接提交；
- 可能的联系/准备说明。

具体是否支持每周重复规则、节假日批量设置、准备缓冲、清场缓冲和多资源排期仍需结合实际经营确认。首版需求只锁定固定时段和工作室整体冲突，不提前扩展复杂资源排程。

### 9.2 后台档期视图

工作室需要在日期/时段视图中区分：

- 可提交申请；
- 待确认申请数量；
- 已确认并占用；
- 临时封档；
- 已释放；
- 改期中的原时段和新时段；
- 需要人工处理的异常占用。

视图不得把待确认申请显示成排他占档，也不得因为显示“可申请”就向工作人员承诺确认一定成功。

### 9.3 线上和线下统一录入

电话/微信形成预约意向后，由后台管理员或负责人录入统一预约流程。录入需保存：

- 来源渠道；
- 联系人和身份关联状态；
- 业务/套餐版本；
- 日期和固定时段；
- 实际拍摄人/参与人；
- 客户已确认的服务内容；
- 客户备注和工作室内部备注；
- 录入人和录入时间。

线下预约不能绕过冲突校验。若工作人员希望直接确认，也必须在确认动作中重新校验时段并自动成单。

### 9.4 预约确认

确认操作前，后台需要让操作人核对：

- 客户和预约联系人身份；
- 摄影业务和套餐版本；
- 当前价格、固定定金和服务项；
- 日期和固定时段；
- 客户提交时看到的条件是否仍然有效；
- 当前是否有硬占档或封档；
- 是否需要客户重新确认变化。

确认成功必须在同一业务动作中：

1. 重新校验日期和固定时段冲突；
2. 建立排他档期占用；
3. 将申请转为已确认；
4. 自动生成唯一订单；
5. 冻结套餐、价格、服务内容、日期和时段快照；
6. 创建定金应付和实际截止时间；
7. 创建客户通知或待发送任务；
8. 记录操作者、时间、来源和审计。

确认失败时不能部分成功。若并发冲突，其他申请应收到清晰的冲突结果，而不是通用系统故障。

### 9.5 拒绝和补充资料

工作人员拒绝申请或要求补充资料时，应选择客户可理解的安全原因，例如：

- 时段无法确认；
- 套餐已变化，需要重新选择；
- 业务条件不满足；
- 缺少必要拍摄信息；
- 工作室暂不提供该时段/服务；
- 需要电话/微信进一步沟通。

不向客户展示其他客户信息、内部排班、成本、授权证据或工作人员争议备注。拒绝和补充资料都要保留内部原因、操作者和客户可见结果的区别。

## 10. 失效、封档和档期释放

### 10.1 申请 48 小时失效

待确认申请默认 48 小时失效，实际截止时间在提交时保存。后续默认配置变更不影响已提交申请。

申请失效时：

- 不创建订单；
- 不产生硬占档；
- 保留申请和客户资料历史；
- 客户看到已失效并可重新提交；
- 工作室可看到失效原因和通知结果；
- 已经处于确认、拒绝或取消的申请不能被定时任务覆盖。

申请临近失效时是否提醒以及提醒渠道由通知和运营规则继续确认。

### 10.2 临时封档

临时封档只影响尚未提交或待确认申请：

- 封档后不能产生新的确认占档；
- 已有待确认申请进入需要处理的状态，不应静默消失；
- 已确认预约不会因封档自动取消；
- 工作室无法履约时，必须联系客户并进入改期/取消/退款流程；
- 封档操作者、原因、生效时间和影响范围可追溯。

解除封档后，仍需以当前套餐、时段和冲突事实重新校验，不自动恢复已经失效的申请。

### 10.3 订单定金逾期导致档期释放

订单生成后定金默认 24 小时内支付。预约确认已完成，因此定金逾期属于订单失效和档期释放规则，不是普通预约申请失效。

释放前必须重新检查：

- 定金是否已成功支付；
- 支付是否处理中或待查单；
- 是否有待核验线下收款；
- 是否有人工延长截止时间；
- 是否已有取消、改期或其他新修订。

在支付事实未知、已成功或待核验时，不得直接释放硬档。订单失效和档期释放完成后，客户看到订单已失效，预约历史仍可追溯。

### 10.4 迟到支付与档期恢复

订单失效后收到迟到支付或迟到回调时：

- 原日期/时段仍可用：重新执行排他校验，成功后恢复订单/占档，并保留迟到处理记录；
- 原日期/时段已被占用：不自动恢复预约，支付进入退款或人工处理；
- 仅收到到账结果不能直接抢回档期；
- 客户侧显示处理中/待人工，不承诺预约恢复；
- 工作室需要看到原订单、迟到支付、时段现状和可执行补偿。

## 11. 改期与取消

### 11.1 改期

改期需要客户与工作室协商。工作室同意后：

- 客户选择新的日期和固定时段；
- 新时段先进行冲突校验和占用尝试；
- 新时段成功后再释放原时段；
- 原预约和订单快照保留；
- 创建新的修订版本；
- 已支付定金可按协商沿用；
- 新修订需要客户确认后成为当前安排；
- 通知客户原安排、新安排和资金处理结果。

改期不能先释放原档再尝试新档，否则失败时会让客户失去原安排。改期提前通知期限、次数和是否有费用仍需工作室确认。

### 11.2 客户取消

客户主动取消或因客户原因无法拍摄时：

- 记录客户发起、时间和原因；
- 释放未继续占用的档期；
- 定金原则上不退；
- 特殊退款或改期由工作室按权限人工决定；
- 已付尾款的处理由 A14 根据未交付部分和责任规则处理；
- 客户看到取消结果、资金处理状态和联系入口。

客户取消申请本身不等于退款成功。退款需经过独立的申请、审核、外部处理和结果确认。

### 11.3 工作室原因取消

工作室原因无法履约时：

- 负责人或管理员发起有原因的取消；
- 联系客户并提供改期或取消处理；
- 已收定金全额退回；
- 释放原档期；
- 保留取消、退款和通知审计；
- 客户看到明确的工作室处理结果。

不得通过临时封档、删除预约或改写客户备注来伪装成客户主动取消。

### 11.4 不可归责事件

天气、公共事件、突发健康或其他暂无法归责事件优先协商改期并沿用定金。无法改期时，由工作室按权限决定退款或其他处理，保留原因、客户沟通和审核记录。

### 11.5 预约取消与订单/退款关系

预约状态、订单状态、支付状态和退款状态分别维护：

- 取消预约不删除订单；
- 已确认预约取消需要同步处理订单和档期，但订单历史保留；
- 退款申请不等于退款成功；
- 支付事实不能被普通预约编辑覆盖；
- 客户侧需要看到当前预约、订单和资金处理的分别结果。

## 12. 异常与人工处理

### 12.1 预约冲突

确认时发现同一日期/固定时段已被其他确认动作占用：

- 当前确认动作失败，不生成订单；
- 当前申请转为冲突或安全拒绝结果；
- 原待确认申请不再占档；
- 客户知道此前“可申请”不是成功保证；
- 客户可重新选择日期/时段或联系工作室；
- 后台可查看竞争处理顺序、业务号和审计，但不显示其他客户资料。

### 12.2 套餐版本变化

申请等待确认期间套餐价格、服务项、固定定金或公开状态发生变化时：

- 不静默替换客户申请内容；
- 工作室可以按原申请条件确认（若仍允许且经营上接受）；
- 或拒绝原申请并说明需要重新选择；
- 或发起重新报价/重新确认；
- 客户确认新条件后才按新版本成单；
- 已有订单快照不受后续套餐修改影响。

### 12.3 申请重复提交

客户因网络超时、返回页面或重复点击再次提交时：

- 同一业务请求返回原申请或明确重复结果；
- 不创建多个相同申请，除非工作室明确允许客户提交多个不同时间意向；
- 后台可以识别重复、原申请和最新状态；
- 客户不因未看到结果而被引导盲目重新提交。

具体“同一客户是否允许同时申请多个不同日期/时段”仍需负责人确认，但无论如何都必须区分合理多意向与同一请求重复提交。

### 12.4 服务暂不可用

日期配置、套餐读取、身份确认或提交服务不可用时：

- 不显示预约成功；
- 保留安全的已填写资料；
- 提示稍后重试或电话/微信联系；
- 返回 request id 或安全联系编号；
- 不要求客户重复输入或重复提交；
- 服务恢复后重新读取当前有效版本和可申请时段。

### 12.5 身份和资料异常

预约联系人资料与已有客户记录冲突、客户身份已过期或无法确认关系时：

- 不自动关联到可能错误的客户；
- 不开放他人预约、订单或交付；
- 引导重新确认身份或联系工作室；
- 后台进入待匹配/人工核验；
- 记录关联尝试和处理结果。

### 12.6 通知失败

预约确认、拒绝、失效、冲突、改期和取消通知失败时：

- 预约和档期事实不回滚；
- 后台显示通知失败和可重发入口；
- 客户打开预约详情时仍能看到服务端真实状态；
- 重发通知不重复创建预约或订单；
- 通知内容区分客户可见信息和内部原因。

## 13. 通知与客户状态反馈

### 13.1 客户需要知道的事实

客户在每个预约状态下至少看到：

- 当前状态；
- 是否已经占档；
- 是否已经生成订单；
- 是否可以支付定金；
- 申请或订单截止时间；
- 工作室是否需要客户补充或确认；
- 下一步和电话/微信联系入口。

### 13.2 状态文案原则

| 业务事实 | 客户可见表达 | 不应使用的表达 |
|---|---|---|
| 已提交待处理 | 预约申请已提交，等待工作室确认 | 预约成功、已锁定 |
| 待确认不占档 | 当前尚未锁定该时间段 | 已为你保留 |
| 已确认成单 | 工作室已确认，时间段已占用，订单已生成 | 已下单但无订单 |
| 发生竞争冲突 | 该时间段在确认时已被占用 | 网络错误 |
| 申请失效 | 申请超过有效时间，请重新提交 | 预约被删除 |
| 套餐变化 | 套餐/价格需要重新确认 | 系统自动更新 |
| 订单定金逾期 | 订单已失效，原时段需要重新确认 | 预约自动取消但无解释 |
| 改期处理中 | 工作室正在处理新的日期/时段 | 已改期 |

### 13.3 预约通知范围

可能需要通知：

- 申请提交；
- 申请临近 48 小时失效；
- 补充资料或重新确认；
- 确认、拒绝、失效或时段冲突；
- 订单生成和定金截止；
- 改期申请、改期确认和新时段；
- 工作室原因取消、客户取消和退款处理；
- 定金逾期、迟到支付和人工处理结果。

通知渠道、是否支持站内记录和哪些通知必须送达仍由 A16 与实际沟通习惯确认。通知不是业务事实唯一来源。

## 14. 功能需求清单

### 14.1 客户预约

- 从业务、套餐、作品关联和联系入口进入预约说明；
- 显示套餐版本、价格、固定定金、服务项和预约前置；
- 触发身份确认并关联预约联系人；
- 选择具体日期和固定时段；
- 收集必要的联系人、拍摄人、参与人和业务资料；
- 提交前明确申请不占硬档、等待工作室确认和 48 小时有效期；
- 提交后显示申请标识、日期/时段、当前状态和实际截止时间；
- 查看补充、重新确认、已确认、拒绝、失效、冲突、取消和处理中；
- 避免重复申请、重复确认和重复通知；
- 从预约确认进入唯一对应订单。

### 14.2 工作室档期

- 配置可预约固定时段；
- 按日期和时段查看申请、占用、封档和异常；
- 临时封档和解除封档；
- 查看待确认申请竞争关系但不暴露其他客户；
- 查看已确认占档和释放历史；
- 支持预约申请失效任务和人工复核；
- 记录时段配置变更、操作者和原因。

### 14.3 后台预约处理

- 接收线上预约；
- 录入电话/微信预约并记录来源；
- 统一关联客户、业务、套餐、日期和时段；
- 补充资料、拒绝、确认、重新报价和重新确认；
- 确认前重新校验冲突；
- 确认时自动占档、生成订单和冻结快照；
- 处理申请失效、时段冲突、套餐变化和身份冲突；
- 发起改期、取消、工作室原因取消和人工异常处理；
- 查看通知、审计、request id 和相关订单。

### 14.4 改期、取消和释放

- 申请客户/工作室协商改期；
- 新时段先校验和占用，成功后释放原时段；
- 保留原预约、订单、支付和修订历史；
- 记录客户原因、工作室原因和不可归责原因；
- 处理定金沿用、退款申请和通知；
- 订单定金逾期前核验支付事实后释放档期；
- 迟到支付重新校验原时段并进入恢复/退款/人工路径。

### 14.5 权限、审计和异常

- 负责人、管理员和摄影师看到不同的预约和客户资料；
- 确认、占档、改期、取消、封档和释放需要相应权限；
- 重复请求、并发确认和任务重试幂等；
- 冲突、失效、处理中、服务异常和失败待人工分开显示；
- 记录操作者、时间、来源、原因、前后状态和通知结果；
- 不通过通用编辑框直接修改预约最终状态；
- 不暴露其他客户、内部排班和敏感资料。

## 15. 验收标准

### 15.1 申请提交

1. 客户可以从有效业务或套餐进入预约，并看到业务、套餐版本和必要前置说明。
2. 客户只能选择工作室当前提供的具体日期和固定时段，不能任意伪造开始/结束时间。
3. 提交前明确说明申请待确认、暂不占硬档、默认 48 小时失效和确认前不支付定金。
4. 提交预约需要可追踪的客户身份或预约联系人关系，但匿名浏览不被强制登录。
5. 申请提交成功显示申请标识、业务/套餐、日期/时段、待确认状态和实际截止时间。
6. 提交失败保留安全输入，并区分字段错误、身份失效、套餐失效、时段不可用和服务异常。
7. 重复点击、刷新和网络超时不会创建重复申请，或能够返回原申请结果。

### 15.2 申请处理和状态

1. 客户可以区分待确认、需要补充、需要重新确认、已确认、已拒绝、已失效、冲突、已取消、已改期和处理中。
2. 待确认申请不占硬档，同一日期和固定时段可以并行存在。
3. 工作室能够查看申请来源、实际截止时间、客户、套餐版本、日期/时段和必要备注。
4. 工作室拒绝或要求补充资料时，客户看到安全原因和明确下一步，其他客户资料不泄露。
5. 申请超过实际截止时间后不能被普通确认动作继续确认。
6. 申请失效保留历史，不创建订单、不生成硬占档且客户可以重新提交。
7. 套餐变化不会静默替换申请内容，重新报价或重新确认有客户可见结果。

### 15.3 并发确认和自动成单

1. 线上和电话/微信后台录入使用同一日期/固定时段冲突规则。
2. 确认前后台显示当前时段状态，确认动作仍会重新校验最新事实。
3. 同一日期和固定时段只有一个确认动作可以成功建立排他占档。
4. 确认成功同时产生已确认预约、有效硬占档、唯一订单和套餐/价格/服务快照。
5. 确认成功后客户能够从预约进入唯一对应订单和定金截止时间。
6. 并发冲突不会生成半个订单、重复订单或重复硬占档。
7. 重复确认请求返回既有订单和当前状态，不产生新的业务事实。
8. 竞争申请收到稳定的冲突结果，不被显示为普通网络错误。

### 15.4 档期配置、封档和释放

1. 负责人或授权管理员能够维护可配置固定时段并查看配置变更记录。
2. 待确认申请、已确认占档、临时封档和已释放时段在后台可区分。
3. 临时封档阻止新的申请确认，但不自动取消已确认预约。
4. 封档影响已确认安排时，后台提供联系客户、改期、取消、退款和通知路径。
5. 定金逾期释放档期前，系统复核成功支付、处理中、待查单和待核验线下收款状态。
6. 迟到支付不会直接抢回已经释放且被其他预约占用的时段。
7. 异常占用释放和恢复需要明确原因、权限、幂等和审计。

### 15.5 改期和取消

1. 改期创建新的修订安排，保留原预约、订单快照和支付事实。
2. 改期先校验/占用新时段，再释放原时段，失败时原安排不被破坏。
3. 已付定金沿用、补收或退款的结果有独立记录，不隐藏在预约状态中。
4. 客户原因、工作室原因和不可归责取消被分别记录和反馈。
5. 工作室原因取消时，客户能看到改期/退款处理路径，定金退款由独立退款流程确认。
6. 取消不会删除订单、支付、沟通和审计历史。
7. 客户和工作室的改期、取消操作受到当前状态和角色限制，不能反复终止同一记录。

### 15.6 身份、隐私和客户反馈

1. 客户只能查看属于自己的预约或被明确授权的记录。
2. 联系人、拍摄人和其他参与人关系在预约中可区分，不因相同手机号或家庭关系自动扩大访问。
3. 无权限、身份过期、关联待核验和服务异常有不同的客户下一步。
4. 客户不会看到其他申请人、已占档客户、内部排班、工作人员备注或冲突竞争细节。
5. 预约通知失败不回滚业务事实，客户打开预约详情仍能看到真实状态。
6. 客户完成身份确认后回到原预约任务，不因会话恢复重复提交。

### 15.7 异常、可靠性和审计

1. 预约冲突、版本过期、重复请求、支付竞争、封档影响和通知失败进入可观察处理路径。
2. 后台能够区分可重试、处理中和失败待人工，并显示业务号、request id 或 task id。
3. 高风险预约确认、封档、释放、改期和取消记录操作者、时间、原因和前后状态。
4. 人工补偿不能直接删除申请、覆盖成功占档或无审计改变客户关系。
5. 错误响应不暴露 SQL、堆栈、外部原始响应、其他客户资料或内部资源标识。
6. 重复任务、重复回调和并发确认不会产生重复订单、占档、通知或释放。

## 16. 验证方式

### 16.1 负责人和工作人员核验

需要工作室负责人和管理员确认：

- 实际提供哪些固定时段，哪些业务需要先咨询；
- 是否有每日、每周或节假日排期规则；
- 是否需要准备/清场缓冲；
- 预约申请最早可以提前多久，最晚需要提前多久；
- 48 小时申请失效是否适用于所有业务；
- 哪些业务需要人数、年龄段、孕周、地点或其他前置资料；
- 电话/微信预约由谁录入、谁确认和谁通知客户；
- 同一客户是否允许同时提交多个不同日期/时段申请；
- 管理员是否可以直接确认，哪些场景需负责人审核；
- 改期提前通知期限、次数、费用和定金沿用规则；
- 取消责任分类、工作室原因取消和不可归责处理方式；
- 临时封档如何影响待确认申请和已确认预约；
- 定金逾期、迟到支付和档期释放由谁跟进；
- 预约冲突发生时客户联系和替代时段如何提供。

### 16.2 脱敏场景验证

至少准备以下场景：

1. 匿名客户浏览套餐，不触发身份确认。
2. 客户选择有效套餐、日期和固定时段并提交待确认申请。
3. 客户重复点击提交或网络超时，系统返回原申请而不是创建多个申请。
4. 两个客户申请同一日期/固定时段，只有一个确认动作成功占档和成单。
5. 线上申请与电话/微信后台录入竞争同一时段，使用相同冲突规则。
6. 申请超过 48 小时未处理，系统失效并释放申请资格但保留历史。
7. 套餐在待确认期间调价或下架，工作室重新报价或拒绝原申请，客户不能被静默替换。
8. 临时封档后，待确认申请不能确认，已确认预约仍保留并产生人工处理待办。
9. 定金逾期任务与支付回调同时到达，未知支付不能直接释放档期。
10. 订单失效后迟到支付，原时段可用时重新占档，已被占用时进入退款/人工路径。
11. 客户申请改期，新时段冲突，原时段和原订单不被破坏。
12. 工作室原因取消已确认预约，释放档期并进入定金退款和客户通知流程。
13. 客户原因取消，预约结束但定金退款单独处理并保留审计。
14. 身份会话过期后客户回到申请，不重复提交且重新读取状态。
15. 预约联系人与实际拍摄人不同，客户和摄影师各看到必要资料。
16. 客户访问其他人的预约标识或历史链接，系统不泄露记录存在性。
17. 通知发送失败，后台重发通知但不生成重复预约或订单。
18. 管理员重复确认、封档或释放，操作返回既有结果并保持审计完整。

### 16.3 客户可用性验证

使用目标客户和工作人员观察：

- 客户是否理解“提交预约申请”不等于“预约成功”；
- 客户是否知道待确认不占硬档；
- 客户是否理解固定时段选择和可申请/已确认的区别；
- 客户能否理解定金支付要等预约确认和订单生成；
- 客户在冲突、失效、套餐变化和身份过期时能否找到下一步；
- 管理员是否能在工作台区分待确认、已确认、冲突和订单待支付；
- 工作人员是否能安全录入电话/微信预约而不绕过冲突；
- 工作人员是否能在改期时保护原档期和订单快照；
- 工作人员是否能判断哪些预约资料是必要的敏感信息；
- 客户是否将电话/微信联系误认为预约已经成立。

没有真实数据前，不设定预约转化率、平均确认时长、冲突率和改期率等目标值；这些指标由 A16 在获得实际基线后确定。

## 17. 待确认经营内容与产品决策

以下事项需要负责人和实际工作人员确认：

1. 六类摄影业务分别是否允许直接提交标准套餐预约，哪些必须电话/微信先沟通。
2. 固定时段的正式名称、开始/结束时间和适用业务。
3. 是否需要准备、清场、化妆或交通缓冲，缓冲是否影响客户可选时段。
4. 客户可以提前多长时间预约，最晚需要提前多久提交。
5. 是否允许节假日、周末和特殊日期使用不同固定时段。
6. 申请默认 48 小时是否适用于所有业务，是否存在更短或更长的业务例外。
7. 申请临近失效是否通知，提醒发送给谁、通过什么渠道。
8. 同一客户是否允许同时存在多个待确认申请，是否限制相同日期/时段重复申请。
9. 电话/微信预约是否直接确认，还是统一先进入待确认后再由工作人员确认。
10. 管理员和负责人在确认、拒绝、封档、改期、取消和释放方面的权限差异。
11. 预约联系人、拍摄人、参与人、监护人和付款人的关系如何记录。
12. 儿童、亲子全家福、婚纱、孕照和证件照分别需要哪些预约前置资料。
13. 套餐在待确认期间变化时，工作室采用按旧版本确认、重新报价还是拒绝重提。
14. 改期提前通知期限、可改期次数、费用和定金沿用规则。
15. 客户原因、工作室原因和不可归责事件的取消处理和客户沟通方式。
16. 临时封档是否允许负责人对个别已确认预约设置人工例外。
17. 定金逾期释放档期的复核责任和人工延长条件。
18. 迟到支付但原时段仍可用时是否允许自动恢复，哪些情况必须负责人审核。
19. 冲突后工作室是否主动提供替代日期/时段，替代信息如何通知。
20. 官网最终采用直接预约还是统一引导小程序，若直提如何保证统一预约记录。
21. 客户是否可以在提交后修改、撤回或补充申请，修改时是否重新计算有效期。
22. 预约通知哪些必须送达、哪些只需在业务详情中可查。
23. 是否需要客户从预约详情直接进入订单、联系工作室和重新预约。
24. 预约数据、客户沟通、冲突和改期记录的保留期限及导出需求。

- A13：确认预约自动生成订单、订单快照、定金截止、改期修订和履约衔接；
- A14：定金逾期、迟到支付、取消责任、退款和线下收款处理；

- A16：预约提交、确认时效、冲突、失效、改期和客户支持负担的衡量方向；
- AT05：固定时段、申请不占档、确认占档、并发申请、线下统一录入、封档和改期规则；
- AT06：预约、档期占用和订单状态机及不变量；
- AT07：客户/负责人/管理员/摄影师的预约访问和操作边界；
- AT08：确认成单、释放、改期、定金逾期和重复请求的事务、并发、幂等与补偿；
- AT09：预约冲突、版本失效、状态非法、身份失效和服务异常的稳定错误语义。

## 19. 结论

当前工程只有预约占位按钮，没有预约表单、固定时段、档期事实、后台录入、冲突校验或确认成单能力。A12 以已确认业务规则为准，建立预约域的完整目标：

```text
客户可以在理解服务条件后选择具体日期和固定时段提交申请；
申请有可追踪联系人、实际截止时间和清晰待确认状态；
待确认申请不占硬档，同一时段可以并行申请；
线上、官网和电话/微信预约进入同一日期/固定时段冲突源；
工作室确认时重新校验，成功后同时确认、排他占档、生成订单并冻结快照；
套餐变化、封档、申请失效、冲突、改期、取消和迟到支付都有独立结果；
客户、负责人、管理员和摄影师只执行与身份和职责相符的动作；
预约异常可以重试、转人工和审计，不通过直接编辑覆盖历史事实。
```

A12 不定义数据库、API、锁或页面组件，而是为 A13 订单与履约、A14 支付退款和 A15 交付授权提供预约事实、客户关系、时间段和异常边界。固定时段表、业务特有字段、改期参数和实际运营排期仍需工作室负责人确认，确认前不应锁定最终技术模型。
