## 1. 专题目的

本专题分析 SouthLeaf 如何识别客户、建立客户资料、关联预约和订单、区分预约联系人与实际拍摄人、控制私密成片访问，并在电话/微信线下沟通、家庭多人参与、资料变更和权限异常时保护客户隐私。

身份在本产品中不是一个简单的“登录/未登录”开关。不同任务需要不同程度的身份可信度：

- 匿名访客只需要浏览公开品牌、作品、业务、套餐和联系方式；
- 提交预约时，需要建立可追踪的预约联系人身份；
- 查看自己的预约、订单和支付时，需要确认当前账号与业务记录的关系；
- 访问私密成片时，还需要满足交付授权、订单归属、尾款和入口期限；
- 后台工作人员还需要受角色、资源归属、业务状态和敏感数据范围共同限制。

本文件回答：

- 客户侧和工作室侧分别有哪些身份；
- 预约联系人、实际拍摄人、被授权交付人和家庭成员如何区分；
- 浏览、提交预约、查看业务记录、支付和访问成片分别需要什么身份条件；
- 电话/微信预约如何与线上客户身份关联；
- 客户更换手机号、多人共用联系方式、重复建档或身份不匹配时如何处理；
- 儿童、亲子全家福和孕照等业务需要怎样收集最小必要资料和监护/授权信息；
- 后台负责人、管理员和摄影师可以看到哪些资料；
- 客户资料如何更正、合并、撤销访问、保留、导出或删除；
- 当前工程存在什么身份和隐私风险，以及如何验收。

本专题不锁定手机号、微信身份、短信验证码或其他认证技术，不定义数据库字段、API、加密方案、存储厂商、后台组件或实施阶段。A11 负责身份关系、资料边界、隐私体验和业务归属；具体认证技术和接口契约由后续详细设计结合 AT07-AT09 确认。

A11 的核心判断是：

```text
身份不是客户资料本身，登录也不自动等于有权访问所有业务；
客户资料、业务关系、交付授权和工作人员角色必须分别判断；
预约联系人可以与实际拍摄人不同，预约联系人默认拥有交付访问资格，其他家庭成员必须显式授权；
公开浏览不要求建立客户档案，私密业务操作必须使用可追踪、可撤销、可审计的身份关系。
```

## 2. 专题边界与规则归属

### 2.1 A11 拥有的需求

A11 负责以下身份、客户资料与隐私需求：

- 客户、预约联系人、实际拍摄人、被授权交付人和家庭成员的关系定义；
- 匿名浏览与需要身份识别的客户任务边界；
- 客户身份与预约、订单、支付、履约和交付记录的归属关系；
- 电话/微信线下客户与线上身份的关联、核验和冲突处理；
- 客户资料的最小收集、用途、展示、修改和敏感范围；
- 儿童、家庭多人和孕照等业务中必要的参与人/监护人信息边界；
- 客户侧、工作室负责人、管理员和摄影师的资料可见性体验；
- 私密交付的默认联系人授权、家庭成员显式授权和授权撤销入口；
- 身份失效、资料冲突、账号更换、重复客户和无权限访问的反馈；
- 客户资料更正、导出、注销、删除和保留策略的产品要求；
- 身份、隐私和资料访问相关的审计与客户可理解反馈；
- 身份和隐私场景的验收与可用性验证。

### 2.2 A11 只引用、不拥有的需求

| 对象或规则 | 主归属 | A11 允许做什么 | A11 不得定义什么 |
|---|---|---|---|
| 公开品牌、作品和套餐 | A05-A07 | 规定公开内容不能携带客户隐私，并提供公开/私密分界 | 品牌、作品、套餐和公开内容事实 |
| 小程序客户体验 | A08 | 定义身份触发点、返回路径和无权限反馈的身份依据 | 小程序页面架构和全部状态文案 |
| 官网体验 | A09 | 规定公开官网不展示客户记录和私密文件 | 官网 SEO、页面结构和预约技术方案 |
| 预约与档期 | A12 | 提供预约联系人、参与人和身份校验输入 | 日期、固定时段、冲突、占档和预约状态转换 |
| 订单与履约 | A13 | 提供订单归属、客户关系和最小履约资料边界 | 订单生成、快照、履约状态和修订规则 |
| 支付、退款与售后 | A14 | 规定支付和退款摘要只向有权客户/工作人员展示 | 金额计算、支付事实、退款责任和对账规则 |
| 成片交付与公开授权 | A15 | 提供交付授权对象、私密/公开边界和撤回影响 | 文件批次、访问门槛、上传校验、公开授权事实主规则 |
| 后台角色和资源权限 | AT07 | 将客户关系和资料敏感范围转为可理解的身份判断 | 负责人/管理员/摄影师最终权限模型和接口授权实现 |
| 事务、幂等和补偿 | AT08 | 规定身份变更、授权变更和资料关联不能产生重复或无审计事实 | 事务、锁、唯一约束和幂等键的技术实现 |
| 错误码与外部身份 | AT09 | 消费认证失效、无权限、资源不可见和外部服务错误结果 | 认证供应商字段、签名和外部协议细节 |

### 2.3 A11 的唯一主规则

客户业务记录的访问必须同时满足身份、关系、状态和用途条件：

```text
匿名浏览公开内容 ≠ 已建立客户档案
提交预约申请 ≠ 已确认预约联系人拥有全部业务访问权
登录成功 ≠ 自动访问所有预约、订单或成片
预约联系人 ≠ 实际拍摄人
实际拍摄人 ≠ 自动拥有交付下载权
同一家庭/同一手机号 ≠ 自动拥有其他人的业务记录
支付成功 ≠ 自动获得公开案例授权
被授权访问成片 ≠ 被授权查看支付凭证或后台备注
客户资料变更 ≠ 既有订单快照和历史审计被回写
```

默认规则如下：

- 匿名客户可以浏览公开内容和联系工作室，不因浏览创建客户档案；
- 提交预约时建立可追踪的预约联系人关系；
- 预约联系人、实际拍摄人和其他参与人可以不同；
- 私密成片默认授权预约联系人，其他家庭成员由后台显式添加；
- 客户身份变更、合并、拆分和授权变更不能通过普通编辑静默完成；
- 无权限反馈不能泄露目标预约、订单、客户姓名、金额或文件是否存在。

## 3. 证据口径

| 标记 | 含义 |
|---|---|
| 已确认需求 | 已由用户讨论、A01-A10 或架构基线明确的身份和隐私约束 |
| 原型证据 | 当前代码、页面、接口或资源中确实存在的内容，只能证明历史原型表达过该方向 |
| 产品建议 | 为形成可运营、可保护隐私的身份体验提出的候选方案，仍需负责人和实际客户验证 |
| 待验证行为 | 尚无真实客户登录、账号变更、家庭成员访问或客户支持记录支持的判断 |
| 待确认经营内容 | 工作室需要提供的身份关联方式、客户资料字段、授权证据和保留要求 |

当前仓库没有真实客户账号、预约联系人记录、身份认证记录、客户资料变更日志、家庭成员授权记录、隐私投诉或交付访问日志。因此，本文可以确立关系和隐私边界，但不能把认证方式、资料字段完整清单、账号复用规则、保留期限或客户更偏好的身份流程当作已验证事实。

## 4. 当前工程证据与问题

### 4.1 请求层只有 token 读取雏形

`frontend/api/api.js` 当前存在：

- 从本地存储读取名为 `token` 的值；
- 请求时附带 `Authorization: Bearer ...`；
- 未授权时显示“未授权，请登录后重试”；
- 权限不足时显示“权限不足”。

但当前工程没有证据证明：

- token 如何签发、刷新、撤销和绑定客户；
- token 对应客户、后台工作人员还是其他身份；
- 客户身份是否与微信身份、手机号或线下联系人关联；
- 会话过期后如何回到原任务；
- 一个身份能看到哪些预约、订单、支付和交付；
- 认证成功后是否存在资源归属和授权校验。

请求层仍用数字 `code === 200` 判断成功，没有完整消费 AT09 的 `UNAUTHENTICATED`、`CUSTOMER_SESSION_EXPIRED`、`RESOURCE_ACCESS_DENIED` 等稳定业务语义。认证失败、资源无权和服务异常不能继续用同一个 Toast 表达。

### 4.2 “我的”页面使用测试身份

`frontend/pages/my/my.vue` 当前直接显示：

```text
momo
01234567891
```

页面还展示未付款、进行中、已完成、全部订单、我的相册、喜欢、积分、优惠券和会员卡等入口，但点击后统一提示“开发中”。当前页面没有：

- 匿名与已识别客户的不同状态；
- 登录或身份确认流程；
- 预约联系人资料；
- 订单归属和客户记录过滤；
- 私密交付授权判断；
- 身份失效、账号更换和无权限反馈；
- 已确认的喜欢、积分、优惠券或会员卡业务规则。

测试姓名和手机号不能出现在正式客户中心，也不能被当作客户身份模型的证据。未识别客户进入“我的”时，应看到身份确认和公开联系入口，而不是测试资料或虚构订单数量。

### 4.3 当前没有客户、身份和后台资料模型证据

当前后端原型主要包含分类、套餐、轮播等公开内容接口，没有可验证的：

- 客户档案和客户身份；
- 手机号/微信身份绑定；
- 预约联系人与拍摄人关系；
- 家庭成员或授权访问人；
- 客户资料变更和合并记录；
- 客户业务记录归属查询；
- 负责人/管理员/摄影师的敏感资料分级；
- 访问审计和隐私操作日志。

因此，当前工程只能证明“未来需要身份和客户资料能力”，不能证明客户登录或后台客户管理已经实现。

### 4.4 业务页面存在公开与私密混淆风险

当前客户侧原型把“我的相册”与订单状态入口放在同一页面，但没有定义：

- “相册”是公开作品、私密交付还是收藏；
- 谁能进入；
- 订单、尾款、发布和授权之间的关系；
- 预约联系人与家庭成员的访问差异；
- 客户公开案例授权和私密成片访问是否独立。

根据 A04、A08、A10 和 AT07，公开作品/案例与私密交付必须分开；客户只有在身份、订单归属、尾款、交付发布、授权和入口期限均满足时才能访问私密交付。

### 4.5 原型联系方式不能作为身份关联事实

关于页、Footer 和其他页面存在电话、微信、地址不一致的问题。电话和微信是公开联系入口，但：

- 客户拨打电话不代表已经建立线上身份；
- 客户添加微信不代表系统已确认预约联系人；
- 后台录入电话/微信预约后，需要经过身份匹配或客户确认才能关联线上记录；
- 公开微信号、二维码和客户身份凭证不能混为一谈。

线下沟通记录需要统一进入业务系统，但不能因为联系方式相同就自动把两个不同的人合并成一个客户。

### 4.6 当前问题结论

| 问题 | 当前表现 | 身份与隐私风险 |
|---|---|---|
| 没有正式认证流程 | 只有 token 读取和通用未授权提示 | 无法证明客户是谁和会话是否有效 |
| 使用测试用户 | “我的”页硬编码姓名和手机号 | 可能泄露假资料或误导客户 |
| 没有客户档案 | 后端无客户身份和业务关联能力 | 预约、订单和交付无法可靠归属 |
| 没有关系模型 | 未区分联系人、拍摄人和授权家庭成员 | 访问权限容易按手机号或家庭关系错误推断 |
| 公开/私密混淆 | “我的相册”没有正式含义 | 公开案例和客户成片可能混用 |
| 线下身份未关联 | 电话/微信只作为页面联系方式 | 线下预约可能无法安全回到客户记录 |
| 错误语义过粗 | 401/403 只显示通用 Toast | 无法区分会话失效和资源无权 |
| 没有资料变更审计 | 没有客户手机号、姓名和授权变更记录 | 争议时无法还原谁修改了什么 |
| 没有敏感范围 | 后台尚未实现角色或字段脱敏 | 摄影师和管理员可能看到不必要资料 |
| 没有隐私生命周期 | 未见保留、注销、删除或导出规则 | 资料长期滞留且无法响应客户请求 |

## 5. 身份与关系模型

### 5.1 匿名访客

匿名访客尚未提交业务申请，也没有需要访问的个人记录。匿名访客可以：

- 浏览已发布品牌、作品、摄影业务和套餐；
- 查看电话、微信、地址、地图和公开服务流程；
- 了解预约说明并决定是否提交申请；
- 从官网进入小程序或从公开页面进入身份确认前的预约说明。

匿名访客不应：

- 查看或推断任何客户档案；
- 查看预约、订单、支付、退款、履约或交付；
- 因浏览或点击联系自动创建客户档案；
- 通过猜测手机号、订单号、文件链接或历史分享访问私密内容。

### 5.2 客户身份

客户身份表示系统能够将一次或多次业务记录关联到某个可识别主体。客户身份的具体认证方式仍需确认，但产品上至少需要区分：

- 身份凭证：例如手机号、微信身份或其他经过确认的入口；
- 客户资料：姓名/称呼、联系方式和必要业务信息；
- 业务关系：作为预约联系人、拍摄人或授权访问人参与的记录；
- 授权关系：可以访问哪些交付内容以及期限；
- 身份状态：有效、待确认、失效、被撤销或需要人工核验。

认证成功只能证明当前会话与某种身份凭证关联，不应单独推导其可以访问所有同手机号、同家庭或同设备下的业务。

### 5.3 预约联系人

预约联系人是提交预约申请或由工作室录入预约时承担沟通责任的人。预约联系人通常负责：

- 提供预约日期和固定时段；
- 接收工作室确认、拒绝、改期和异常通知；
- 核对预约和订单约定；
- 支付定金和尾款，或确认线下收款；
- 在满足交付条件后作为默认私密交付授权对象。

预约联系人可以不是实际拍摄人。例如家长为儿童预约、家庭成员为全家福预约、伴侣为孕照预约或一人代另一人沟通。系统不能把预约联系人姓名自动写成所有拍摄人的姓名，也不能因联系人不是拍摄人就否定其业务沟通关系。

### 5.4 实际拍摄人和参与人

实际拍摄人是服务履约中被拍摄的个人或家庭成员。参与人可以有多人，尤其涉及亲子全家福、儿童、婚纱和孕照等业务。

后台和客户侧只收集完成当前业务所必需的信息。需要进一步确认：

- 是否需要记录每位参与人的姓名或称呼；
- 是否需要记录年龄段、孕周或其他业务前置资料；
- 是否允许客户自行补充所有参与人；
- 哪些信息只供工作室履约使用；
- 哪些信息应从客户可见订单中隐藏。

在没有业务必要性前，不应因为“客户画像”或营销需要收集与拍摄无关的敏感资料。

### 5.5 被授权交付人和家庭成员

被授权交付人是经过工作室明确授权，可以访问某个订单交付的身份。首版规则为：

- 预约联系人默认具备交付访问资格；
- 其他家庭成员不因同一家庭、同一手机号、同一地址或共同拍摄自动获得权限；
- 其他家庭成员由后台显式添加；
- 授权需要记录对象、交付范围、有效期、授权人、操作者和变更原因；
- 授权撤销只影响相应交付访问，不自动改变订单、支付或公开案例授权；
- 被授权交付人不能因此获得支付凭证、后台备注或其他客户订单。

客户侧首版不直接开放自由邀请家庭成员，除非后续验证身份强度、授权确认和撤销流程足够安全。

### 5.6 工作室工作人员

工作人员身份与客户身份完全分开：

- 负责人拥有高风险经营和敏感资料处理权限；
- 管理员按日常运营职责访问客户和订单；
- 摄影师只访问被分配安排和完成履约所需的最小资料；
- 支付回调、系统任务和对象存储服务身份不等于人工员工。

工作人员即使登录成功，也必须通过角色、资源归属、当前状态和敏感范围判断能否访问具体客户记录。

### 5.7 关系矩阵

| 关系 | 形成方式 | 默认可见/可操作范围 | 不能自动推出的权限 |
|---|---|---|---|
| 匿名访客 | 未建立业务身份 | 公开内容、公开联系方式 | 任何客户记录和私密文件 |
| 预约联系人 | 提交预约或后台录入并确认 | 自己的预约，确认后对应订单；满足条件时默认交付 | 其他家庭成员记录、后台审计 |
| 实际拍摄人 | 在预约/订单中被记录 | 由业务需要决定的必要拍摄信息 | 自动查看订单、支付和下载 |
| 被授权家庭成员 | 工作室显式授权 | 指定订单交付范围 | 其他订单、支付凭证和后台备注 |
| 摄影师 | 后台分配履约资源 | 被分配安排和最小履约资料 | 客户财务、其他订单、发布和授权 |
| 管理员 | 后台员工角色 | 日常运营范围内的客户和业务资料 | 默认最终退款、公开授权和完整审计 |
| 负责人 | 后台高风险角色 | 工作室范围内必要的完整资料和审核 | 不因权限而跳过业务授权事实 |

## 6. 身份触发与客户任务

### 6.1 不需要身份识别的任务

以下任务原则上允许匿名完成：

- 查看首页、品牌、团队、服务流程和 FAQ；
- 浏览作品分类、案例详情和公开图片；
- 查看六类摄影业务和已发布套餐；
- 查看固定定金说明、预约须知和联系方式；
- 拨打电话、复制微信信息、查看地址和地图；
- 阅读进入预约前的说明。

公开浏览不应创建客户档案、设置客户姓名或写入身份凭证。若产品为了统计访问而生成技术日志，也不能把匿名访问日志当作客户业务身份。

### 6.2 需要建立或确认身份的任务

以下任务需要客户建立可追踪的身份关系：

- 提交预约申请；
- 查看自己的预约和处理结果；
- 补充预约资料或重新确认套餐版本；
- 查看订单、支付和退款摘要；
- 发起定金或尾款支付；
- 查看履约进度和工作室要求；
- 查看或下载私密成片；
- 处理与本人相关的取消、改期或售后申请。

身份方式可以由手机号、微信身份、短信验证码或其他方案实现，但客户完成身份确认后必须回到原任务，不能被无条件送回首页。

### 6.3 身份强度与业务动作

| 任务 | 最低身份要求 | 还需满足的关系/状态 |
|---|---|---|
| 浏览公开内容 | 无需客户身份 | 内容已发布且公开资格有效 |
| 提交预约 | 可追踪的预约联系人身份 | 套餐、日期和固定时段可提交 |
| 查看待确认预约 | 当前身份与预约联系人关系匹配 | 预约仍可见且未被隐私限制 |
| 查看订单 | 当前身份与联系人/授权关系匹配 | 订单对当前身份可见 |
| 发起支付 | 客户身份已确认 | 对应分期待支付、金额固定且订单有效 |
| 查看履约状态 | 客户身份与订单关系匹配 | 只展示客户可见状态 |
| 预览/下载成片 | 身份有效且被授权 | 订单归属、尾款、发布、期限和授权均满足 |
| 添加家庭成员 | 首版由后台执行 | 负责人/管理员权限和明确业务原因 |
| 查看后台资料 | 工作人员身份有效 | 角色、资源、状态和敏感范围均允许 |

### 6.4 会话过期和身份切换

客户在预约、订单、支付或交付页面会话过期时：

1. 保留不敏感的业务上下文，例如来源套餐、返回路径和当前任务类型；
2. 说明需要重新确认身份，不直接显示旧页面中的敏感资料；
3. 身份确认成功后重新读取服务端状态并返回原任务；
4. 身份确认失败、取消或切换账号时，返回安全版本或公开页面；
5. 不因恢复页面重复提交预约、重复支付、重复下载授权或改变订单状态。

客户主动切换账号时，需要明确提示当前账号将不再看到前一账号的业务记录。不能把设备缓存、浏览历史或页面快照当作新账号的授权依据。

## 7. 客户资料收集与可见性

### 7.1 最小必要原则

客户资料只为明确业务目的收集和使用：

- 预约联系：联系称呼、可用联系方式和必要沟通偏好；
- 预约判断：日期、固定时段、业务/套餐和该业务确实需要的需求信息；
- 拍摄履约：参与人数、拍摄对象和必要准备信息；
- 订单执行：地址、地点、服务约定和付款/联系信息；
- 交付访问：预约联系人、显式授权人和必要身份凭证；
- 公开案例：客户明确同意的公开授权范围和有效期。

产品默认不收集与业务无关的身份证件、精确住址、健康信息、家庭关系证明或营销画像。某类业务确实需要额外资料时，应在预约前说明用途、必要性、可见范围和不提供资料的后果。

### 7.2 资料分类

| 资料类别 | 示例 | 主要用途 | 默认敏感范围 |
|---|---|---|---|
| 身份凭证 | 手机号、微信身份或其他已确认凭证 | 识别客户和找回业务记录 | 客户本人、负责人、受限管理员 |
| 基础资料 | 称呼、姓名、头像、联系方式 | 沟通和订单展示 | 客户本人、业务相关工作人员 |
| 预约资料 | 业务、套餐、日期、时段、备注 | 处理预约 | 客户本人、负责人、管理员 |
| 拍摄资料 | 参与人、人数、年龄段、孕周等必要信息 | 履约准备 | 负责人、管理员、被分配摄影师的最小范围 |
| 财务摘要 | 应付、已付、退款和核验结果 | 订单和对账 | 客户本人、负责人、财务相关管理员 |
| 支付凭证 | 外部流水、截图、线下凭证 | 核验和争议处理 | 负责人和受限授权人员，脱敏展示 |
| 履约资料 | 到场、缺席、补拍、异常和内部备注 | 服务执行 | 客户可见投影、相关工作人员 |
| 私密文件资料 | 成片、文件范围、访问记录 | 交付和授权 | 明确授权客户、负责人、必要工作人员 |
| 公开授权资料 | 同意范围、对象、时间和撤回 | 公开案例资格 | 负责人、授权工作人员；公开端不展示证据 |
| 审计资料 | 操作者、时间、原因、前后状态 | 追责和排障 | 负责人和受限审计角色 |

### 7.3 客户侧可见范围

客户侧只显示与自身业务有关且适合客户理解的内容：

- 自己作为预约联系人或被授权人有权查看的预约、订单和交付；
- 订单中的客户可见套餐、价格、日期、固定时段和服务进度；
- 支付分期和安全摘要，不展示完整支付渠道凭证；
- 成片访问状态、范围和期限，不展示对象存储地址；
- 工作室对客户的公开说明和下一步行动。

客户侧不显示：

- 其他客户姓名、联系方式、订单、档期或文件；
- 工作室内部备注、成本、人员权限、审计意见和授权证据原件；
- 数据库字段、外部平台原始响应、永久文件地址和服务器路径；
- 其他家庭成员未授权的业务记录。

### 7.4 后台工作人员可见范围

| 工作人员 | 默认可见资料 | 限制 |
|---|---|---|
| 负责人 | 经营所需完整客户、订单、支付、授权和审计资料 | 仍需遵守最小必要和业务授权，不得随意公开 |
| 管理员 | 日常预约、客户联系、订单、履约和必要支付摘要 | 敏感凭证、最终退款、完整审计和授权变更按配置限制 |
| 摄影师 | 被分配拍摄的最小客户和履约资料 | 不看其他客户、完整财务、支付凭证、授权证据和审计 |
| 系统任务 | 执行任务所需的最小业务标识和状态 | 不通过任务身份扩大客户或文件访问范围 |
| 支付回调 | 外部支付校验和对应订单/分期标识 | 不读取无关客户资料，不代替人工授权 |

### 7.5 内部备注与客户可见信息分离

后台应将客户可见信息与内部备注明确区分：

- 客户可见：拍摄日期、固定时段、地点、准备事项、服务约定和下一步；
- 内部备注：沟通摘要、人员安排、风险提醒、成本、授权审核意见和异常排查；
- 客户可见通知不能直接引用内部备注；
- 摄影师记录的履约备注不能自动全部显示给客户；
- 内部备注中的客户敏感信息不能被公开端、通知摘要或分享卡片带出。

## 8. 线下客户与线上身份关联

### 8.1 电话/微信联系不自动完成身份绑定

电话和微信是基础联系渠道，但联系动作本身不代表：

- 客户已经提交预约；
- 客户已经确认预约联系人身份；
- 当前微信账号与某个手机号或客户档案属于同一人；
- 客户可以查看订单或成片。

工作人员需要在后台记录线下来源和关联依据。客户要在小程序查看记录或支付时，应通过受支持的身份确认方式完成关联。

### 8.2 后台录入线下预约

后台录入电话/微信预约时，至少需要记录：

- 线下来源渠道；
- 联系人称呼和联系方式；
- 是否已由客户确认将该联系方式作为预约联系人；
- 摄影业务、套餐版本、日期和固定时段；
- 实际拍摄人/参与人是否与联系人不同；
- 客户备注、工作室承诺和待补资料；
- 录入人、时间和后续身份关联状态。

线下记录在客户尚未完成线上身份确认前，可以由工作室跟进，但不能默认开放给任意登录客户。客户通过小程序请求查看时，需要提供安全的匹配或确认流程，失败时不泄露后台记录是否存在。

### 8.3 关联、合并和拆分

两个客户资料是否属于同一人不能只依据一个手机号、姓名、微信号或地址自动决定。后台应区分：

- 待匹配：存在可能关系，需要人工核验；
- 已确认关联：客户完成必要确认或负责人按证据处理；
- 不匹配：明确属于不同主体；
- 关联争议：客户或工作人员提出异议，暂停敏感访问；
- 合并/拆分待处理：需要保留原记录和操作原因。

合并客户资料时：

- 保留原业务记录、支付事实和审计；
- 不把两个不同客户的交付权限合并扩大；
- 不覆盖历史订单中的联系人快照；
- 记录操作者、依据、时间和影响范围；
- 对可能涉及支付和交付的关联至少需要负责人或受限管理员处理。

拆分或纠正关联时：

- 先冻结有争议的敏感访问；
- 重新确认预约、订单和交付的归属；
- 不删除原始审计和支付事实；
- 通知受影响客户并提供联系工作室路径。

### 8.4 客户更换联系方式

客户更换手机号、微信身份或主要联系渠道时，不能仅通过修改一个字段把全部历史记录无条件转移。产品需要支持：

- 新联系方式的确认；
- 旧身份与新身份的关联依据；
- 既有预约/订单是否继续由新身份查看；
- 私密交付授权是否需要重新确认；
- 原联系方式是否保留为历史联系记录；
- 变更时间、操作者和客户确认记录。

在身份变更未完成核验前，客户可以通过工作室人工处理当前业务，但不应自动获得更大范围的私密文件访问。

## 9. 特殊参与人和敏感场景

### 9.1 儿童摄影

儿童摄影可能由家长或监护人预约，预约联系人、监护人和实际拍摄对象可能不是同一人。需求上需要明确：

- 谁可以提交和修改预约；
- 谁接收订单、支付和交付通知；
- 是否需要记录监护关系或监护人确认；
- 公开案例授权应由谁明确同意；
- 儿童姓名、年龄或其他信息是否需要在客户侧隐藏；
- 其他家庭成员是否需要显式授权才能访问成片。

在负责人确认前，系统不能仅因“家长”“同一家庭”或共同手机号自动扩大儿童成片访问或公开授权范围。儿童业务的客户资料应采用最小必要信息，公开端不得出现可识别儿童的业务记录。

### 9.2 亲子全家福

亲子全家福可能包含多名成人和儿童。后台需要能够区分：

- 预约联系人；
- 代表家庭沟通的人；
- 实际参与拍摄的人；
- 允许访问交付的人；
- 同意公开案例的人及其授权范围。

一名家庭成员提交预约，不代表所有参与人都同意公开展示，也不代表所有成员都可以下载全部成片。公开案例授权和私密交付授权需要分别确认。

### 9.3 孕照

孕照可能需要提前收集孕周、陪同人员或拍摄注意事项，但这些信息是否必要、谁能查看、保存多久必须由工作室和实际流程确认。默认要求：

- 只收集完成预约和安全沟通所需的最小信息；
- 不将健康或孕期信息用于公开展示、营销或无关统计；
- 摄影师只看到完成拍摄所需的必要提示；
- 内部敏感备注不得出现在客户通知或公开案例描述中；
- 公开授权不能因为客户提交过业务资料而自动成立。

### 9.4 婚纱和多人参与业务

婚纱等多人参与业务可能由一方联系人提交预约，但订单、付款、拍摄和交付可能涉及另一方。后台需要明确：

- 谁是订单联系人；
- 谁可以确认订单变更；
- 谁可以访问交付；
- 是否允许添加另一方为授权访问人；
- 公开案例授权是否需要双方或全部必要主体同意。

在关系和授权未确认前，不能因姓名相似、同一电话或共同地址自动开放全部交付。

## 10. 私密交付与公开授权的身份边界

### 10.1 私密交付访问条件

客户访问私密成片至少需要同时满足：

```text
身份有效
+ 订单或显式授权关系匹配
+ 交付已发布
+ 尾款已付清
+ 授权范围覆盖当前批次/文件
+ 小程序入口未到期
```

任一条件不满足，客户侧需要显示对应的安全结果，但不能泄露私密文件是否存在、文件数量、其他授权人或内部审核意见。

### 10.2 预约联系人默认授权

首版默认预约联系人是私密交付的授权对象，但这不是一个可以被页面推断的永久事实：

- 预约确认时形成客户与业务记录的关系；
- 交付发布时按当前订单和授权状态判断；
- 联系人身份变更或客户提出争议时，需要重新核验；
- 交付授权可以按批次、文件范围或期限管理；
- 预约联系人不能未经进一步业务规则确认，把访问权自动转交给任意家庭成员。

### 10.3 公开案例授权

公开案例授权与私密交付授权是两套独立事实：

- 客户可以获得私密成片但不同意公开；
- 客户可以在明确范围内同意某些图片公开，但不允许公开全部原片；
- 公开授权可以有图片、案例、人物、渠道、期限和撤回范围；
- 授权撤回后，公开端隐藏相应内容并重新计算案例资格；
- 授权撤回不自动删除客户私密交付；
- 公开端不展示客户授权证据、签署细节或撤回原因。

### 10.4 交付链接安全

客户访问交付时：

- 先完成应用层身份、归属和授权判断，再生成短期访问地址；
- 不在页面、通知或分享内容中暴露永久对象地址；
- 下载地址不能脱离业务状态长期有效；
- 分享公开案例链接不能变成私密交付链接；
- 客户转发业务页面时，接收方需要重新确认自己的身份和授权。

## 11. 资料变更、纠正与生命周期

### 11.1 客户可自行修改的资料

客户可以修改的资料范围需要结合认证强度和业务影响确认。产品建议将低风险资料与高风险资料分开：

- 低风险：显示称呼、通知偏好或非关键公开头像；
- 中风险：联系电话、联系渠道和预约备注；
- 高风险：预约联系人身份、订单归属、支付相关资料、交付授权和公开案例授权。

高风险资料不能通过普通个人中心直接覆盖，应进入重新确认或联系工作室流程，并保留历史值和操作记录。

### 11.2 工作室修正资料

负责人或授权管理员可以根据客户确认修正资料，但：

- 修正原因和依据必须记录；
- 不能把修正后的客户资料回写成历史订单的原始快照；
- 不能通过改姓名/手机号绕过交付授权；
- 涉及身份合并、联系人变更、家庭成员或公开授权的操作需要更高权限；
- 修正完成后，客户侧只看到适合客户理解的结果，不显示内部审计细节。

### 11.3 资料删除、注销和保留

客户资料的删除、注销、匿名化和保留范围需要结合业务、支付、审计和法律要求继续确认。当前产品边界至少要求：

- 删除客户资料不能删除订单、支付、退款、授权和审计事实；
- 私密成片原文件保管与客户侧交付入口是不同生命周期；
- 交付入口到期不等于客户档案或工作室原文件删除；
- 已产生财务或争议的记录不能通过普通删除操作消失；
- 客户提出资料更正、访问、导出或删除请求时，后台需要有受控处理入口；
- 处理结果、范围、责任人和时间要可追溯。

具体保留期限、客户注销后的交付处理和原文件最终删除策略属于待确认事项，不能在本专题虚构固定天数。

### 11.4 数据导出和客户支持

如果后续支持客户查看或导出自己的资料，导出内容应：

- 只包含当前身份有权访问的记录；
- 隐藏其他客户、内部备注、支付凭证原件和永久文件地址；
- 说明导出范围和生成时间；
- 记录请求人、审核人和交付方式；
- 不能通过导出绕过交付入口期限、授权或订单状态。

没有完成身份核验时，客服不能仅凭客户口述、姓名或手机号发送订单、支付或成片资料。

## 12. 状态、异常与隐私反馈

### 12.1 身份相关状态

| 状态 | 客户侧含义 | 后台处理 |
|---|---|---|
| 未识别 | 当前可以浏览，但不能访问个人业务 | 引导身份确认，不创建虚假记录 |
| 身份确认中 | 正在等待认证结果 | 避免重复提交，保留安全上下文 |
| 已确认 | 当前会话与客户身份关联 | 仍需按业务关系判断资源权限 |
| 会话过期 | 当前身份凭证不能继续使用 | 重新确认并刷新业务状态 |
| 关联待核验 | 线下记录可能属于当前客户 | 后台核验，不自动开放敏感资源 |
| 关联冲突 | 多个客户或凭证存在冲突 | 暂停敏感访问，联系工作室 |
| 无业务关系 | 当前身份不能访问目标记录 | 不泄露记录存在性 |
| 授权已撤销 | 曾经的交付授权不再有效 | 联系工作室，保留审计 |
| 账号切换 | 当前身份已改变 | 重新读取业务，不复用旧账号缓存 |

### 12.2 不能统一显示为“权限不足”

身份和隐私异常至少需要区分：

- 未登录或会话过期：重新确认身份；
- 已登录但与资源无关系：安全返回，不泄露资源；
- 预约联系人尚未确认：联系工作室或完成关联；
- 交付授权缺失：由工作室核验和显式授权；
- 尾款未付：进入支付流程，但不透露文件细节；
- 交付入口到期：联系工作室补充交付；
- 资料冲突：停止敏感操作并等待人工处理；
- 服务异常：使用 request id 联系工作室，不要求反复认证。

后台需要看到更完整的处理建议，但客户侧不得显示内部身份匹配算法、其他客户资料或授权证据。

### 12.3 无权限反馈

当客户访问不属于自己的预约、订单或交付时：

- 提示当前身份无法访问；
- 可以提供重新认证和联系工作室入口；
- 不说明记录是否存在；
- 不显示客户姓名、订单金额、日期、文件数量或授权人；
- 不通过 URL、错误日志或分享摘要泄露资源标识。

### 12.4 后台隐私异常

后台出现以下异常时，应进入受控处理：

- 客户声称手机号被他人占用；
- 两个客户被错误合并；
- 预约联系人要求更换交付访问人；
- 家庭成员之间对交付或公开授权有争议；
- 摄影师看到超出分配范围的客户资料；
- 客户请求删除、导出或更正资料；
- 公开案例授权与私密交付权限不一致。

任何人工修正都要保留原始关系、处理依据和负责人，不允许为“让客户看到内容”直接关闭权限校验。

## 13. 功能需求清单

### 13.1 客户身份和会话

- 匿名浏览公开内容；
- 在提交预约、查看个人记录、支付和交付时触发身份确认；
- 识别未认证、会话过期、身份切换和身份关联待核验；
- 身份确认后回到原任务并重新读取服务端状态；
- 不因浏览、联系或失败认证创建虚假客户记录；
- 不能通过缓存、旧链接或猜测标识访问业务。

### 13.2 客户关系和资料

- 建立预约联系人；
- 区分预约联系人、实际拍摄人和参与人；
- 关联电话/微信线下预约和线上客户身份；
- 处理重复客户、关联待核验、合并和拆分；
- 支持高风险资料变更的人工核验；
- 展示和修改资料时遵守最小必要原则；
- 分离客户可见信息和内部备注。

### 13.3 家庭成员和交付授权

- 预约联系人默认作为私密交付授权对象；
- 后台显式添加其他家庭成员；
- 记录授权范围、期限、操作者、原因和撤销；
- 首版不默认开放客户自由邀请家庭成员；
- 交付授权与公开案例授权分开；
- 授权撤销不删除订单、支付和私密原文件。

### 13.4 工作人员资料访问

- 负责人查看工作室范围内必要的客户、支付、授权和审计资料；
- 管理员查看日常运营所需的客户和订单资料；
- 摄影师只查看被分配安排和最小拍摄资料；
- 支付回调、系统任务和对象存储不能扩大人工或客户权限；
- 敏感凭证、完整审计和私密文件按角色脱敏；
- 每次敏感资料访问可追溯。

### 13.5 资料生命周期和客户支持

- 受控更正、关联、合并、拆分和高风险变更；
- 客户资料访问、导出、注销、删除或匿名化的受控入口；
- 保留订单、支付、授权和审计事实的历史完整性；
- 交付入口到期与原文件保管分离；
- 资料争议和无权限访问有客户支持路径；
- 记录请求人、处理人、范围、原因和结果。

## 14. 验收标准

### 14.1 匿名和身份触发

1. 访客可以不登录浏览已发布品牌、作品、业务、套餐和联系方式。
2. 浏览、拨号、查看微信或查看地址不会自动创建客户档案或预约。
3. 提交预约、查看个人预约/订单、支付和访问私密成片时，在任务节点触发身份确认。
4. 身份确认成功后回到原任务，并重新读取服务端真实状态。
5. 会话过期、认证取消和切换账号不会重复提交预约、支付、授权或下载。
6. 客户侧不显示测试姓名、测试手机号、虚构订单数量或未确认的个人功能。

### 14.2 客户关系和业务归属

1. 系统能够区分预约联系人、实际拍摄人、参与人和被授权交付人。
2. 预约联系人可以不是实际拍摄人，但仍可按规则接收业务通知和访问默认交付。
3. 实际拍摄人不会仅因被记录在预约中就自动获得订单、支付或下载权限。
4. 同一家庭、同一设备、同一地址或相同手机号不会自动扩大其他人的业务访问权。
5. 客户查看预约、订单和交付时，系统同时校验身份和业务关系。
6. 客户访问无权资源时不泄露资源存在、姓名、金额、日期、文件数量或授权人。

### 14.3 线下身份关联

1. 后台录入电话/微信预约时记录来源、联系人、业务关系和关联状态。
2. 线下联系不自动等同于已确认线上身份，客户查看记录前需要完成受支持的身份确认。
3. 可能重复的客户资料进入待匹配或人工核验，不通过单一姓名、手机号或微信号静默合并。
4. 客户更换联系方式时，历史业务、交付授权和订单快照不会被无审计地转移。
5. 客户资料合并、拆分和关联纠正保留原记录、处理依据、操作者和时间。
6. 线下预约和线上预约能够在客户侧呈现为统一、可理解的业务记录，但不泄露内部关联细节。

### 14.4 资料最小化与可见性

1. 预约表单和后台只收集完成业务所需的最小资料。
2. 儿童、亲子全家福、孕照和多人业务的参与人/监护资料有明确用途、必要性和可见范围。
3. 客户侧不显示内部备注、授权证据原件、完整支付凭证、对象存储地址或其他客户资料。
4. 摄影师只能查看被分配订单和完成履约所需的最小客户信息。
5. 管理员默认不能查看不必要的完整支付凭证、完整审计或其他客户记录。
6. 负责人查看敏感资料时仍有最小必要原则和访问审计。
7. 内部备注、客户可见说明和通知内容相互隔离。

### 14.5 私密交付与公开授权

1. 预约联系人默认具备私密交付访问资格，但仍需满足订单归属、尾款、发布、授权和入口期限。
2. 其他家庭成员必须由后台显式添加，授权范围、期限、操作者和原因可追溯。
3. 实际拍摄人、同家庭成员或共同付款人不会自动获得全部交付权限。
4. 公开案例授权与私密交付授权独立管理。
5. 客户支付尾款不会自动产生公开案例授权。
6. 公开授权撤回不会自动删除客户私密交付、订单或支付事实。
7. 交付访问使用短期受控地址，不暴露永久文件地址。
8. 授权撤销、交付到期和身份切换后，旧页面、旧链接和缓存不能继续访问私密文件。

### 14.6 资料生命周期和审计

1. 客户资料更正、关联、合并、拆分、授权变更、导出、注销或删除请求均有受控处理路径。
2. 资料变更不会覆盖既有订单、支付、退款、授权和审计事实。
3. 删除或注销客户资料不会无记录地删除财务、交付或争议相关事实。
4. 交付入口到期与工作室原文件保管分离，不能向客户错误表示文件已被删除。
5. 敏感资料访问、授权变更和身份关联处理记录操作者、时间、原因和结果。
6. 客户支持人员不能仅凭姓名、手机号或口述发送订单、支付或成片资料。
7. 身份异常和隐私争议能够通过业务号、request id 或审计关联继续排查。

## 15. 验证方式

### 15.1 负责人和工作人员核验

需要工作室负责人、管理员和摄影师确认：

- 实际使用哪些身份凭证和联系渠道；
- 电话/微信预约如何记录联系人和拍摄人；
- 哪些客户资料是预约、拍摄、支付和交付所必需；
- 儿童、亲子、婚纱、孕照和证件照分别需要哪些参与人资料；
- 谁可以作为预约联系人，谁可以接收交付；
- 家庭成员由谁添加、需要什么确认、是否设定期限；
- 负责人和管理员的敏感资料、支付凭证和审计可见范围；
- 摄影师现场需要查看哪些信息；
- 客户更换联系方式、重复建档和身份争议如何处理；
- 客户资料、订单、支付凭证、授权证据和原文件分别保留多久；
- 客户提出更正、导出、注销、删除或补充交付请求时由谁处理。

### 15.2 脱敏场景验证

至少准备以下脱敏场景：

1. 匿名访客浏览作品和套餐，不产生客户档案。
2. 客户从套餐进入预约，身份确认后回到原套餐和预约任务。
3. 客户提交预约后会话过期，重新确认后不会重复提交。
4. 预约联系人为家长，实际拍摄人为儿童，客户侧和后台侧分别展示必要资料。
5. 亲子全家福有多名参与人，但只有预约联系人默认拥有交付访问资格。
6. 孕照预约需要必要前置资料，摄影师只能看到完成拍摄所需的最小提示。
7. 电话预约录入后，客户通过线上身份确认查看自己的预约。
8. 两个客户共用一个手机号或一人代另一人预约，系统进入人工核验而不是自动合并。
9. 客户更换手机号，原订单快照和交付授权不被新手机号无条件继承。
10. 两个家庭成员访问同一交付，其中一个被后台显式授权，另一个无权访问。
11. 客户已支付尾款但没有公开授权，交付可访问而公开案例不能发布。
12. 公开案例授权撤回，公开端隐藏图片，但预约联系人仍按交付规则访问私密成片。
13. 客户访问他人订单号或旧交付链接，系统不泄露记录存在性。
14. 摄影师尝试查看未分配客户，系统拒绝并记录访问审计。
15. 管理员尝试直接改写客户归属或公开授权，系统要求受控业务动作和更高权限。
16. 客户请求资料更正或删除，后台保留财务、订单和审计事实并给出处理结果。
17. 客户切换账号后，页面不显示前一个账号的预约、订单或下载入口。
18. 客户端缓存旧授权或短期地址失效后，不能绕过最新权限访问文件。

### 15.3 客户可用性和隐私理解验证

通过目标客户、家庭预约人和工作人员测试观察：

- 客户是否理解为什么浏览时不需要登录、提交预约时需要身份；
- 客户是否理解预约联系人与拍摄人的区别；
- 客户是否知道共享手机号或家庭关系不自动等于有权访问；
- 客户是否能看懂“没有权限”“需要补充授权”“交付入口到期”的区别；
- 客户是否知道支付尾款和公开授权是不同事情；
- 家长/家庭联系人是否理解谁可以接收订单和成片；
- 工作人员是否能判断某项资料是否必要；
- 摄影师是否会把客户内部资料误认为拍摄必需资料；
- 客户在身份失效和切换账号后是否仍能找到正确下一步；
- 客户是否信任资料更正、授权撤回和隐私问题的人工处理路径。

没有真实访问和支持数据前，不设定虚构的登录转化率、认证成功率、隐私投诉率或资料处理时效目标。A16 负责继续确定可衡量指标和数据来源。

## 16. 待确认经营内容与产品决策

以下事项需要负责人、管理员、摄影师和代表性客户进一步确认：

1. 客户侧最终采用手机号、微信身份、短信验证码还是其他身份方式。
2. 客户是否必须绑定手机号，微信身份与手机号如何关联或更换。
3. 电话/微信预约录入后，客户如何确认自己是预约联系人。
4. 一个客户是否可能有多个手机号、多个微信身份或多个家庭业务关系。
5. 预约联系人、实际拍摄人和支付人不同的常见场景有哪些。
6. 六类摄影业务分别需要收集哪些参与人、人数、年龄段、孕周或准备信息。
7. 儿童业务是否要求监护人确认，监护关系需要收集或仅通过人工确认。
8. 多人/家庭拍摄中，哪些人可以访问交付，是否需要逐人授权。
9. 预约联系人默认交付授权是否适用于所有业务和所有交付批次。
10. 家庭成员由后台添加时是否需要对方再次确认，授权是否有期限和范围。
11. 客户是否需要在首版自行修改手机号、联系人和参与人资料。
12. 哪些资料客户可以改，哪些资料必须联系工作室并由后台核验。
13. 客户身份合并、拆分、重复建档和争议归属由谁审核。
14. 客户可以申请哪些资料访问、更正、导出、注销或删除操作。
15. 订单、支付、授权证据、客户沟通记录和原文件分别保留多久。
16. 客户注销或联系方式失效后，私密交付如何继续访问或补充交付。
17. 负责人、管理员和摄影师分别能看到哪些客户字段、支付凭证和内部备注。
18. 摄影师首版是否启用独立账号，是否按订单、日期或任务分配资源。
19. 客户身份失效、身份冲突和交付授权争议的联系渠道和响应人是谁。
20. 公开案例授权需要哪些主体同意，授权范围、期限和撤回规则是什么。
21. 是否允许客户侧直接邀请家庭成员，若不允许，后台添加的实际工作流程是什么。
22. 客户是否需要查看自己的访问、下载、授权变更和资料处理记录。
23. 客户支持人员如何在不泄露资料的前提下帮助客户找回订单或交付。
24. 真实客户最担心哪些隐私问题，哪些身份提示会造成不必要的打扰。

## 17. 后续专题输入

A11 为后续专题提供以下输入：

- A08：客户在提交预约、查看个人记录、支付和交付时触发身份确认，并在会话过期后回到原任务；
- A09：官网公开页面不展示客户记录和私密成片，客户业务入口转入受控的小程序或统一服务；
- A10：后台需要按负责人、管理员和摄影师的职责展示客户资料，并为身份关联、授权变更和敏感访问提供审计；
- A12：预约申请需要预约联系人、实际拍摄人/参与人等必要资料，线上和线下身份关系需可追踪；
- A13：订单归属、套餐快照、订单联系人和履约参与人不能因资料变更被静默覆盖；
- A14：支付和退款只向有权客户展示安全摘要，完整凭证和对账信息按工作人员权限限制；
- A15：预约联系人默认私密交付授权，其他家庭成员由后台显式添加，公开案例授权独立于私密交付；
- A16：身份确认成功率、无权限反馈、客户支持负担、资料处理和隐私异常需要可衡量但不能先设虚构目标；
- AT07：权限判断必须结合角色、操作、资源归属、业务状态和敏感数据范围；
- AT08：身份关联、授权变更、资料合并和补偿动作必须幂等、可追溯、不可无审计覆盖；
- AT09：认证失效、资源无权、资源不可见和服务异常需要稳定错误语义，客户侧不暴露内部细节。

## 18. 结论

当前 SouthLeaf 工程只有 token 读取雏形和一个使用测试用户的“我的”页面，没有正式客户身份、客户档案、线上/线下身份关联、家庭成员授权、资料生命周期或隐私审计能力。现有电话、微信、姓名和手机号只能作为历史页面内容或联系线索，不能直接作为客户业务归属和私密交付权限的依据。

A11 确立的目标是：

```text
匿名客户可以可信地浏览公开内容，不因浏览被迫建立身份；
提交预约时建立可追踪的预约联系人关系；
预约联系人、实际拍摄人、参与人和被授权交付人保持可区分；
电话/微信预约与线上身份可以经过核验关联，但不自动合并或扩大权限；
客户资料按最小必要原则收集、展示、修改和保留；
负责人、管理员和摄影师按职责看到不同范围的敏感资料；
私密交付授权和公开案例授权相互独立，身份切换、授权撤回和入口到期都能安全生效；
资料变更、身份关联、授权和隐私处理均可追溯，不能覆盖历史订单、支付和审计事实。
```

A11 不定义最终认证技术、数据库、API 或字段模型，而是为预约、订单、支付、交付和后台详细设计提供身份关系、资料可见性、隐私反馈和授权边界。客户身份方式、参与人字段、家庭成员授权、资料保留和客户支持流程仍需负责人和真实场景确认，确认前不应锁定最终实现方案。
