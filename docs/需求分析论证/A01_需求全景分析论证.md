# SouthLeaf 需求全景分析论证

> 文档编号：A01  
> 文档类型：需求分析论证  
> 状态：讨论基线，非最终 PRD  
> 更新日期：2026-10-01  
> 适用范围：单摄影工作室产品

本文只讨论产品对象、用户需求、完整业务能力、业务约束与待论证问题。实施阶段、优先级的交付安排与验收计划见 [P01_三阶段实施计划](../计划/P01_三阶段实施计划.md)；本文不做技术选型、系统架构或具体实现设计。

## 1. 目的与证据边界

本文件是需求地图，回答“为什么做、服务谁、用户要完成什么、需要哪些能力、目前还有哪些疑问”。它不是旧代码功能清单，也不预先决定所有业务规则。

标记说明：

- **已确认**：本轮需求讨论中用户明确认可的产品方向或规则。
- **产品建议**：基于完整用户旅程提出的候选能力，尚待工作室经营实际情况验证。
- **待确认**：会改变业务流程、内容口径或产品体验的问题。

当前没有工作室经营记录、真实客户访谈、站点行为数据或竞品验证材料。以下问题与设计方向不得被表述为“已验证的用户事实”；相关目标值也不能凭空设定。

## 2. 产品定位与范围

**已确认**：SouthLeaf 面向一个摄影工作室，历史版本已覆盖的摄影业务均应纳入需求梳理，不能因功能建设先后而删减业务范围。产品应兼顾品牌展示、服务了解、客户联系、预约、订单、交易及成片交付。

**已确认**：对外有微信小程序与品牌官网两种产品形态，内部由工作室后台维护内容与业务。架构需要专业、解耦、可扩展，但技术方案另行讨论。

产品不是多工作室入驻平台、通用电商商城或公开客户照片社区；上述边界不等于否定长期可能性。

**待确认**：历史版本完整业务清单、真实经营范围与各业务的套餐/定制化比例。举例说明个人写真、亲子、婚礼或商业拍摄的差异，不意味着已核实这些就是完整的既有业务清单。

## 3. 用户与使用场景

| 角色 | 要完成的任务 | 当前认知边界 |
|---|---|---|
| 潜在客户 | 判断风格与可信度、比较服务与作品、联系工作室 | 接触渠道与选择因素待访谈 |
| 已预约客户 | 提交日期和具体时间段、确认预约结果、查看订单 | 身份识别和沟通方式待确认 |
| 已成交客户 | 支付定金及尾款、了解服务与交付进度、获取成片 | 例外规则和交付形式待确认 |
| 工作室负责人/管理员 | 发布内容、处理预约、管理订单与交易、安排交付 | 内部人员分工和现有工具待确认 |
| 摄影师等内部人员 | 参与服务安排、拍摄及后期 | 是否需要独立系统账户待确认 |

同一人可能跨多个角色。客户不应仅为浏览公开内容而被迫登录；涉及预约、订单或私密交付时，需要可靠地识别其身份。具体识别方式另议。

## 4. 完整业务旅程

下述是目标业务全景，不代表每个能力同时上线，也不等于所有异常路径已经确定。

```text
发现工作室 → 浏览作品与业务 → 了解套餐与须知 → 电话或微信联系 / 提交预约申请
→ 工作室核对时间与服务 → 确认预约 → 形成订单 → 支付定金
→ 拍摄完成 → 支付尾款 → 后期制作 → 私密成片交付
```

**已确认**：客户可通过电话和微信联系；无需在线咨询表单作为基础要求。预约申请需明确具体日期和时间段；申请提交不等于预约成功，工作室确认后才有订单，订单后才进入支付。支付模式为定金先付、拍摄完成后付剩余尾款。成片交付属于整体能力，但不是比交易更紧急的目标。

**产品建议**：作品与套餐之间建立双向关联，减少“看了作品却不知道怎样获得类似服务”的断点；客户能理解预约待确认的含义和下一步；管理人员可从预约查看套餐、联系人、时间和备注，避免反复核对。

**已确认**：电话/微信形成的线下预约统一录入系统并与线上预约共用档期冲突源；预约申请不占硬档，工作室确认时占档并自动生成订单；尾款付清前不开放成片预览和下载；拍摄完成后尾款逾期不自动取消订单或退款。完整规则见 [A04_全程用户旅程与业务规则](A04_全程用户旅程与业务规则.md)。

## 5. 产品形态与职责

### 5.1 微信小程序

客户移动端入口：展示品牌、作品、服务、套餐、工作室信息和联系方式；承载预约、结果查看、订单查看、支付、交付访问等客户操作。页面结构与登录时机需要另行分析，不由现有五个 Tab 直接决定。

### 5.2 品牌官网

公众了解工作室与案例的入口：承载品牌故事、完整作品、服务说明、团队信息、地址及联系/预约入口。与小程序复用一致的业务内容，但信息层次和浏览场景可不同。官网是否允许完整提交预约，还是引导到小程序，**待确认**。

### 5.3 管理后台

工作室内部工具：维护品牌/首页/作品/业务与套餐、团队、图片和发布状态；处理预约、客户和订单；后续管理支付、服务与成片交付。各项内容应由工作室自主维护，不能长期依赖开发者改写前端数据。

### 5.4 跨端内容口径

同一项公开套餐、作品和工作室资料由工作室统一维护，在不同客户端保持名称、内容、价格、状态一致；各端可以有不同的展示编排。订单在形成时保留当时套餐内容和价格，不随日后公开内容修改而改变。

## 6. 业务能力地图

这里按业务对象组织，不把页面、后台功能和业务规则混为一层。每个专题仍需详细分析用户动作、规则和异常情形。

### 6.1 品牌、首页与工作室资料

- **客户任务**：快速了解定位、拍摄风格、服务区域、工作室背景、流程、地址和联系方法。
- **工作室任务**：维护品牌文案、代表图片、业务推荐、营业/联系时间、联系方式、地点和常见问题。
- **产品建议**：首页用代表案例和服务导流，而非只摆放轮播图；电话、微信和地图入口清晰可达。
- **待确认**：可公开展示哪些资质、评价或团队资料；微信联系的准确呈现方式；不同业务是否需要不同首页入口。

### 6.2 作品与案例

- **客户任务**：浏览分类和案例详情，查看有代表性的完整作品，理解风格与其对应服务。
- **工作室任务**：上传图片、设置封面/顺序、撰写说明、建立分类及与业务/套餐的关联，控制发布、下架。
- **产品建议**：明确图片质量、裁切、版权和隐私授权的产品规范；区分公开案例与客户私密成片。
- **待确认**：案例最小单元是一张图、一组图还是一次拍摄；标签与分类方式；客户授权发布与撤回的流程。

### 6.3 摄影业务与套餐

- **客户任务**：按业务类型找到可选服务，比较价格、时长、包含项、服务结果、地点与预约须知。
- **工作室任务**：维护业务分类与标准套餐、内容/价格/适用范围、展示顺序、上下架及历史版本口径。
- **已确认**：标准套餐预约为当前主流程；确认预约后原则上不随意更改客户所选套餐价格和内容。
- **待确认**：历史业务清单是否全部有固定套餐；商业/婚礼等可能需要定制报价的需求如何接待；不同业务的时长与参与人数是否影响预约。

### 6.4 团队与服务流程

- **客户任务**：认识工作人员与其擅长风格，理解从咨询到拍摄及交付的一般步骤。
- **工作室任务**：维护成员资料、介绍和展示排序。
- **待确认**：是否允许指定摄影师；对外展示人员是否等于实际排班人员；团队成员退出后如何处理既有案例。

### 6.5 联系与客户身份

- **已确认**：公开浏览不以在线咨询表单为前提，电话与微信可满足基础联系。
- **客户任务**：随时找到准确的联系信息；在需要预约、查看订单或照片时识别自己的业务记录。
- **工作室任务**：维护联系方式，避免不公开的客户信息被误展示。
- **待确认**：手机号、微信身份如何与电话/线下预约合并；客户更换手机号后的记录归属和隐私处理。

### 6.6 预约、档期与冲突

- **已确认**：预约需客户提交具体日期和时间段；工作室确认后预约才成立，之后产生订单。
- **客户任务**：选择业务/套餐、时间、联系人及必要的拍摄需求；看到提交结果、当前状态与工作室反馈。
- **工作室任务**：维护可预约时间、查看申请、核对资源，确认/拒绝及处理冲突，记录联系与处理结果。
- **已确认**：首版采用后台可配置固定时段；同一日期和时段只能有一组已确认预约，但允许多笔待确认申请并行竞争；待确认申请默认 48 小时失效；临时封档不自动取消已确认预约；改期保留原记录并重新校验新时段。业务特有时长、休息日和提前通知期限在 A12 继续分析。

### 6.7 订单与服务执行

- **已确认**：工作室确认预约时自动生成订单并冻结套餐、价格、服务内容、日期和时段快照；不把每次预约申请都当作正式订单。
- **客户任务**：核对约定的日期、时间、地点、套餐、价格、支付与服务进度。
- **工作室任务**：查看订单、关联客户和预约，记录拍摄完成情况，处理异常。
- **已确认**：订单生成后进入待支付定金，默认 24 小时逾期失效并释放档期；改期保留原记录并创建修订版本。支付进度、履约进度和交付进度分开表达。具体字段和页面验收在 A13 继续分析。

### 6.8 定金、尾款与交易异常

- **已确认**：订单生成后支付套餐配置的固定金额定金；负责人或管理员确认拍摄完成后触发尾款。
- **客户任务**：看清应付金额、支付结果与剩余款项。
- **工作室任务**：查看付款情况、核对异常、登记并核验线下收款、处理退款。
- **已确认**：首版支持线下收款登记，不支持任意部分付款；支付或退款未知进入处理中；客户原因取消定金原则上不退，工作室原因取消定金全退；尾款逾期不自动取消订单。支付渠道和页面验收在 A14 继续分析。

### 6.9 成片与交付

- **已确认**：首版交付精修图片和原片；尾款付清前不开放成片预览或下载。
- **已确认**：尾款付清后提供带水印预览和不限次数的无水印正式下载；默认授权预约联系人，公开案例必须明确同意。
- **已确认**：小程序交付入口默认开放 1 周且支持配置，到期仅下架入口，不自动删除工作室原文件；必要时可由工作室通过网盘人工补充交付。选片、修片反馈和内部文件保管策略在 A15 继续分析。

### 6.10 消息、评价、客户经营和统计

以下是**候选扩展能力**，不是已确认要全部建设的需求：预约和拍摄提醒、付款/交付通知、评价、客户偏好与复购、活动营销、浏览/联系/预约/成交等业务指标。应先明确经营目标、用户触达方式和可获得的基线，再判断有无必要。

## 7. 横向业务规则待论证

| 主题 | 已知边界 | 必须继续论证的决策 |
|---|---|---|
| 套餐变更 | 确认成单时冻结明确套餐版本；待确认期间变化不得静默替换 | A07 继续分析重新报价和客户确认交互 |
| 档期竞争 | 待确认申请不占档并允许并行；确认时排他占档；线上线下共用冲突源 | A12 继续分析字段、休息日和运营界面 |
| 状态表达 | 预约、订单、支付、履约和交付分别维护状态 | A12-A15 定义各端展示和验收文案 |
| 取消与改期 | 客户原因定金原则不退；工作室取消定金全退；改期保留修订版本并可沿用定金 | A12-A14 继续分析提前期限、次数和页面流程 |
| 隐私与授权 | 私密交付默认授权联系人；公开案例必须明确同意 | A11/A15 继续分析身份绑定、撤回和文件保管 |
| 跨端一致性 | 工作室内容需统一维护 | 下架对官网/小程序的影响；订单历史可见性 |

先把真实业务规则及其责任主体论证清楚，再写各端交互与验收条件，避免先画页面后补规则。

## 8. 体验与质量需求

- 作品应真实、清楚地展现风格；图片组织应帮助客户比较服务，而不仅是装饰。
- 客户从案例到套餐再到联系方式/预约的路径应连贯，公开浏览不应因无账号受阻。
- 价格、包含项、时长和交付预期要明确；不清楚的特殊报价不能误写为统一标准价。
- 操作反馈应说清预约“已提交”与“已确认”的差别；不可预约时间与冲突处理不能误导客户。
- 工作室常做的内容发布与预约处理应易于查看、修改和核对；重要变更应可追溯。
- 客户联系人与照片属于敏感业务资料，公开展示、内部处理和私密交付应有明确边界。

视觉方向、品牌素材与页面信息层级仍须进一步定义。此处不指定色彩、组件或实现技术。

## 9. 非目标与范围边界

当前产品方向不包括多工作室入驻、平台抽佣、通用商品商城或客户照片公开社区。实时自动资源调度、复杂营销自动化、会员积分、在线选片和多轮修片协作均作为需要实际场景支持才能决策的候选能力，不在全景文档中预设为主路径。

“非目标”表示当前需求基线不以它们为前提；何时建设或是否建设由计划和后续验证决定。

## 10. 待确认问题与证据获取

1. **业务清单**：对照历史版本及工作室现有服务，确认每种摄影业务名称、服务结果、套餐与定制比例。
2. **真实经营方式**：访谈负责人并查看脱敏的近期预约记录，梳理线上/电话/微信的接单与排期流程；未经授权不读取客户资料。
3. **用户选择路径**：通过客户访谈或可用性测试了解其看作品、比较套餐、决定联系/预约时的实际困惑；当前没有这类证据。
4. **预约与档期**：固定时段、并行申请、确认占档和线下统一录入已确认；继续核对每类业务时长、预约字段、休息日和改期提前期限。
5. **合同与交易**：订单成单、固定定金、尾款触发、取消/退款和线下收款主规则已确认；继续细化退款页面、部分退款计算和人工处理流程。
6. **照片与授权**：精修图/原片交付、尾款门槛、预览/下载和公开授权已确认；继续核对工作室内部文件保管、备份、恢复和最终删除要求。
7. **产品形态**：官网是否直接可预约、各端是否共享内容但使用不同入口、内部人员是否需要各自账号。
8. **衡量方式**：先确定真实的内容维护频率、客户咨询来源、预约与成交基线，再定义产品改进指标。

每个专题后续应注明适用的摄影业务类型和证据状态（已确认事实 / 经营者陈述 / 产品假设 / 待验证问题），并将决策回写 A01。具体分析专题的组织方式另见 [A02_深入需求分析框架](A02_深入需求分析框架.md)。

## 11. 结论

当前已确定单工作室、多业务类型、内容自主维护，以及“浏览与联系 → 提交固定时段预约 → 工作室确认并成单 → 定金 → 拍摄 → 尾款 → 成片交付”的完整目标链路；预约竞争、占档、订单快照、收退款、履约和交付授权的核心规则已在 A04/AT05 确认。不同摄影业务的字段差异、各端页面体验、人工运营流程和真实用户证据仍需按 A05-A16 分专题继续论证。本文保持需求全景视角，不承载实施阶段拆分。
