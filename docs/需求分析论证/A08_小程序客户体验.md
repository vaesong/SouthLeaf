## 1. 专题目的

本专题分析客户在微信小程序中如何发现 SouthLeaf、理解摄影业务、浏览作品和套餐、联系工作室、提交预约申请、查看预约与订单、完成支付，并在后续获取私密成片。

A08 关注的是客户侧的任务路径、信息层级、入口关系、身份触发时机和状态反馈。它不把当前原型页面直接当作最终信息架构，也不在本专题中锁定数据库、接口、组件或具体技术实现。

本文件回答：

- 潜在客户不登录时可以完成哪些浏览和联系任务；
- 客户如何从首页、作品、业务、套餐和关于页面进入下一步；
- 联系、提交预约、预约确认、生成订单、支付和交付如何在体验上被清楚区分；
- 哪些动作需要可靠识别客户身份，什么时候触发登录或身份确认；
- 客户从一个页面进入另一个页面时需要保留哪些上下文；
- 加载、空结果、下架、过期、冲突、处理中、无权限和入口到期时应如何反馈；
- 当前小程序原型存在什么内容、导航和状态表达问题；
- 如何验证客户能否理解并完成关键任务。

A08 的核心结论可以概括为：

```text
A08 决定客户如何找到、理解、进入和反馈；
A05-A07、A11-A15 决定客户看到的业务事实；
AT01-AT09 决定状态、权限、并发、可靠性和错误语义；
P01 决定这些能力何时开放。
```

## 2. 专题边界与规则归属

### 2.1 A08 拥有的需求

A08 负责以下小程序客户体验需求：

- 客户任务地图和主要使用情境；
- 小程序页面信息架构和导航关系；
- 首页、作品、业务、套餐、关于、联系和个人入口的客户侧组织方式；
- 作品、套餐、业务、联系、预约、订单、支付和交付之间的上下文传递；
- 匿名浏览、联系和需要身份识别的操作边界；
- 登录或身份确认的触发时机和返回路径；
- 页面级加载、空状态、失效、下架、冲突、处理中、无权限和到期反馈；
- 客户能理解的状态文案、下一步行动和返回路径；
- 客户侧通知、待办入口和当前状态查询的体验要求；
- 小程序公开内容和客户业务记录的跨页面一致性验收；
- 小程序客户体验相关的可用性验证和体验验收。

### 2.2 A08 只引用、不拥有的需求

| 对象或规则 | 主归属 | A08 允许做什么 | A08 不得定义什么 |
|---|---|---|---|
| 品牌、首页内容、联系资料 | A05 | 组织首页区块、品牌入口和联系方式的客户侧呈现 | 品牌名称、电话、微信、地址、内容发布状态和公共内容事实 |
| 作品与案例 | A06 | 组织作品列表、详情、分类、图片浏览和关联服务入口 | 案例粒度、图片授权、公开资格、案例状态和授权撤回事实 |
| 摄影业务与套餐 | A07 | 展示业务/套餐并提供了解、联系或预约入口 | 业务目录、价格、定金、服务项、版本和套餐选择资格的主规则 |
| 客户身份和隐私 | A11 | 在客户任务需要时触发身份识别，并按允许范围展示资料 | 客户身份绑定、联系人/拍摄人关系、敏感资料和隐私保留规则 |
| 预约与档期 | A12 | 呈现预约表单、申请结果、确认/拒绝/冲突等客户反馈 | 固定时段、申请失效、占档、冲突、改期和预约状态转换 |
| 订单与履约 | A13 | 展示订单约定、履约进度和下一步待办 | 订单生成条件、快照、履约主状态、修订和异常终止规则 |
| 支付、退款与售后 | A14 | 展示应付金额、支付结果、退款处理状态和客户行动 | 支付事实、回调、金额校验、退款责任、退款状态和对账规则 |
| 成片交付与公开授权 | A15 | 提供交付入口、预览/下载反馈和访问失效提示 | 尾款门槛、交付批次、授权事实、文件访问权限、公开授权和撤回规则 |
| 状态、权限、错误和可靠性 | AT01-AT09 | 将稳定业务结果转为客户可理解反馈 | 数据库、API、事务、并发、锁、重试和错误码实现契约 |
| 通知与衡量 | A16 | 消费通知和衡量要求，形成客户侧待办入口 | 通知渠道最终选择、指标口径的技术采集方式和运营目标 |

### 2.3 A08 的唯一主规则

小程序必须让客户能够区分以下事实：

```text
浏览公开内容 ≠ 联系工作室 ≠ 提交预约申请
提交预约申请 ≠ 预约成功
预约确认 = 工作室确认并占用档期，随后生成订单
订单生成 ≠ 定金已支付
支付操作完成 ≠ 支付事实已经最终确认
拍摄完成 ≠ 尾款已支付
尾款已支付 ≠ 成片已经发布
交付入口到期 ≠ 工作室已经删除原文件
```

小程序只消费各业务域的有效结果，不在客户端自行推导预约成功、订单成立、支付成功、尾款已付或交付授权。客户页面显示的最终状态必须以服务端真实业务状态为依据。

## 3. 证据口径

| 标记 | 含义 |
|---|---|
| 已确认需求 | 已由用户讨论、A01-A07 或架构基线明确的产品要求 |
| 原型证据 | 当前代码、页面、文案或资源中确实存在的内容，只能证明历史原型表达过该能力 |
| 产品建议 | 为形成可运营、可理解的小程序提出的候选方案，仍需结合工作室经营情况验证 |
| 待验证行为 | 尚无真实客户访谈、可用性测试或行为数据支持的判断 |
| 待确认经营内容 | 电话、微信、地址、品牌资料、套餐内容等需要负责人提供权威答案的内容 |

当前仓库没有经过验证的客户访谈、访问路径、转化数据、预约行为数据或客户对页面文案的理解记录。因此，本专题可以基于已有工程和已确认业务规则建立目标体验，但不能把页面偏好、入口顺序和功能使用频率表述为已验证的用户事实。

## 4. 当前小程序工程证据与问题

### 4.1 页面注册和 TabBar

当前 `frontend/pages.json` 注册了：

```text
pages/index/index
pages/works/works
pages/works/workdetail
pages/package/package
pages/package/pkgdetail
pages/about/about
pages/my/my
```

当前 TabBar 为：

```text
首页 / 作品 / 套系 / 关于 / 我的
```

原型中没有正式注册或实现以下客户业务页面：

- 登录或身份确认；
- 预约申请；
- 预约结果或预约详情；
- 订单列表和订单详情；
- 支付结果与处理中页面；
- 履约进度；
- 成片交付入口；
- 消息或待办中心。

这说明当前页面结构只能证明公开展示原型，不足以证明客户业务旅程已经闭环。未来页面和入口不应被当前五个 TabBar 机械限制。

### 4.2 全局状态契约

`frontend/App.vue` 当前只在 `data()` 中声明 `selectedCategory`，但首页和作品页通过 `getApp().globalData.selectedCategory` 传递分类状态。当前没有明确声明 `globalData`，因此存在以下风险：

- 首页点击分类后，作品页可能无法可靠读取筛选上下文；
- 作品页和套餐页对同名全局状态的使用可能互相覆盖；
- 页面返回或重复进入时，筛选状态可能残留或丢失；
- 详情页返回列表时，原来的分类、布局和滚动位置没有稳定恢复规则。

A08 将该问题定义为上下文和返回体验缺口，不在本专题直接确定全局状态的技术实现。

### 4.3 首页原型

`frontend/pages/index/index.vue` 当前包含轮播图、分类入口、作品欣赏、服务套餐、用户评价占位和 Footer 联系信息。

当前证据包括：

- 分类入口可跳转到作品 Tab，并尝试传递分类名称；
- 首页作品数据直接硬编码，和作品列表不是同一份权威内容；
- 套餐列表调用接口，但首页只按当前返回结果展示，未呈现完整的价格、选择资格和失效状态；
- 用户评价区域只有占位图片；
- 首页缺少明确的品牌首屏信息、预约/联系关系和内容为空时的反馈；
- 网络加载或接口失败主要写入控制台，没有面向客户的稳定状态反馈；
- 套餐详情和作品详情都通过 ID 跳转，但目标详情页并不保证能够正确加载所有 ID。

首页已经表达“作品”和“服务套餐”是主要导流内容，但尚未形成公开内容、状态和客户行动之间的完整关系。

### 4.4 作品列表和详情原型

`frontend/pages/works/works.vue` 当前通过页面内硬编码数组维护作品和分类，并提供分类切换、网格/列表布局切换以及搜索图标。

当前问题包括：

- 作品列表、首页作品和详情页分别维护数据副本；
- 作品分类与摄影业务名称混用，且列表中有“创始人档”等未确认概念；
- 搜索入口点击后只显示“开发中，敬请期待”；
- 详情跳转依赖 ID，但详情页只内置固定作品；
- 分类无结果、图片加载失败、作品下架或授权撤回没有明确反馈；
- 列表筛选状态主要依赖全局对象，返回和重复进入行为不稳定；
- 作品详情没有稳定的关联业务、套餐、联系和预约上下文。

`frontend/pages/works/workdetail.vue` 当前只在传入 ID 为 `1` 时赋值，且列表中作品分类和详情中的分类不一致。这是内容事实和上下文一致性的原型缺陷，不应由客户承担理解成本。

### 4.5 套餐列表和详情原型

`frontend/pages/package/package.vue` 和 `frontend/pages/package/pkgdetail.vue` 当前大量使用页面内硬编码数据。

已观察到：

- 套餐列表存在测试分类和测试文案；
- 已确认保留的证件照没有稳定出现在正式套餐分类中；
- 列表和详情的标题、图片、价格、活动时间和服务描述存在漂移；
- 历史数据同时出现 50% 和 30% 定金比例文案，与当前确认的固定金额定金规则不一致；
- 详情页固定展示“全天”“拍摄100张”“15张精修”等图标信息，不能证明适用于每个套餐；
- 价格排序逻辑被注释，界面提供的排序操作与实际结果可能不一致；
- 套餐下架、过期、需咨询、固定定金缺失和预约不可选没有客户侧状态表达；
- 从套餐详情进入联系或预约的上下文没有形成正式契约。

A08 的体验要求是客户看到的价格、服务、定金和可选状态必须来自 A07 的有效公开事实，不能继续依赖各页面自由组合或历史占位文案。

### 4.6 关于页和联系入口原型

`frontend/pages/about/about.vue` 当前硬编码品牌名称、标语、地区、工作室介绍、团队资料、电话、地图坐标和地址。

同时存在：

- 在线预约和日历入口均显示“开发中，敬请期待”；
- 关于页电话与 Footer 电话不一致；
- 关于页展示的“广东 深圳”与地图和 Footer 的东莞凤岗地址不一致；
- 联系、预约、日历三个动作的业务含义未清晰区分；
- 地图操作失败时没有稳定的文字地址降级体验；
- 团队公开资料没有内容状态和可信度标识。

`frontend/components/FooterInfo/FooterInfo.vue` 也硬编码微信、电话和地址，且小红书、微博、抖音弹窗复用了微信图片资源。A08 只能消费 A05 的统一内容源，并要求不同页面不能各自维护联系事实。

### 4.7 我的页面原型

`frontend/pages/my/my.vue` 当前显示硬编码用户 `momo`、测试手机号、未付款/进行中/已完成/全部订单等订单入口，以及相册、喜欢、积分、优惠券和会员卡等功能入口。

当前所有入口都统一显示“开发中，敬请期待”，没有：

- 匿名和已识别客户的不同状态；
- 登录或身份确认入口；
- 预约申请和预约结果；
- 订单列表、订单详情和支付状态；
- 私密成片访问控制；
- 无订单、无交付、身份失效和访问被拒绝的反馈；
- 对“我的相册”“我的喜欢”“积分”“优惠券”“会员卡”的已确认业务需求。

这些入口只能作为历史原型线索，不能直接转化为正式需求。当前确认的客户核心入口应优先围绕预约、订单、支付和交付组织，其他客户经营能力仍需另行验证。

### 4.8 请求层和错误反馈原型

`frontend/api/api.js` 当前已经有统一请求封装、超时、网络失败提示和 token 读取雏形，但存在以下体验契约问题：

- 请求地址硬编码为 `http://localhost:8090`，不能证明正式环境可访问；
- 业务结果只按数字 `code === 200` 判断；
- 错误处理主要把 400、401、403、500 当作 HTTP 类似码，尚未消费 AT09 定义的稳定业务错误码；
- 预约冲突、套餐版本失效、支付处理中、交付到期和无权限等情况没有对应的客户行动；
- 网络异常、服务异常和业务拒绝都可能只显示通用 Toast；
- 请求失败后没有明确的重试、返回列表、联系工作室或查看当前状态路径。

A08 不定义错误码，但要求客户界面能根据 AT09 的稳定业务语义给出适合当前任务的反馈。

### 4.9 现状问题结论

| 问题 | 当前表现 | 客户体验风险 |
|---|---|---|
| 页面只有公开展示原型 | 没有正式预约、订单、支付和交付入口 | 客户无法完成已确认的完整业务旅程 |
| 内容源分散 | 首页、列表、详情和 Footer 各自硬编码 | 客户看到的品牌、作品、价格和联系方式可能矛盾 |
| 详情不稳定 | 作品和套餐详情只支持固定 ID | 点击列表后可能看到空白或错误内容 |
| 业务概念混用 | 作品分类、摄影业务和套餐分类混在一起 | 客户无法判断作品是否对应可预约服务 |
| 身份边界不清 | `我的` 页面显示测试用户且无登录流程 | 个人业务记录和公开浏览容易混淆 |
| 状态反馈不足 | 接口失败主要写控制台，搜索和预约只是占位提示 | 客户不知道问题原因和下一步怎么做 |
| 全局上下文不稳定 | `globalData` 未明确声明且多个页面复用分类状态 | 页面跳转、返回和筛选可能丢失上下文 |
| 交易事实未区分 | 原型文案存在定金比例和成功暗示 | 可能将查看、提交、支付和确认混为一谈 |
| 公开与私密边界未建立 | 作品页与未来相册入口没有明确分域 | 存在隐私和授权误导风险 |
| 入口未经过任务验证 | 功能入口以“开发中”占位 | 用户无法判断哪些功能当前可用 |

## 5. 客户角色与任务地图

### 5.1 潜在访客

潜在访客尚未提交预约或没有需要查看的业务记录，主要任务是：

1. 确认工作室是谁、在哪里、擅长什么；
2. 浏览公开作品并理解风格；
3. 了解摄影业务和标准套餐；
4. 比较服务内容、价格、定金说明、时长和适用范围；
5. 通过电话、微信或后续预约入口咨询；
6. 在提交前知道预约需要具体日期和固定时段，并理解申请不等于成功。

潜在访客不应因为浏览、查看作品或查看套餐被强制登录。

### 5.2 预约申请人

预约申请人已经决定尝试预约，需要：

1. 从作品、业务或套餐进入预约入口；
2. 保留当前选择的业务、套餐版本和上下文；
3. 选择具体日期和工作室提供的固定时段；
4. 填写预约联系人及业务所需的必要信息；
5. 提交申请并获得可识别的提交结果；
6. 查看待确认、已确认、已拒绝、已失效或冲突结果；
7. 在需要时补充资料、重新选择或联系工作室。

提交前可以是匿名浏览状态，但提交预约需要可靠识别客户或建立可追踪的客户联系关系，具体身份方式由 A11 继续确认。

### 5.3 已预约客户

已预约客户的任务是：

- 查看申请是否仍待工作室处理；
- 查看日期、固定时段、业务、套餐和申请有效期；
- 理解已确认、被拒绝、已失效和时段冲突的区别；
- 在工作室要求补充信息或重新确认时完成下一步；
- 从确认结果进入对应订单，而不是自行寻找或重复创建订单。

### 5.4 已成交客户

已成交客户的任务是：

- 查看订单中冻结的套餐、服务、价格、定金、尾款、日期和时段；
- 知道定金应付金额和支付截止时间；
- 查看定金支付成功、处理中、失败或待核验状态；
- 了解拍摄准备、履约状态和工作室通知；
- 在拍摄完成后查看尾款应付；
- 查看尾款支付和订单履约进度；
- 在交付发布且满足授权条件后进入成片预览和下载。

### 5.5 被授权的家庭成员

被授权家庭成员可能不是预约联系人，但可以在 A15 和 A11 的规则下访问特定成片。

小程序需要：

- 在身份不匹配时说明当前账号没有访问权限；
- 不泄露订单是否存在、客户姓名或文件信息；
- 提供联系工作室申请授权的下一步；
- 授权失效或交付入口到期时给出不同反馈。

### 5.6 客户任务地图

| 客户任务 | 入口 | 是否需要身份识别 | 成功结果 | 失败/异常后的下一步 |
|---|---|---:|---|---|
| 了解品牌 | 首页、关于 | 否 | 看到已发布品牌和工作室资料 | 返回首页或联系工作室 |
| 浏览作品 | 首页、作品 Tab、分类入口 | 否 | 查看有效公开案例和详情 | 返回列表、切换分类或联系工作室 |
| 了解业务 | 首页、作品关联、套餐 Tab | 否 | 看到已发布摄影业务说明 | 查看套餐、联系或返回 |
| 查看套餐 | 首页、套餐 Tab、业务详情、作品关联 | 否 | 看到有效套餐版本和选择资格 | 查看下架说明、联系或重新选择 |
| 联系工作室 | 首页、关于、套餐、订单异常 | 否，除非客户主动进入记录处理 | 拨号、查看微信或其他联系渠道 | 显示可复制的联系方式和文字地址 |
| 提交预约 | 套餐/业务/联系入口 | 是或需要建立可追踪联系人 | 申请已提交并显示待确认 | 修正字段、重新提交或联系客服 |
| 查看预约 | 我的、提交结果、通知 | 是 | 查看当前真实预约状态 | 重新认证、返回或联系客服 |
| 查看订单 | 我的、预约确认结果 | 是 | 查看订单约定和履约状态 | 无权限提示或重新认证 |
| 支付定金/尾款 | 订单详情 | 是 | 显示已确认的支付事实或处理中状态 | 不重复支付、查看状态或联系客服 |
| 查看交付 | 我的、订单详情、通知 | 是且需有授权 | 查看预览、下载或交付状态 | 尾款、发布、授权或入口到期提示 |

## 6. 目标信息架构与导航

### 6.1 信息架构原则

小程序信息架构应围绕客户任务，而不是围绕后台对象名称堆叠页面。客户需要在每个公开页面回答三件事：

1. 我现在看到的是什么；
2. 它是否可以继续选择、联系或提交；
3. 下一步应该做什么。

页面可以共享内容，但不应在多个地方复制价格、服务项、联系方式或状态。客户从作品进入套餐，从套餐进入联系/预约，从预约确认进入订单，从订单进入支付和交付时，应保留必要的业务上下文。

### 6.2 目标页面分组

| 页面分组 | 主要页面/入口 | 主要任务 | 访问要求 |
|---|---|---|---|
| 公开发现 | 首页、作品列表、案例详情、业务列表/详情、套餐列表/详情 | 认识工作室、浏览作品和服务 | 匿名可访问已发布内容 |
| 公开联系 | 关于/工作室、电话、微信、地址地图、联系须知 | 咨询和了解位置 | 匿名可使用 |
| 预约申请 | 预约入口、预约表单、提交结果 | 选择日期/时段并提交申请 | 提交前完成身份识别或联系人确认 |
| 预约跟进 | 预约列表、预约详情、补充/重新确认 | 查看处理结果和下一步 | 仅客户本人或允许的授权关系 |
| 订单履约 | 订单列表、订单详情、准备事项、履约进度 | 核对交易约定和服务进度 | 仅客户本人或允许的授权关系 |
| 交易处理 | 定金/尾款支付、支付处理中、支付结果、退款处理 | 查看并完成应付事项 | 仅客户本人，金额以订单事实为准 |
| 成片交付 | 交付列表、批次详情、带水印预览、正式下载 | 获取私密成片 | 身份、归属、尾款、发布、授权和入口期限均满足 |
| 客户中心 | 登录/身份确认、我的、消息/待办、帮助与联系 | 汇总业务记录和待办 | 未识别时显示公开入口和身份入口 |

该信息架构描述目标客户体验，不表示所有页面必须放入 TabBar，也不表示所有页面需要同时出现在主导航。主导航应保持公开发现和联系可达，预约、订单、支付和交付可以由上下文入口和客户中心进入。

### 6.3 主导航建议

当前五个 TabBar 可以作为公开内容原型的证据，但后续应根据真实客户任务重新确认。产品建议：

- 首页：品牌首屏、代表作品、重点业务/套餐、联系入口和主要行动；
- 作品：公开案例列表、分类、筛选和详情；
- 服务/套餐：摄影业务、标准套餐和咨询/预约入口；
- 关于：工作室、团队、地址、联系渠道和服务流程；
- 我的：身份确认后的预约、订单、支付和交付待办。

“我的”在未识别状态下不应展示测试姓名、测试手机号或看似真实的订单数量，而应明确提供身份确认入口和公开联系入口。

### 6.4 上下文入口规则

客户从以下来源进入下一步时，应尽量保留上下文：

| 来源 | 进入目标 | 应保留的上下文 |
|---|---|---|
| 首页作品卡片 | 案例详情 | 案例标识、返回首页/作品入口 |
| 案例详情 | 业务或套餐详情 | 案例来源、关联业务/套餐、返回案例 |
| 首页业务卡片 | 业务详情 | 业务标识、返回首页 |
| 套餐列表 | 套餐详情 | 套餐标识、所属业务、筛选条件 |
| 套餐详情 | 联系 | 套餐名称/版本、咨询来源、返回套餐 |
| 套餐详情 | 预约 | 套餐版本、业务、客户选择来源 |
| 预约提交结果 | 预约详情/我的 | 预约标识、提交时间、当前状态 |
| 预约确认结果 | 订单详情 | 预约标识、订单标识、确认时间 |
| 订单详情 | 支付 | 订单标识、应付分期、金额快照、返回订单 |
| 订单详情 | 交付 | 订单标识、交付批次/可用入口、返回订单 |
| 通知/待办 | 对应记录 | 业务记录标识、触发通知原因、当前状态 |

上下文只用于帮助客户继续任务，不得让客户端缓存的旧价格、旧套餐状态或旧支付结果覆盖服务端有效事实。

### 6.5 返回与中断规则

客户在以下情况下离开页面后，回到原任务时应有可理解的恢复行为：

- 从预约表单返回套餐详情：保留已选择的套餐和已填写但未提交的非敏感内容，是否保留敏感内容由 A11 确认；
- 从支付页返回订单：明确显示支付未完成、处理中或需要重新发起，不直接显示成功；
- 从登录页返回原页面：完成身份确认后回到原任务，取消或失败时保留原上下文但不重复提交；
- 从交付预览返回订单：回到对应订单或交付详情，而不是回到首页；
- 从下架或冲突提示返回：提供重新选择、联系工作室或回到列表的路径；
- 重复点击提交、确认或支付入口：不能产生重复预约、重复订单或重复支付意图。

## 7. 匿名浏览与身份识别

### 7.1 不应强制登录的任务

以下任务原则上允许匿名完成：

- 查看首页和已发布品牌内容；
- 浏览作品分类、案例列表和案例详情；
- 查看已发布摄影业务和套餐；
- 查看公开服务流程、团队和联系方式；
- 拨打公开电话、复制微信信息、查看公开地址和地图；
- 从公开页面进入登录前的预约说明页。

匿名浏览不应创建客户档案、预约、订单或支付记录。

### 7.2 需要身份识别的任务

以下任务需要可靠识别客户或建立可追踪的联系人关系：

- 提交预约申请；
- 查看个人预约、订单或付款状态；
- 处理预约补充资料、重新确认和改期请求；
- 发起定金或尾款支付；
- 查看私密成片、预览或下载；
- 查看与个人相关的退款、售后或补充交付记录。

具体采用何种认证方式、是否允许手机号验证码、微信身份或其他方式由 A11 和后续技术设计确认。A08 只规定触发时机和体验连续性。

### 7.3 登录触发时机

登录或身份确认应在客户已经理解当前任务后触发：

- 客户点击“提交预约”后，再提示身份确认，不在首页首次打开时强制弹出；
- 客户点击“查看我的订单”或“支付”时，再提示身份确认；
- 客户点击“查看成片”时，先说明需要验证身份和授权，再进入身份确认；
- 已识别客户再次进入同一任务时，尽量不重复打断；
- 身份会话过期时，保留当前任务和安全的非敏感上下文，完成确认后返回原任务；
- 身份确认失败时，说明无法继续的原因和联系客服路径，不泄露资源存在性。

### 7.4 身份与公开资料的隔离

小程序不能因为客户处于匿名状态就展示测试账号，也不能因为身份确认成功就让客户看到不属于自己的业务记录。公开作品和品牌内容不应携带客户真实姓名、联系方式、订单号、授权证据或私密文件地址。

## 8. 各主要页面的客户体验需求

### 8.1 首页

首页应帮助客户在较短浏览路径内完成：

- 识别品牌和工作室定位；
- 进入代表作品；
- 进入摄影业务或套餐；
- 找到电话、微信、地址或后续预约入口；
- 理解联系与提交预约的区别。

首页应满足：

- 只展示 A05 已发布的品牌内容；
- 作品区块只引用 A06 当前具备公开资格的案例；
- 业务和套餐区块只引用 A07 有效公开版本；
- 价格、服务和公开状态不在首页复制维护；
- 推荐内容失效时不显示空卡片或错误跳转；
- 可选区块没有有效内容时隐藏或使用明确空状态，不显示测试图片和占位评价；
- 联系入口明确标识“电话联系”“添加微信”“查看位置”和“提交预约”；
- 首页加载失败时，保留可用的导航或联系兜底，不将空白页面误认为没有内容。

首页不应把“在线预约”作为唯一首要行动，也不应暗示点击作品或套餐已经锁定档期。

### 8.2 作品列表

作品列表应帮助客户：

- 按作品分类浏览有效公开案例；
- 在内容足够时使用标签或搜索缩小范围；
- 看到封面、标题、摘要和必要的公开分类；
- 判断当前看到的是公开案例而非私密相册；
- 从案例进入相关业务、套餐或联系入口。

列表要求：

- 匿名可访问；
- 只读取已发布且公开资格有效的案例；
- “全部”表示当前有效公开案例聚合，不表示摄影业务或套餐分类；
- 作品分类和摄影业务在标签、标题和入口上保持可区分；
- 无案例、筛选无结果、加载失败和授权失效分别有可理解反馈；
- 下架或撤回后的案例不能因列表缓存继续出现；
- 布局切换属于展示偏好，不改变筛选和业务事实；
- 从首页带入分类后，列表应显示当前分类并允许清除筛选。

搜索是否建设、搜索哪些公开字段，待 A06、A09 和负责人结合案例数量确认。未建设搜索时，不应保留点击后只显示“开发中”的正式入口。

### 8.3 案例详情

案例详情应帮助客户回答：

- 这组作品是什么主题或风格；
- 包含多少张公开图片，图片顺序是什么；
- 属于哪些公开作品分类或标签；
- 是否有经过确认的作者/工作室署名；
- 是否关联某个摄影业务或套餐；
- 下一步应继续浏览、了解服务、联系还是预约。

详情要求：

- 只展示当前有效的公开图片集合；
- 图片加载失败时隐藏异常资源或显示可理解的降级反馈；
- 案例失效、下架或公开授权撤回时，不显示客户身份、撤回原因、内部订单或私密文件；
- 关联业务或套餐失效时移除失效入口，不复制旧价格或服务文案；
- 提供稳定的返回作品列表/原分类路径；
- 进入相关业务或套餐时传递案例来源，但不把案例内容当作套餐承诺；
- 不因客户拥有交付文件或已支付尾款而自动显示私密成片。

### 8.4 摄影业务列表和详情

业务页面应表达工作室提供哪些摄影方向，以及每类业务适合的对象和场景。已确认保留的六类业务为：

```text
儿童、亲子全家福、婚纱、写真、孕照、证件照
```

业务详情可以展示：

- 业务名称和定位；
- 适用场景或人群；
- 公开说明；
- 代表作品入口；
- 当前已发布套餐；
- 是否需要先咨询；
- 地点/服务区域和预约前置提示；
- 联系、查看套餐或预约入口。

业务页不得：

- 把业务公开展示当作存在可用档期的承诺；
- 把业务列表当作预约成功或订单列表；
- 将“创始人档”在未确认前展示为正式摄影业务；
- 用其他业务的套餐、图片或价格填充暂无内容的业务；
- 在 A08 中重新定义不同业务的预约字段和冲突规则。

### 8.5 套餐列表

套餐列表应帮助客户快速比较标准服务：

- 套餐名称和所属摄影业务；
- 当前有效价格表达；
- 固定定金说明；
- 摘要、封面和关键服务概览；
- 是否可以直接进入预约、需要咨询或已下架；
- 进入详情、联系或预约的路径。

列表要求：

- 只展示 A07 已发布的有效套餐版本；
- 价格、活动价和生效时间使用同一份公开事实；
- 没有正式价格时显示“需咨询”或等价明确表达，不显示历史测试数字；
- 固定定金缺失或不合法的套餐不能显示为可直接成单的选择；
- 过滤和排序必须与页面实际结果一致；
- 没有套餐时提示暂无标准套餐，并提供电话/微信咨询入口；
- 套餐下架、过期或版本替代时不能继续显示为可选。

### 8.6 套餐详情

套餐详情应帮助客户在提交预约前理解：

- 选择的是什么业务和套餐版本；
- 当前价格属于标准价、活动价、起始价、区间价还是咨询报价；
- 固定定金金额和尾款说明是什么；
- 服务项、数量、单位、时长和适用范围是什么；
- 拍摄地点、服务区域和业务前置条件是什么；
- 哪些内容包含、哪些是可选附加项、哪些需要沟通；
- 是否可以直接提交预约；
- 如何联系工作室。

详情要求：

- 列表和详情必须展示同一套餐版本事实；
- 套餐变更、下架或版本失效时，已进入详情的客户看到明确状态并被引导重新选择或联系工作室；
- 详情页不得使用不属于该套餐的固定图标和服务数量；
- 定金说明不能被显示为已支付；
- “提交预约”按钮不能被误解为预约成功或订单成立；
- 进入预约时传递套餐版本和客户来源；
- 套餐只供客户理解和选择，不直接生成订单。

### 8.7 关于、工作室和联系方式

关于页面应集中展示 A05 发布的：

- 品牌名称、Logo、标语和介绍；
- 工作室定位、服务区域和团队公开资料；
- 电话、微信、其他公开渠道；
- 地址、地点名称、地图和可复制文字地址；
- 联系时间和联系须知；
- 通用服务流程和必要 FAQ；
- 联系工作室和进入预约的入口。

体验要求：

- 联系方式在首页、关于页和 Footer 中保持一致；
- 拨打电话只反馈正在发起联系，不反馈预约成功；
- 微信入口说明添加方式，不将打开二维码等同于预约或客户身份绑定；
- 地图打不开时仍显示可复制地址和电话/微信；
- 未配置真实社交账号时不显示相应图标；
- 预约入口说明提交后需要工作室确认；
- 没有可用预约能力时，提供明确的电话/微信咨询入口，不继续使用“开发中”作为唯一反馈。

### 8.8 预约入口和预约表单

预约入口可以从套餐详情、业务详情、首页和关于页进入，但入口文案和上下文应保持一致。

预约表单需要根据 A12 和 A07 提供的业务事实收集：

- 所选摄影业务；
- 所选套餐及其可识别版本；
- 具体日期；
- 工作室提供的固定时段；
- 预约联系人；
- 业务所需的拍摄对象、人数或其他必要信息；
- 客户备注和工作室需要确认的事项。

A08 的体验约束：

- 不允许客户把任意开始/结束时间伪装成固定时段选择；
- 表单清楚标示“提交预约申请，等待工作室确认”；
- 提交前提示待确认申请不占硬档，可能因冲突、套餐变化或服务条件被拒绝；
- 提交成功显示可识别的申请结果、所选日期和时段、待确认状态及实际失效时间；
- 提交成功不出现定金支付按钮，直到预约确认并生成订单；
- 套餐版本已下架、不可选择或价格需要重新确认时，阻止静默提交并引导客户重新选择或联系工作室；
- 提交失败时保留安全的已填写信息，并说明是字段错误、身份问题、套餐失效还是服务暂不可用。

### 8.9 预约结果和跟进

客户需要在小程序中看到以下预约结果的可理解区别：

| 预约结果 | 客户应看到的含义 | 建议下一步 |
|---|---|---|
| 待确认 | 申请已收到，工作室尚未确认，尚未锁定档期 | 查看详情、等待处理或联系工作室 |
| 需要补充/重新确认 | 工作室需要更多信息或套餐变化需要客户确认 | 补充资料、确认新内容或联系客服 |
| 已确认 | 工作室已确认并占用档期，订单已经生成或可进入订单 | 查看订单和定金截止时间 |
| 已拒绝 | 本次申请未被接受 | 查看安全原因、重新选择或联系客服 |
| 已失效 | 申请超过有效期限或已不再可处理 | 重新提交预约 |
| 时段冲突 | 确认时该时段已被其他预约占用 | 重新选择日期/时段 |
| 处理中 | 系统或工作室仍在处理，尚无最终结果 | 查看当前状态，避免重复提交 |

页面不得仅显示“失败”或“成功”而不说明下一步。

### 8.10 我的与客户中心

未识别客户进入“我的”时，页面应提供：

- 身份确认入口；
- 预约、订单和交付功能的简短说明；
- 联系工作室入口；
- 公开作品、业务和套餐入口。

已识别客户进入“我的”时，页面建议围绕已确认的客户任务展示：

- 待处理预约；
- 待支付定金或尾款；
- 即将到来的拍摄安排；
- 履约异常或待补充信息；
- 已发布交付；
- 全部预约和订单入口；
- 联系工作室和帮助入口。

“喜欢”“积分”“优惠券”“会员卡”等原型入口在需求、运营规则和数据来源没有确认前，不应作为客户中心的正式承诺。没有记录时需要显示可信空状态，不显示测试数量或虚假的订单卡片。

### 8.11 订单详情

订单详情应以 A13 的订单快照为准，展示：

- 订单识别信息；
- 预约确认的日期和固定时段；
- 套餐名称、版本、服务内容和适用说明；
- 订单总价、定金应付、尾款应付；
- 定金支付截止时间；
- 拍摄地点和准备事项；
- 支付状态、履约状态和交付状态的分开表达；
- 订单修订、改期、取消或异常的客户可见结果；
- 当前允许的下一步，例如支付定金、查看准备事项、支付尾款、查看交付或联系工作室。

订单页面不得直接读取当前套餐价格覆盖订单快照，也不得用支付状态推导履约完成或交付可访问。

### 8.12 支付和退款

支付页面要求：

- 明确当前支付的是定金还是尾款；
- 显示订单中冻结的应付金额；
- 在客户重复进入时显示已支付或处理中状态，而不是再次默认发起支付；
- 支付前端返回不是最终支付事实；
- 结果未知时显示处理中/待查单，并提示不要重复付款；
- 金额不符、订单不符或重复支付时，不要求客户自行重试；
- 线下收款待核验时显示等待工作室确认，不显示为已支付；
- 退款处理中、成功、失败待人工需要分别表达；
- 退款失败或未知时提供联系工作室和查看当前状态入口。

A08 不定义支付渠道、退款责任或金额计算，但客户页面必须准确消费 A14 的结果。

### 8.13 履约和拍摄进度

客户应能看到有意义的履约状态，例如：

```text
待安排 → 已安排/待拍摄 → 拍摄中（如启用） → 已完成
```

异常结果独立表达：

- 需要补充拍摄信息；
- 客户缺席；
- 工作室取消；
- 已协商改期；
- 需要补拍；
- 服务异常处理中；
- 已取消。

履约状态不能从支付状态自动推导。负责人或管理员确认拍摄完成后，客户才应看到尾款待支付；摄影师的内部操作不应被客户页面直接解释为尾款已触发。

### 8.14 成片交付

交付入口应让客户理解以下状态：

- 后期制作中；
- 文件处理中或待校验；
- 交付尚未发布；
- 交付已发布但尾款未付清；
- 交付已发布且当前账号无权访问；
- 交付已发布且可预览/下载；
- 小程序交付入口已到期；
- 交付文件暂不可用，需要联系工作室。

满足 A15 规定的身份、订单归属、尾款、交付发布、授权和入口期限后：

- 小程序内提供带水印预览；
- 正式精修图和原片提供不加水印下载；
- 首版不限制下载次数；
- 不向客户展示永久文件地址；
- 客户返回订单时，仍能看到交付状态和访问期限。

尾款未付清时，页面应明确需要先完成尾款，但不泄露私密文件是否已经存在。入口到期时，应提示联系工作室补充交付，不表述为文件已删除。

## 9. 状态反馈与异常体验

### 9.1 反馈的统一结构

每个客户可见状态至少应回答：

1. 当前发生了什么；
2. 这是否已经产生业务事实；
3. 客户下一步可以做什么；
4. 如果需要工作室处理，如何联系。

状态反馈不应直接暴露数据库字段、内部角色、Java 异常、SQL、对象存储路径、第三方原始响应或授权审核细节。

### 9.2 页面通用状态

| 状态 | 客户应看到 | 下一步 |
|---|---|---|
| 首次加载 | 页面正在加载，避免空白或错误内容 | 等待，超时后重试 |
| 局部加载 | 当前区块正在更新，其他内容仍可使用 | 等待或继续浏览 |
| 无内容 | 当前没有可公开内容，不是系统故障 | 返回上级、查看其他分类或联系 |
| 筛选无结果 | 当前条件下没有有效案例/套餐 | 清除筛选、查看全部或返回 |
| 内容已下架 | 当前内容已不可选择或不可公开 | 返回列表、重新选择或联系 |
| 内容版本失效 | 客户打开的版本已被替代或不再可用 | 查看当前版本或联系 |
| 网络失败 | 当前服务暂时无法访问 | 重试、使用公开联系信息或稍后查看 |
| 服务异常 | 系统暂时无法完成操作 | 保留 request id 的客服路径或稍后重试 |
| 处理中 | 已收到请求但没有最终结果 | 查看当前状态，避免重复操作 |
| 无权限 | 当前身份不能访问该记录 | 重新认证或联系工作室，不泄露资源存在性 |
| 入口到期 | 当前小程序访问期限已结束 | 联系工作室获取补充交付 |

### 9.3 加载状态

- 首页关键内容加载时不得把空数组当作“没有作品/套餐”；
- 作品列表分页或刷新时保留已加载内容，避免页面闪烁；
- 套餐详情加载时显示当前套餐上下文或明确的加载占位；
- 预约提交、支付、退款和下载操作需要有进行中反馈，并防止重复点击；
- 加载超过可接受时间时提供重试和联系客服，而不是无限转圈；
- 失败重试不会丢失安全的客户输入或重复提交业务动作。

### 9.4 空状态

空状态必须区分：

- 业务没有已发布套餐；
- 当前分类没有公开作品；
- 客户没有预约；
- 客户没有订单；
- 客户没有可访问交付；
- 当前筛选没有结果；
- 内容尚未加载成功。

空状态不得使用测试数据、历史过期数据或虚假的数量。每个空状态应提供合适的动作，例如返回全部、查看其他业务、联系工作室或提交新的预约。

### 9.5 下架和失效

客户从历史链接或通知进入已下架作品、套餐或业务时：

- 显示统一、明确的不可用提示；
- 不显示未发布版本、内部下架原因、客户授权信息或旧的不可用价格；
- 提供返回列表、查看当前替代内容或联系工作室的入口；
- 不把下架自动解释为预约取消、订单取消或支付退款，除非对应业务域已经产生并提供该事实。

### 9.6 预约冲突

预约确认时发生冲突属于业务结果，不是普通系统故障。客户应看到：

- 原申请已经无法按该日期/时段确认；
- 客户之前看到可申请不代表已占档；
- 可重新选择其他日期/固定时段；
- 如需要可联系工作室；
- 不出现重复订单、定金支付入口或“预约成功”状态。

### 9.7 支付处理中和未知结果

- 点击支付后进入处理中时，订单页保留当前分期和金额；
- 不允许客户因为看不到立即成功而重复创建支付；
- 已支付但客户端没有收到最终结果时，优先引导查看支付状态；
- 金额不匹配、订单不匹配和重复支付需要进入人工处理，不要求客户反复点击；
- 支付最终结果由 A14 的确认事实决定，不能以前端回调或返回页单独判定。

### 9.8 无权限和隐私反馈

对于客户无权访问的预约、订单、交付或历史链接：

- 提示当前身份无权访问；
- 提供重新认证和联系工作室入口；
- 不泄露资源是否存在、客户姓名、订单金额、文件数量或撤回原因；
- 不显示永久文件地址和内部诊断信息。

### 9.9 交付到期和文件异常

- 尾款未付：显示完成尾款后才能访问，不透露文件细节；
- 交付未发布：显示工作室尚未发布，允许查看订单或联系客服；
- 文件校验失败：显示文件暂不可用，客户不应反复下载；
- 入口到期：显示小程序访问已到期，但工作室原文件不等同于已删除；
- 网盘补充交付：提示由工作室人工提供，链接有效期和范围以工作室通知为准；
- 下载链接生成失败：允许按安全规则重试，不暴露对象存储地址。

## 10. 客户侧主路径和例外路径

### 10.1 公开浏览到联系

```text
首页
  → 作品 / 摄影业务 / 套餐
  → 案例详情或套餐详情
  → 电话联系 / 添加微信 / 查看位置
  → 客户完成咨询，未产生预约或订单
```

验收重点：联系入口清楚，联系动作不显示预约成功，客户返回后仍能回到原来的案例或套餐上下文。

### 10.2 公开浏览到预约申请

```text
套餐详情或业务详情
  → 了解预约前置说明
  → 点击提交预约
  → 身份确认
  → 选择具体日期和固定时段
  → 填写必要信息
  → 提交申请
  → 显示待确认和实际失效时间
```

验收重点：提交申请不占硬档、不生成订单、不开放定金支付；客户知道工作室还需要确认。

### 10.3 预约确认到订单

```text
待确认预约
  → 工作室确认并重新校验冲突
  → 客户收到确认结果
  → 进入唯一对应订单
  → 查看订单快照和定金截止时间
```

验收重点：确认即成单，客户不能看到已确认但没有订单的长期中间状态；重复进入不会创建重复订单。

### 10.4 预约被拒绝或时段冲突

```text
预约待确认
  → 工作室拒绝或确认时发生冲突
  → 客户看到明确结果和安全原因
  → 重新选择套餐/日期/固定时段，或联系工作室
```

验收重点：不显示支付入口，不把拒绝或冲突显示为网络故障，不泄露其他客户资料。

### 10.5 订单到定金支付

```text
订单生成
  → 查看订单金额和定金截止时间
  → 发起定金支付
  → 成功 / 处理中 / 失败 / 待核验
  → 进入订单状态
```

验收重点：订单金额以快照为准，处理中不允许重复支付，定金逾期不与未知支付结果混淆。

### 10.6 拍摄到尾款

```text
订单已安排
  → 客户参加拍摄
  → 负责人或管理员确认拍摄完成
  → 客户看到尾款应付
  → 发起尾款支付
  → 尾款已付或处理中
```

验收重点：履约状态和支付状态分开；摄影师的内部操作不直接显示为拍摄完成或尾款已触发。

### 10.7 尾款到成片交付

```text
尾款已付
  → 工作室完成后期并发布交付
  → 客户身份和授权校验
  → 带水印预览
  → 精修图/原片无水印下载
  → 小程序入口在期限内开放
```

验收重点：尾款付清前没有预览或下载；交付发布、身份、授权和入口期限任何一项不满足，都显示对应原因和下一步。

### 10.8 订单失效后迟到支付

客户打开旧订单或支付返回时，如果订单已经因定金逾期失效：

- 显示订单已失效，不继续默认支付；
- 如果系统已收到支付但结果未知，显示处理中/待人工核对；
- 如果原时段仍可用，后续由系统或工作室按 A04/A14 规则重新校验；
- 如果原时段已被占用，不向客户承诺恢复预约；
- 客户可以联系工作室获取处理结果。

### 10.9 身份会话过期

客户在预约、订单、支付或交付页面会话过期时：

1. 保留不敏感的当前任务上下文；
2. 说明需要重新确认身份；
3. 完成后返回原页面并刷新服务端状态；
4. 取消或失败时返回原页面的安全版本；
5. 不因重新进入页面而重复提交、重复支付或重复下载授权。

## 11. 通知、待办与客户可见记录

A08 不拥有通知渠道，但需要将客户待办集中到可进入的业务页面。通知或站内状态至少可能涉及：

- 预约申请已提交；
- 预约确认、拒绝、失效或时段冲突；
- 需要补充信息或重新确认套餐版本；
- 订单生成和定金截止时间；
- 定金支付成功、处理中、失败或待核验；
- 定金临近逾期或订单已失效；
- 拍摄安排变化、改期确认或异常；
- 拍摄完成和尾款应付；
- 尾款支付结果和逾期；
- 交付发布和交付入口到期提醒；
- 退款处理中、成功或需要人工跟进。

通知不应是客户获取事实的唯一方式。客户打开预约、订单、支付或交付页面时，必须能看到当前真实状态。通知失败不能回滚业务事实，通知重复也不能创建重复业务动作。

## 12. 权限、隐私和公开边界的客户呈现

### 12.1 客户只看到属于自己的业务记录

小程序客户中心只展示当前身份有权访问的预约、订单、支付、履约和交付。家庭成员访问成片时，以 A11/A15 的显式授权为依据，不因同一家庭、同一设备或相同联系方式自动推断权限。

### 12.2 公开与私密内容分离

- 作品列表和案例详情是匿名公开内容；
- 私密交付入口是客户授权内容；
- 公开案例授权和私密交付授权不是同一件事；
- 客户支付尾款不自动授予公开案例授权；
- 案例公开授权撤回不自动删除客户私密交付文件；
- 交付文件不因被上传到工作室系统就自动成为公开作品。

### 12.3 客户可见文案不得暴露内部信息

客户侧不能看到：

- 数据库字段、内部状态名和实现异常；
- 其他客户的姓名、订单或档期；
- 授权证据、内部审核意见和撤回原因；
- 工作室内部备注、成本、权限判断；
- 本机路径、对象存储永久地址和第三方原始错误。

## 13. 功能需求清单

### 13.1 公开发现和浏览

- 查看已发布品牌和工作室资料；
- 查看首页区块和有效引用；
- 按作品分类浏览案例；
- 查看案例详情和有序图片；
- 查看摄影业务和标准套餐；
- 从作品进入关联业务/套餐；
- 从业务/套餐进入联系和预约；
- 在下架、无结果、加载失败和引用失效时显示明确状态；
- 公开浏览不强制登录。

### 13.2 联系和位置

- 一键拨打已发布电话；
- 查看/复制微信号或二维码；
- 查看地址、地图和文字地址；
- 查看联系时间和须知；
- 地图不可用时保留文字地址和其他联系方式；
- 未配置的社交渠道不显示；
- 联系动作不创建预约、订单或支付事实。

### 13.3 预约

- 从业务或套餐上下文进入预约；
- 显示预约前置条件；
- 选择具体日期和固定时段；
- 收集联系人和必要业务信息；
- 提交前完成身份确认或建立可追踪联系人；
- 提交后显示待确认、申请标识和实际失效时间；
- 查看待确认、补充、已确认、拒绝、失效和冲突结果；
- 避免重复提交；
- 预约确认前不展示定金支付入口。

### 13.4 订单、履约和支付

- 从预约确认进入唯一对应订单；
- 查看套餐、价格、服务、日期和时段快照；
- 查看定金和尾款应付及截止时间；
- 查看履约状态和客户准备事项；
- 发起定金或尾款支付；
- 查看支付成功、处理中、失败、待核验和逾期；
- 查看改期、取消、退款和异常的客户可见结果；
- 不用支付状态覆盖履约状态；
- 不用当前套餐数据覆盖订单快照。

### 13.5 交付

- 查看交付是否准备、发布和可访问；
- 在尾款、身份、归属、授权和期限均满足后查看预览；
- 查看带水印预览；
- 下载无水印精修图和原片；
- 查看交付入口开放截止时间；
- 访问到期、授权不足、尾款未付、文件异常时提供对应反馈；
- 不暴露永久文件地址；
- 入口到期后提供联系工作室的补充交付路径。

### 13.6 客户中心

- 未识别时显示身份确认和公开联系入口；
- 已识别时显示预约、订单、支付、履约和交付待办；
- 查看全部预约和订单；
- 快速进入待处理记录；
- 显示无记录空状态；
- 不把未确认的积分、优惠券、会员卡和喜欢功能当作正式承诺。

## 14. 验收标准

### 14.1 公开浏览

1. 匿名访客可以查看已发布品牌内容、作品、摄影业务、套餐和联系方式。
2. 首页、作品列表、案例详情、业务详情和套餐详情之间可以相互导航，并保留必要的返回上下文。
3. 公开端只展示 A05-A07 当前有效的公开内容，不显示草稿、未授权案例、已下架套餐和测试数据。
4. 作品分类、摄影业务和套餐所属关系在客户可见文案和入口上可以区分。
5. “查看作品”“查看套餐”“电话联系”“添加微信”“提交预约”不会被反馈为同一种结果。
6. 无内容、筛选无结果、下架、图片失效和加载失败有清晰的客户反馈和返回路径。

### 14.2 内容一致性

1. 首页、作品列表和详情读取同一案例事实，不出现固定 ID 导致的空白或内容错配。
2. 套餐列表和详情的名称、图片、业务、价格、定金说明和服务项一致。
3. 价格、活动价和固定定金读取同一有效套餐版本，不使用历史比例文案推导当前金额。
4. 首页、关于页和 Footer 的品牌、电话、微信、地址和地图口径一致。
5. 作品或套餐失效后，首页、列表、详情和相关入口不会继续展示失效卡片。
6. 客户无法通过客户端缓存的旧数据绕过服务端的版本、权限或状态校验。

### 14.3 预约体验

1. 客户可从业务或套餐进入预约，并看到所选业务和套餐上下文。
2. 客户只能选择工作室提供的具体日期和固定时段。
3. 提交前明确说明申请待确认、不占硬档、可能因冲突或套餐变化被拒绝。
4. 提交成功显示可识别申请、所选日期/时段、待确认状态和实际失效时间。
5. 提交预约不会生成订单、占用排他档期或开放定金支付。
6. 预约确认后客户可以进入唯一对应订单；重复确认不会产生重复订单。
7. 预约拒绝、申请失效和时段冲突分别有清晰状态、下一步和联系入口。
8. 套餐版本发生变化时，客户不会在没有说明和确认的情况下看到新价格或新服务被静默替换。

### 14.4 订单、支付和履约

1. 订单页面展示确认时冻结的套餐、服务、价格、日期和固定时段。
2. 定金和尾款分开显示，应付金额和截止时间与订单事实一致。
3. 支付未知结果显示处理中或待查单，不显示为成功或失败，也不引导重复付款。
4. 线下收款待核验时不显示为已支付。
5. 尾款只有在负责人或管理员确认拍摄完成后才成为客户可见的应付事项。
6. 支付状态、履约状态和交付状态分别展示，不互相自动推导。
7. 订单失效、迟到支付、改期、取消、退款处理中和退款失败待人工均有可理解反馈。
8. 客户无法通过刷新、返回或重复点击创建重复支付或重复业务记录。

### 14.5 交付和隐私

1. 尾款付清前，客户无法查看任何成片预览或下载入口。
2. 尾款付清后，仍需满足交付已发布、身份有效、订单归属正确、授权有效和入口未到期。
3. 满足条件时，小程序提供带水印预览和不加水印的正式精修图/原片下载。
4. 无权限、尾款未付、交付未发布、授权失效、文件异常和入口到期显示不同的客户反馈。
5. 公开案例授权和私密交付授权保持独立，作品页面不会泄露私密交付文件。
6. 客户页面不暴露客户真实姓名、订单内部信息、授权证据、内部备注、永久文件地址或其他客户资料。
7. 交付入口到期后明确提示联系工作室，不表述为工作室原文件已删除。

### 14.6 身份和返回路径

1. 浏览公开内容时不强制登录。
2. 提交预约、查看个人记录、支付和访问交付时，在合适的任务节点触发身份确认。
3. 身份确认成功后返回原任务，不把客户送回无关首页。
4. 身份会话过期后，重新确认不会重复提交预约、重复支付或改变订单状态。
5. 未识别的“我的”页面不显示测试姓名、测试手机号和虚假的订单数量。
6. 无权限反馈不泄露资源是否存在和其他客户信息。

### 14.7 可运营和可维护

1. 客户可通过统一内容源看到一致的品牌、作品、业务、套餐和联系方式。
2. 客户侧不依赖“开发中，敬请期待”作为正式功能的唯一反馈。
3. 业务记录页面能够提供当前状态和下一步，不依赖通知消息才能理解事实。
4. 发生错误时，客户看到安全、可理解的提示，必要时可携带 request id 联系工作室。
5. 公开页面和客户业务页面对加载、空状态、失败、处理中和权限异常有一致的交互原则。

## 15. 验证方式

### 15.1 工程和内容核验

在进入详细设计前，至少核验：

- 首页、作品、套餐、关于、Footer 和客户中心是否都读取统一公开内容；
- 任意有效作品和套餐 ID 是否可以正确打开详情；
- 下架、授权撤回、套餐版本替代后，首页和列表是否停止展示失效入口；
- 业务分类、作品分类和套餐所属业务是否在页面上保持可区分；
- 联系电话、微信、地址和地图是否来自同一权威内容；
- 错误码和客户侧文案是否能覆盖 AT09 的主要业务结果。

### 15.2 脱敏场景验证

至少准备以下脱敏客户场景：

1. 只浏览作品，不登录、不联系；
2. 从作品进入关联套餐，再返回作品详情；
3. 查看没有有效套餐的摄影业务并转电话/微信咨询；
4. 套餐有明确固定价格和定金，客户提交预约申请；
5. 预约提交后仍待确认，客户重复进入申请结果；
6. 两个客户申请同一日期和固定时段，其中一个确认成功，另一个发生冲突；
7. 套餐提交预约后下架或调价，客户需要重新确认；
8. 预约确认后生成订单，客户查看定金截止时间；
9. 支付结果未知，客户返回订单并避免重复支付；
10. 线下定金已登记但待核验；
11. 拍摄完成后出现尾款待支付；
12. 尾款逾期但订单未自动取消；
13. 尾款付清但交付尚未发布；
14. 交付发布后预约联系人正常预览和下载；
15. 非授权家庭成员访问交付；
16. 交付入口到期后申请补充交付；
17. 公开案例授权撤回，但客户私密交付仍需保留；
18. 身份会话过期后回到预约、支付和交付页面。

### 15.3 可用性测试

在没有真实客户数据前，应先用可控的目标用户访谈或原型测试观察：

- 客户能否分辨作品分类、摄影业务和标准套餐；
- 客户是否理解“提交预约”不是“预约成功”；
- 客户是否知道何时需要登录，是否在浏览阶段感到被打断；
- 客户是否能从作品自然进入服务、联系和预约；
- 客户是否能看懂固定定金、尾款和支付处理中；
- 客户是否能在下架、冲突、无结果和权限不足时找到下一步；
- 客户是否会把“我的相册”理解为已支付客户的私密交付；
- 客户是否把电话/微信联系理解为预约已经成立。

不应在缺少测试前设定虚构的转化率、完成时长或满意度目标。指标口径由 A16 结合真实业务基线继续确认。

## 16. 待确认经营内容与产品决策

以下事项需要工作室负责人或后续专题确认：

1. 小程序主导航是否继续保留“首页、作品、套系、关于、我的”五个 TabBar，还是将“服务/套餐”作为更清晰的命名。
2. 预约、订单、消息和交付是否集中在“我的”，还是需要额外的主入口；客户实际使用频率如何。
3. 小程序是否允许完整提交预约，还是部分业务只提供电话/微信咨询。
4. 六类摄影业务分别需要哪些预约前置信息，哪些信息只能在身份确认后收集。
5. 是否支持客户在预约申请提交后修改、补充或撤回；客户侧入口和人工处理方式是什么。
6. 客户身份采用手机号、微信身份、短信验证码或其他方式；电话/微信线下客户如何关联线上记录。
7. 客户更换手机号、多人共用联系方式或预约联系人与拍摄人不一致时，客户中心如何展示。
8. 预约确认、拒绝、冲突、失效和重新报价分别通过哪些通知方式告知客户。
9. 是否建设站内消息或待办中心，哪些通知必须可追溯查看。
10. 客户是否可以在小程序中直接发起改期、取消、退款或售后申请，还是统一联系工作室。
11. 作品搜索和套餐排序是否有真实使用需求；客户常用的筛选条件是什么。
12. “创始人档”在小程序中最终作为作品/品牌栏目、套餐档位还是其他概念展示。
13. 套餐价格、固定定金、尾款和交付说明需要以何种客户可理解的正式文案表达。
14. 没有标准套餐的业务是否统一显示“电话/微信咨询”，是否允许显示价格区间。
15. 关于页、Footer 和首页最终使用哪个电话、微信号、地址、地图和社交账号。
16. 是否展示用户评价、喜欢、积分、优惠券和会员卡；这些能力是否有真实经营规则和数据来源。
17. 客户在交付入口到期后希望通过网盘、重新开放小程序还是其他方式补充获取成片。
18. 是否允许客户在小程序中选择授权家庭成员或只能由后台添加。
19. 公共内容和客户业务记录的删除、导出、隐私查看和客户注销需求是什么。
20. 真实客户完成“浏览→联系/预约→确认→支付→交付”的典型路径和主要流失点是什么。

- A12：预约表单、固定时段、申请结果、冲突、改期和取消的客户呈现；

## 18. 结论

当前工程已经证明 SouthLeaf 需要一个以公开展示为入口、能够逐步承载预约、订单、支付、履约和成片交付的微信小程序，但现有实现仍主要是页面视觉原型：公开内容存在硬编码和多处副本，作品与套餐详情不稳定，关于页与 Footer 联系事实不一致，客户中心使用测试用户和占位功能，正式业务状态和身份边界尚未建立。

A08 确立的客户体验目标是：

```text
匿名客户可以可信地发现、浏览和理解工作室；
客户可以从作品/业务/套餐自然进入联系或预约；
提交预约、预约确认、订单生成、支付、履约和交付被明确区分；
需要身份时在任务节点触发，并能返回原任务；
每个状态、异常和权限结果都有安全、可理解的下一步；
公开内容、客户业务记录和私密成片保持清晰边界。
```

A08 不拥有品牌、作品、套餐、客户身份、预约、订单、支付、交付或授权事实；它负责把这些模块的有效结果组织成客户能够理解和完成的任务路径。当前仍需通过负责人确认、脱敏业务案例和客户可用性测试验证导航结构、身份方式、预约入口、客户中心和通知体验。未完成这些验证前，不应据此锁定最终数据库结构、API 契约、页面组件或具体编码方案。
