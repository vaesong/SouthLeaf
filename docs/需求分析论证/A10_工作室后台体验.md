## 1. 专题目的

本专题分析 SouthLeaf 工作室工作人员如何通过受控后台维护公开内容、处理预约和档期、跟进客户与订单、记录支付和履约、完成成片交付，并在支付、授权、通知和文件异常时进行人工补偿。

后台不是面向客户的公开展示页面，也不是把数据库对象直接堆成菜单。后台要帮助一个单工作室在每天的经营任务中回答：

- 今天有哪些预约申请需要处理；
- 哪些日期和固定时段已经确认、待确认或临时封档；
- 哪些客户需要联系、补充资料或重新确认；
- 哪些订单等待定金、拍摄、尾款、后期或交付；
- 哪些线上支付、线下收款、退款和通知需要核验；
- 哪些文件没有校验、交付没有发布或客户访问出现问题；
- 哪些高风险操作由谁执行、为什么执行、是否需要负责人审核；
- 外部服务或异步任务失败后，工作室如何看到并处理，而不是直接改一个最终状态。

本文件回答：

- 工作室负责人、管理员和摄影师各自承担哪些后台任务；
- 后台工作台应该围绕哪些待办、风险和客户服务任务组织；
- 品牌内容、作品、业务和套餐如何维护、预览、发布和下架；
- 电话/微信形成的预约如何录入并与线上申请共用同一档期事实；
- 预约确认、成单、支付、履约、交付和授权在后台如何连续处理；
- 线下收款、退款、通知、文件和档期异常如何进入人工处理；
- 哪些操作需要负责人权限、二次确认、审计或补偿记录；
- 当前工程已经具备什么、缺少什么，以及后台体验如何验收。

本专题不定义最终数据库表、API 字段、后台框架、页面组件、部署方式或实施阶段。业务状态和可靠性规则由 A04、A11-A15 及 AT05-AT09 分别负责；A10 负责把这些事实组织成工作室能够理解、执行和追溯的后台任务体验。

A10 的核心判断是：

```text
后台负责让工作室看见待办、理解业务事实、执行受控动作、处理异常并留下证据；
后台不能把“直接编辑状态”当作业务流程，也不能用一个万能管理员角色替代负责人、管理员和摄影师的职责边界；
客户侧看到的预约、订单、支付、履约和交付结果，必须来自后台已经完成且可追溯的业务动作。
```

## 2. 专题边界与规则归属

### 2.1 A10 拥有的需求

A10 负责以下工作室后台体验需求：

- 工作室负责人、管理员和摄影师的后台角色任务地图；
- 工作台首页、待办、风险提示和跨模块导航；
- 内容、作品、摄影业务、套餐、档期、客户、预约、订单、支付、履约和交付任务的后台组织方式；
- 后台操作前置条件、需要确认的风险、操作结果和下一步；
- 线上预约与电话/微信预约进入同一后台处理流程的体验要求；
- 内容草稿、预览、发布、下架、恢复、版本替代和变更记录的后台任务表达；
- 客户联系、资料补充、敏感信息最小展示和客户业务关联的工作体验；
- 高风险财务、授权、档期和交付动作的审核、二次确认和审计提示；
- 支付处理中、线下收款待核验、退款失败、通知失败、文件异常和档期异常的人工补偿入口；
- 后台加载、空状态、冲突、版本过期、权限不足、处理中和失败待人工的反馈；
- 后台操作可追溯、可解释和可恢复的体验验收标准。

### 2.3 A10 的唯一主规则

工作室工作人员在后台执行的操作必须遵守以下关系：

```text
查看记录 ≠ 修改业务事实
编辑草稿 ≠ 公开发布
提交预约申请 ≠ 确认预约
确认预约 = 重新校验冲突、占档并自动成单
登记线下收款 ≠ 收款已核验
发起退款 ≠ 退款已成功
摄影师记录拍摄信息 ≠ 拍摄已完成且尾款已激活
上传文件 ≠ 文件已校验或交付已发布
交付发布 ≠ 客户一定有权访问
公开案例发布 ≠ 客户已经同意公开授权
人工补偿 ≠ 可以无审计地覆盖原始事实
```

后台应让操作人清楚看到当前事实、可执行动作、动作前置条件、动作风险和动作结果。高风险操作需要使用明确的业务动作，不允许通过通用编辑入口直接把最终状态改成目标值。

## 3. 证据口径

| 标记 | 含义 |
|---|---|
| 已确认需求 | 已由用户讨论、A01-A09 或架构基线明确的工作室业务约束 |
| 原型证据 | 当前代码、页面、接口或资源中确实存在的内容，只能证明历史原型表达过该方向 |
| 产品建议 | 为形成可运营后台提出的候选任务和交互方式，仍需结合工作室日常工作验证 |
| 待验证行为 | 尚无真实工作人员访谈、处理记录、操作时长或异常统计支持的判断 |
| 待确认经营内容 | 负责人需要提供的正式套餐、联系方式、排班、审核和授权内容 |

当前仓库没有真实后台用户、后台操作日志、工作室人员访谈、预约处理量、支付对账记录、文件交付记录或异常处理统计。因此，本专题可以建立后台任务和安全边界，但不能把菜单顺序、待办优先级、审批人数、处理时效或角色配置假设为已验证事实。

## 4. 当前工程证据与问题

### 4.1 没有独立后台前端和后台路由

当前工程主要是 `frontend/` 下的 uni-app 客户侧公开展示原型，以及 `backend/` 下的 Spring Boot 原型服务。当前没有可验证的：

- 独立后台前端目录或后台应用入口；
- 后台登录页、身份会话和员工账号管理；
- 负责人、管理员、摄影师的角色切换或权限界面；
- 工作台、预约处理、订单跟进、支付核验或交付管理页面；
- 后台待办、异常队列、操作确认和审计查询入口；
- 后台预览、发布、下架和版本回滚体验。

当前客户侧 `frontend/pages.json` 只有首页、作品、套餐、关于和我的页面，不能证明存在后台业务入口。客户侧 `my` 页面中的订单、相册等入口均为测试或占位体验，也不能直接转化为后台已实现能力。

### 4.2 后端只有原型级公开数据接口

当前后端可以观察到分类、套餐和轮播相关控制器，例如：

- `backend/src/main/java/cn/zhinan/uniapp/controller/CategoryController.java`；
- `backend/src/main/java/cn/zhinan/uniapp/controller/PackageController.java`；
- `backend/src/main/java/cn/zhinan/uniapp/controller/SwipperController.java`。

这些接口主要提供分类、套餐和轮播的基础查询或 CRUD 原型，当前没有独立的：

- 后台认证、员工账号、角色和资源权限；
- 内容草稿、预览、发布、下架、恢复和版本历史；
- 预约申请、固定时段、冲突校验和确认成单；
- 客户档案和线上/线下联系人关联；
- 订单、支付分期、线下收款、退款和对账；
- 履约事件、拍摄完成和尾款激活；
- 文件上传校验、交付批次、授权和访问控制；
- 通知任务、失败重试、人工补偿和审计记录。

因此，现有基础接口只能作为历史原型证据，不能被描述为“后台已经具备内容和经营管理能力”。

### 4.3 内容维护缺口

A05 已记录当前品牌、团队、电话、地址和首页内容大量硬编码，`about.vue` 与 `FooterInfo.vue` 之间还存在电话、地区和地址不一致。后端没有品牌资料、首页编排、团队、服务流程、联系方式、地址、营业时间、FAQ 或评价的内容模型和后台维护能力。

后台需要解决的不是让工作人员修改更多硬编码，而是让统一内容事实经历：

```text
编辑草稿 → 校验完整性 → 受控预览 → 发布 → 公开端读取已发布版本 → 下架/恢复/版本追踪
```

### 4.4 套餐和分类原型不能直接作为后台经营模型

当前 `Package` 和通用 `Category` 只能说明历史原型有套餐和分类概念，不能证明：

- `Category` 是摄影业务、作品分类还是套餐展示分组；
- 套餐有稳定摄影业务归属和版本；
- 价格和活动价当前有效；
- 定金已经符合固定金额规则；
- 服务内容已经结构化且可以冻结到订单；
- 套餐具备发布、下架、替代和历史追溯能力。

后台应按照 A07 的业务边界维护摄影业务、标准套餐和可选展示分组，而不是继续以通用分类名称承载不同业务含义。

### 4.5 当前错误反馈无法支持后台运营

客户侧请求封装已经有 token 读取、超时和部分 HTTP 错误提示雏形，但仍以 `code === 200` 判断成功，未形成 AT09 定义的稳定业务错误码消费方式。后台若沿用这种方式，将无法区分：

- 固定时段冲突；
- 套餐版本失效；
- 订单已存在；
- 支付处理中；
- 线下收款待核验；
- 退款失败待处理；
- 文件校验失败；
- 交付发布条件不足；
- 当前角色无权操作。

后台必须能让工作人员知道是刷新、联系客户、重试、转负责人审核还是进入人工补偿，而不是只看到一个通用失败提示。

### 4.6 当前问题结论

| 问题 | 当前表现 | 工作室运营风险 |
|---|---|---|
| 没有后台应用 | 只有客户侧展示原型 | 无法持续维护公开内容和处理业务 |
| 没有员工身份边界 | 没有后台登录、角色和权限证据 | 敏感客户、支付和成片可能被越权访问 |
| 内容硬编码 | 品牌、联系方式、作品和套餐分散在页面 | 更新依赖开发者，容易出现跨端矛盾 |
| 业务对象不清 | 通用分类混用作品、业务和套餐概念 | 后台操作容易误改错误对象 |
| 没有预约处理链路 | 无线上/线下统一录入和冲突校验 | 电话微信预约可能与线上档期冲突 |
| 没有订单快照 | 无确认成单、价格冻结和修订记录 | 套餐变更可能影响既有客户承诺 |
| 没有支付和退款台账 | 无回调、查单、线下核验和退款队列 | 账实不符或重复处理无法追踪 |
| 没有履约确认边界 | 无拍摄完成和尾款触发动作 | 摄影师或错误操作可能误触发收费 |
| 没有交付工作流 | 无上传、校验、发布和授权流程 | 未校验或未授权文件可能被开放 |
| 没有异常补偿 | 失败只能依赖手工数据库修改或口头处理 | 无法安全恢复和证明操作原因 |
| 没有审计 | 无操作者、原因、前后状态和请求标识 | 高风险操作不可追溯 |

## 5. 后台角色与任务地图

### 5.1 工作室负责人

负责人是单工作室经营和高风险事项的最终责任人，主要任务包括：

- 确认品牌、作品、套餐、联系方式和公开授权等正式内容；
- 决定套餐版本、价格、固定定金和服务承诺的生效；
- 审核退款、特殊取消、重大改期和异常财务处理；
- 处理预约冲突、工作室原因取消和不可归责事件；
- 确认或复核公开案例授权、私密成片授权和交付补充；
- 查看高风险操作、敏感客户资料和完整审计；
- 处理通知、支付、退款、文件和档期失败待人工事项；
- 检查运营数据和未完成待办，决定是否需要人工联系客户。

负责人不应被迫处理所有低风险日常录入，也不应依赖“万能管理员”身份才能完成高风险审核。后台需要把需要负责人介入的任务集中呈现，并说明介入原因。

### 5.2 管理员

管理员负责日常运营和客户跟进，主要任务包括：

- 编辑内容草稿、整理作品和套餐资料；
- 查看和处理线上预约申请；
- 录入电话/微信形成的线下预约；
- 联系客户、补充客户资料和记录沟通结果；
- 查看确认订单、安排拍摄和跟进履约；
- 记录拍摄完成、缺席、取消、补拍和服务异常；
- 录入线下收款、核对凭证并提交复核；
- 上传和校验被授权的成片文件；
- 发送或补发客户通知；
- 处理不涉及最终财务或公开授权的日常异常。

管理员默认不能直接修改已生成订单的价格和服务快照，不能绕过负责人审核确认高风险退款或改变客户公开授权，不能把上传文件直接发布为客户可访问交付。

### 5.3 摄影师

摄影师是履约协作角色，任务范围应尽可能聚焦于被分配的拍摄：

- 查看自己被分配的预约和拍摄安排；
- 查看完成拍摄所需的最小客户信息；
- 记录必要的拍摄备注、到场情况和履约事件；
- 按授权上传对应订单的文件，查看上传和校验结果；
- 向负责人或管理员反馈拍摄异常、补拍建议和文件问题。

摄影师默认不能：

- 查看其他订单或客户；
- 确认预约、占用或释放档期；
- 修改套餐、价格、订单快照或退款；
- 确认拍摄完成并直接激活尾款；
- 发布、撤回或公开授权成片；
- 查看完整支付凭证、审计记录或系统配置。

首版是否启用独立摄影师账号仍需负责人确认。即使首版暂不启用，后台任务和权限边界也不能把摄影师假设成负责人或管理员。

### 5.4 客户和非人工身份

客户使用客户侧身份入口，不使用后台菜单。支付回调、系统任务和对象存储服务身份也不是后台工作人员：

- 支付回调只能验证和落支付事实，不能代替负责人审核退款；
- 系统任务只能执行明确授权的失效、查单、通知或到期处理，不能绕过业务审计；
- 对象存储只提供受控上传或短期访问能力，不能自行判断客户是否有权访问文件。

### 5.5 后台任务地图

| 角色 | 高频任务 | 任务成功结果 | 主要风险 |
|---|---|---|---|
| 负责人 | 审核退款/授权/特殊取消 | 形成明确审核事实和后续任务 | 财务、隐私和不可逆操作 |
| 负责人 | 发布正式套餐或公开案例 | 公开端读取有效版本 | 错价、未授权或错误发布 |
| 负责人 | 处理异常队列 | 失败事项有补偿结果 | 覆盖原事实或重复处理 |
| 管理员 | 处理待确认预约 | 确认成单或给出拒绝/补充结果 | 时段冲突、客户沟通遗漏 |
| 管理员 | 录入线下预约 | 线上线下共用档期事实 | 绕过冲突产生双重占档 |
| 管理员 | 跟进订单和履约 | 客户状态和内部任务同步 | 把支付、履约、交付混为一谈 |
| 管理员 | 登记线下收款 | 收款事实待核验或已核验 | 金额、凭证和重复收款 |
| 管理员 | 上传和校验成片 | 文件具备发布前条件 | 文件归属、完整性和隐私 |
| 摄影师 | 查看分配安排 | 按正确订单完成拍摄 | 越权访问客户 |
| 摄影师 | 记录履约/上传文件 | 内部履约事实或待校验文件 | 误触发尾款或公开访问 |

## 6. 工作台与待办体验

### 6.1 工作台目标

后台首页应围绕“今天需要处理什么”和“哪些事情可能造成损失”组织，而不是只展示访问量或孤立的数量卡片。工作台至少应能进入：

- 待确认预约；
- 即将失效的预约申请；
- 待支付定金或即将逾期的订单；
- 即将到来的拍摄安排；
- 待确认拍摄完成或履约异常；
- 待支付尾款和尾款逾期；
- 待上传、待校验、待发布的交付；
- 待核验线下收款；
- 支付处理中、退款处理中和失败待人工；
- 通知失败、任务失败和需要负责人处理的高风险事项；
- 内容草稿、待预览、待发布、已过期或失效引用。

具体数量、排序和提醒时效应由 A16 和实际运营验证，不能在需求分析阶段虚构经营指标。

### 6.2 待办分组

后台应区分以下待办含义：

| 待办类型 | 说明 | 操作人应看到的下一步 |
|---|---|---|
| 待处理 | 业务记录等待工作人员作出正常决定 | 打开记录、补充信息、确认或拒绝 |
| 即将到期 | 记录在默认期限内即将失效 | 联系客户、完成处理或记录原因 |
| 待核验 | 外部或线下事实已登记但尚未确认 | 查看凭证、核验或转负责人 |
| 处理中 | 已发起动作，尚无最终结果 | 查看状态、等待查单或避免重复操作 |
| 失败可重试 | 明确失败且符合重试条件 | 按稳定动作重试并记录结果 |
| 失败待人工 | 自动重试不足或结果不确定 | 进入补偿流程、联系外部或负责人 |
| 权限受限 | 当前角色不能完成下一步 | 查看原因、申请负责人处理，不绕过权限 |
| 信息不完整 | 缺少完成任务所需资料 | 联系客户或补齐内部资料 |

同一记录可以同时有多个提示，例如“支付处理中且预约申请临近失效”。后台不能用一个笼统的红色错误覆盖所有业务事实。

### 6.3 工作台操作原则

- 待办卡片必须能进入具体业务记录，不只显示不可操作的数字；
- 进入详情时显示来源、当前状态、最近动作、操作者和下一步；
- 处理完成后从待办移除或转入历史，但历史记录仍可查询；
- 批量操作只用于低风险、同一业务含义且可以安全撤销的动作；
- 确认预约、退款、公开发布、授权变更和交付发布默认不做无提示批量处理；
- 失败操作显示稳定业务错误和 request id，必要时进入异常队列；
- 刷新和重复点击不能创建重复订单、支付、退款、通知或授权；
- 工作台不能把“没有待办”解释为“没有业务记录”。

## 7. 内容、作品与套餐维护体验

### 7.1 公共内容维护

后台需要支持负责人或授权管理员维护：

- 品牌名称、Logo、标语和介绍；
- 首页区块和推荐顺序；
- 工作室资料、服务区域和服务流程；
- 团队公开资料；
- 电话、微信、社交渠道、地址、地图和联系时间；
- 预约须知、FAQ 和公开通知。

编辑页面应标明内容的适用端，例如官网、小程序或两者共享；共享内容不能在不同端分别维护出两套联系方式、地址、价格或授权状态。

### 7.2 草稿、预览、发布和下架

公共内容、作品和套餐应有清晰的后台生命周期：

```text
草稿 → 校验通过 → 受控预览 → 发布 → 下架/替代/恢复
```

后台体验至少需要：

- 编辑内容时显示必填资料和影响范围；
- 预览使用接近公开端的内容编排，但不能被匿名搜索或公开分享；
- 发布前检查图片、联系方式、价格、固定定金、授权和关联对象；
- 发布后明确显示当前生效版本和发布时间；
- 下架时说明对官网、小程序、搜索/分享链接和已有业务记录的影响；
- 已被预约或订单引用的套餐版本不能通过普通编辑覆盖；
- 发布失败时保留上一个有效公开版本，不出现半发布状态；
- 恢复或替代需要保留操作者、原因和前后版本；
- 高风险公开发布和客户授权变更按权限要求负责人确认。

### 7.3 作品与案例

作品后台应支持工作室完成以下任务：

- 创建或编辑作品案例；
- 维护作品分类、标题、摘要、排序和关联业务；
- 上传图片、调整顺序、选择封面并查看文件状态；
- 查看图片公开资格和授权状态；
- 预览公开案例；
- 处理案例级、人物级和单图级授权撤回；
- 在文件、授权或内容异常时阻止公开发布；
- 下架案例或移除单图后看到公开资格重新计算结果。

A10 不重新定义 A06 的公开资格规则。后台必须把“无法公开”的原因表达为待处理事实，例如“缺少授权”“图片未校验”“关联内容已失效”，而不是允许工作人员直接勾选“公开”绕过规则。

公开案例和私密交付文件必须在后台任务和预览入口上分开。客户已支付尾款、已获得交付或已被授权访问，不等于可以把同一文件直接公开为案例。

### 7.4 摄影业务与套餐

后台需要区分：

- 摄影业务目录：儿童、亲子全家福、婚纱、写真、孕照、证件照；
- 作品分类：服务于作品浏览，不自动等同于业务；
- 标准套餐：归属于某一摄影业务并供客户理解和选择；
- 套餐展示分组：只有负责人确认有实际运营需要时才建立。

套餐编辑和发布任务至少应能表达：

- 所属摄影业务；
- 可识别版本；
- 标题、摘要、封面和服务说明；
- 当前价格表达、固定定金金额和尾款说明；
- 服务项、数量、单位、时长、适用范围和地点；
- 预约前置条件和是否需要咨询；
- 公开作品关联；
- 公开状态、生效时间、替代版本和下架原因。

后台必须明确提示：

- 修改已发布套餐会影响新的预约展示，但不能回写已有订单快照；
- 待确认预约引用的套餐版本发生变化时，不能静默替换为新版本；
- 价格、固定定金或服务项缺失时，套餐不能被发布为可直接选择；
- 历史 30%/50% 定金比例不能作为当前套餐规则；
- 删除不是默认的历史处理方式，已被业务引用的版本应可追溯。

## 8. 档期、预约与客户跟进体验

### 8.1 档期工作视图

后台应提供围绕日期和固定时段的工作视图，帮助工作人员区分：

- 可提交申请的固定时段；
- 待确认申请数量；
- 已确认并排他占用的时段；
- 临时封档；
- 已取消、已失效或已释放的时段；
- 改期中的原时段和目标时段。

待确认申请不应在视图中伪装成排他占用。对同一日期和固定时段存在多个待确认申请时，后台应显示竞争关系和确认风险，但不能让工作人员误以为所有申请都已经占档。

### 8.2 线上申请和线下预约统一进入

电话或微信沟通形成预约意向后，管理员需要能够录入系统，并至少记录：

- 来源为电话、微信、官网、小程序或其他已配置渠道；
- 客户联系人和必要身份关联；
- 摄影业务和套餐版本；
- 日期和固定时段；
- 客户需求、备注和工作室承诺；
- 当前处理人和处理时间。

线下录入必须复用同一档期冲突规则，不能因为是工作人员在后台录入就绕过占档校验。录入失败时应说明冲突、套餐失效、字段不完整或服务不可用，并保留可安全修正的资料。

### 8.3 预约审核和确认

预约详情应集中显示：

- 申请来源、申请时间和实际失效时间；
- 客户联系人及允许展示的必要资料；
- 摄影业务、套餐版本和客户提交时看到的内容；
- 日期、固定时段和当前档期占用情况；
- 客户备注、工作室备注和待补信息；
- 当前状态、最近动作、操作者和通知结果。

工作人员可以按权限执行：

- 接受并补充信息；
- 拒绝申请并选择安全原因；
- 要求客户补充或重新确认；
- 确认预约并自动生成订单；
- 记录客户已通过电话/微信确认的内容；
- 在允许条件下发起改期或取消处理。

确认预约时后台体验必须明确显示这是高风险业务动作。确认前应让操作人核对日期、固定时段、客户、套餐版本、价格、固定定金和服务内容；确认后应显示排他占档和订单生成结果。重复确认应返回既有订单，而不是创建新订单。

### 8.4 冲突、失效和封档

后台发生以下情况时应分别反馈：

| 情况 | 后台含义 | 后续动作 |
|---|---|---|
| 待确认申请失效 | 超过该申请保存的实际截止时间 | 联系客户或重新提交，不直接确认 |
| 确认时段冲突 | 另一确认动作已先占用时段 | 通知客户冲突，提供改期或重新申请 |
| 套餐版本失效 | 原申请依赖的套餐已替代/下架 | 重新确认版本或拒绝并说明 |
| 临时封档 | 不再接受新的申请 | 不自动取消已确认预约，人工处理受影响客户 |
| 订单定金逾期 | 订单失效条件已满足 | 先核验支付/线下收款/处理中状态，再释放档期 |
| 迟到支付未知 | 可能已发生外部支付事实 | 查单、重新校验时段或进入退款/人工处理 |

临时封档不能静默取消已有确认预约。工作室原因无法履约时，后台必须进入联系客户、协商改期或取消、退款和通知链路。

## 9. 客户、订单与履约跟进体验

### 9.1 客户资料和业务关联

后台客户视图应服务于当前业务，不是无限收集个人资料。工作人员需要能够：

- 查找和识别预约联系人；
- 将电话/微信客户与线上身份关联；
- 区分预约联系人、实际拍摄人和被授权家庭成员；
- 查看与当前工作人员权限相符的预约、订单和交付记录；
- 补充必要的联系、拍摄和交付信息；
- 记录客户沟通结果和待办；
- 在资料冲突时发起人工核验，而不是静默合并两个客户。

敏感信息需要最小必要展示、脱敏和访问审计。A11 将继续确定客户身份绑定、资料变更、家庭成员和隐私保留规则。

### 9.2 订单详情

订单后台详情应以确认时冻结的订单事实为中心展示：

- 订单识别信息和来源预约；
- 客户联系人、拍摄人和允许查看的关系；
- 套餐名称、版本、价格、固定定金、尾款和服务内容快照；
- 日期、固定时段、地点和拍摄准备事项；
- 定金、尾款和退款的分开事实；
- 履约状态、支付状态和交付状态的分开表达；
- 改期、取消、修订、补拍和异常记录；
- 最近操作、处理人、通知结果和审计入口；
- 当前允许的业务动作及其前置条件。

后台不能直接编辑订单快照来“修正”新套餐内容。需要调整时必须通过改期、订单修订、协商补充或人工补偿等明确业务动作，保留原快照和修订原因。

### 9.3 拍摄安排和履约

后台应让管理员和摄影师看到与角色相符的拍摄安排：

- 日期、固定时段、地点和客户准备事项；
- 摄影业务、套餐服务范围和必要拍摄信息；
- 被分配的摄影师和协作人员；
- 到场、缺席、取消、补拍和服务异常记录；
- 客户可见通知和内部备注的区分。

履约状态不能从定金或尾款支付状态自动推导。负责人或管理员确认拍摄完成后，才能激活尾款应付。摄影师可以记录履约事实或提交完成建议，但不能直接把记录解释为尾款已触发。

### 9.4 改期、取消和订单异常

改期应保留原预约、原订单快照和支付事实，后台需显示：

- 原日期和固定时段；
- 新日期和固定时段；
- 新时段冲突校验结果；
- 修订版本和客户确认状态；
- 定金沿用、补收或退款待处理结果；
- 客户通知和负责人审核记录。

取消应区分客户原因、工作室原因、不可归责事件和其他待审核原因。后台不能仅把订单状态改成“取消”而不记录责任原因、退款处理、档期释放和通知结果。

## 10. 支付、线下收款、退款与对账体验

### 10.1 支付状态工作视图

后台应能从订单或支付任务进入：

- 定金待支付、处理中、成功、失败、逾期和待核验；
- 尾款未激活、待支付、处理中、成功、逾期；
- 重复支付、超额支付、金额不匹配和订单不匹配；
- 线上支付回调、主动查单和对账结果；
- 线下现金、转账、线下微信等收款记录；
- 退款申请、审核、处理中、成功和失败待人工。

后台必须同时显示“支付操作/请求”“支付事实”“订单摘要”三者的关系，不能因为点击了支付或收到了前端返回就显示为成功。

### 10.2 线下收款

管理员可以按权限登记线下收款，但记录至少需要包含：

- 收款订单和分期；
- 实收金额；
- 收款方式；
- 收款时间；
- 经办人；
- 凭证、截图或备注；
- 核验状态；
- 核验人和核验时间。

未核验的线下收款不能满足定金、尾款或交付访问门槛。重复凭证、金额不符、分期不符或无法确认来源时，应进入待处理而不是自动计入其他分期。

### 10.3 退款和财务高风险动作

退款后台体验应分开呈现：

```text
退款申请 → 责任与金额审核 → 外部退款请求 → 处理中/查单 → 成功或失败待人工 → 客户通知
```

负责人需要看到：

- 原订单、原支付事实和可退金额；
- 客户/工作室/不可归责原因；
- 退款金额和计算依据；
- 关联的取消、改期或履约异常；
- 审核意见、操作人、幂等号和外部结果；
- 是否需要联系客户或人工补偿。

管理员可以发起退款申请，但默认不能绕过负责人完成最终审核和金额确认。网络超时不允许直接重复发起退款；明确失败达到重试阈值后进入失败待人工。

## 11. 成片、交付与公开授权体验

### 11.1 上传和文件校验

后台需要区分上传会话、业务文件、文件校验和交付批次。工作人员应看到：

- 文件属于哪个订单、客户和交付批次；
- 文件类型是精修图、原片或其他已确认类型；
- 上传进度和上传结果；
- 文件大小、类型、哈希或其他校验结果；
- 文件缺失、对象不存在、元数据缺失和校验失败；
- 可以重传、等待处理或进入人工补偿的下一步。

上传成功不等于文件可以交付。未完成校验的文件不能发布；业务记录不存在但对象存在时，需要进入孤立对象处理，不应让工作人员通过文件地址直接分享。

### 11.2 发布交付

发布交付批次前，后台应让操作人核对：

- 订单和客户归属；
- 尾款是否已经形成有效支付事实；
- 所有要发布的文件是否已校验；
- 交付范围、精修图和原片是否清楚；
- 预约联系人和显式授权家庭成员；
- 小程序入口开放期限；
- 客户通知内容和发布影响。

发布成功后应显示批次、发布时间、开放截止时间和客户可见状态。发布失败时保持未发布，不产生半可访问交付。

### 11.3 私密交付授权

后台需要明确区分：

- 预约联系人默认交付授权；
- 其他家庭成员由后台显式添加；
- 客户身份、订单归属、尾款、交付发布和入口期限共同决定访问；
- 公开案例授权和私密交付授权相互独立；
- 客户支付尾款不自动授权公开案例；
- 公开案例撤回不自动删除客户私密交付。

授权变更必须显示授权对象、范围、起止时间、操作者、原因和通知结果，不能通过修改客户姓名或手机号绕过授权校验。

### 11.4 公开案例授权

公开案例发布前，后台需要能够查看客户明确同意的公开授权事实及其范围。授权缺失、过期或撤回时：

- 阻止公开发布或继续公开；
- 显示安全的内部处理原因；
- 触发 A06 的案例资格重新计算；
- 保留客户私密交付，不把公开撤回解释为交付删除；
- 记录处理人、时间和通知结果。

### 11.5 入口到期和补充交付

小程序交付入口默认开放 1 周，实际截止时间保存在批次记录。入口到期时：

- 关闭客户侧小程序访问；
- 不删除工作室原文件；
- 后台生成到期或补充交付待办；
- 负责人可以按权限登记网盘或其他人工补充交付；
- 补充交付需要记录接收人、范围、链接有效期、操作者和原因；
- 失效链接可以重新生成，旧链接的撤回或替换仍需可追溯。

## 12. 异常、通知和人工补偿体验

### 12.1 异常队列

后台应有统一的异常入口，但异常列表仍要按业务类型和下一步分组。至少覆盖：

- 预约确认冲突；
- 预约或订单失效任务失败；
- 支付结果未知、主动查单失败和金额不匹配；
- 线下收款待核验或凭证重复；
- 退款处理中、退款失败或外部结果未知；
- 通知发送失败或模板内容失效；
- 文件上传失败、对象缺失、完整性校验失败；
- 交付发布失败、授权不足或入口恢复失败；
- 公开案例授权缺失或撤回；
- 角色无权、版本过期或重复操作。

每条异常至少显示：

- 业务类型和关联记录；
- 当前安全状态；
- 发生时间、最近尝试和失败次数；
- 最后错误的安全摘要；
- request id、task id 或外部业务号；
- 当前角色能执行的动作；
- 是否需要负责人、外部平台或客户介入；
- 处理结果、原因和审计入口。

### 12.2 人工补偿动作

后台需要提供明确的补偿动作，而不是开放“强制成功/强制失败”编辑框。可包括：

- 重新查单；
- 重新发送通知；
- 核验、驳回或补充线下收款凭证；
- 审核退款失败并登记外部处理结果；
- 释放异常档期占用；
- 恢复误下架的交付入口；
- 重新发起文件校验或上传会话；
- 登记网盘补充交付；
- 记录客户已通过电话/微信获知的处理结果。

补偿动作需要说明影响、操作者、原因和幂等关系。补偿不能删除原始失败记录、覆盖已成功支付事实或绕过负责人权限。

### 12.3 通知任务

后台需要能够查看客户通知是否：

- 已创建；
- 待发送；
- 已发送；
- 失败待重试；
- 失败待人工。

通知失败不回滚预约确认、订单生成、支付事实、退款结果或交付发布。重复补发不能创建重复业务事实，后台应显示已发送内容的摘要和发送时间，避免工作人员误以为客户一定未收到通知。

### 12.4 后台通用状态

| 状态 | 后台反馈 | 建议行动 |
|---|---|---|
| 加载中 | 正在读取记录 | 等待，不重复提交 |
| 空状态 | 当前筛选下没有记录 | 清除筛选、创建新任务或返回 |
| 信息不完整 | 继续处理缺少必要资料 | 补充资料或联系客户 |
| 版本过期 | 当前页面不是最新业务版本 | 刷新后重新确认 |
| 冲突 | 目标动作与最新事实冲突 | 查看当前状态，选择改期或人工处理 |
| 无权限 | 当前角色不能执行 | 申请负责人或按允许动作继续 |
| 处理中 | 已发起且尚无最终结果 | 查看任务，不重复发起 |
| 可重试失败 | 明确失败且可以再次执行 | 按业务动作重试 |
| 失败待人工 | 自动流程不能安全得出结论 | 进入补偿、联系外部或负责人 |
| 已完成 | 业务事实已经产生 | 查看后续待办和审计 |

## 13. 权限、隐私与审计体验

### 13.1 权限判断

后台不能只根据角色显示一个固定菜单。每次操作至少需要结合：

```text
角色 + 操作 + 资源归属 + 当前业务状态 + 敏感数据范围
```

例如：

- 管理员可以处理预约，但不能直接审核最终退款；
- 摄影师可以看被分配的拍摄，但不能查看其他客户；
- 管理员可以上传文件，但不能自动发布未经校验的交付；
- 负责人可以审核公开授权，但仍需存在客户明确同意事实；
- 已认证角色如果资源不属于其工作范围，也不能通过详情链接绕过列表权限。

### 13.2 敏感信息展示

后台应按任务展示必要资料：

- 拍摄执行只显示完成工作所需的客户信息；
- 财务处理显示必要的收款和退款资料，敏感凭证按角色脱敏；
- 文件处理显示归属、类型和授权范围，不默认开放永久对象地址；
- 完整审计和客户敏感资料仅向负责人或受限授权角色开放；
- 客户内部备注、授权证据和隐私内容不能出现在公开端或不相关角色界面。

### 13.3 高风险操作确认

以下动作至少需要清晰风险提示、原因和操作者记录：

- 确认预约并生成订单；
- 录入线下预约并占用已确认档期；
- 取消、改期、释放档期和延长定金期限；
- 核验或冲正线下收款；
- 审核、发起和人工处理退款；
- 确认拍摄完成并激活尾款；
- 发布、撤回和恢复交付；
- 变更私密交付授权；
- 发布、撤回公开案例和公开授权；
- 查看完整客户敏感资料和审计记录；
- 通过外部网盘补充交付。

二次确认不能只做一个“确定”弹窗。确认内容需要包括目标记录、影响金额/日期/范围、当前状态、操作者将产生的业务结果和无法自动撤销的风险。

### 13.4 审计记录

后台应能从业务记录进入相关审计，不要求工作人员在多个系统之间手工拼接。审计至少包括：

- 谁在什么时间对什么业务记录执行了什么动作；
- 动作前后状态或版本；
- 操作原因、备注和来源渠道；
- request id、task id、外部业务号或幂等关联；
- 是否由系统任务、支付回调或人工补偿触发；
- 客户通知结果；
- 失败、重试和最终处理结论。

审计记录不可通过普通业务编辑删除或覆盖。客户隐私、支付凭证、授权证据和内部备注需要按权限访问，并保留必要的脱敏和访问记录。

## 14. 功能需求清单

### 14.1 后台身份和工作台

- 工作室员工登录和会话失效反馈；
- 负责人、管理员和摄影师的角色边界；
- 按角色和资源显示可执行任务；
- 工作台待办、即将到期、处理中和失败待人工入口；
- 从待办进入具体业务记录；
- 显示当前状态、最近动作、下一步和审计入口；
- 防止重复点击、重复提交和重复补偿；
- 支持 request id、task id 或业务号检索。

### 14.2 内容、作品和套餐

- 维护品牌、首页、团队、联系方式、地址、流程和 FAQ 草稿；
- 受控预览、发布、下架、恢复和版本追踪；
- 维护作品案例、图片、分类、排序、公开资格和授权异常；
- 维护六类摄影业务；
- 维护标准套餐、固定定金、服务项、版本和公开状态；
- 预览发布影响和失效引用；
- 阻止未授权、未校验、缺少固定定金或信息不完整的内容发布；
- 已被业务引用的历史内容可追溯。

### 14.3 档期和预约

- 配置和查看固定时段；
- 查看待确认申请、确认占档和临时封档；
- 录入电话/微信预约并记录来源；
- 线上、线下预约使用同一冲突校验；
- 补充资料、拒绝、确认、失效、改期和取消；
- 确认时显示套餐版本、价格、固定定金和日期/时段核对信息；
- 确认预约幂等生成唯一订单；
- 冲突、版本失效和处理超时进入明确异常路径。

### 14.4 客户、订单和履约

- 查找和关联客户身份；
- 区分预约联系人、拍摄人和交付授权对象；
- 查看客户业务记录和必要沟通历史；
- 查看订单快照、支付分期、履约状态和交付状态；
- 安排拍摄、分配摄影师和记录履约事件；
- 负责人或管理员确认拍摄完成并激活尾款；
- 发起改期、订单修订、取消和异常处理；
- 不直接覆盖历史订单快照。

### 14.5 支付、退款和对账

- 查看定金/尾款分期和支付尝试；
- 处理支付处理中、主动查单和金额不匹配；
- 登记和核验线下收款；
- 发起退款申请、负责人审核和外部结果跟进；
- 处理退款失败待人工；
- 显示支付事实与订单摘要的差异；
- 防止重复支付、重复退款和超额分配。

### 14.6 交付和授权

- 创建上传会话和登记文件归属；
- 查看上传进度、校验结果和待重传；
- 发布交付批次、设置入口期限和发送通知；
- 管理预约联系人和家庭成员的私密交付授权；
- 管理公开案例授权、撤回和案例资格变化；
- 到期关闭小程序入口但保留工作室原文件；
- 登记网盘补充交付并记录链接有效期；
- 不向普通角色暴露永久对象地址。

### 14.7 异常、通知和审计

- 异常队列按业务类型、失败原因和下一步分组；
- 重新查单、重发通知、补充核验、重新校验和恢复入口；
- 查看重试次数、最后错误、下次执行时间和关联任务；
- 高风险人工补偿需要负责人权限和原因；
- 查看业务操作、前后状态、操作者和通知记录；
- 区分可重试、处理中和失败待人工；
- 不通过普通编辑框覆盖原始业务事实。

## 15. 验收标准

### 15.1 角色与权限

1. 负责人、管理员和摄影师能够看到与自身职责匹配的任务和资源。
2. 管理员不能直接覆盖既有订单价格、服务快照、支付成功事实或最终退款审核结果。
3. 摄影师只能访问被分配的拍摄安排和完成任务所需的最小客户信息。
4. 摄影师不能确认预约、占用档期、确认拍摄完成、触发尾款、退款或发布成片。
5. 负责人可以进入高风险审核和人工补偿，但所有动作仍需满足业务前置条件和审计要求。
6. 无权限角色通过详情链接、刷新或重复请求也不能绕过资源和状态限制。

### 15.2 工作台与待办

1. 工作台能够进入待确认预约、即将失效、待核验、处理中、失败待人工和待交付等真实业务记录。
2. 待办项显示当前状态、关联业务、最近动作、风险和下一步，而不只有一个数量。
3. 已完成、已转人工或已处理的待办有可追溯历史，不因从首页消失而丢失记录。
4. 重复刷新、重复点击和网络重试不会产生重复订单、支付、退款、通知或授权。
5. 后台能够使用业务号、request id 或 task id 定位需要处理的异常。
6. 没有记录、筛选无结果、权限受限、处理中和失败待人工有不同的后台反馈。

### 15.3 内容、作品和套餐

1. 品牌、联系方式、作品、业务和套餐能够通过后台维护，不依赖修改前端硬编码。
2. 草稿、预览、发布、下架、恢复和版本替代有清楚的状态和操作结果。
3. 发布前能够发现缺失授权、未校验文件、失效关联、缺少固定定金或不完整公开资料。
4. 官网和小程序读取同一已发布内容，后台不能通过端侧副本制造不同电话、地址、价格或授权状态。
5. 作品公开资格无效时，后台不能强行发布其公开案例；公开撤回不会删除私密交付。
6. 摄影业务、作品分类、标准套餐和展示分组在后台含义清楚，不继续用一个通用分类对象混淆它们。
7. 修改或下架套餐不会回写既有订单快照，历史版本可追溯。
8. 历史 30%/50% 定金比例不会被后台当作当前固定金额规则发布。

### 15.4 预约与订单

1. 后台可以查看线上预约申请和录入电话/微信预约。
2. 线上和线下预约使用同一日期/固定时段冲突规则。
3. 待确认申请不会被误显示为排他占档。
4. 确认预约前，操作人能核对客户、套餐版本、价格、固定定金、日期和固定时段。
5. 确认动作重新校验冲突，成功后同时确认预约、占档、生成唯一订单并冻结快照。
6. 重复确认返回既有订单，不产生第二个订单或第二个硬占档。
7. 申请失效、确认冲突、套餐版本失效、临时封档和定金逾期分别显示不同结果。
8. 改期和取消保留原记录、修订关系、支付事实、档期释放和客户通知。

### 15.5 支付、退款和履约

1. 后台能区分支付请求、处理中、已确认支付事实、线下待核验和失败待人工。
2. 支付未知或查单中不会被显示为失败，也不会允许工作人员盲目创建第二笔支付。
3. 线下收款包含金额、方式、时间、经办人、凭证/备注和核验状态。
4. 未核验线下收款不会满足定金、尾款或交付访问条件。
5. 退款申请、审核、外部请求、处理中、成功和失败待人工有独立记录。
6. 退款超时或失败不会被普通编辑直接改成成功，重复退款请求使用稳定幂等关系。
7. 负责人或管理员确认拍摄完成后才激活尾款；摄影师的履约记录不能直接触发尾款。
8. 支付状态、履约状态和交付状态在后台分别展示，不相互自动推导。

### 15.6 文件、交付和授权

1. 工作人员能够看到文件所属订单、批次、类型、上传结果和完整性校验结果。
2. 未校验、归属不明或对象缺失的文件不能发布给客户。
3. 发布交付前能够核对尾款、授权对象、文件范围、入口期限和客户通知。
4. 交付发布失败时不出现部分文件可访问的不可解释状态。
5. 预约联系人和显式授权家庭成员的私密交付权限可以被分别追溯。
6. 公开案例授权和私密交付授权相互独立，撤回公开授权不会自动删除私密交付。
7. 小程序入口到期后关闭客户访问但保留原文件，网盘补充交付有负责人授权、范围和期限记录。
8. 普通后台角色不能获取永久对象地址或绕过应用权限直接访问私密文件。

### 15.7 异常、补偿和审计

1. 支付、退款、通知、档期、文件和交付失败能够进入异常队列。
2. 每条异常显示安全错误摘要、重试次数、任务标识、业务号和下一步。
3. 重新查单、重发通知、收款核验、文件重试、释放占用和补充交付等补偿动作有明确入口。
4. 人工补偿不能删除失败事实、覆盖成功支付、重复退款或绕过负责人权限。
5. 高风险操作记录操作者、时间、原因、前后状态、来源请求和客户通知结果。
6. 后台响应不暴露 SQL、Java 堆栈、对象存储永久路径、第三方原始响应或不相关客户资料。
7. 操作完成、处理中、可重试失败和失败待人工在页面上有可区分结果。
8. 发生错误时工作人员可以凭 request id、task id 或业务号继续排查，而不是只能依赖口头描述。

## 16. 验证方式

### 16.1 工程与内容核验

在进入详细设计前，至少核验：

- 是否存在独立后台入口、员工身份和角色资源边界；
- 品牌、联系方式、作品、业务和套餐是否可以从后台维护；
- 草稿、预览、发布、下架、恢复和版本历史是否可追溯；
- 线上预约和电话/微信预约是否进入同一冲突源；
- 确认预约是否能产生唯一订单和不可覆盖的订单快照；
- 线下收款、支付回调、查单、退款和通知是否进入可观察任务；
- 履约完成、尾款激活和交付发布是否有正确角色边界；
- 文件校验、交付授权、公开案例授权和到期入口是否严格分开；
- 每个高风险动作是否有前置条件、幂等、审计和失败补偿入口；
- AT09 错误码是否能被后台转化为刷新、重试、转人工或负责人审核。

### 16.2 脱敏后台场景验证

至少准备以下脱敏场景：

1. 负责人编辑品牌联系方式并预览，发布后官网与小程序同步，旧内容不再继续公开。
2. 管理员编辑套餐但未发布，客户侧仍看到上一个有效版本。
3. 套餐调价后，待确认预约不能静默替换旧版本，管理员需要重新确认或拒绝。
4. 线上和电话预约申请同一日期/固定时段，确认动作只有一个能够成功占档并成单。
5. 两名管理员同时确认同一待确认申请，重复动作返回同一订单。
6. 临时封档后，待确认申请不能继续确认，但已有确认预约不会自动取消。
7. 定金逾期任务与支付回调同时到达，后台不会在未知支付结果时直接释放档期。
8. 管理员登记线下定金但凭证待核验，客户侧不会显示已支付。
9. 退款请求超时，后台显示处理中并可查单，不创建第二笔退款。
10. 摄影师记录拍摄完成建议，但只有负责人或管理员能够正式确认并激活尾款。
11. 文件上传成功但校验失败，交付不能发布，后台显示重传或人工处理入口。
12. 尾款付清但交付尚未发布，客户没有预览和下载，后台显示待发布任务。
13. 公开案例授权撤回，案例从公开端隐藏，但客户私密交付仍可按授权访问。
14. 交付入口到期，后台保留原文件并生成补充交付待办，网盘链接有接收人和有效期。
15. 管理员尝试查看不属于其范围的客户敏感资料，系统拒绝并留下安全审计。
16. 通知发送失败，业务事实不回滚，后台可重发并看到原发送记录。
17. 操作者刷新或重复提交发布、确认、收款核验和授权操作，不产生重复事实。
18. 后台请求返回业务错误码和 request id，工作人员可以按错误语义采取正确下一步。

### 16.3 工作人员可用性验证

在没有真实后台操作数据前，应通过负责人、管理员和摄影师的脱敏访谈或任务测试观察：

- 工作人员能否在工作台找到当天最重要的待办；
- 管理员能否区分待确认申请、已确认预约和已生成订单；
- 工作人员是否理解待确认申请不占硬档；
- 负责人是否能快速判断退款、授权和异常任务的责任和金额；
- 摄影师是否能只看到完成拍摄所需的信息；
- 工作人员能否从订单详情判断当前是支付、履约还是交付问题；
- 线下收款待核验、支付处理中和退款失败是否容易混淆；
- 文件上传、文件校验和交付发布是否被理解为不同步骤；
- 人工补偿入口是否可找到，是否会诱导直接改最终状态；
- 审计记录是否足以还原一次争议操作；
- 工作人员在权限不足或版本过期时是否知道找谁处理。

不能在没有实际观察前虚构每天处理数量、平均响应时间、审批时长或后台转化目标。A16 负责继续确定可衡量的运营指标和数据来源。

## 17. 待确认经营内容与产品决策

以下事项需要工作室负责人、管理员和摄影师共同确认：

1. 工作室日常由几名负责人、管理员和摄影师使用后台，是否由同一人兼任多个角色。
2. 首版是否启用独立摄影师账号，还是由管理员统一记录履约。
3. 负责人是否需要对退款、公开授权、交付发布、套餐发布和线下收款实行二次复核。
4. 哪些内容必须负责人发布，哪些内容管理员可以直接发布或下架。
5. 电话/微信预约由谁录入，客户是否需要在录入后收到确认信息。
6. 工作室每天最需要查看的是预约、拍摄安排、收款、交付还是内容任务。
7. 是否需要日历、列表、看板或其他档期视图，固定时段如何配置和临时封档。
8. 预约申请超过 48 小时未处理时，谁负责跟进，是否需要提醒和升级。
9. 定金 24 小时逾期时，是否由系统任务自动复核，哪些情况必须人工确认。
10. 改期、取消、补拍和工作室原因取消的审批责任和客户沟通方式是什么。
11. 管理员可以登记哪些线下收款，核验是否由负责人或双人复核完成。
12. 支付、退款和对账异常每天由谁处理，外部平台无法确认时的人工联系路径是什么。
13. 拍摄完成由负责人还是管理员确认，摄影师是否只能提交完成建议。
14. 文件上传由摄影师、管理员还是后期人员完成，哪些文件类型需要首版支持。
15. 成片发布前是否需要负责人检查客户授权、文件范围和交付说明。
16. 默认预约联系人的身份如何确认，其他家庭成员由谁、在什么场景下添加。
17. 公开案例授权如何取得、保存和撤回，负责人是否需要查看授权证据。
18. 交付入口到期后，工作室使用哪种补充交付方式，链接默认有效多久。
19. 通知渠道、失败重试和客户联系记录由谁维护，哪些通知必须可追溯。
20. 审计记录需要谁能查看、保留多久，敏感字段和支付凭证如何脱敏。
21. 工作人员是否需要导出客户、订单、收款或交付列表，导出权限和用途是什么。
22. 是否需要批量操作，哪些低风险任务可以批量处理，哪些动作必须逐条确认。
23. 工作室希望如何处理历史原型中的测试套餐、错误联系方式和旧作品数据。
24. 工作台是否需要统计经营指标，哪些数据能够真实获得，哪些指标暂不建立。

## 18. 后续专题输入

A10 为后续专题提供以下输入：

- A05：后台需要维护统一品牌、首页、团队、联系方式、流程和公共内容发布生命周期；
- A06：后台需要处理案例、图片、公开资格、授权撤回和公开下架；
- A07：后台需要维护六类摄影业务、标准套餐、固定定金、版本和公开选择资格；
- A08：后台动作必须产生客户侧可理解的预约、订单、支付、履约和交付状态；
- A09：后台需要支持官网和小程序共享内容、预览、发布、下架和旧链接失效结果；
- A11：后台需要遵守身份绑定、客户资料、家庭成员、敏感信息和隐私保留规则；
- A12：后台需要处理线上/线下预约、固定时段、申请有效期、冲突、确认、改期和取消；
- A13：后台需要查看订单快照、修订、履约事件、拍摄完成和客户可见异常；
- A14：后台需要处理在线支付、查单、线下收款、退款、对账和财务人工补偿；
- A15：后台需要处理文件上传、校验、交付发布、私密授权、公开授权和补充交付；
- A16：后台需要提供待办处理、异常负担、处理时效、客户联系和运营质量的衡量方向；
- AT07：后台权限必须结合角色、操作、资源归属、当前状态和敏感数据范围；
- AT08：后台高风险动作必须满足事务、并发、幂等、补偿和审计要求；
- AT09：后台必须消费稳定业务错误码、request id、task id 和外部服务结果，不暴露内部实现细节。

## 19. 结论

当前 SouthLeaf 工程只有面向客户的公开展示原型和分类、套餐、轮播基础后端接口，没有正式的后台应用、员工身份、角色权限、工作台、预约处理、订单跟进、支付核验、履约记录、交付发布、异常补偿或审计能力。原型中的内容硬编码、联系方式冲突、测试套餐和占位入口不能作为后台运营基础直接延续。

A10 确立的后台体验目标是：

```text
负责人能够审核经营和高风险事项；
管理员能够完成日常内容、预约、订单、履约和交付运营；
摄影师只访问被分配且完成任务所需的最小资源；
线上和电话/微信业务进入同一真实业务链路；
后台始终区分查看、编辑、确认、支付、履约、发布和授权；
支付、退款、通知、文件、档期和授权异常都有可观察、可重试、可转人工的路径；
所有高风险动作都能说明谁在何时因为什么改变了什么，并且不会通过普通编辑覆盖原始事实。
```

A10 不定义最终后台菜单、数据库、接口或技术实现，而是为后续 A11-A16 和详细设计提供工作室任务、权限、异常和验收输入。在负责人和实际工作人员确认日常分工、审批强度、通知方式、文件流程和人工补偿习惯前，不应锁定后台页面结构、角色配置、字段模型或编码方案。
