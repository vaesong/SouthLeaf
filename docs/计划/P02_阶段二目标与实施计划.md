## 1. 阶段二总目标

从“可验证的演示展示端”推进到“工作室能够维护真实资料、客户能够提交预约、工作人员能够确认占档并自动成单的可运营系统”。

阶段二按“先完成基本功能，再集中接入真实业务”拆分：

- **2A：基本功能开发与联调。** 完成管理后台、媒体上传处理、内容维护与发布撤回、公开授权管理、客户身份、档期、预约确认、排他占档、自动成单、订单快照、改期取消、通知任务和审计。使用隔离测试环境、虚构资料及有明确来源的测试媒体完成工程验证。
- **2B：真实业务接入、内容运营与正式上线。** 2A 达到功能验收门槛后，工作室集中介入：真实资料与授权核验、经营配置、人员账号、正式 AppID/域名/TLS/存储/通知接入、真机及用户验收、备份恢复和部署回退验证，最终正式开放。
- 不是把两项功能简单对调：内容管理后台在 2A 开发完成，真实内容录入、真实经营验证和正式展示放在 2B；预约订单也先开发，再统一真实接入。
- 2A 完成只代表基本功能和测试环境闭环完成，不等于真实微信身份、生产通知或正式上线已验收；2B 不以“只填数据”概括，保留真实接入缺陷修复与复验时间。
- 开发期间不要求工作室持续上传真实资料或参与逐页联调。确实影响业务正确性的少量规则决策须在对应设计前确认，不以延后真实对接为由猜测经营规则。

依据：原 P01 第四节已包含预约和订单；阶段一交付另将真实内容、后台维护、权属材料、正式 AppID/域名/TLS/凭据及生产验收明确交接到阶段二。不能把阶段二缩减为“补一个后台界面”。

## 3. 不可弱化的规则

1. 公开浏览不强制登录；提交预约和查看本人业务记录需要可靠身份。
2. 客户身份、联系人、拍摄人和参与人分开表达；客户端参数不是资源归属依据。
3. 待确认申请不占硬档，同一时段可以有多个待确认申请。默认 48 小时有效，实际截止时间逐笔保存。
4. 确认动作必须重新检查资格和冲突，并原子完成：排他占档、预约确认、唯一订单、订单快照、审计及可靠通知任务登记。外部消息发送不放在数据库事务中。
5. 重复确认返回原结果或明确冲突，不产生重复订单。失败不能留下占档无订单或订单无预约的半成功状态。
6. 套餐调价、改名、下架不回写既有订单。改期和约定变化形成可追溯修订；新档占用失败不得破坏旧档。
7. 临时封档不自动取消已确认预约；线下录入不能绕过冲突源。
8. 订单存在、计划金额、工作人员备注都不是已支付事实。阶段二不得提供“标记已收款”来绕过阶段三。
9. 公开授权与发布分离；发布和历史版本恢复都必须再次核验当前授权。儿童、多人或监护关系不明确时默认不公开。
10. 保留阶段一公开资格及媒体复核守卫；不为方便上传改为永久公开原图，不承诺撤回已下载的字节。
11. 新 schema 采用 V2 等增量迁移；不得修改已应用 V1、重建现有库或自动 repair。

决策分成两类：

1. **开发前必须明确的规则**：定金过渡策略、身份归属、确认/改期/取消的权限和状态边界。优先提出成套建议，集中确认，避免反复要求工作室介入。用户尚未确认的建议不能写成既定经营规则。
2. **最后集中提供的真实事实和外部资源**：实际价格/时段、真实图片与授权、工作人员、正式账号、域名证书及渠道资质。2A 做配置能力和接口适配，2B 再录入、接通并验证；不以这些尚未提供阻塞可独立完成的开发。

若缺少正式微信或通知资质，2A 可用隔离、可替换的测试适配器验证应用规则；必须标识为模拟外部依赖，不允许生产配置启用，不得冒充真实身份认证或实际消息送达。真实平台限制与集成风险登记到 2B 验收项。

**归属：S0–S6 为 2A；S7 为 2B。** 运维脚本、存储/身份适配和配置校验能力在 2A 开发，生产资源绑定及现场验证在 2B 完成。开发顺序中的媒体/内容能力是预约套餐等功能的基础依赖，不代表提前进行真实内容对接。

开发以纵向切片推进：数据库迁移和领域规则 → API/权限/审计 → 后台及小程序 → 集成与端到端测试 → 文档证据。不能先堆全部后台页面，再补后端一致性。

后台沿用 Vue 3 + TypeScript + Vite 的既有方向，UI 组件库和具体版本用 ADR 在 S1 确认。小程序继续原生微信；后端延续 Java 21 / Spring Boot / JDBC / Flyway 模块化单体。不默认引入微服务、Redis、消息队列或复杂工作流。

写模型与公开只读投影分离：管理命令生成受控发布快照，公开端继续消费发布读模型。不能暴露 Reader 表 CRUD 作为管理能力。运行 Reader、管理 Writer、迁移身份按职责最小授权；授权撤回独立生效，旧发布恢复不能复活已撤回媒体。

## 7. 测试与验收门禁

### G0：范围与开发规则

- 采用用户明确的“先基本功能、后真实对接”顺序；开发、真实接入和正式验收的结论分开。
- 影响正确性的规则先确认；真实经营资料与资质集中到 2B，不作为开发期间常态输入。
- 每个未决项有责任、关闭时点及阻断范围，不用隐含默认值代替决策。

### G1：当前切片可编码设计

- 每个切片有状态机、数据约束、接口、权限、事务/幂等、失败处理和可执行用例。
- 内容切片含上传发布撤回链；预约切片含确认成单与改期事务，Q02 已关闭。
- 测试身份、测试授权、虚构经营值和生产配置有明确隔离及生产防误用检查。

### G2A：基本功能开发完成

使用隔离测试库、虚构客户/套餐/授权和可合法用于测试的媒体，验证真实代码、数据库、后台及小程序；不以纯页面 mock 替代后端实现。

- 无需改库即可完成内容录入、上传、处理、授权核验、预览、发布、下架与撤回。
- 无权限、授权不足/过期/撤回、媒体未就绪时拒绝发布/访问；旧 URL、HEAD、历史发布恢复均验证。
- 文件伪装、过大/超像素、路径穿越、预览泄露、重复处理和失败重试有测试。
- 本人权限可靠；不能枚举其他测试客户的预约、订单、联系方式或冒用线下记录。
- 多个待确认申请不占档；真实 MySQL 并发确认同档仅一笔成功、仅一张订单；重复申请/确认幂等。
- 确认故障全事务回滚；套餐变更不覆盖订单快照；改期失败保留原档。
- 封档/确认、取消/改期、过期/确认竞争及跨日/时区边界、任务重复和重启恢复有测试。
